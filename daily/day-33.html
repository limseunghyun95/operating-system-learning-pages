OPERATING SYSTEM · DAY 33 / 63 · MEMORY PRESSURE

reclaim, swap, thrashing, OOM killer

한 줄 요약: memory 부족은 곧 OOM이 아니라, 먼저 cold page를 reclaim하고 file page는 drop·writeback하며 anonymous page는 swap으로 보존하는 과정이다. working set이 다시 필요해 계속 refault하면 thrashing이 되고, reclaim으로도 allocation을 만족하지 못할 때 scope 안의 OOM killer가 최후의 복구를 시도한다.

1. 초보자 용어 사전

2. mental model: 비상 창고를 운영하는 도서관

RAM은 책상, page cache는 원본 책이 서가에 있는 복사본, anonymous page는 원본이 없는 메모다. 자리가 부족하면 차가운 깨끗한 복사본은 버리고, dirty 복사본은 서가에 반영한 뒤 치운다. 원본 없는 메모는 swap 창고에 맡겨야 한다. 방금 치운 자료를 계속 다시 가져오면 직원은 운반만 하고 독서는 멈춘다. 그것이 thrashing이며, 더 치울 수도 저장할 곳도 없으면 관리자가 한 작업을 종료하는 것이 OOM kill이다.

4. 상태 전이 그림: healthy → pressure → thrashing → OOM

[HEALTHY: working set fits]
      │ allocation 증가 / limit 감소 / traffic 증가
      ▼
[PRESSURE: kswapd reclaim]
      │ cold page가 충분함 ─────────────────────────────→ [RECOVERED]
      │ cold page 부족, allocator stall
      ▼
[DIRECT RECLAIM / SWAP]
      │ eviction한 page를 곧 refault, PSI some/full 증가
      ▼
[THRASHING: useful throughput 급락]
      │ load shed·scale·memory release ────────────────→ [RECOVERED]
      │ reclaim progress 없음, hard limit/allowed memory 소진
      ▼
[OOM DECISION] → victim SIGKILL → exit/reap으로 pages 반환 → [RECOVERY or REPEAT]

주의: 모든 allocation 실패가 OOM kill을 부르지는 않는다.
high-order·NOWAIT 성격 요청은 -ENOMEM/fallback으로 끝날 수 있다.

6. CS·kernel·hardware deep dive

6.1 reclaim은 정확한 LRU가 아니라 비용 있는 근사다

모든 memory access 시 global 순서를 갱신하면 overhead가 너무 크다. Linux는 accessed bit, active/inactive 정보 또는 Multi-Gen LRU의 generation·refault feedback으로 hot/cold를 근사한다. shared page, scan overhead, workload phase change 때문에 오판은 가능하다.

6.2 Multi-Gen LRU는 aging과 eviction의 feedback loop다

aging은 page-table walk와 accessed bit로 최근 page를 젊은 generation에 둔다. eviction은 오래된 generation을 소비하며 file/anon refault 비율을 관찰해 어느 type을 더 보호할지 조정한다. 즉 “anonymous 먼저”나 “file 먼저”라는 고정 규칙이 아니다.

6.3 kswapd와 direct reclaim의 latency 위치가 다르다

kswapd가 미리 free page를 회복하면 application은 덜 멈춘다. 따라잡지 못하면 allocation을 요청한 task가 scan·writeback·swap을 수행하거나 기다리므로 p99에 비용이 직접 나타난다. `pgscan_direct*`, `allocstall`, memory PSI가 중요한 이유다.

6.4 swap은 RAM 확장이 아니라 latency를 사는 보존 계층이다

swap이 있으면 cold anonymous data를 보존해 file cache와 active working set에 RAM을 돌릴 수 있고 급작스러운 OOM을 늦춘다. 그러나 hot page를 내보내면 swap-in I/O와 page fault가 반복된다. zram·zswap은 storage 대신 CPU·compressed RAM을 쓰므로 병목 위치만 달라진다.

6.5 swappiness는 RAM 사용률도 swap 비율도 아니다

Linux의 `vm.swappiness` 0~200은 swap I/O와 filesystem paging의 상대 비용 힌트다. 100은 비용이 같다고 보는 기준이고, 0도 swap을 완전히 금지하는 switch가 아니다. storage·zram·workload refault 비용을 측정해 정한다.

6.6 thrashing은 capacity cliff다

resident frame 수가 working set보다 조금만 작아져도 cyclic workload는 방금 내보낸 page를 곧 다시 fault할 수 있다. throughput은 memory 사용량에 선형으로 감소하지 않고 급락한다. 높은 `pswpin/pswpout`, major fault, refault와 memory PSI full을 함께 본다.

6.7 PSI는 “얼마나 찼나”가 아니라 “얼마나 멈췄나”다

memory PSI `some`은 적어도 일부 task가 memory 때문에 멈춘 시간, `full`은 모든 non-idle task가 동시에 멈춘 시간이다. extended full은 kernel 문서가 thrashing으로 보는 심각한 생산성 손실이다. MemFree 하나보다 SLO와 직접 연결된다.

6.8 OOM의 scope는 machine 전체가 아닐 수 있다

`memory.max`, cpuset, NUMA mempolicy가 허용한 memory만 소진돼도 그 scope에서는 OOM이다. 다른 node나 host에 free memory가 보여도 사용할 수 없다. memcg OOM은 해당 cgroup 밖 task를 kill하지 않는다.

6.9 overcommit과 OOM은 다른 시점의 계약이다

overcommit은 virtual memory reservation을 허용할지 판단한다. `malloc` 성공 뒤 실제 page touch에서 physical backing이 부족해 OOM이 날 수 있다. 반대로 strict commit policy는 실제 RAM pressure 전에도 allocation을 `ENOMEM`으로 거절할 수 있다.

6.10 OOM kill은 종료가 아니라 회복 시작이다

victim에 SIGKILL을 보낸 즉시 모든 page가 사라지는 것은 아니다. task가 exit하고 shared reference·I/O·kernel path가 정리돼야 memory가 돌아온다. 같은 압력이 계속되면 연속 OOM이 날 수 있으므로 restart backoff와 load shedding이 필요하다.

8. 실무 best practice

  • capacity는 peak RSS가 아니라 working set, page cache, kernel memory, swap latency, failover headroom을 합쳐 잡는다.
  • `memory.high`에서 먼저 throttle·alert하고 `memory.max`는 최종 blast-radius guardrail로 둔다. 두 값을 같게 두어 warning window를 없애지 않는다.
  • PSI some/full, allocation latency, `pgscan_direct*`, refault, swap-in/out, major fault를 application p99와 같은 timestamp로 수집한다.
  • stat counter는 boot 이후 누적값이므로 rate·delta로 비교하고 kernel version별 field 존재 여부를 확인한다.
  • restartable batch와 stateful quorum member의 `oom_score_adj`·`memory.oom.group` 정책을 다르게 설계하고 이유를 문서화한다.
  • load shedding, queue bound, concurrency cap, autoscaling을 OOM 전 PSI threshold에 연결한다.
  • swappiness·swap size·zram/zswap은 canary에서 throughput·p99·CPU·I/O·OOM 빈도를 함께 비교한다.
  • 모든 daemon을 `oom_score_adj=-1000`으로 보호하지 않는다. system이 희생할 안전한 후보와 recovery service의 memory reserve를 남긴다.

9. error handling runbook

  1. scope 식별: global, NUMA/cpuset, container cgroup 중 어디의 allowed memory가 소진됐는지 확인한다.
  2. stall 확인: `/proc/pressure/memory`와 cgroup `memory.pressure`, p99를 보고 “가득 참”과 “멈춤”을 구분한다.
  3. reclaim 분해: vmstat delta로 kswapd/direct scan·steal, refault, major fault, swap-in/out, writeback을 묶는다.
  4. 즉시 완화: admission을 닫고 low-priority traffic·batch를 줄이며 concurrency를 제한한다. 무작정 cache를 drop하지 않는다.
  5. OOM 증거: `memory.events.local`, kernel journal, victim·scope·constraint·order, restart 횟수를 보존한다.
  6. 복구: victim을 backoff와 readiness gate로 재시작하고 memory가 실제 반환될 때까지 traffic을 서서히 연다.
  7. 근본 수정: leak/retention, working-set 증가, limit 오설정, cache growth, unevictable memory, swap latency 중 하나를 증거로 좁힌다.
  8. rollback: 새 limit·swappiness·page policy와 동시에 시작된 회귀라면 한 변수만 되돌리고 같은 지표로 확인한다.

10. 놓치기 쉬운 함정

  • free memory가 적으면 장애: file cache 활용은 정상이며 stall·reclaim efficiency를 봐야 한다.
  • swap 사용량이 있으면 thrashing: cold page가 오래 swap에 있는 것은 문제 아닐 수 있다. 지속 swap-in/out과 refault·PSI가 핵심이다.
  • swappiness 0이면 swap off: 완전 금지가 아니라 reclaim 비용 선호가 크게 바뀐다.
  • OOM은 host RAM 100%에서만: cgroup·cpuset·mempolicy scope exhaustion도 OOM을 만든다.
  • OOM killer가 가장 큰 RSS를 죽임: allowed memory 기준 badness와 `oom_score_adj`, scope가 함께 작동한다.
  • OOM kill 즉시 정상: victim exit와 memory 반환, restart storm까지 관찰해야 한다.
  • drop_caches가 leak 치료: 재구성 가능한 cache를 버릴 뿐 live object leak을 고치지 않고 다음 I/O를 악화시킨다.
  • pressure 중 swapoff가 안전: swap page를 RAM으로 되돌릴 공간이 없어 실패하거나 더 큰 stall을 만들 수 있다.

11. 30분 실습: working-set cliff simulator

8-page working set을 다섯 번 순회하는 fully-associative LRU 모델이다. frame이 8개면 첫 pass 뒤 hit지만 6개면 방금 쫓아낸 page를 다시 요구해 모든 access가 miss가 된다.

python3 - <<'PY'
from collections import OrderedDict

def run(working_set=8, frames=8, passes=5):
    resident, seen = OrderedDict(), set()
    hits = misses = evictions = refaults = 0
    for page in list(range(working_set)) * passes:
        if page in resident:
            hits += 1
            resident.move_to_end(page)
            continue
        misses += 1
        if page in seen:
            refaults += 1
        seen.add(page)
        if len(resident) == frames:
            resident.popitem(last=False)
            evictions += 1
        resident[page] = None
    return hits, misses, evictions, refaults

for frames in (8, 6, 4):
    print("frames=", frames, "hits/miss/evict/refault=", run(frames=frames))

assert run(frames=8) == (32, 8, 0, 0)
assert run(frames=6) == (0, 40, 34, 32)
assert run(frames=4) == (0, 40, 36, 32)
PY
  1. 0~10분: frame 8과 6의 첫 두 pass를 손으로 그린다.
  2. 10~20분: working set·frame·access pattern을 바꿔 miss cliff를 찾는다.
  3. 20~30분: 실제 system의 `workingset_refault`, `pswpin/out`, major fault, PSI와 모델 변수를 연결한다.

모델 한계: Linux의 active/inactive·Multi-Gen LRU, file/anon 비용, dirty writeback, swap readahead, shared page, cgroup scope를 생략한다. “working set이 resident capacity를 넘으면 refault feedback이 폭발할 수 있다”는 불변식을 분리해 본다.

13. 실패 시나리오

cache service의 dataset이 20% 늘자 `memory.current`가 `memory.high`를 넘고 direct reclaim이 시작됐다. 평균 RSS만 보면 limit 아래였지만 `memory.events.local high`, `pgscan_direct`, `workingset_refault`, memory PSI full, p99가 함께 상승했다. 운영자가 swap을 끄거나 cache를 전부 drop하지 않고 admission을 줄여 working set을 낮춘 뒤 replica를 추가했다. `memory.max` 직전 OOM을 피하고, 이후 key density와 object retention을 수정해 high event rate와 refault/PSI가 baseline으로 돌아온 것을 확인했다.

15. 퀴즈·누적 리뷰

  1. clean file page가 anonymous page보다 보통 싸게 회수되는 이유는? storage의 원본에서 다시 만들 수 있어 swap write가 필요 없기 때문이다.
  2. swap used가 높지만 pswpin/out과 PSI가 안정적이면 즉시 thrashing인가? 아니다. cold data가 오래 보관된 상태일 수 있다.
  3. `memory.high` 초과가 바로 OOM kill을 일으키는가? 아니다. throttle과 heavy reclaim을 만들며 OOM은 `memory.max` reclaim 실패에서 발생한다.
  4. Day 28 연결: RSS가 유지돼도 live object가 bounded면 allocator/page cache retention일 수 있고, pressure·refault 증거 없이 leak으로 단정하지 않는다.
  5. Day 32 연결: huge page의 sparse allocation과 split/compaction이 reclaim pressure·RSS amplification을 키울 수 있다.
