Operating System · Day 11 / 63 · CPU Scheduling

multicore, run queue, load balancing, CPU affinity

한 줄 요약 — Linux는 확장성과 cache locality를 위해 CPU마다 run queue를 두고, wakeup placement와 계층적 load balancing으로 일을 옮긴다. CPU affinity는 실행 가능한 CPU 집합을 제한할 뿐 전용 CPU나 성능을 보장하지 않으며, 균형·migration 비용·SMT/NUMA locality·cgroup 제한을 함께 설계해야 한다.

1. 선수 용어 사전

logical CPUkernel scheduler가 task를 배치하는 실행 단위. SMT가 있으면 한 physical core가 여러 logical CPU로 보일 수 있다.
physical core / socketcore는 명령을 실행하는 hardware core, socket/package는 하나의 CPU package다. logical CPU 수와 physical core 수는 다를 수 있다.
SMTSimultaneous Multithreading. 한 core의 pipeline/cache 등 일부 resource를 여러 hardware thread가 공유해 utilization을 높이는 기술.
run queue / rq특정 CPU에서 실행될 runnable scheduling entity와 현재 task, clock/accounting, class별 queue를 묶은 kernel 자료구조의 mental model.
load balancingCPU 간 runnable work·utilization·capacity 불균형을 줄이기 위해 task placement를 선택하거나 task를 migrate하는 과정.
migrationtask가 마지막/현재 CPU와 다른 CPU에서 이어 실행되는 것. idle CPU를 쓰지만 cache·TLB·NUMA locality 비용을 낼 수 있다.
scheduling domainSMT siblings→같은 package→NUMA node처럼 topology 계층별로 balancing 범위와 group을 표현하는 kernel 구조.
CPU affinity maskthread가 실행될 자격이 있는 logical CPU의 bit set. 여러 bit면 그 안에서 migrate할 수 있고, 한 bit면 그 CPU만 허용한다.
cpusetcgroup 계층에서 workload가 사용할 CPU와 NUMA memory node를 관리자가 제한하는 mechanism.
NUMANon-Uniform Memory Access. CPU와 가까운 local memory가 다른 node의 remote memory보다 보통 낮은 latency·높은 bandwidth를 갖는 구조.
CPU capacityCPU가 제공할 수 있는 상대 처리 능력. heterogeneous core, frequency, IRQ time 때문에 logical CPU 수만으로 capacity가 같다고 볼 수 없다.

2. mental model: 계산대마다 줄을 따로 두는 마트

모든 계산대가 하나의 거대한 줄과 lock을 공유하면 “다음 손님”을 정할 때마다 중앙 병목이 생긴다. CPU별 줄은 각 CPU가 대부분 local decision을 하게 해 확장성과 cache locality를 얻는다.

대신 0번 줄에 열 명, 1번 줄에 0명이 될 수 있다. 새 손님을 처음부터 덜 바쁜 줄에 놓는 placement와, 빈 계산대가 바쁜 줄에서 옮겨오는 balancing이 필요하다.

“항상 가장 짧은 줄로 즉시 이동”도 최선은 아니다. 손님의 물건이 기존 계산대 cache에 있고, 다른 계산대가 느린 core·SMT sibling·remote NUMA node라면 이동 비용이 절약한 queue wait보다 클 수 있다.

3. architecture·흐름: wakeup placement에서 migration까지

task wakeup / fork
       │ allowed = affinity ∩ cpuset.effective ∩ online CPUs
       ▼
select target CPU: previous CPU/cache locality, idle state,
                   utilization, capacity, scheduling domain
       │
       ├───────────────┬────────────────┬───────────────┐
       ▼               ▼                ▼               ▼
 CPU0 rq            CPU1 rq          CPU2 rq          CPU3 rq
 [A,B,current]       [C,current]      [idle]           [D,current]
       │               │                │               │
       └──── local pick_next + context switch per CPU ──┘

balancing events
  • wakeup/fork placement: 처음부터 target rq 선택
  • newly-idle balance   : idle 직전 busy rq에서 runnable task pull
  • periodic balance    : sched-domain별 interval에 imbalance 검사
  • active balance      : 필요한 경우 task 이동을 더 적극적으로 시도

topology domains (개념)
  SMT sibling ⊂ physical cores/package ⊂ NUMA node(s)
  가까운 domain부터 balance하되 affinity·cpuset·capacity·cache-hot 제약 고려

migrate: source rq와 destination rq 동기화 → dequeue → CPU 변경 → enqueue
         다음 실행에서 cache/TLB/NUMA locality 재구축 비용 가능

핵심: Linux multicore scheduling은 하나의 global FIFO에서 빈 CPU가 pop하는 단순 work stealing이 아니다. kernel version·class·topology에 따라 placement/balance 경로가 달라지지만, per-CPU decision과 계층적 imbalance 수정이라는 중심 trade-off는 유지된다.

4. affinity의 정확한 계약

effective allowed CPUs = application이 요청한 affinity mask ∩ 현재 존재/online CPU ∩ cpuset/cgroup이 허용한 CPU.

kernel은 cpuset 제한과 교집합을 조용히 적용할 수 있다. 교집합이 비면 sched_setaffinity()는 EINVAL로 실패한다. 성공 뒤에도 반드시 sched_getaffinity()나 Cpus_allowed_list로 실제 mask를 다시 읽는다.

mask가 {2,3}이면 “CPU 2에 고정”이 아니라 CPU 2 또는 3에서만 실행 가능하다는 뜻이다. mask가 {2}여도 다른 task, IRQ, SMT sibling의 공유 resource 경쟁을 제거하지 않으므로 전용 CPU 보장이 아니다.

scopeLinux affinity는 per-thread다. PID로 main thread만 변경하고 worker thread는 그대로 두는 실수가 흔하다.
lifecyclefork child는 parent mask를 상속하고 execve 뒤에도 보존된다. library/runtime worker 생성 시 상속 시점도 확인한다.
migration현재 CPU가 새 mask 밖이면 허용 CPU로 migrate한다. 넓은 mask 안에서는 scheduler가 계속 옮길 수 있다.
quota와 차이cpuset/affinity는 “어디서”, cpu.max quota는 “얼마나 오래”를 제한한다. 8 CPU mask여도 1 CPU quota일 수 있다.

5. CS·kernel·hardware deep dive

5.1 per-CPU run queue: 중앙 lock을 없애고 imbalance를 산다

N개 CPU가 하나의 global queue lock을 매 scheduling event마다 잡으면 cache-line bouncing과 lock contention이 증가한다. per-CPU struct rq는 current, runnable count, class별 queue, clock/load state를 CPU local하게 유지해 대부분의 enqueue/pick을 병렬화한다.

대가는 global fairness가 즉시 보이지 않고 CPU별 queue가 어긋나는 것이다. migration은 두 rq 상태를 일관되게 바꿔야 하므로 locking/order와 task의 on-rq/running state를 확인한다. 정확한 field와 lock path는 kernel version 내부 구현이므로 source와 tracepoint로 검증한다.

5.2 load는 runnable task 개수가 아니다

CPU0에 1개의 100% CPU-bound task, CPU1에 5개의 1% periodic task가 있다면 queue length 1 vs 5만으로 CPU1을 더 바쁘다고 판단하면 틀린다. Linux fair balancing은 task/group의 load·utilization average, runnable state, CPU capacity, priority/weight와 misfit 여부를 본다.

capacity도 동일하다고 가정할 수 없다. heterogeneous system의 성능 core와 효율 core, DVFS maximum, IRQ 처리 시간은 흡수 가능한 work를 바꾼다. utilization ≤ available capacity라는 placement 관점이 단순 task-count보다 정확하다.

5.3 sched domain은 topology-aware balancing hierarchy다

각 CPU의 sched-domain chain은 가까운 SMT sibling, package/core group, NUMA 범위처럼 점점 넓은 CPU span을 표현한다. domain 안에서는 CPU group load를 비교하고 불균형일 때 source run queue에서 destination으로 movable task를 고른다.

가까운 domain은 migration locality가 좋고 검사 비용이 작다. 넓은 NUMA domain은 idle capacity를 찾을 가능성이 크지만 balancing scan과 remote memory 비용이 커진다. cpuset/affinity가 domain을 잘라 usable capacity와 balancing 범위를 제한할 수 있다.

5.4 balance와 cache affinity는 반대 방향으로 당긴다

task를 idle CPU로 옮기면 run-queue wait는 줄지만 이전 CPU의 L1/L2 working set, TLB entries, branch history를 잃을 수 있다. shared LLC 안의 migration과 socket/NUMA를 넘는 migration 비용도 다르다. 그래서 cache-hot task를 무조건 옮기지 않고 imbalance 이득과 비교한다.

memory page는 CPU task보다 느리게 따라올 수 있다. remote NUMA access가 늘면 CPU utilization은 높아도 useful throughput이 떨어진다. CPU pinning을 바꿀 때 /proc/PID/numa_maps, memory bandwidth, local/remote access와 page migration까지 같이 본다.

5.5 SMT logical CPUs는 독립 core 두 개가 아니다

같은 core의 SMT siblings는 front-end, execution units, cache/bandwidth 일부를 공유한다. 서로 다른 bottleneck을 가진 task는 빈 pipeline slot을 채워 throughput이 늘 수 있지만, 같은 vector unit·cache·memory bandwidth를 쓰는 두 task는 심하게 경쟁한다.

“8 logical CPUs니까 worker=8”을 기본값으로 두지 않는다. lscpu -e와 sysfs topology로 CPU→core→socket/node mapping을 확인하고 1/core, 1/SMT thread, oversubscription을 workload로 benchmark한다.

5.6 virtual CPU에서는 host scheduler가 한 층 더 있다

VM의 guest CPU0은 physical core0이 아니라 host가 scheduling하는 vCPU thread다. guest가 두 vCPU에 task를 균등 배치해도 host contention/steal, vCPU pinning, NUMA placement가 어긋나면 동시에 실행되지 않는다.

container는 host kernel scheduler를 직접 공유하고 cpuset·quota를 받는다. os.cpu_count()나 /proc/cpuinfo의 논리 CPU 수만으로 실제 parallel capacity를 계산하지 말고 effective cpuset, cpu.max, throttling, PSI를 함께 읽는다.

6. 실무 best practice

  1. 먼저 scheduler 기본값을 baseline으로 둔다. 근거 없는 pinning은 balancing 기회를 없앤다. p99·throughput·migration/cache/NUMA 지표로 이득을 증명한다.
  2. topology와 제한을 snapshot한다. online CPU, core/socket/node, SMT siblings, effective cpuset, quota, affinity, governor/kernel을 결과와 함께 versioning한다.
  3. thread role 단위로 배치한다. latency thread, worker, GC, I/O completion의 dependency를 그린 뒤 서로를 굶기지 않는 CPU set과 capacity reserve를 둔다.
  4. CPU와 memory policy를 함께 설계한다. NUMA node를 넘겨 pin하면 local allocation/first-touch, mbind/numactl, automatic NUMA balancing과 충돌하지 않는지 확인한다.
  5. SMT sibling을 구분해 실험한다. same-core siblings, different cores, different sockets를 따로 비교하고 security/isolation requirement도 반영한다.
  6. affinity 변경은 read-after-write한다. 실제 allowed list와 thread 전체 적용 여부, CPU hotplug/cpuset reconcile, rollback mask를 검증한다.
  7. 여유 CPU를 남긴다. IRQ, kernel worker, control plane, failover와 burst를 위한 capacity 없이 application thread를 모두 hard-pin하지 않는다.

7. error handling과 운영 실패 대응

EINVAL요청 mask와 present/allowed cpuset의 교집합이 비었거나 mask buffer가 작다. online/effective list와 large CPU mask allocation을 확인한다.
EPERM다른 UID/thread affinity 변경 권한이나 CAP_SYS_NICE 범위를 확인한다. 권한을 자동 확장하지 않고 대상 identity를 재검증한다.
ESRCH racethread list 조회와 적용 사이 worker가 종료될 수 있다. TID/start time을 검증하고 새 worker 생성 policy를 별도로 둔다.
성공했지만 mask 축소cpuset이 요청을 조용히 제한할 수 있다. set 성공만 믿지 말고 get/status/cpuset.cpus.effective를 다시 읽는다.
hot CPU 한 개affinity·cpuset이 movable task를 없앴는지, IRQ/kworker가 같은 CPU에 몰렸는지 확인한다. mask를 넓히거나 role별 set을 재분배한다.
migration stormcpu-migrations, cache misses, throughput/p99를 함께 본다. 너무 넓은 pool·짧은 task·thread oversubscription·NUMA crossing을 줄인다.
CPU hotplugonline/effective set 변경 event에 mask를 재계산한다. 특정 CPU 번호를 영구 identity로 가정하지 않고 empty-set fallback과 rollback을 둔다.
분리했는데 느림cgroup quota, SMT sibling, CPU capacity/frequency, remote NUMA memory, VM steal을 확인한다. affinity 하나로 원인을 단정하지 않는다.

8. 놓치기 쉬운 함정

  • load average를 CPU별 run-queue 길이로 읽지 않는다. Linux load에는 D-state wait도 포함된다.
  • logical CPU 수를 physical core 수나 동일 capacity 수로 취급하지 않는다.
  • affinity mask 한 bit가 exclusive core를 뜻하지 않는다. 다른 task·IRQ·SMT sibling을 별도로 관리해야 한다.
  • main PID에만 taskset을 적용하고 worker TID 전체가 고정됐다고 생각하지 않는다.
  • CPU utilization 균형이 application throughput/latency 균형을 보장하지 않는다. task size와 capacity·memory locality가 다르다.
  • migration 0을 무조건 목표로 삼지 않는다. overloaded queue에서 idle CPU로 옮기는 편이 cache loss보다 이득일 수 있다.
  • container에서 보이는 CPU 수와 quota-based capacity를 섞지 않는다.
  • NUMA page가 CPU task와 자동으로 즉시 함께 이동한다고 가정하지 않는다.

9. 30분 실습: 같은 CPU 두 worker vs 서로 다른 CPU

Linux 개인 VM/container에서 실행한다. 허용 CPU가 2개 이상일 때 두 child가 각각 1.2 CPU-second를 계산하도록 하고, 같은 CPU에 pin한 phase와 다른 CPU에 pin한 phase의 wall time·run-queue wait를 비교한다. root와 외부 package가 필요 없다.

LAB_DIR=$(mktemp -d)
python3 - "$LAB_DIR" <<'PY'
import multiprocessing as mp
import os, queue, sys, time

lab = sys.argv[1]
if not hasattr(os, "sched_setaffinity"):
    raise SystemExit("Linux sched_setaffinity required")
allowed = sorted(os.sched_getaffinity(0))
if len(allowed) < 2:
    raise SystemExit("at least 2 effective CPUs required: " + repr(allowed))
cpu0, cpu1 = allowed[:2]
burn_cpu_seconds = 1.2

def schedstat():
    try:
        with open("/proc/self/schedstat") as f:
            values = [int(x) for x in f.read().split()[:3]]
        return tuple(values)
    except (FileNotFoundError, PermissionError, ValueError):
        return (0, 0, 0)

def worker(label, cpu, gate, resultq):
    os.sched_setaffinity(0, {cpu})
    resultq.put(("ready", label, os.getpid(), cpu,
                 sorted(os.sched_getaffinity(0))))
    if not gate.wait(5):
        raise SystemExit("start gate timeout")
    before = schedstat()
    wall0 = time.monotonic()
    cpu_start = time.process_time()
    loops, value = 0, 1
    while time.process_time() - cpu_start < burn_cpu_seconds:
        value = (value * 1103515245 + 12345) & 0x7fffffff
        loops += 1
    cpu_used = time.process_time() - cpu_start
    wall_used = time.monotonic() - wall0
    after = schedstat()
    resultq.put(("done", label, os.getpid(), cpu, cpu_used, wall_used,
                 (after[0]-before[0])/1e9,
                 (after[1]-before[1])/1e9,
                 after[2]-before[2], loops, value))

def run_phase(name, cpus):
    ctx = mp.get_context("fork")
    gate, resultq = ctx.Event(), ctx.Queue()
    workers = [ctx.Process(target=worker,
                           args=(f"w{i}", cpu, gate, resultq))
               for i, cpu in enumerate(cpus)]
    started = []
    try:
        for p in workers:
            p.start()
            started.append(p)
        ready = [resultq.get(timeout=5) for _ in workers]
        phase0 = time.monotonic()
        gate.set()
        done = [resultq.get(timeout=10) for _ in workers]
        phase_wall = time.monotonic() - phase0
        for p in workers:
            p.join(2)
        if any(p.exitcode != 0 for p in workers):
            raise RuntimeError("worker exit: " + repr([p.exitcode for p in workers]))
        return name, phase_wall, ready, done
    except queue.Empty as error:
        raise RuntimeError("worker result timeout") from error
    finally:
        for p in started:
            if p.is_alive():
                p.terminate()
                p.join()

phases = [run_phase("same-cpu", [cpu0, cpu0]),
          run_phase("split-cpu", [cpu0, cpu1])]
with open(lab + "/result.txt", "w") as f:
    f.write(f"effective={allowed} chosen={cpu0},{cpu1}\n")
    for name, phase_wall, ready, done in phases:
        f.write(f"{name} phase_wall_s={phase_wall:.3f}\n")
        for row in sorted(done, key=lambda x: x[1]):
            _, label, pid, cpu, cpu_s, wall_s, sched_cpu_s, wait_s, slices, loops, _ = row
            f.write(f"  {label} pid={pid} cpu={cpu} cpu_s={cpu_s:.3f} "
                    f"wall_s={wall_s:.3f} rq_wait_s={wait_s:.3f} "
                    f"sched_cpu_s={sched_cpu_s:.3f} slices={slices} "
                    f"loops={loops}\n")
PY

lscpu -e=CPU,CORE,SOCKET,NODE,ONLINE 2>/dev/null || true
printf 'shell_allowed='; sed -n '/^Cpus_allowed_list:/p' /proc/self/status
test -r /sys/fs/cgroup/cpuset.cpus.effective &&
  printf 'cgroup_effective=' && sed -n '1p' /sys/fs/cgroup/cpuset.cpus.effective
sed -n '1,20p' "$LAB_DIR/result.txt"

예상: 같은 CPU에서는 두 worker의 합 2.4 CPU-second 때문에 phase wall이 약 2.4초 이상이고 runnable wait가 커진다. 서로 다른 physical capacity를 실제로 동시에 쓸 수 있으면 split phase는 약 1.2초에 가까워진다.

split이 빨라지지 않으면 실패가 아니라 증거다. 두 logical CPU가 같은 SMT core인지, container cpu.max가 1 CPU인지, VM vCPU가 host에서 동시 실행되는지, system load·capacity가 같은지 확인한다. 이어 same-SMT-sibling과 different-core를 topology로 골라 반복한다.

10. production 실패 시나리오

상황: low-latency service worker 12개를 CPU 2 하나에 잘못 pin한다. host 전체 CPU는 18%라 autoscaler는 정상으로 보지만 request p99가 4초이고 CPU2 run queue만 포화된다.

원인: main PID mask만 검사했고 runtime이 생성한 모든 thread가 parent의 single-CPU mask를 상속했다. scheduler는 affinity 밖의 idle CPU로 task를 옮길 수 없다.

증거: ps -L의 PSR, TID별 Cpus_allowed_list/schedstat, per-CPU utilization/run queue, cpuset effective, cpu.max, migrations와 application queue age를 같은 timeline에서 본다.

대응: canary에서 worker mask를 physical core pool로 넓히고 IRQ/control-plane reserve를 유지한다. topology·NUMA를 반영해 재배치하고 p99·cache miss·migration·throughput 회귀 test 후 rollout한다.

11. 대기업 면접 질문 3개

Q1. Linux가 global run queue 대신 per-CPU run queue를 쓰는 이유와 대가는?
답변 포인트: local lock/cache로 scheduling decision을 병렬화해 확장성과 locality를 얻는다. 즉각적 global fairness와 균형을 잃으므로 wakeup placement, newly-idle/periodic domain balancing, migration locking이 필요하고 cache/NUMA 비용과 trade-off한다.

Q2. CPU affinity를 설정하면 어떤 일이 보장되고 무엇은 보장되지 않습니까?
답변 포인트: thread가 실행 가능한 logical CPU mask를 제한하고 현재 CPU가 밖이면 migrate한다. effective set은 requested∩online/present∩cpuset이며 per-thread·fork 상속·exec 보존이다. exclusive core, CPU time, latency, physical core 분리, NUMA locality는 별도 보장이다.

Q3. CPU0 100%, CPU1 0%인데 scheduler가 task를 안 옮긴다면 무엇을 확인합니까?
답변 포인트: task runnable 여부와 affinity/cpuset, RT/deadline class, migration-disabled/lock state, CPU capacity, cache-hot/NUMA cost, cgroup quota, isolated CPU, VM steal을 확인한다. task count가 아니라 utilization/capacity·runqueue wait와 trace evidence로 판단한다.
