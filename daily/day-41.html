실패 실습: partial write와 crash-safe file update

한 줄 요약: write() 성공은 요청한 모든 byte나 disk durability를 뜻하지 않는다. 반환한 byte 수만큼 전진하는 loop와 temp write→file fsync→same-filesystem rename→directory fsync protocol을 사용해야 crash 뒤 OLD 또는 완전한 NEW만 허용할 수 있다.

1. 초보자 용어 사전

short / partial writewrite(fd, buf, N)가 오류가 아닌 양수 n < N을 반환해 일부 byte만 받아들인 상태.
torn writecrash·device failure로 하나의 logical record/block 일부만 새 값이 된 상태. syscall partial return과 원인은 다르지만 결과 검증이 필요하다.
EINTRsignal 때문에 syscall이 중단됐다는 errno. Linux write는 byte를 하나도 쓰기 전에 중단된 경우 EINTR을 반환한다.
ENOSPC / EDQUOTdevice 공간 부족 / 사용자·project quota 초과. 이미 일부 write가 성공한 다음 호출에서 나타날 수 있다.
delayed EIOpage cache에 받아들인 write가 나중 writeback에서 실패해 이후 write나 fsync에서 보고되는 I/O error.
O_TRUNC기존 regular file을 open 시 길이 0으로 줄이는 flag. 이후 write 실패 시 원본이 이미 사라졌을 수 있다.
temp file완성 전에는 target pathname으로 공개하지 않는 staging file. target과 같은 directory/filesystem에 둬야 atomic rename을 쓸 수 있다.
atomic rename같은 mounted filesystem에서 target name을 한 순간에 교체하는 namespace operation. visibility atomicity이지 자동 durability는 아니다.
fsyncfile의 dirty data와 관련 metadata를 storage로 보내고 completion 또는 error를 기다리는 system call.
directory fsyncrename으로 바뀐 name→inode 관계 자체의 durability를 요구하는 단계.
reconciliation결과가 uncertain할 때 retry만 하지 않고 version·checksum·target 상태를 다시 읽어 실제 적용 여부를 판정하는 절차.

2. mental model: 완성본 교체와 프린터 잉크 부족

기존 계약서 위에 바로 인쇄하다 잉크가 떨어지면 앞부분만 새 내용이고 뒤는 옛 내용이거나 file 길이가 잘린다. 안전한 방법은 별도 종이에 끝까지 인쇄하고 검수·봉인한 뒤, 표지의 계약서 이름을 한 번에 새 종이로 바꾸고 서류함 색인까지 확정하는 것이다. write_all은 끝까지 인쇄, file fsync는 봉인, rename은 표지 교체, directory fsync는 색인 확정이다.

3. architecture: byte가 durable name이 되기까지

  │ write(fd, remaining)

  │   EINTR      → 같은 remaining 재시도

  ▼

      ─rename→ NEW atomically visible ─fsync(parent dir)→ durable NEW name

5. CS·kernel deep dive

5.1 write의 return value가 protocol state다

write는 최대 count byte를 쓰며 성공해도 더 작은 양수를 반환할 수 있다. cursor는 요청량이 아니라 실제 반환값만큼만 전진해야 한다. 처음부터 다시 쓰면 중복, 요청량만큼 전진하면 hole/누락이 생긴다. 0 return은 regular-file progress invariant 위반으로 fatal 처리하는 편이 안전하다.

5.2 EINTR와 partial success를 함께 처리한다

Linux에서는 아무 byte도 쓰기 전에 signal로 중단되면 -1/EINTR이다. byte를 쓴 뒤 중단되면 성공한 byte 수를 반환한다. 따라서 EINTR은 remaining buffer 그대로 retry하고, 양수는 errno와 무관하게 그 수만큼 progress로 반영한다.

5.3 successful write는 allocation·media completion이 아니다

buffered write는 page cache copy 뒤 성공할 수 있다. NFS를 포함한 일부 filesystem에서는 space reservation 실패도 뒤늦게 나타날 수 있다. 완료한 payload 전체를 쓴 뒤 fsync 결과까지 확인해야 durable success를 말할 수 있다.

5.4 Linux writeback error cursor

kernel은 address_space의 writeback error stream을 추적하고, file description별 cursor를 통해 당시 열려 있던 descriptor의 fsync에 error를 보고한다. “write에서 EIO가 없었다”는 증거만으로 storage 성공을 결론 내리면 안 된다.

5.5 in-place overwrite는 multi-byte atomicity가 없다

regular-file write가 여러 page/block을 건너가면 crash 시 어떤 prefix가 persistence됐는지 application이 통제하기 어렵다. O_TRUNC 후 overwrite는 시작 순간 OLD를 제거하므로 error rollback이 불가능하다. small aligned write라도 hardware/filesystem별 atomicity를 문서 없이 가정하지 않는다.

5.6 O_DIRECT error는 범위 전체 실패를 뜻하지 않는다

Linux write(2)는 direct I/O error 뒤에도 일부 data가 써졌을 수 있어 해당 range를 inconsistent로 취급하라고 명시한다. direct I/O는 page cache 우회이지 transaction 또는 durability primitive가 아니다.

5.7 preallocation은 실패 확률을 줄이지 원자성을 만들지 않는다

fallocate로 space를 예약하면 late ENOSPC 위험과 fragmentation을 줄일 수 있지만 quota change, device EIO, metadata failure는 남는다. allocation 성공 뒤에도 write loop, fsync, checksum, rename protocol이 필요하다.

5.8 rename의 atomicity는 같은 mounted filesystem 안이다

target이 있으면 rename은 atomically replace하지만 cross-mount는 EXDEV로 실패한다. /tmp에서 copy 후 target을 덮는 fallback을 atomic이라고 부르면 안 된다. temp를 target directory에 만들고 directory fd 기반 API로 path race도 줄인다.

5.9 checksum과 generation은 publication 검증 계약이다

payload에 schema version, monotonic generation, length, checksum을 넣으면 startup이 partial/torn/stale file을 구분할 수 있다. checksum은 corruption을 고치는 backup은 아니므로 OLD copy, replica 또는 source of truth도 필요하다.

5.10 concurrent writer는 last rename wins 문제다

각 writer가 crash-safe해도 둘이 동시에 OLD를 읽고 서로 다른 NEW를 rename하면 lost update가 생긴다. lock, generation compare-and-swap, single writer, RENAME_NOREPLACE 등 별도의 concurrency policy가 필요하다.

7. 실무 best practice

  • write wrapper는 short count, EINTR, zero progress, count overflow를 명시적으로 처리하고 실제 byte count를 metric으로 남긴다.
  • target과 같은 directory에 mode 0600·exclusive unique temp를 만들고 완성 뒤 최종 permission·owner·xattr를 설정한다.
  • payload는 header(version, generation, length) + body + checksum/footer 구조로 만들어 startup 검증이 가능하게 한다.
  • 모든 byte와 필수 metadata 설정 후 file fsync, 그 뒤 rename, 그 뒤 parent directory fsync 순서를 고정한다.
  • fsync 성공 뒤에만 durable acknowledgment를 외부에 보낸다. group commit을 쓰면 최대 loss window를 RPO로 명시한다.
  • ENOSPC 대비 reserve, quota alert, temp cleanup policy를 두되 preallocation 성공을 durability로 오해하지 않는다.
  • temp filename에 service instance와 random nonce를 넣고, recovery는 checksum·ownership marker를 확인한 자기 temp만 정리한다.
  • same-directory protocol, NFS/overlay/container volume 의미, directory fsync 지원을 실제 배포 filesystem에서 crash test한다.
  • concurrent writer는 generation conflict로 검출하고 blind overwrite/retry하지 않는다.

8. error handling runbook

  1. short positive: written prefix를 확정하고 buffer pointer·offset·remaining을 n만큼만 이동한다.
  2. EINTR: progress가 없는 호출만 같은 remaining으로 retry한다. retry budget보다 cancellation/deadline 상태도 확인한다.
  3. EAGAIN: nonblocking fd면 readiness를 기다리고 busy loop를 피한다. regular file API와 stream API의 정책을 분리한다.
  4. ENOSPC/EDQUOT/EFBIG: target publication을 중단하고 temp를 진단 가능하게 격리한다. 공간을 비운 뒤 같은 fd를 맹목적으로 이어 쓰지 말고 payload checksum부터 재평가한다.
  5. EIO/fsync failure: 성공을 응답하지 않고 filesystem/device health를 조사한다. 다른 file의 writeback failure일 가능성도 correlation한다.
  6. EXDEV: atomic rename 요구를 낮추지 않는다. target filesystem 안에 staging 영역을 다시 설계한다.
  7. rename uncertain: NFS timeout/error라면 미실행을 가정하지 말고 target generation/checksum을 reread한다.
  8. directory fsync failure: NEW가 runtime에 보일 수 있지만 durable success는 아니다. 상태를 uncertain으로 기록하고 reboot-safe reconciliation을 예약한다.
  9. startup: target checksum/version을 검증하고 owned orphan temp만 quarantine/cleanup하며 source of truth와 reconcile한다.

9. 놓치기 쉬운 함정

  • ret >= 0이면 전체 성공: 반드시 ret == requested 또는 loop 완료를 확인한다.
  • EINTR이면 아무것도 안 써짐: portable code는 반환 byte 수를 우선 해석한다.
  • close가 fsync 대체: close 성공도 disk durability를 보장하지 않는다.
  • fflush가 media flush: stdio buffer를 kernel로 보낼 뿐이다.
  • O_DIRECT가 atomic/durable: cache bypass와 crash consistency는 다른 문제다.
  • O_TRUNC 뒤 실패하면 OLD로 rollback: truncation 자체가 이미 namespace의 inode 내용을 파괴했다.
  • rename 뒤 file fsync만 추가: directory entry durability는 parent directory fsync가 담당한다.
  • orphan temp를 나이만 보고 삭제: 다른 live writer의 staging file일 수 있다.

10. 30분 실패 실습

고의 short writer와 fault point를 사용해 unsafe in-place update는 target을 훼손하고 safe replace는 OLD를 보존함을 검증한다. process crash를 흉내 낸 논리 실습이며 실제 power-cut 보장 시험은 별도 장비/VM에서 수행한다.

python3 - <<'PY'
import hashlib, os, pathlib, tempfile

OLD=b'gen=1\nbody=OLD\n'
NEW=b'gen=2\nbody=NEW-COMPLETE\n'

def write_all(fd, data, max_chunk=5, fail_after=None):
    done=0
    while done < len(data):
        if fail_after is not None and done >= fail_after:
            raise OSError('injected ENOSPC')
        chunk=data[done:done+max_chunk]
        n=os.write(fd, chunk)       # 실제 반환값만큼 전진
        if n == 0: raise OSError('zero progress')
        done += n
    return done

def sync_dir(path):
    fd=os.open(path, os.O_RDONLY)
    try: os.fsync(fd)
    finally: os.close(fd)

with tempfile.TemporaryDirectory(prefix='os-day41-') as raw:
    d=pathlib.Path(raw); target=d/'config'
    target.write_bytes(OLD)

    # unsafe: truncate 뒤 일부만 쓰고 실패 → OLD 소실
    fd=os.open(target, os.O_WRONLY|os.O_TRUNC)
    try:
        try: write_all(fd, NEW, fail_after=10)
        except OSError: pass
    finally: os.close(fd)
    assert target.read_bytes() == NEW[:10]
    print('unsafe=',target.read_bytes())

    # safe: temp 실패는 target OLD를 건드리지 않음
    target.write_bytes(OLD); temp=d/'.config.tmp-owned'
    fd=os.open(temp, os.O_WRONLY|os.O_CREAT|os.O_EXCL, 0o600)
    try:
        try: write_all(fd, NEW, fail_after=10)
        except OSError: pass
    finally: os.close(fd)
    assert target.read_bytes() == OLD
    temp.unlink()

    # complete protocol
    fd=os.open(temp, os.O_WRONLY|os.O_CREAT|os.O_EXCL, 0o600)
    try:
        assert write_all(fd, NEW) == len(NEW)
        os.fsync(fd)
    finally: os.close(fd)
    os.replace(temp, target)
    sync_dir(d)
    assert target.read_bytes() == NEW
    print('safe_sha256=',hashlib.sha256(target.read_bytes()).hexdigest())
PY
  1. 0~10분: max_chunk를 바꾸며 write_all이 정확히 N byte를 전달하는지 확인한다.
  2. 10~20분: fail_after=10에서 unsafe target은 partial NEW, safe target은 OLD임을 비교한다.
  3. 20~30분: generation·length·checksum header를 추가하고 startup quarantine decision table을 작성한다.

12. 실패 시나리오

배포 agent가 config를 O_TRUNC로 열고 한 번의 write를 성공으로 간주했다. quota가 임계치에 도달해 64KiB 중 12KiB만 써졌지만 return value를 확인하지 않았고, close 뒤 성공을 응답했다. 새 process는 partial JSON을 읽지 못해 재시작 loop에 빠졌다. 해결은 same-directory temp, write_all, schema/generation/checksum 검증, fsync(temp), atomic rename, fsync(dir), durable ack 순서였고, ENOSPC injection과 startup fallback을 release gate에 추가했다.
