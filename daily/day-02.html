한 줄 요약
user program은 임의의 kernel 함수를 호출하지 않는다. 정해진 system-call ABI에 번호와 인자를 놓고 CPU의 통제된 진입 명령을 실행하면, kernel이 호출자를 대신해 권한이 필요한 작업을 검증·수행하고 결과를 돌려준다.

1. 초보자를 위한 용어 사전

User modeapplication이 실행되는 제한된 CPU 권한 상태. 임의의 device 접근, page table 변경 같은 privileged operation을 직접 할 수 없다.
Kernel modeOS kernel이 hardware와 모든 주소 공간을 관리할 수 있는 높은 권한 상태. “root 사용자”와 다른 개념이다.
System callapplication이 kernel service를 요청하는 안정된 binary interface. Linux에서는 system call number와 architecture별 register 규약을 사용한다.
ABIApplication Binary Interface. 인자를 어느 register에 두고 결과를 어디서 받는지 같은 binary 수준 계약.
Trap넓게는 현재 instruction과 동기적으로 CPU 제어를 OS handler로 넘기는 사건. 교재와 CPU 문서마다 좁은 분류가 다르므로 문맥을 확인한다.
Interruptdevice·timer 등 현재 instruction 흐름 바깥에서 비동기적으로 도착할 수 있는 사건.
Exceptiondivide-by-zero, page fault처럼 instruction 실행 중 CPU가 감지한 동기 사건. 정상 복구 가능한 fault와 치명적 abort 등이 있다.
libc wrapperC library가 제공하는 `read()` 같은 함수. architecture별 syscall 진입과 오류를 `errno`로 바꾸는 세부를 감춘다.

2. Mental model: 호텔 프런트가 아니라 보호된 API gateway

user/kernel 경계를 “kernel에게 부탁하는 창구”라고 이해하면 시작하기 쉽다. 하지만 더 정확한 핵심은 권한 분리와 검증이다. 모든 program에 device와 memory 관리 권한을 주면 한 process의 버그가 다른 process와 kernel을 망가뜨릴 수 있다. CPU와 MMU는 kernel만 특정 instruction·address를 사용할 수 있도록 강제하고, system call entry만 통제된 문으로 연다.

구분: root process도 평소에는 user mode에서 실행된다. root는 OS가 확인하는 credential이 강한 사용자일 뿐, application instruction이 계속 kernel mode에서 실행된다는 뜻이 아니다.

3. Architecture: `read(fd, buf, n)`의 경계 왕복

1 · App`read(fd, buf, n)` 호출. 아직 일반 function-call 문맥.
2 · libcABI에 맞춰 syscall number와 인자를 register에 배치.
3 · CPU entryx86-64라면 보통 `syscall` instruction. return 위치·flags를 보존하고 kernel entry로 이동.
4 · Entry codearchitecture state와 kernel stack/frame을 정립하고 tracing·seccomp·audit 등 진입 작업 수행.
5 · Handlerfd와 접근 권한, user buffer 범위를 검증하고 VFS/device path에서 데이터를 읽음.
6 · Exitreturn value를 저장하고 signal·task work·reschedule 필요를 처리한 뒤 user state 복원.
7 · App성공 byte 수, EOF 0, 또는 `-1`과 `errno`를 보고 partial result까지 처리.

4. CS Deep Dive: syscall은 context switch인가?

항상 process/thread context switch인 것은 아니다. system call entry는 user mode에서 kernel mode로 execution domain을 바꾸고 register state와 stack/frame을 다룬다. 그러나 같은 thread가 kernel code를 실행하다 그대로 user mode로 돌아올 수 있다. kernel 안에서 I/O를 기다리며 block되거나 더 높은 우선순위 task가 runnable이면 그때 scheduler가 다른 task로 context switch할 수 있다.

전이무엇이 바뀌나task가 바뀌나
Function call같은 privilege, call frame아니오
System call entryuser → kernel, entry state필수 아님
Scheduler context switchCPU register·address-space 관련 실행 context예

Linux의 공통 syscall 진입 경로는 단순히 handler를 호출하지 않는다. kernel 문서에 따르면 RCU/context tracking, lockdep, tracing 상태를 순서대로 갱신하고 ptrace, seccomp, audit, syscall tracing 같은 entry work를 처리한다. return 직전에는 signal과 task work도 확인한다. 그래서 “mode bit 하나만 바꾼다”는 설명은 지나치게 얕다.

5. Trap, exception, interrupt를 섞지 않는 법

  • 동기성: syscall과 divide-by-zero는 현재 instruction 흐름에 동기적이다. keyboard/network interrupt는 보통 비동기다.
  • 의도: syscall은 application이 의도적으로 요청한다. page fault는 memory access의 결과로 발생하지만 demand paging에서는 정상 처리 경로일 수 있다.
  • 용어 문맥: x86의 `SYSCALL`은 전용 fast-entry instruction이다. 이를 교재 수준에서 “software trap”이라 부를 수 있지만, `int 0x80`과 동일한 hardware path라고 단정하면 틀린다.
  • handler 이후: faulting instruction을 재시작할지, 다음 instruction으로 갈지, process에 signal을 보낼지는 사건 종류와 처리 결과에 달렸다.

6. Error handling: return value가 protocol이다

`read()`는 요청한 `n`보다 적은 byte를 읽고도 성공할 수 있다. 0은 EOF이며 `-1`일 때만 `errno`가 오류 이유를 나타낸다. wrapper가 없는 syscall을 `syscall()`로 직접 호출하면 architecture별 ABI와 kernel/version 차이를 호출자가 떠안는다.

EINTRsignal로 중단. operation이 아무 효과도 없었는지 API 계약을 확인한 뒤 재시도한다.
EAGAIN/EWOULDBLOCKnonblocking 자원이 지금 준비되지 않음. busy loop 대신 readiness/timeout/backoff와 연결한다.
EFAULTkernel이 접근할 수 없는 user address. 보통 application bug 또는 잘못된 직접 syscall.
ENOSYS해당 syscall number가 구현되지 않음. runtime feature detection 또는 fallback 필요.
함정: `errno`는 모든 성공 호출 뒤 0으로 초기화되지 않는다. 함수가 실패를 표시했을 때만 즉시 읽고, 로그를 위해 다른 함수부터 호출해 값을 덮어쓰지 않는다.

7. Production Best Practice

  • 표준 wrapper 우선: libc/runtime이 ABI, cancellation, compatibility를 처리하게 한다. 직접 syscall은 wrapper가 없고 fallback을 통제할 때만 고려한다.
  • 입력 검증: kernel이 user pointer를 신뢰하지 않듯, service boundary에서도 size, ownership, lifetime을 검증한다.
  • syscall budget: 작은 read/write 반복은 경계 왕복과 downstream I/O 비용을 키운다. correctness를 지키면서 batching과 buffering을 측정한다.
  • 관찰 도구: `strace` 결과가 곧 병목 원인은 아니다. 호출 횟수·latency·block 상태·page cache·device latency를 함께 본다.
  • 보안: seccomp allowlist는 필요한 syscall surface를 줄이지만 argument semantics와 application update를 함께 관리해야 한다.

8. 놓치기 쉬운 예외: vDSO

모든 “system API” 호출이 실제 privilege transition을 만들지는 않는다. Linux는 시간 조회처럼 자주 호출되고 공개 가능한 정보를 vDSO라는 작은 ELF image로 process에 mapping할 수 있다. libc는 가능한 경우 kernel mode 진입 없이 user-space function과 memory read로 답한다. 그래서 `strace`에 `clock_gettime`이 보이지 않는 경우가 있으며, “관찰 안 됨 = 호출 안 함”으로 단정하면 안 된다.

9. 30분 실습: wrapper와 syscall을 관찰

Linux 준비: `strace`와 C compiler가 있는 환경에서 실행한다. macOS의 `dtruss`는 권한·SIP 제약이 있으므로 결과가 다를 수 있다.

# 1) shell built-in과 외부 program을 구분해 관찰
strace -f -e trace=read,write,openat,close /bin/echo hello

# 2) syscall 통계
strace -c /bin/sh -c 'printf hello >/tmp/os-day02.txt'

# 3) vDSO 가능성을 관찰
strace -e trace=clock_gettime python3 -c \
  'import time; [time.clock_gettime(time.CLOCK_REALTIME) for _ in range(1000)]'

기록할 것: application function 수와 실제 syscall 수가 같은지, `write`의 return byte 수, file open/close 순서, clock 호출이 trace에 나타나는지를 표로 남긴다.

실패 시나리오: `strace: command not found`면 도구 부재다. permission denied면 ptrace 정책·container capability를 확인한다. trace가 비어 있으면 필터 이름, vDSO, 다른 architecture ABI를 가설로 분리한다. 권한을 무작정 높이기 전에 관찰 범위를 확인한다.

10. 대기업 면접 질문 3개

  1. System call과 function call의 차이는?
    답변 포인트: privilege boundary, ABI, controlled entry, kernel validation, return/error protocol을 말한다. syscall도 libc wrapper라는 function을 통해 보통 호출된다는 계층을 분리한다.
  2. System call마다 context switch가 발생하나?
    답변 포인트: mode transition과 task switch를 구분한다. 같은 thread가 kernel을 실행하고 바로 복귀할 수 있지만 blocking·preemption이면 scheduler switch가 추가될 수 있다.
  3. `read(fd, buf, 4096)`이 100 byte만 반환하면 오류인가?
    답변 포인트: short read는 성공 가능, 0은 EOF, -1과 errno가 오류다. protocol/pipe/socket에서는 원하는 길이만큼 loop하되 EINTR·EAGAIN·timeout을 구분한다.
