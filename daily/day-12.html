Linux CFS에서 EEVDF로 이어지는 mental model

한 줄 요약 — CFS는 weight로 보정한 vruntime이 가장 뒤처진 task를 골라 장기 CPU share를 맞췄고, EEVDF는 여기에 lag로 받을 자격을 제한한 뒤 가장 이른 virtual deadline을 선택해 fairness와 latency 요구를 더 분리한다. virtual deadline은 실시간 완료 보장이 아니다.

1. 선수 용어 사전

fair classLinux의 normal task(SCHED_OTHER/NORMAL, BATCH, IDLE)를 다루는 scheduling class. RT·DEADLINE class와 별도다.
scheduling entityscheduler가 CPU service를 배분하는 단위. thread일 수도 있고 group scheduling에서는 task group을 대표할 수도 있다.
weightnice에서 변환되는 상대 CPU share 값. weight가 클수록 같은 실제 CPU time에 vruntime이 천천히 증가한다.
vruntimevirtual runtime. 실제 실행 시간을 weight로 정규화한 공정성 좌표. 작을수록 상대적으로 service를 덜 받은 상태다.
min_vruntimerun queue의 virtual timeline이 전진한 기준점. CFS 문서는 단조 증가하며 새/깨어난 entity 배치에 쓰인다고 설명한다.
red-black tree삽입·삭제·검색을 O(log n)에 유지하는 balanced binary search tree. fair run queue의 ordered timeline을 구현한다.
ideal service모든 runnable entity가 weight 비율대로 나눴다면 지금까지 받았어야 할 CPU service.
lagideal service−actual service의 공정성 빚 mental model. 양수면 CPU를 받을 빚이 남았고 음수면 share보다 앞서 받았다.
eligibilityEEVDF가 next 후보로 인정하는 조건. Linux 문서는 lag≥0인 entity를 eligible로 설명한다.
virtual deadlinevirtual timeline에서 이번 service request가 끝나야 할 순서 좌표. wall-clock deadline이나 SCHED_DEADLINE 보장이 아니다.
requested sliceentity가 한 번에 받고자 하는 service 크기. 짧은 request는 VD를 앞당겨 latency에 유리할 수 있지만 switch 비용을 늘릴 수 있다.
deferred dequeuesleeping entity를 즉시 완전히 제거하지 않고 lag가 virtual time에 따라 decay하도록 표시하는 현재 EEVDF sleep 처리 방식.

2. mental model: 주행거리계에서 빚 장부+예약표로

CFS 주행거리계: 각 task의 실제 주행 시간을 weight로 보정해 vruntime 계기판에 더한다. 가장 작은 계기판, 즉 가장 덜 달린 task를 먼저 태운다.

EEVDF 빚 장부: 먼저 “이 task가 공정 share보다 덜 받아 CPU를 받을 자격이 있는가?”를 lag로 거른다. 이미 앞서 받은 task는 짧은 slice를 요청해도 잠시 제외된다.

EEVDF 예약표: eligible task 중 이번 요청의 virtual deadline이 가장 이른 task를 고른다. 짧은 요청은 빨리 응답받되 eligibility가 장기 share 탈취를 막는 구조다.

4. 숫자로 잡는 공정성 좌표

Δvruntime ≈ Δexec × NICE_0_LOAD / weight. NICE_0_LOAD를 1024라고 단순화하자.

A: weight 10242ms 실행 → vruntime +2. A는 기준 속도로 virtual clock이 간다.
B: weight 5121ms 실행 → vruntime +2. 낮은 weight라 실제 CPU를 절반만 받아도 A와 virtual progress가 맞는다.

따라서 둘이 계속 runnable이면 장기 actual service는 약 2:1을 향한다. vruntime의 목표는 실제 밀리초를 같게 만드는 것이 아니라 weight-normalized service를 맞추는 것이다.

EEVDF snapshot에서 total service=10, weights A:B:C=2:2:1이면 ideal은 4:4:2다. actual이 5:2:3이면 lag는 A=-1, B=+2, C=-1이므로 우선 B만 eligible하다. 여러 entity가 eligible일 때 그중 VD가 가장 이른 요청이 next가 된다.

5. CS·kernel·hardware deep dive

5.1 CFS의 ideal multitasking CPU 근사

이상적인 CPU가 n개 runnable task를 무한히 잘게 동시에 실행한다면 각 task는 weight 비율의 service를 받는다. 실제 CPU는 하나만 실행할 수 있으므로 CFS는 vruntime이 작은 entity를 골라 이상적 timeline과의 차이를 줄인다.

ordered red-black tree의 왼쪽에는 뒤처진 entity가 있고 실행한 entity는 vruntime이 증가해 오른쪽으로 이동한다. 삽입·삭제 O(log n), cached leftmost로 next lookup을 효율화한다. granularity는 너무 잦은 preemption과 cache trashing을 막는다.

5.2 CFS는 고전적 fixed-quantum RR이 아니다

CFS 문서는 nanosecond accounting과 vruntime distance를 중심으로 설명하며, 옛 scheduler의 고정 quantum array와 다르다. base slice/granularity는 batching↔latency를 조정하지만 timer tick마다 무조건 task를 교체하는 계약이 아니다.

nice를 높이면 weight가 줄어 vruntime이 빨리 증가하므로 덜 실행된다. 그러나 share와 wakeup latency를 같은 weight 축만으로 조정하면 “같은 share를 유지하면서 더 짧은 응답 주기”를 표현하기 어렵다.

5.3 EEVDF는 fairness gate와 latency ordering을 분리한다

lag≥0이라는 gate는 fair share를 덜 받은 entity만 후보로 만든다. 그 안에서 virtual deadline은 request size를 weight-normalized virtual distance로 반영한다. 짧은 slice는 VD가 가까워 first response를 앞당길 수 있다.

하지만 짧은 slice task가 service를 앞서 받으면 lag가 음수가 되어 eligibility를 잃는다. 이 조합이 “짧은 요청 우선”과 “장기 share 보존”을 함께 노린다. 아래 실습의 VD 식은 이 원리를 보여주는 축약 model이며 kernel emulator가 아니다.

5.4 virtual deadline ≠ real-time deadline

EEVDF의 VD는 fair class 내부 선택 순서 좌표다. “10ms 안에 완료” 같은 wall-clock guarantee, admission control, runtime/deadline/period contract는 SCHED_DEADLINE의 영역이다.

CPU overload, higher scheduling class, IRQ, lock, affinity, cgroup throttling이 있으면 EEVDF task의 actual dispatch는 늦을 수 있다. API SLO는 application queue→completion histogram으로 별도 측정한다.

5.5 sleeper가 공정성 빚을 reset하는 문제

sleeping task를 즉시 새 task처럼 취급하면 짧게 sleep/wakeup을 반복해 매번 유리한 위치를 얻는 공격이 가능하다. 반대로 과거 음수 lag를 영원히 유지하면 오래 잔 interactive task의 wakeup latency가 나빠진다.

현재 kernel 문서는 sleeping task를 deferred dequeue 상태로 run queue에 남겨 virtual runtime에 따라 lag를 decay시키고, 오래 자면 결국 reset되도록 설명한다. 이 영역은 ongoing discussion이므로 운영 문서는 kernel version과 source를 함께 고정한다.

5.6 hierarchy와 multicore에서는 entity가 thread 하나가 아니다

CONFIG_FAIR_GROUP_SCHED에서는 cgroup/task group도 scheduling entity가 되어 parent share를 먼저 받고 내부 child가 다시 나눈다. task nice만 봐서는 host 전체 share를 설명할 수 없다.

Day 11처럼 CPU마다 cfs_rq가 있고 migration 때 virtual timeline을 보정한다. 서로 다른 CPU의 raw vruntime 숫자를 단순 비교하거나 /proc 값 하나를 global fairness score로 쓰지 않는다.

5.7 짧은 slice의 hardware 비용

slice를 줄이면 latency-sensitive task가 빨리 돌아올 수 있지만 context switch, scheduler code, cache/TLB/predictor working-set 교대가 늘어난다. CPU가 같은 task를 재선택하면 switch가 없을 수도 있으므로 slice event와 switch를 동일시하지 않는다.

최적값은 workload dependent다. first-response p99, completions/s, context-switches, cache miss, CPU migration, energy를 같이 sweep하고 tiny request를 무제한 허용하지 않는다.

6. 실무 best practice

  1. kernel과 scheduler evidence를 먼저 고정한다. uname, distro config, policy, nice/cgroup, affinity/quota를 기록하고 “Linux면 CFS”라고 뭉뚱그리지 않는다.
  2. share와 latency SLO를 분리한다. CPU service ratio·runqueue wait와 first-response/completion p99를 각각 정의한다.
  3. nice는 entitlement, slice는 cadence hint로 본다. 짧은 slice로 CPU share를 얻으려 하지 않고 cgroup weight·quota와 함께 설계한다.
  4. custom slice는 feature-detect한다. kernel/man-pages가 지원하는 ABI와 privilege·range를 확인하고 실패 시 default로 fallback한다.
  5. sleep/wakeup workload로 regression test한다. CPU-bound만 돌리지 말고 interactive burst, many sleepers, fork storm, cgroup throttle을 replay한다.
  6. 내부 /proc field에 alert contract를 걸지 않는다. field 존재·단위·semantics를 version별 검증하고 stable application metric과 schedstat delta를 중심으로 본다.
  7. scheduler tuning 전에 overload를 막는다. EEVDF도 capacity를 만들지 않는다. bounded queue, backpressure, admission, quota를 먼저 둔다.

8. 놓치기 쉬운 함정

  • EEVDF virtual deadline을 SCHED_DEADLINE의 wall-clock deadline과 혼동하지 않는다.
  • CFS를 fixed-quantum round robin이라고 설명하지 않는다.
  • vruntime이 실제 CPU nanoseconds와 같다고 보지 않는다. weight-normalized coordinate다.
  • 가장 작은 raw vruntime을 CPU 전체에서 직접 비교하지 않는다. per-rq 기준과 migration 보정이 있다.
  • 짧은 slice가 long-term CPU share까지 늘린다고 생각하지 않는다. eligibility가 과다 service를 제한한다.
  • kernel 6.6 이상이라는 version만으로 vendor kernel의 정확한 EEVDF behavior를 단정하지 않는다.
  • cfs_rq라는 이름이 남았다는 이유로 pick policy가 옛 CFS 그대로라고 결론 내리지 않는다.
  • 평균 CPU share가 공정하다는 사실로 짧은 window starvation·p99 latency까지 증명하지 않는다.

9. 30분 실습: CFS-like와 EEVDF-like 선택 비교

표준 Python으로 축약 simulator를 실행한다. A/B는 같은 weight지만 B만 짧은 request를 갖고 C는 절반 weight다. 실제 kernel emulator가 아니라 vruntime→eligibility+VD 차이를 분리하는 사고 실험이다.

LAB_DIR=$(mktemp -d)
python3 - "$LAB_DIR" <<'PY'
from dataclasses import dataclass
import copy, sys
from typing import Optional

@dataclass
class Task:
    name: str
    weight: int
    request: int
    service: int = 0
    vruntime: float = 0.0
    first: Optional[int] = None

base = [Task("A", 1024, 4),
        Task("B", 1024, 1),
        Task("C", 512, 2)]

def run(mode, ticks=25):
    tasks = copy.deepcopy(base)
    timeline, rows = [], []
    total_weight = sum(t.weight for t in tasks)
    for now in range(ticks):
        total_service = sum(t.service for t in tasks)
        lag = {t.name: total_service * t.weight / total_weight - t.service
               for t in tasks}
        if mode == "CFS-like":
            candidates = tasks
            chosen = min(candidates, key=lambda t: (t.vruntime, t.name))
            vd = None
        else:
            candidates = [t for t in tasks if lag[t.name] >= -1e-9]
            chosen = min(candidates,
                         key=lambda t: (t.vruntime +
                                        t.request * 1024 / t.weight,
                                        t.name))
            vd = chosen.vruntime + chosen.request * 1024 / chosen.weight
        if chosen.first is None:
            chosen.first = now
        rows.append((now, chosen.name, lag[chosen.name], vd))
        timeline.append(chosen.name)
        chosen.service += 1
        chosen.vruntime += 1024 / chosen.weight
    return tasks, timeline, rows

lines = []
for mode in ("CFS-like", "EEVDF-like"):
    tasks, timeline, rows = run(mode)
    lines.append(f"{mode} timeline={' '.join(timeline)}")
    for t in tasks:
        lines.append(f"  {t.name}: weight={t.weight} request={t.request} "
                     f"service={t.service} vruntime={t.vruntime:.1f} "
                     f"first={t.first}")
    lines.append("  first 8 decisions: " + ", ".join(
        f"t={now}:{name}(lag={lag:+.2f}" +
        (f",vd={vd:.2f})" if vd is not None else ")")
        for now, name, lag, vd in rows[:8]))
with open(sys.argv[1] + "/result.txt", "w") as f:
    f.write("\n".join(lines) + "\n")

관찰: CFS-like는 동일 vruntime tie에서 A를 먼저 고르지만 EEVDF-like는 같은 weight의 B가 짧은 request라 t=0에 선택된다. B가 앞서 service를 받으면 lag가 음수가 되어 연속 독점하지 못하고, 25 tick 뒤 service는 weight 2:2:1 비율에 근접한다.

확장: B request를 1→4→8로 바꿔 first-run 순서를 비교하고, tick마다 switch cost 0.05를 더해 latency 개선과 goodput 손실을 함께 계산한다. /proc/self/sched field는 없을 수 있으며 이름·단위는 안정 ABI로 간주하지 않는다.

10. production 실패 시나리오

상황: latency service가 가능한 최소 slice를 모든 worker에 적용한다. 첫 응답 p50은 좋아졌지만 context switches와 LLC miss가 4배, throughput은 22% 감소하고 p99 completion은 악화된다.

오진: “EEVDF는 earliest deadline이므로 slice가 작을수록 무조건 좋다”고 결론 내리고 virtual deadline을 SLO deadline으로 해석했다.

증거: request class별 first/completion histogram, service share, schedstat wait/slices, context-switches, cache miss, cgroup throttling과 CPU goodput을 같은 canary에서 비교한다.

대응: default slice로 rollback한 뒤 latency-critical thread만 bounded range에서 sweep한다. admission·batching·dependency bottleneck을 먼저 고치고 kernel upgrade마다 workload replay를 수행한다.

11. 대기업 면접 질문 3개

Q1. CFS가 fair CPU share를 만드는 원리를 설명하세요.
답변 포인트: ideal multitasking CPU를 근사하며 actual runtime을 nice weight로 정규화한 vruntime을 증가시킨다. vruntime-ordered rbtree에서 뒤처진 entity를 골라 weight 비율 service를 맞추고 min_vruntime·granularity·group hierarchy를 언급한다.

Q2. EEVDF가 CFS mental model에 추가한 두 단계는?
답변 포인트: ideal−actual service lag가 0 이상인 entity만 eligible하게 하고, 그 안에서 earliest virtual deadline을 선택한다. 짧은 request가 latency를 앞당기되 음수 lag가 장기 share 탈취를 막는다.

Q3. virtual deadline이 있는데 왜 real-time guarantee가 아닙니까?
답변 포인트: fair-class virtual order일 뿐 wall deadline/admission contract가 아니다. higher class, IRQ/lock, affinity, overload, cgroup throttle이 actual dispatch를 늦춘다. SCHED_DEADLINE의 runtime/deadline/period와 구분하고 application SLO를 직접 측정한다.
