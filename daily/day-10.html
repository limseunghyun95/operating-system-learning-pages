Operating System · Day 10 / 63 · CPU Scheduling

priority, preemption, time slice

한 줄 요약 — priority는 누가 더 먼저/많이 CPU를 받을 자격이 있는지, preemption은 현재 실행을 중단하고 그 결정을 적용하는 mechanism, time slice는 한 번의 연속 실행 예산이다. Linux에서는 scheduling class마다 세 단어의 의미가 다르며, 높은 priority만으로 즉시 실행·deadline 충족·안전성이 보장되지 않는다.

1. 선수 용어 사전

priority경쟁하는 runnable task 중 먼저 선택되거나 더 큰 CPU share를 받을 상대적 자격. 숫자의 방향과 의미는 policy마다 다르다.
scheduling classfair, real-time, deadline처럼 서로 다른 선택 규칙을 구현하는 kernel 계층. class 사이 우선순위와 class 내부 규칙을 분리해 봐야 한다.
nice valueLinux normal task가 fair class 안에서 받을 상대적 CPU weight에 영향을 주는 값. -20이 더 유리하고 +19가 더 양보한다.
static / dynamic prioritystatic은 사용자가 policy parameter로 지정한 값, dynamic은 scheduler가 실행량·대기·deadline 같은 상태를 반영해 내부적으로 계산한 순서다.
preemptionrunning task가 자발적으로 block/exit하지 않아도 scheduler가 CPU를 회수해 다른 task를 실행시키는 것.
need_resched현재 CPU가 가능한 reschedule 지점에서 scheduler를 실행해야 함을 나타내는 kernel 상태/flag의 mental model.
preempt countkernel critical section 등에서 지금 선점해도 안전한지를 추적하는 중첩 counter. 0이 아니면 즉시 선점이 지연될 수 있다.
time slice / quantumtask가 한 차례에 연속 실행할 수 있는 예산. fixed wall-clock quantum일 수도, fair scheduler의 요청 slice/virtual deadline input일 수도 있다.
scheduler tick주기적 timer interrupt에서 실행 시간 회계와 reschedule 필요성을 갱신하는 기회. tick 한 번이 곧 context switch 한 번은 아니다.
preemption latency더 우선인 task가 runnable이 된 뒤 실제 CPU에서 명령을 시작할 때까지의 지연. IRQ-off/선점 금지 구간과 더 높은 priority 실행 등이 포함된다.
priority inversion / PI높은 priority H가 낮은 L의 lock 때문에 기다리고 중간 M이 L을 선점해 H를 간접 지연시키는 현상. priority inheritance는 L에 H priority를 임시 상속한다.

2. mental model: 응급실의 세 가지 레버

priority는 triage 표다. 누가 더 긴급한지 표현하지만 의사가 실제 환자를 바꾸는 순간까지 정하지는 않는다.

preemption은 진료를 중단하고 환자를 교체하는 권한이다. 수술의 안전한 단계처럼 중단 불가능한 critical section이 있으면 더 긴급한 환자가 와도 잠시 기다린다.

time slice는 한 번의 진료 예산이다. 너무 길면 다른 환자의 첫 응답이 늦고, 너무 짧으면 인계 비용이 커진다. deadline을 보장하려면 priority만 올리는 것이 아니라 worst-case 실행·blocking·interrupt 시간을 계산해야 한다.

3. architecture·상태 전이: “더 우선”에서 실제 switch까지

wake-up / fork / timer tick / priority change
                 │ enqueue + account runtime
                 ▼
        runnable queues by scheduling class
        ┌──────────┬──────────┬──────────┐
        │ deadline │ RT FIFO/RR│ fair     │   (개념적 class ordering)
        │ D/R/T    │ prio 1-99│ nice/lag │
        └──────────┴──────────┴──────────┘
                 │ candidate outranks current?
                 ├─ no ───────────────────────────────┐
                 └─ yes → set need_resched            │
                              │                       │
           ┌──────────────────┼───────────────────┐   │
           │ IRQ/user return  │ preempt_enable    │ voluntary block/yield
           │                  │ preempt_count==0  │
           └──────────────────┴───────────────────┘
                              │ legal reschedule point
                              ▼
                         schedule()
                     account current runtime
                     pick next within class
                     context_switch(prev,next)
                              │
                              ▼
                         next RUNNING

실제 시작 지연 = wakeup→reschedule point + scheduler/switch 비용
              + 더 높은 class/priority interference + lock/IRQ blocking

핵심: “H가 runnable”과 “H가 지금 실행” 사이에는 gap이 있다. need_resched는 switch 요청이지 결과가 아니며, scheduler에 들어가도 같은 task가 다시 선택될 수 있다.

4. priority를 하나의 숫자로 보면 실패한다

normal fairSCHED_OTHER/SCHED_BATCH의 sched_priority는 0이어야 한다. nice -20..+19는 절대 실행 순위가 아니라 같은 fair hierarchy 안의 상대 weight에 영향을 준다.
real-timeSCHED_FIFO/SCHED_RR는 Linux에서 static priority 1..99, 큰 수가 더 높다. portable code는 min/max API로 범위를 조회한다.
deadlineSCHED_DEADLINE은 priority 숫자보다 runtime/deadline/period contract와 admission을 사용하며 GEDF+CBS로 구현된다.
group hierarchycgroup CPU weight와 autogroup이 먼저 group share를 나누고, 그 안에서 task nice가 작동한다. 다른 terminal/session의 두 task에 nice만 바꿔도 기대한 global 비율이 안 나올 수 있다.

Linux man-pages는 nice 한 단계 차이가 scheduler favoring에 약 1.25배 영향을 준다고 설명한다. 동일 group의 두 CPU-bound task가 nice 0과 +10이면 단순 기대 비율은 약 1.25¹⁰≈9.31:1, 즉 약 90%:10%다. 이는 share 직관이지 매 100ms window의 보장이나 latency SLO가 아니다.

5. CS·kernel·hardware deep dive

5.1 policy와 mechanism을 분리하라

priority·deadline·fair lag는 누가 next인가를 정하는 policy input이다. timer interrupt, need_resched, kernel preemption point, context switch는 결정을 언제 적용하는가를 담당하는 mechanism이다.

priority를 바꿨는데 latency가 그대로라면 policy가 틀렸다고 단정하지 않는다. task가 다른 CPU에 있거나 lock/IRQ/preempt-disabled 구간에 막혔는지, cgroup hierarchy가 다른지, 더 높은 class가 실행 중인지 분해한다.

5.2 user preemption과 kernel preemption

userspace task는 interrupt·system-call return 같은 경계에서 reschedule될 수 있다. preemptible kernel은 kernel code 안에서도 안전한 지점이면 current task를 선점할 수 있지만, per-CPU data나 lock-protected invariant를 다루는 critical section은 preempt_disable()로 중첩 금지할 수 있다.

preempt count가 다시 0이 되고 need_resched가 있으면 reschedule check가 작동한다. IRQ disable은 local CPU의 interrupt도 막으므로 긴 구간은 interrupt latency까지 키운다. “kernel은 절대 선점되지 않는다”와 “높은 priority면 kernel 어디서든 즉시 선점한다”는 둘 다 틀린 일반화다.

5.3 time slice는 scheduling class마다 다른 계약이다

SCHED_RR은 같은 RT priority peer 사이에서 maximum quantum이 만료되면 queue tail로 이동한다. sched_rr_get_interval()로 조회하며, 이 값을 normal task의 quantum이라고 부르면 안 된다.

SCHED_FIFO는 time slice가 없다. block, yield, 더 높은 priority에 의한 선점 전까지 실행하므로 CPU-bound runaway가 normal task를 굶길 수 있다.

modern fair class는 모든 task에 고정 RR quantum을 돌리는 모델이 아니다. Linux EEVDF 문서는 lag가 0 이상인 eligible task 중 earliest virtual deadline을 고르고, shorter requested slice가 virtual deadline을 앞당겨 responsiveness를 높일 수 있다고 설명한다.

5.4 tick, timer expiry, switch는 1:1이 아니다

timer tick은 runtime을 account하고 slice/priority 조건을 확인해 need_resched를 세울 수 있다. 하지만 더 나은 candidate가 없으면 current가 다시 선택될 수 있고, tickless idle/full-nohz 환경에서는 주기 tick 자체가 줄어든다. 반대로 I/O wakeup은 다음 tick을 기다리지 않고 preemption 판단을 유발할 수 있다.

운영에서 timer interrupt 수, scheduler invocation, context-switch 수, migration 수를 서로 다른 counter로 본다. “100Hz니까 task가 초당 100번 switch된다” 같은 계산은 성립하지 않는다.

5.5 priority inversion: scheduler 순위보다 lock dependency가 먼저다

time ─────────────────────────────────────────────→
L(low) : lock X ── work ──[ M에게 preempt됨 ]── unlock X
H(high):             wake → lock X에서 BLOCK ─────────→ run
M(mid) :                    └──── CPU hog ─────┘

겉보기: M이 L보다 높으니 정상
실제  : H의 진행은 X owner L의 진행에 의존 → M이 H를 간접 지연

Priority Inheritance 적용:
H가 X에서 block → L이 H priority를 임시 상속 → L이 unlock
→ L priority 복원 → H가 lock 획득 (dependency chain 전체 처리 필요)

PI는 lock-holder가 release할 때까지의 scheduling inversion을 제한하지만 critical section 자체의 길이, page fault, I/O, nested PI chain을 없애지 않는다. mutex protocol과 worst-case blocking bound를 함께 설계해야 한다.

5.6 높은 priority는 deadline 보장이 아니다

H의 response에는 wakeup/preemption latency, 더 높은 priority interference, 같은/상위 IRQ handler, lock blocking, cache/TLB cold-start, migration이 포함된다. average가 아니라 worst-case execution time과 blocking upper bound, overload admission을 봐야 한다.

높은 priority task가 CPU를 무한 사용하면 더 낮은 task는 starvation한다. Linux는 RT bandwidth control과 RLIMIT_RTTIME 같은 안전 장치를 제공하지만, 설정·kernel config·cgroup에 따라 다르므로 rescue path와 watchdog 없이 RT를 production에 적용하지 않는다.

6. 실무 best practice

  1. class·scope·숫자 방향을 runbook에 쓴다. nice인지 RT priority인지, thread인지 cgroup인지, 큰 수가 높은지 낮은지 명시한다.
  2. normal service는 nice/cgroup weight부터 시작한다. RT class는 correctness requirement와 bounded runtime이 증명된 소수 thread에만 최소 권한으로 쓴다.
  3. priority는 dependency graph와 함께 리뷰한다. high-priority path가 low-priority worker, mutex, I/O thread, memory reclaim에 의존하면 inversion 가능성을 찾는다.
  4. preemption-off·IRQ-off 구간을 짧게 유지한다. allocation, blocking I/O, unbounded loop를 넣지 않고 tracing으로 max latency를 회귀 검증한다.
  5. 평균 share와 tail dispatch latency를 따로 본다. CPU%, schedstat wait, wakeup→first-run histogram, context switches, migrations, throttling을 같은 timeline에 둔다.
  6. group hierarchy를 고정한다. benchmark task를 같은 cgroup·autogroup·CPU affinity에 두고 kernel, CPU governor, SMT/NUMA 조건을 기록한다.
  7. rollback과 liveness guard를 준비한다. runtime quota, watchdog, health check, out-of-band console, reset-on-fork와 canary rollout을 갖춘다.

7. error handling과 운영 실패 대응

EPERM / EACCESnegative nice나 RT policy에는 privilege/resource limit이 필요할 수 있다. 현재 값을 다시 읽고 실패를 기록하며 권한을 자동 상승시키지 않는다.
EINVALpolicy에 맞지 않는 priority, 잘못된 deadline/runtime/period, 범위 밖 값을 의심한다. min/max API와 ABI size를 조회한다.
ESRCH race조회와 변경 사이 thread가 종료될 수 있다. PID/TID와 start time을 재검증하고 종료된 대상은 정상 race로 처리한다.
priority 변경 무효다른 autogroup/cgroup, CPU idle capacity, affinity 분리, RT/deadline competitor를 확인한다. 설정 성공과 효과 검증을 분리한다.
RT runawayGmail/SSH 같은 control plane까지 굶을 수 있다. runtime cap·watchdog·rescue console로 복구하고 일반 load test host에서 무제한 FIFO를 실행하지 않는다.
PI로도 긴 stallowner critical section의 page fault/I/O/nested lock과 PI chain을 본다. inheritance는 priority 문제만 완화하고 긴 resource hold를 고치지 않는다.
관측 파일 없음/proc/PID/schedstat·tracepoint 가용성은 kernel config/version/container mount에 의존한다. application monotonic timestamp와 승인된 profiler로 대체한다.

8. 놓치기 쉬운 함정

  • nice -20의 음수가 “낮은 priority”가 아니다. nice 숫자는 작을수록 유리하다.
  • normal nice와 RT static priority 1..99를 같은 축에서 비교하지 않는다.
  • priority가 높아졌다고 즉시 preempt하거나 deadline을 충족한다고 단정하지 않는다.
  • timer tick, slice expiry, scheduler entry, context switch를 1:1로 세지 않는다.
  • sched_rr_get_interval() 결과를 fair class의 고정 quantum으로 해석하지 않는다.
  • process에 nice를 줬다고 모든 thread가 항상 같은 값을 공유한다고 가정하지 않는다. Linux nice는 per-thread다.
  • CPU share 개선과 latency 개선을 동일시하지 않는다. 낮은 share task도 I/O wakeup 직후 빠르게 실행될 수 있고 반대도 가능하다.
  • priority inversion을 단순 starvation으로 부르지 않는다. inversion에는 lock/dependency가 있고 PI라는 별도 대응이 있다.

9. 30분 실습: 같은 CPU에서 nice weight 관찰

Linux 개인 VM/container에서 실행한다. 두 child를 같은 허용 CPU에 pin하고 하나만 nice +10으로 낮춰 6초간 CPU service와 run-queue wait를 비교한다. RT policy·root 권한·외부 package는 사용하지 않는다.

LAB_DIR=$(mktemp -d)
python3 - "$LAB_DIR" <<'PY' &
import multiprocessing as mp
import os, sys, time

lab = sys.argv[1]
if not hasattr(os, "sched_setaffinity"):
    raise SystemExit("Linux sched_setaffinity required")
allowed = os.sched_getaffinity(0)
if not allowed:
    raise SystemExit("empty CPU affinity mask")
core = min(allowed)
start = time.monotonic() + 1.0
end = start + 6.0

def worker(label, nice_delta, resultq):
    os.sched_setaffinity(0, {core})
    if nice_delta:
        os.nice(nice_delta)
    while time.monotonic() < start:
        time.sleep(.001)
    cpu0 = time.process_time()
    loops = 0
    value = 1
    while time.monotonic() < end:
        value = (value * 1103515245 + 12345) & 0x7fffffff
        loops += 1
    resultq.put((label, os.getpid(), os.nice(0),
                 time.process_time() - cpu0, loops, value))

resultq = mp.Queue()
workers = [mp.Process(target=worker, args=("normal", 0, resultq)),
           mp.Process(target=worker, args=("nice+10", 10, resultq))]
for p in workers:
    p.daemon = True
    p.start()
with open(lab + "/pids", "w") as f:
    f.write(" ".join(str(p.pid) for p in workers) + "\n")
for p in workers:
    p.join(10)
if any(p.exitcode != 0 for p in workers):
    raise SystemExit("worker failed: " + repr([p.exitcode for p in workers]))
rows = sorted(resultq.get() for p in workers)
with open(lab + "/result.txt", "w") as f:
    for label, pid, nice, cpu, loops, value in rows:
        f.write(f"{label} pid={pid} nice={nice} "
                f"cpu_s={cpu:.3f} loops={loops}\n")
    ratio = max(r[3] for r in rows) / max(.001, min(r[3] for r in rows))
    f.write(f"observed_cpu_ratio={ratio:.2f}:1\n")
PY

DRIVER=$!
PIDS=
cleanup() { kill $PIDS "$DRIVER" 2>/dev/null || true; }
trap cleanup EXIT
while [ ! -s "$LAB_DIR/pids" ]; do
  kill -0 "$DRIVER" 2>/dev/null || { wait "$DRIVER"; exit 1; }
  sleep .1
done
PIDS=$(sed -n '1p' "$LAB_DIR/pids")
for sample in 1 2 3 4; do
  ps -o pid,cls,rtprio,pri,ni,psr,stat,pcpu,cmd -p "${PIDS// /,}"
  for pid in $PIDS; do
    test -r "/proc/$pid/schedstat" &&
      printf 'pid=%s schedstat=' "$pid" && sed -n '1p' "/proc/$pid/schedstat"
  done
  sleep 1
done
wait "$DRIVER"
trap - EXIT
sed -n '1,10p' "$LAB_DIR/result.txt"

예상: 같은 CPU·task group에서 normal child의 CPU time이 nice+10보다 훨씬 크고, 후자는 schedstat의 runnable-wait가 더 커진다. 이론 직관은 약 9.31:1이지만 짧은 실험·kernel version·accounting 오차로 정확히 일치하지 않아도 된다.

반증 실험: affinity 고정을 제거해 idle CPU가 충분해지면 둘 다 거의 6 CPU-second를 받을 수 있다. 이것이 nice가 속도 제한이 아니라 contention 때의 상대 weight라는 증거다. cgroup을 다르게 배치한 뒤에는 group weight가 결과를 어떻게 바꾸는지도 기록한다.

10. production 실패 시나리오

상황: audio callback을 SCHED_FIFO high priority로 올리자 평균 jitter는 줄었지만, 오류 path의 무한 loop에서 health agent와 SSH가 실행되지 않아 node가 응답 불능이 된다.

근본 원인: priority를 latency hint가 아니라 무제한 CPU 소유권으로 사용했고 runtime bound, RT throttling, watchdog, recovery CPU를 검증하지 않았다.

증거: policy/priority, per-thread CPU time, RT throttling, sched_switch trace, watchdog heartbeat, IRQ/lock max latency를 보존한다. 높은 thread가 어떤 lock과 worker에 의존하는지도 그린다.

대응: 즉시 rollback하고 normal fair class+bounded workload로 복구한다. RT가 정말 필요하면 runtime budget, reset-on-fork, watchdog, out-of-band control, failure injection과 admission test를 먼저 배치한다.

11. 대기업 면접 질문 3개

Q1. priority가 높은 task가 runnable이 되면 어떻게 실제 실행됩니까?
답변 포인트: wakeup enqueue→class 내부/사이 우선 비교→need_resched→IRQ/user return 또는 preempt_enable 같은 안전 지점→schedule/account/pick→context switch 순서다. preempt-disabled·IRQ-off·higher-class interference 때문에 즉시는 아니며 scheduler entry가 switch를 보장하지 않는다.

Q2. nice, RT priority, time slice는 Linux에서 어떻게 다릅니까?
답변 포인트: nice -20..+19는 normal fair hierarchy의 상대 weight, RT 1..99는 FIFO/RR static priority다. RR만 같은 priority peer에 fixed maximum quantum이 있고 FIFO는 slice가 없으며 EEVDF fair slice는 virtual deadline/lag와 연결된다.

Q3. priority inversion을 설명하고 해결의 한계까지 말해 보세요.
답변 포인트: H→L lock dependency와 M의 L 선점으로 H가 간접 지연된다. PI는 L이 H priority를 상속해 release를 앞당기지만 긴 critical section, I/O/page fault, nested chain을 없애지 않으므로 protocol·bounded hold time·timeout·관측이 필요하다.

정답 포인트: -5가 fair class에서 더 유리하지만 RT 5와 직접 비교할 수 없다. 나머지는 policy→reschedule mechanism→blocking/interference→metric 순서로 설명한다.
