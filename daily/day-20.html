Operating System · Day 20 / 63 · Failure Lab

실패 실습: lost update, deadlock, timeout 복구

한 줄 요약: 동시성 장애는 재현 → wait-for graph와 상태 증거 수집 → deadline 전파 → 역순 rollback → 불변식 검증의 닫힌 루프로 다뤄야 한다.

1. 초보자 용어 사전

failure injection실패 경로가 실제로 동작하는지 확인하려고 지연·충돌·프로세스 종료를 의도적으로 넣는 실험이다.
lost update둘 이상의 실행 흐름이 같은 이전 값을 읽고 각각 새 값을 써서, 한 번의 갱신이 사라지는 논리적 경쟁이다.
compound operationread-modify-write처럼 여러 단계가 합쳐져 하나의 의미를 이루는 연산. 각 단계가 atomic이어도 전체는 atomic이 아닐 수 있다.
invariant모든 허용된 실행 뒤에도 반드시 참이어야 하는 조건. 예: 출금+입금 전후 전체 잔액 합은 같다.
deadlock서로가 가진 자원을 기다리는 cycle 때문에 누구도 더 진행할 수 없는 상태다.
wait-for graphthread를 정점, “누구를 기다리는가”를 간선으로 나타낸 그래프. cycle은 deadlock의 핵심 증거다.
timeout / deadlinetimeout은 기다릴 기간, deadline은 완료해야 할 절대 시각이다. 여러 단계를 거칠 때는 하나의 deadline에서 남은 시간을 계산해야 예산이 늘어나지 않는다.
cancellation작업에게 중단을 요청하는 프로토콜. timeout이 났다는 사실만으로 실행 중인 작업이 자동 정지하지는 않는다.
rollback부분 적용된 상태와 획득한 자원을 안전한 이전 상태로 되돌리는 보상 처리다.
idempotency동일 요청을 여러 번 실행해도 최종 효과가 한 번 실행한 것과 같은 성질. timeout 후 안전한 retry의 전제다.
fencing token매번 증가하는 세대 번호. 늦게 살아난 과거 작업의 쓰기를 저장소가 거절하도록 해 lease 만료 뒤의 stale writer를 막는다.

2. mental model: 수술이 아니라 비행기 사고 훈련

동시성 장애는 “코드 한 줄을 고치면 끝”이 아니다. 실제 incident에서는 증상이 관찰될 때 원인 interleaving은 이미 지나갔고, timeout을 받은 caller 뒤에서 작업이 계속될 수도 있다. 따라서 실험의 산출물은 성공 로그가 아니라 아래 네 가지다.

  1. 재현 계약: 어떤 스케줄에서 실패가 반드시 나타나는가?
  2. 증거: counter, thread state, lock owner, deadline, request ID가 원인을 구분하는가?
  3. 복구 불변식: 실패 뒤에도 lock·permit·메모리·외부 효과가 새지 않았는가?
  4. 재발 방지: global order, atomic RMW, idempotency key처럼 설계 수준의 guardrail이 있는가?

4. 상태 전이: 실패도 명시적인 state다

NEW ──admit──> ACQUIRING ──all locks──> MUTATING ──commit──> COMMITTED
                  │                         │
                  ├─ wait cycle ─> DEADLOCK_DETECTED
                  ├─ deadline ───> CANCELLING
                  │                    │
                  │                    └─> ROLLING_BACK ──invariant ok──> FAILED/RETRYABLE
                  └─ owner died ─> INCONSISTENT ──repair+consistent──> ACQUIRED

금지 전이: TIMED_OUT ──근거 없이 retry──> 두 번째 side effect
완료 조건: acquired_count == released_count AND partial_effects == 0

5. CS·kernel·hardware deep dive

5.1 atomic load와 atomic store도 lost update를 만들 수 있다

두 thread가 각각 atomic_load(counter)로 0을 읽고 atomic_store(counter, snapshot+1)로 1을 쓰면 모든 메모리 접근은 atomic이지만 최종값은 1이다. data race는 없지만 compound read-modify-write의 linearization point가 없다. 해결은 mutex로 전체 불변식을 보호하거나 atomic_fetch_add/CAS loop처럼 하나의 atomic RMW를 쓰는 것이다.

5.2 deadlock은 “느림”이 아니라 wait-for graph의 cycle이다

T1이 A를 가진 채 B를 기다리고 T2가 B를 가진 채 A를 기다리면 T1→T2→T1 cycle이 생긴다. CPU가 낮다는 관찰만으로 deadlock이라고 단정할 수 없다. overload queue나 외부 I/O stall도 비슷하다. owner/waiter, stack, lock 획득 순서를 함께 수집해야 한다. Linux lockdep은 실제로 관찰한 lock-class 순서를 dependency graph에 축적해 위험한 closed path를 탐지한다.

5.3 timeout은 detector이지 recovery가 아니다

deadline 경과는 “더 기다리지 않겠다”는 관찰일 뿐이다. kernel wait queue에서 waiter가 빠졌는지, 소유한 lock을 풀었는지, 하위 RPC가 취소됐는지, side effect가 commit됐는지는 별도 상태다. 안전한 경로는 deadline 확인 → 새 작업 시작 금지 → cooperative cancellation → cleanup handler/RAII → 역순 해제 → 불변식 검사다.

5.4 relative timeout을 단계마다 다시 주면 예산이 증식한다

A, B, C 단계에 각각 100ms timeout을 주면 100ms 요청이 300ms 이상 걸릴 수 있다. ingress에서 절대 deadline D를 만들고 매 단계에서 remaining = D - monotonic_now()를 계산한다. 벽시계는 NTP 조정으로 점프할 수 있어 경과시간 측정에는 monotonic clock이 적합하다. 단, POSIX pthread_mutex_timedlock()의 표준 계약은 absolute CLOCK_REALTIME 기반이므로 API별 clock 계약을 확인해야 한다.

5.5 mutex 반환값은 errno 전역값이 아니라 함수 반환값이다

pthread mutex API는 0 또는 오류 번호를 직접 반환한다. trylock의 EBUSY는 contention, timedlock의 ETIMEDOUT은 deadline 경과다. ERRORCHECK mutex의 EDEADLK는 자기 자신을 다시 잠그는 오류를 잘 잡지만 모든 multi-thread cycle 탐지를 보장하지 않는다. POSIX mutex lock 계열은 EINTR로 반환하지 않는다.

5.6 EOWNERDEAD는 “실패했으니 lock 없음”이 아니다

robust mutex owner가 죽으면 다음 획득자는 EOWNERDEAD를 받으면서 mutex를 소유한다. 보호 상태는 inconsistent다. journal/checksum 등으로 복구한 뒤 pthread_mutex_consistent()를 호출해야 한다. 복구할 수 없으면 consistent 없이 unlock해 ENOTRECOVERABLE 상태로 만들고 fail closed해야 한다.

5.7 condition variable와 futex는 깨어남 뒤 predicate를 다시 본다

condition wait는 mutex를 atomic하게 놓고 sleep하며 돌아올 때 mutex를 다시 잡지만 spurious wakeup이 가능하다. 따라서 while (!predicate) wait()가 계약이다. Linux FUTEX_WAIT도 EAGAIN, EINTR, ETIMEDOUT과 spurious wakeup을 고려해 user-space state를 재검사해야 한다. wakeup 자체가 자원 소유권을 주는 것은 아니다.

5.8 retry는 concurrency control이 아니다

timeout 뒤 blind retry는 이미 성공한 첫 작업과 겹쳐 double charge를 만들 수 있다. 동일 idempotency key로 결과를 조회하고, retry budget·exponential backoff·jitter를 두며, lease 기반 writer라면 fencing token을 저장 계층에서 검사한다. “클라이언트가 응답을 못 받음”과 “서버가 commit하지 않음”은 동치가 아니다.

7. 실무 best practice

  • 공유 상태마다 소유권, 보호 lock, 불변식, 허용 전이를 문서화한다.
  • 여러 lock은 전역 순위로 획득하고, 코드 리뷰와 lockdep 같은 동적 검증으로 순서를 검사한다.
  • lock을 잡은 채 외부 RPC·disk I/O·callback·user code를 호출하지 않는다.
  • 요청마다 하나의 absolute deadline을 만들고 context를 통해 하위 호출로 전파한다.
  • cleanup은 획득의 정확한 역순으로 하며 각 단계의 소유 여부를 별도 flag로 기록한다.
  • timeout·cancellation·owner death를 정상적인 state transition으로 테스트한다.
  • 재시도 가능한 작업은 idempotency key, retry budget, backoff+jitter, fencing을 함께 설계한다.
  • 관측성에 request/attempt ID, lock wait 시간, remaining budget, queue depth, rollback 결과를 넣는다.
  • race detector·stress test는 증거 도구이지 correctness proof가 아니다. invariant와 happens-before 설명이 최종 근거다.

9. 놓치기 쉬운 함정

  • atomic 변수니까 전체 로직도 atomic이라고 믿기: load와 store 사이에 다른 thread가 들어올 수 있다.
  • timeout을 deadlock 증거로 쓰기: overload, page fault, swap, 외부 I/O도 timeout을 만든다.
  • lock timeout 뒤 바로 return: 이전에 얻은 lock·permit·메모리·예약을 역순으로 해제해야 한다.
  • 각 하위 호출에 원래 timeout 재사용: 전체 요청 예산이 단계 수만큼 늘어난다.
  • wall clock으로 duration 측정: 시계 보정 때문에 음수·급증이 생길 수 있다.
  • EOWNERDEAD를 일반 실패처럼 return: 이미 mutex를 소유하므로 처리 없이 나가면 또 다른 장애를 만든다.
  • 재현 코드가 영원히 hang: 별도 process, watchdog, hard cap으로 실험 자체의 종료를 보장한다.
  • retry storm: 동일 timeout에 모든 client가 즉시 재시도하면 장애를 증폭한다.

10. 30분 실습: 세 실패를 안전하게 재현하고 복구 증명

아래는 macOS/Linux의 C11+pthreads에서 실행한다. 첫 실험은 data race 없이도 atomic load/store 조합이 lost update를 만든다는 점을 보이고, 두 번째는 watchdog이 ABBA cycle의 증거를 남기고 process를 종료하며, 세 번째는 monotonic absolute deadline 뒤 A를 rollback한다.

set -eu
lab_dir="$(mktemp -d)"
trap 'rm -rf "$lab_dir"' EXIT

cat > "$lab_dir/failure_lab.c" <<'C'
#include <pthread.h>
#include <stdatomic.h>
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

static atomic_int counter, ready, completed, released_a, timed_out, effects;
static pthread_mutex_t a = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t b = PTHREAD_MUTEX_INITIALIZER;

static void pause_ms(long ms) {
  struct timespec t = { .tv_sec = ms / 1000,
                        .tv_nsec = (ms % 1000) * 1000000L };
  nanosleep(&t, NULL);
}
static long long mono_ns(void) {
  struct timespec t;
  clock_gettime(CLOCK_MONOTONIC, &t);
  return (long long)t.tv_sec * 1000000000LL + t.tv_nsec;
}
static void rendezvous(void) {
  atomic_fetch_add_explicit(&ready, 1, memory_order_relaxed);
  while (atomic_load_explicit(&ready, memory_order_acquire) != 2) sched_yield();
}
static void *split_rmw(void *unused) {
  (void)unused;
  int snapshot = atomic_load_explicit(&counter, memory_order_relaxed);
  rendezvous();
  atomic_store_explicit(&counter, snapshot + 1, memory_order_relaxed);
  return NULL;
}
static void *one_rmw(void *unused) {
  (void)unused;
  atomic_fetch_add_explicit(&counter, 1, memory_order_relaxed);
  return NULL;
}
static void run_lost(void) {
  pthread_t x, y;
  atomic_store(&counter, 0); atomic_store(&ready, 0);
  pthread_create(&x, NULL, split_rmw, NULL);
  pthread_create(&y, NULL, split_rmw, NULL);
  pthread_join(x, NULL); pthread_join(y, NULL);
  printf("lost_update final=%d expected=2\n", atomic_load(&counter));

  atomic_store(&counter, 0);
  pthread_create(&x, NULL, one_rmw, NULL);
  pthread_create(&y, NULL, one_rmw, NULL);
  pthread_join(x, NULL); pthread_join(y, NULL);
  printf("atomic_rmw final=%d expected=2\n", atomic_load(&counter));
}
static void *lock_ab(void *unused) {
  (void)unused; pthread_mutex_lock(&a); rendezvous();
  pthread_mutex_lock(&b); atomic_fetch_add(&completed, 1); return NULL;
}
static void *lock_ba(void *unused) {
  (void)unused; pthread_mutex_lock(&b); rendezvous();
  pthread_mutex_lock(&a); atomic_fetch_add(&completed, 1); return NULL;
}
static void *watchdog(void *unused) {
  (void)unused; pause_ms(120);
  printf("deadlock cycle=T1->B->T2->A->T1 ready=%d completed=%d\n",
         atomic_load(&ready), atomic_load(&completed));
  fflush(stdout); _Exit(0);
}
static void run_deadlock(void) {
  pthread_t x, y, w; atomic_store(&ready, 0); atomic_store(&completed, 0);
  pthread_create(&x, NULL, lock_ab, NULL); pthread_create(&y, NULL, lock_ba, NULL);
  pthread_create(&w, NULL, watchdog, NULL); pthread_join(w, NULL);
}
static void *bounded_worker(void *unused) {
  (void)unused;
  if (pthread_mutex_lock(&a) != 0) return NULL;
  long long deadline = mono_ns() + 100000000LL;
  for (;;) {
    int rc = pthread_mutex_trylock(&b);
    if (rc == 0) {
      atomic_fetch_add(&effects, 1); pthread_mutex_unlock(&b); break;
    }
    if (rc != EBUSY || mono_ns() >= deadline) {
      atomic_store(&timed_out, 1); break;
    }
    pause_ms(1);
  }
  pthread_mutex_unlock(&a); atomic_store(&released_a, 1); return NULL;
}
static void run_timeout(void) {
  pthread_t x; atomic_store(&released_a, 0); atomic_store(&timed_out, 0);
  atomic_store(&effects, 0); pthread_mutex_lock(&b);
  pthread_create(&x, NULL, bounded_worker, NULL); pthread_join(x, NULL);
  pthread_mutex_unlock(&b);
  printf("timeout_recovery timed_out=%d released_A=%d side_effects=%d\n",
         atomic_load(&timed_out), atomic_load(&released_a), atomic_load(&effects));
}
int main(int argc, char **argv) {
  if (argc != 2) return 2;
  if (!strcmp(argv[1], "lost")) run_lost();
  else if (!strcmp(argv[1], "deadlock")) run_deadlock();
  else if (!strcmp(argv[1], "timeout")) run_timeout();
  else return 2;
  return 0;
}

  1. 0~10분: 각 출력이 어떤 invariant 위반/복구 증거인지 한 문장씩 적는다.
  2. 10~20분: ABBA 두 함수가 모두 A→B 순서로 획득하도록 고쳐 watchdog 전에 completed=2가 되게 한다.
  3. 20~30분: timeout 경로의 ownership flag를 두 개로 확장하고, 모든 return에서 acquired==released를 assert한다.

해석 포인트: 첫 결과는 C data race가 아니다. 모든 접근이 atomic이어도 “두 단계를 하나의 거래처럼” 묶지 않으면 논리적 race가 남는다. 반대로 final=2 한 번만 관찰했다고 correctness가 증명되는 것도 아니다.

11. 실패 시나리오: 결제 timeout 뒤 이중 승인

API gateway는 800ms deadline을 주었지만 결제 service가 DB lock을 기다리며 남은 예산을 전달하지 않았다. gateway는 504를 반환했고 client는 새 request ID로 즉시 재시도했다. 첫 worker는 뒤늦게 lock을 얻어 승인했고 두 번째 worker도 승인했다. 운영자는 timeout 그래프만 보고 DB가 느리다고 판단했지만 실제 결함은 cancellation 미전파와 idempotency 부재였다.

복구: 신규 결제를 일시 차단하고 logical payment key로 중복 승인을 찾아 보상한다. 재발 방지: ingress deadline 전파, commit 전 deadline 재검사, idempotency record의 pending→committed state machine, 같은 key 결과 재사용, late attempt를 막는 fencing version, timeout과 cleanup-complete를 분리한 metric을 도입한다.

12. 대기업 면접 질문 3개

  1. “atomic load/store만 사용했는데 lost update가 가능한가요?”
    답변 포인트: 각 access의 atomicity와 compound operation의 atomicity는 다르다. 두 thread가 같은 snapshot을 읽어 덮어쓸 수 있다. fetch_add/CAS loop 또는 mutex로 linearization point를 만든다. 여러 변수 invariant라면 mutex/transaction이 더 자연스럽다.
  2. “timeout이 deadlock을 해결합니까?”
    답변 포인트: timeout은 waiter의 관찰·대기 제한이지 cycle 제거와 rollback을 자동 보장하지 않는다. wait-for graph로 원인을 구분하고, absolute deadline·cancellation·역순 cleanup·idempotency를 설계해야 한다. global lock order가 1차 예방이다.
  3. “robust mutex에서 EOWNERDEAD를 받으면 무엇을 합니까?”
    답변 포인트: 호출자는 이미 lock을 획득했고 보호 상태는 inconsistent다. journal/checksum으로 검증·복구하고 mutex_consistent를 호출한다. 복구 불가하면 consistent 없이 unlock해 poison하고 fail closed한다.
