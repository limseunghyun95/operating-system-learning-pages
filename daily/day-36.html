OPERATING SYSTEM · DAY 36 / 63 · FILESYSTEM

file, inode, directory entry, file descriptor

한 줄 요약: pathname은 file 자체가 아니라 directory entry를 찾는 문자열이고, inode는 filesystem object의 identity·metadata, open file description은 열린 instance의 offset·status, file descriptor는 process가 그 instance를 가리키는 작은 정수다. 이 네 층을 구분해야 rename·unlink·dup·fork·exec·fd leak을 정확히 설명할 수 있다.

1. 초보자 용어 사전

filebyte data와 metadata를 가진 filesystem object. regular file뿐 아니라 directory·device·pipe·socket도 “file-like object”로 같은 fd API를 쓸 수 있다.
pathname`/srv/app/data.txt`처럼 directory name을 순서대로 걷게 하는 문자열. object identity가 아니며 rename·link로 바뀌거나 여러 개일 수 있다.
directory entry한 directory 안의 `name → inode` 연결. 저장장치의 directory record와 VFS가 cache하는 dentry를 문맥에 따라 구분한다.
dentryLinux VFS의 pathname component cache object. name, parent dentry, inode pointer를 가지며 “그 이름이 없음”을 기억하는 negative dentry도 있다.
inodetype, mode, owner, size, timestamps, link count, data-block mapping 등 metadata를 나타내는 filesystem object. 이름 자체는 inode에 들어 있지 않다.
inode number한 filesystem 안에서 inode를 식별하는 번호. 전역 identity는 아니므로 보통 `(st_dev, st_ino)` 쌍으로 비교하고, 삭제 뒤 재사용될 수도 있다.
hard link같은 inode를 가리키는 또 다른 directory entry. 두 pathname은 동등하며 inode의 link count가 증가한다.
symbolic link다른 pathname 문자열을 data로 가진 별도 inode. path resolution이 그 문자열을 다시 따라간다.
open file description`open()`마다 만들어지는 system-wide 열린 instance. Linux kernel의 `struct file`에 해당하며 current offset과 file status flags를 가진다.
file descriptor(fd)process별 fd table의 index인 작은 nonnegative integer. inode 번호도 pointer도 아니며 보통 가장 낮은 빈 번호가 재사용된다.
file offset다음 read/write가 시작할 byte 위치. fd가 아니라 open file description에 있어 `dup`·`fork`로 만든 fd끼리 공유할 수 있다.
FD_CLOEXEC`execve()` 성공 시 해당 fd를 자동 close하는 descriptor flag. `O_CLOEXEC`로 생성 순간 원자적으로 설정한다.
reference countkernel object를 누가 얼마나 참조하는지 세는 값. link count와 open reference는 다른 수명 축이다.

2. mental model: 주소·건물·방문증을 분리하라

pathname은 주소, directory entry는 주소록의 이름→건물 연결, inode는 건물의 등기 identity와 속성, open file description은 한 번의 방문 상태, fd는 방문자가 가진 번호표다. 주소가 바뀌거나 지워져도 이미 들어간 방문자는 번호표로 건물에 접근할 수 있다. 번호표를 복사하면 같은 방문 상태와 현재 위치를 공유하지만, 주소를 다시 검색해 새로 들어가면 같은 건물이어도 별도의 현재 위치를 가진다.

fd는 per-process index이고, data path의 실제 상태는 open file description과

4. 관계 그림: 같은 inode, 같은 open instance, 다른 fd

directory A: "report" ─┐
                        ├── inode #421  (nlink=2, size, mode, block map)
directory B: "latest" ─┘

open("report") ─→ OFD X { offset=0, O_RDONLY } ←─ fd 3
                                              └─ fd 8 = dup(3)
                                              └─ child fd 3 after fork()

open("latest") ─→ OFD Y { offset=0, O_RDONLY } ←─ fd 4

X와 Y는 같은 inode를 가리켜도 offset은 독립이다.
fd 3·8·child fd 3은 같은 X를 가리켜 offset·status flags를 공유한다.
각 fd의 FD_CLOEXEC 같은 descriptor flag는 별도다.

5. 상태 전이: link, open, unlink, close

create("a")         link("a", "b")       open("a")
inode nlink=1  ───→  inode nlink=2  ───→  open reference +1
   │ a→inode            │ a,b→same inode       │ fd→OFD→inode
   │                    │                      │
unlink("a")             unlink("b")            close(last fd)
nlink=1            ───→ nlink=0, open ref=1 ─→ open ref=0

                        기존 fd I/O는 계속 가능

rename("b","c")는 directory mapping을 바꾸지만 이미 열린 fd의 identity를
바꾸지 않는다. inode storage 수명은 pathname 수명과 open reference 수명을 모두 본다.

6. CS·kernel deep dive

6.1 “파일 이름”은 inode의 속성이 아니다

한 inode에 hard link 여러 개가 있으면 대표 이름이 없다. 이름은 부모 directory 안의 entry가 보유한다. 따라서 `stat(path)`은 path lookup 뒤 inode metadata를 읽고, `fstat(fd)`는 이미 열린 reference로 inode metadata를 읽는다.

6.2 identity는 pathname보다 `(device, inode)`에 가깝다

같은 pathname은 rename·replacement 뒤 다른 inode를 가리킬 수 있고, 다른 pathname이 hard link로 같은 inode를 가리킬 수 있다. `(st_dev, st_ino)`는 한 시점의 local filesystem identity 비교에 유용하지만 삭제·재사용, network filesystem, snapshot 때문에 영구 global ID로 쓰면 안 된다.

6.3 dentry는 단순 cache 이상이다

Linux VFS dentry는 component name, parent, inode 연결을 표현하고 mount traversal과 rename concurrency에도 관여한다. negative dentry는 존재하지 않는 이름을 cache해 반복 miss를 빠르게 한다. network filesystem은 server에서 이름이 바뀔 수 있어 dentry revalidation이 필요하다.

6.4 path walk에는 권한·symlink·mount·race가 함께 있다

absolute path는 process root에서, relative path는 cwd 또는 `openat`의 dirfd에서 시작한다. 중간 directory마다 search 권한을 확인하고 symlink와 mountpoint를 처리한다. lookup 중 rename이 일어날 수 있어 VFS는 RCU/refcount/lock과 retry로 일관성을 지킨다.

6.5 open은 inode를 fd로 직접 바꾸지 않는다

성공한 `open()`은 새로운 open file description을 만들고 process fd table의 빈 slot에 reference를 설치한다. 같은 path를 두 번 open하면 같은 inode라도 OFD가 둘이므로 offset이 독립이다. `dup`은 새 OFD가 아니라 같은 OFD를 가리키는 fd를 추가한다.

6.6 offset과 flags의 소유자를 구분한다

current offset과 `O_APPEND`, `O_NONBLOCK` 같은 file status flags는 OFD에 있어 dup/fork descriptor가 공유한다. `FD_CLOEXEC`은 fd entry의 descriptor flag라 서로 공유하지 않는다. `lseek(fd8)`이 fd3 read 위치를 바꿀 수 있는 이유가 여기 있다.

6.7 fork와 exec는 fd graph를 다르게 바꾼다

`fork()` child는 parent fd의 duplicate를 받아 같은 OFD를 참조한다. `execve()`는 process image를 교체하지만 기본적으로 fd는 남고, `FD_CLOEXEC`이 설정된 것만 닫힌다. multithreaded program에서 open 뒤 `fcntl`로 flag를 붙이면 그 사이 fork+exec가 비밀 fd를 leak할 수 있으므로 `O_CLOEXEC`가 필요하다.

6.8 unlink는 “열린 파일을 즉시 파괴”하지 않는다

`unlink()`는 directory entry와 link count를 바꾼다. 마지막 이름이 사라져도 open reference가 있으면 기존 fd로 read/write할 수 있다. 이 특성은 temporary file과 atomic replacement에 유용하지만, 오래 열린 deleted log가 disk block을 계속 점유하는 장애도 만든다.

6.9 close는 fd 번호 재사용 race를 만든다

Linux에서 `close()` 처리 초기에 fd slot이 해제될 수 있어 다른 thread가 같은 번호를 재사용할 수 있다. error가 났다고 무조건 `close(fd)`를 재시도하면 새 object를 닫을 수 있다. fd ownership을 명확히 하고 concurrent close/use를 설계로 막는다.

6.10 “everything is a file”은 API 통일이지 의미 통일이 아니다

regular file, directory, pipe, socket, device는 fd로 다루지만 seek 가능성, blocking, durability, readiness, error semantics가 다르다. `read`·`write` 이름이 같다고 같은 guarantee를 주는 것은 아니다.

8. 실무 best practice

  • 모든 fd에 단일 owner와 close 지점을 정하고, error path·timeout·cancellation에서도 같은 cleanup contract를 적용한다.
  • 생성 시 `O_CLOEXEC`, 복제 시 `dup3(..., O_CLOEXEC)`를 사용해 exec leak race를 원자적으로 차단한다.
  • untrusted pathname은 `openat`/`openat2`와 안정된 dirfd를 사용한다. Linux에서는 필요에 따라 `RESOLVE_BENEATH`, `RESOLVE_IN_ROOT`, `RESOLVE_NO_SYMLINKS`, `RESOLVE_NO_XDEV`를 검토한다.
  • `access()` 후 `open()`처럼 검사와 사용을 분리하지 않는다. 실제 open operation의 결과와 atomic flag를 신뢰한다.
  • create는 `O_CREAT|O_EXCL`, temporary file은 안전한 library API 또는 `O_TMPFILE` 지원 여부를 사용하고 예측 가능한 name을 피한다.
  • fd metric을 process count 하나로 끝내지 말고 type, owner component, age, open/close rate, soft limit 대비 비율로 본다.
  • log rotation은 pathname rename만 하지 말고 writer가 reopen하는 protocol과 deleted-open file 탐지를 갖춘다.
  • metadata identity 비교에는 path string보다 `fstat`의 `(st_dev, st_ino)`를 쓰되 inode reuse와 filesystem semantics를 문서화한다.
  • network filesystem은 dentry/attribute cache, ESTALE, server-side permission·failure가 있으므로 local filesystem 가정을 일반화하지 않는다.

9. error handling runbook

  1. open failure를 분류: `ENOENT`는 component 부재, `ENOTDIR`는 중간 component type, `EACCES`는 search/access 권한, `ELOOP`는 symlink loop, `EMFILE`은 process limit, `ENFILE`은 system-wide open-file limit 후보이다.
  2. retry 조건: `EINTR`만 API·platform contract에 따라 안전하게 재시도하고, permission·bad path·limit 오류를 무한 retry하지 않는다.
  3. partial acquisition: 여러 fd 중간 실패 시 이미 연 fd를 역순 close하고 임시 name·lock·buffer를 cleanup한다.
  4. EMFILE 대응: admission을 줄이고 fd owner별 leak을 찾는다. network server는 관찰·복구를 위한 reserve fd 패턴을 검토하되 accept storm을 backoff한다.
  5. close 결과: delayed I/O error가 보고될 수 있어 error를 log한다. Linux에서는 close 재시도가 fd reuse를 해칠 수 있으므로 blind retry하지 않는다.
  6. durability: 중요한 data는 `close()` 성공만으로 durable이라 가정하지 말고 Day 39의 `fsync`·directory sync protocol을 따른다.
  7. evidence: `/proc/PID/fd`, `fdinfo`, limits, `(dev,ino)`, flags, owning stack/operation을 timestamp와 함께 보존한다.
  8. verify: fd count·deleted-open bytes·error rate가 baseline으로 회복되고 leak 재현 test가 통과해야 종료한다.

10. 놓치기 쉬운 함정

  • fd 숫자가 identity: close 뒤 가장 낮은 빈 번호가 즉시 다른 object에 재사용될 수 있다.
  • inode 안에 filename: 이름은 directory entry에 있고 한 inode에 여러 hard link가 가능하다.
  • 같은 inode면 같은 offset: offset은 inode가 아니라 OFD에 있다. 별도 open은 독립, dup/fork는 공유한다.
  • unlink하면 열린 fd도 invalid: name만 사라지고 open reference가 남으면 I/O는 계속된다.
  • rename하면 fd가 새 path를 따라감: fd는 기존 object reference를 유지한다.
  • O_NOFOLLOW가 전체 path 보호: 일반적으로 final component에 대한 의미이므로 전체 containment에는 openat2 정책을 검토한다.
  • FD_CLOEXEC와 O_CLOEXEC가 같은 종류의 flag: 결과는 연결되지만 전자는 descriptor flag, 후자는 open 시 원자 설정 요청이다.
  • close를 retry하면 안전: multithreaded process에서는 재사용된 fd를 닫을 수 있다.
  • 모든 fd는 seek 가능: pipe·socket은 `lseek`가 실패하고 readiness·blocking semantics도 다르다.

11. 30분 실습: offset·hard link·unlink lifetime

안전한 temporary directory에서 같은 inode를 두 번 open하고 한 번 dup한다. `dup`만 offset을 공유하고, 마지막 pathname을 unlink한 뒤에도 fd가 data를 읽는지 검증한다.

python3 - <<'PY'
import os, tempfile

with tempfile.TemporaryDirectory(prefix="os-day36-") as d:
    a, b = os.path.join(d, "a.txt"), os.path.join(d, "b.txt")
    with open(a, "wb") as f:
        f.write(b"ABCDEFGHIJ")
    os.link(a, b)
    sa, sb = os.stat(a), os.stat(b)
    assert (sa.st_dev, sa.st_ino) == (sb.st_dev, sb.st_ino)
    assert sa.st_nlink == 2

    fd1 = os.open(a, os.O_RDONLY)
    fd2 = os.open(a, os.O_RDONLY)   # 새 open file description
    fd3 = os.dup(fd1)               # fd1과 같은 description
    try:
        assert os.read(fd1, 2) == b"AB"
        assert os.read(fd3, 2) == b"CD"  # shared offset: 2 → 4
        assert os.read(fd2, 2) == b"AB"  # independent offset
        print("offsets", os.lseek(fd1,0,os.SEEK_CUR),
              os.lseek(fd2,0,os.SEEK_CUR), os.lseek(fd3,0,os.SEEK_CUR))

        os.unlink(a)
        assert os.path.exists(b) and os.fstat(fd1).st_nlink == 1
        os.unlink(b)
        assert not os.path.exists(a) and not os.path.exists(b)
        assert os.fstat(fd1).st_nlink == 0
        os.lseek(fd1, 0, os.SEEK_SET)
        assert os.read(fd1, 10) == b"ABCDEFGHIJ"
        print("unlinked_but_open", os.fstat(fd1).st_ino,
              os.fstat(fd1).st_nlink)

        proc = f"/proc/{os.getpid()}/fd/{fd1}"
        if os.path.exists("/proc/self/fd"):
            print("proc_fd", os.readlink(proc))
    finally:
        for fd in (fd3, fd2, fd1):
            os.close(fd)
PY
  1. 0~10분: 출력이 `offsets 4 2 4`가 되는 이유를 fd table과 OFD 그림으로 설명한다.
  2. 10~20분: 두 pathname의 `(dev,ino)`와 link count 변화를 기록한다.
  3. 20~30분: Linux에서 `/proc/self/fd` link가 `(deleted)`를 보여도 read가 가능한 이유와 마지막 close 뒤 storage 회수 조건을 설명한다.

12. Linux production 관찰

# pathname과 inode metadata
stat /path/to/file
namei -l /path/to/file
findmnt -T /path/to/file

# process fd table과 open file description 정보
ls -l /proc/<PID>/fd
cat /proc/<PID>/fdinfo/<FD>
grep -E 'Max open files' /proc/<PID>/limits

# deleted pathname인데 아직 열린 object
lsof -nP +L1
find /proc/<PID>/fd -lname '* (deleted)' -ls 2>/dev/null

# syscall boundary 추적: production overhead·민감 path를 고려
strace -f -yy -e trace=openat,openat2,dup,dup2,dup3,close,link,unlink,rename \
  -p <PID>

`/proc/PID/fd` 접근은 ptrace permission check와 namespace/credential 제약을 받는다. `lsof` 결과도 snapshot이라 concurrent open/close와 race가 있으며, path 출력에 secret이 들어갈 수 있어 수집·보관 범위를 제한한다.

13. 실패 시나리오: rotation 뒤에도 disk가 줄지 않는다

운영자가 40GiB `app.log`를 rename 후 unlink했지만 disk usage가 줄지 않았다. `df`는 가득 찼고 `du` 합은 작았다. writer process의 fd가 link count 0인 inode를 계속 참조해 block이 유지된 것이 원인이었다. process를 즉시 kill하기보다 `lsof +L1`과 `/proc/PID/fdinfo`로 owner·offset을 확인하고, service가 signal/API로 log를 reopen하도록 traffic-safe하게 조치했다. 이후 rotation protocol에 reopen acknowledgement, deleted-open bytes alert, `O_CLOEXEC`, fd owner metric을 추가했다.

15. 퀴즈·누적 리뷰

  1. 한 inode가 이름 두 개를 가질 수 있는가? hard link 두 directory entry가 같은 inode를 가리킬 수 있다.
  2. fd 4를 close한 직후 새 open이 fd 4를 받을 수 있는가? 가능하다. fd는 재사용되는 table index다.
  3. dup(fd) 뒤 한쪽에서 `lseek`하면 다른 쪽 offset은? 같은 OFD를 공유하므로 함께 바뀐다.
  4. 같은 path를 두 번 open하면 offset은? 별도 OFD이므로 독립이다.
  5. link count 0인데 read가 가능한 이유는? pathname reference는 없지만 open reference가 inode/data 수명을 유지한다.
  6. Day 25 연결: fd를 close한 뒤에도 file-backed mmap이 계속 유효할 수 있는 이유를 object lifetime 관점에서 설명해 보자.
