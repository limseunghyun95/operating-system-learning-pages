리뷰: scheduler 선택을 SLO로 방어

한 줄 요약 — 좋은 scheduler 답변은 알고리즘 이름이 아니라 workload·SLO·capacity·isolation·overload policy를 먼저 고정하고, Linux scheduling class와 weight/affinity를 최소 변경한 뒤 application latency·runqueue wait·PSI로 검증하고 rollback 조건까지 제시한다.

1. 리뷰용 용어 사전

SLOService Level Objective. 예: 성공 요청의 99%를 100ms 안에 완료. 평균이 아니라 대상 population·window·percentile·성공 조건까지 포함한다.

entitlement경쟁 시 받아야 할 상대 service 몫. nice·cgroup cpu.weight가 표현하지만 idle CPU 사용 상한은 아니다.
headroom평상시 사용량과 최대 capacity 사이 여유. burst·GC·failover·noisy neighbor를 흡수한다.

2. mental model: scheduler는 응급실의 한 층이다

입구는 admission control이다. 병상보다 환자가 무한히 들어오면 의사 순번표만 바꿔서는 대기열 폭발을 막지 못한다.

병동 분리는 cgroup·CPU isolation이다. 응급·일반·batch가 같은 quota를 놓고 싸우면 process nice 하나로 service boundary를 보장하기 어렵다.

진료 순번이 scheduler다. fair class는 장기 몫과 응답성을 균형 잡고, RT/DEADLINE은 더 강한 계약과 더 큰 실패 반경을 가진다. 선택은 SLO와 검증 가능한 workload model로 방어한다.

4. 면접·설계 답변 프레임: W-SAFE-R

WWorkload — arrival/burst, service distribution, CPU/I/O-bound, core와 dependency를 수치화한다.
SSLO — p99 response, throughput, fairness, deadline miss, window와 error budget을 정의한다.
AAdmission — ρ와 headroom을 계산하고 queue bound, shedding, backpressure를 먼저 둔다.
FFairness/isolation — tenant/service boundary를 cgroup·cpuset으로, 내부 상대 share를 nice/weight로 표현한다.
EEvidence — application metric과 schedstat/PSI/throttle/switch를 같은 timeline에서 비교한다.
RRollback — 변경 전 config, abort threshold, feature flag, 소유자와 복구 시간을 명시한다.

5. CS·kernel·hardware deep dive

5.1 ρ가 1에 가까우면 scheduler tuning 여지가 사라진다

단순화한 m-core CPU에서 평균 offered utilization은 ρ=λ×E[S]/m이다. 평균 ρ가 0.8이어도 service variance와 burst가 크면 순간 queue가 생긴다. ρ≥1이 지속되면 들어오는 work가 처리 capacity보다 많아 queue는 안정 상태를 갖지 못한다.

scheduler는 먼저 처리할 job을 바꿀 수 있지만 총 service 수요를 제거하지 않는다. 특정 class의 p99를 낮추면 다른 class의 wait나 throughput이 악화될 수 있으므로 overload policy가 선행한다.

5.2 FCFS·SJF·RR은 목적 함수가 다르다

FCFS는 단순하고 switch가 적지만 긴 CPU burst가 뒤의 짧은 job을 막는 convoy를 만든다. SJF/SRPT는 service time을 정확히 안다면 평균 completion을 줄이지만 예측 오류와 긴 job starvation 문제가 있다.

RR은 time quantum으로 first response와 fairness를 개선하지만 quantum이 작으면 switch/cache 비용이 커진다. Linux fair scheduler를 fixed-quantum RR로 동일시하지 않는다.

5.3 normal service의 기본값은 fair class다

SCHED_OTHER(NORMAL)는 일반 application의 표준 time-sharing 정책이다. nice→weight로 장기 entitlement를 표현하고, Linux의 fair scheduler는 weight-normalized vruntime과 EEVDF의 lag/eligibility/virtual deadline으로 share와 latency ordering을 조절한다.

EEVDF virtual deadline은 wall-clock SLO deadline이 아니다. higher class, IRQ, lock, cgroup throttle, affinity imbalance와 overload가 actual dispatch를 늦출 수 있다.

5.4 RT/DEADLINE은 “더 빠른 옵션”이 아니다

SCHED_FIFO는 같은/낮은 class를 time slice 없이 막을 수 있고 SCHED_RR도 normal task보다 우선한다. runaway RT loop는 system responsiveness를 잃게 할 수 있다. capability, runtime limit, watchdog, emergency CPU와 bounded critical section이 필요하다.

SCHED_DEADLINE은 runtime≤deadline≤period와 admission test를 가진 sporadic task 계약이다. 일반 API p99를 빠르게 하려고 쓰는 기능이 아니며 page fault, I/O/lock dependency까지 자동 보장하지 않는다.

5.5 multicore에서는 topology와 hierarchy가 정책 일부다

per-CPU run queue와 load balancing 때문에 global runnable 수만으로 local queue를 설명할 수 없다. affinity는 cache locality를 높일 수 있지만 좁게 고정하면 idle core가 있어도 hot run queue가 생긴다. SMT sibling은 완전한 독립 core가 아니고 NUMA migration은 memory latency를 바꾼다.

cgroup cpu.weight는 group 사이 상대 몫, cpu.max는 bandwidth 상한이다. process nice는 group 내부 지분일 수 있다. throttle로 생긴 latency를 scheduler unfairness로 오진하지 않는다.

5.6 preemption은 latency와 efficiency를 교환한다

짧은 slice와 wakeup preemption은 latency-sensitive job을 빨리 실행하지만 scheduler overhead, context switch, cache/TLB/predictor working-set 교대를 늘릴 수 있다. switch count만으로 비용을 확정하지 말고 goodput·cache miss·energy를 함께 측정한다.

반대로 긴 nonpreemptive burst는 switch cost를 줄이지만 head-of-line blocking을 만든다. SLO가 first response인지 completion인지에 따라 최적점이 다르다.

5.7 관찰은 application→kernel 순서로 drill down한다

먼저 p50/p99와 goodput, queue age, rejection을 본다. 다음으로 CPU utilization/PSI, cgroup throttle, per-task schedstat runtime/wait/slices, context switches와 migrations를 대조한다. kernel metric 하나만으로 user-visible SLO를 대체하지 않는다.

CPU PSI some은 적어도 한 task가 CPU를 기다린 stall을 집계하지만 특정 PID 원인을 단독 증명하지 않는다. scope와 delta, 같은 시간축이 중요하다.

7. 실무 best practice

  1. SLO를 workload class별로 분리한다. interactive, batch, control-plane의 latency·throughput·fairness 목표를 섞지 않는다.
  2. default fair class에서 시작한다. cgroup isolation과 overload control로 해결 가능한지 먼저 검증한다.
  3. headroom을 failure mode에 맞춘다. single-node loss, failover, GC, burst 때의 effective core를 기준으로 capacity를 계산한다.
  4. canary 한 축만 바꾼다. nice·weight·quota·affinity·concurrency를 동시에 조정하지 않고 config와 kernel version을 기록한다.
  5. 양방향 guardrail을 둔다. latency class 개선뿐 아니라 batch starvation, total goodput, switch/cache cost를 제한한다.
  6. RT 변경은 별도 change class로 관리한다. privilege, watchdog, runtime budget, rollback shell, emergency CPU를 사전 검증한다.
  7. 문서에 반증 조건을 쓴다. “scheduler 원인”이라면 schedstat wait/PSI가 어떤 방향으로 변해야 하는지 명시한다.

8. error handling과 운영 대응

ρ≥1 또는 queue 증가tuning을 중지하고 admission, shedding, retry budget, scale을 적용한다. 오래된 request는 deadline-aware하게 폐기한다.

metric 없음/버전 차이feature probe 후 unavailable로 기록한다. /proc 내부 field를 stable ABI로 가정하거나 0으로 대체하지 않는다.

9. 놓치기 쉬운 함정

  • “latency가 중요하니 priority를 높인다”에서 답을 끝내지 않는다. 누구의 latency가 희생되는지 말한다.
  • 평균 CPU 60%로 headroom이 충분하다고 단정하지 않는다. per-core hot spot과 burst percentile을 본다.
  • nice를 CPU 상한이나 deadline 보장으로 설명하지 않는다.
  • EEVDF virtual deadline과 SCHED_DEADLINE의 wall-clock contract를 혼동하지 않는다.
  • affinity를 성능 만능키로 쓰지 않는다. load imbalance와 hotplug 장애 경로를 만든다.
  • CPU utilization만 보고 scheduler 병목을 확정하지 않는다. runnable wait와 PSI가 필요하다.
  • RT benchmark를 production 권한·lock·page fault 조건 없이 일반화하지 않는다.
  • 좋은 canary 평균이 전체 p99·starvation·failover 안전성을 증명한다고 생각하지 않는다.

10. 30분 실습: SLO defense simulator

표준 Python으로 interactive(I)와 batch(B) job을 한 CPU에서 실행한다. FCFS와 작은-quantum RR을 비교해 “한 지표 개선=좋은 정책”이 아님을 확인한다. 이 코드는 Linux kernel emulator가 아니라 면접용 decision lab이다.

LAB_DIR=$(mktemp -d)
python3 - "$LAB_DIR/result.txt" <<'PY'
from collections import deque
import math, sys

# (arrival, service, class, id): 긴 batch 사이에 짧은 interactive burst
jobs = [(0, 18, "B", "B0"), (1, 2, "I", "I1"),
        (2, 1, "I", "I2"), (3, 2, "I", "I3"),
        (4, 1, "I", "I4"), (6, 8, "B", "B1")]

def percentile(values, p):
    values = sorted(values)
    return values[math.ceil(p * len(values)) - 1]

def simulate(quantum=None, switch_cost=0.0):
    pending = [dict(arr=a, rem=s, service=s, cls=c, id=i)
               for a, s, c, i in jobs]
    ready, done, first = deque(), {}, {}
    now, switches, prev = 0.0, 0, None
    while pending or ready:
        for j in list(pending):
            if j["arr"] <= now:
                ready.append(j); pending.remove(j)
        if not ready:
            now = min(j["arr"] for j in pending); continue
        j = ready.popleft()
        if prev is not None and prev != j["id"]:
            now += switch_cost; switches += 1
        first.setdefault(j["id"], now)
        run = j["rem"] if quantum is None else min(quantum, j["rem"])
        now += run; j["rem"] -= run
        for n in list(pending):
            if n["arr"] <= now:
                ready.append(n); pending.remove(n)
        if j["rem"] > 0: ready.append(j)
        else: done[j["id"]] = now
        prev = j["id"]
    response = {c: [done[i] - a for a, s, c2, i in jobs if c2 == c]
                for c in ("I", "B")}
    first_wait = {c: [first[i] - a for a, s, c2, i in jobs if c2 == c]
                  for c in ("I", "B")}
    return dict(makespan=now, switches=switches,
                i_p99=percentile(response["I"], .99),
                i_first_p99=percentile(first_wait["I"], .99),
                b_p99=percentile(response["B"], .99),
                throughput=len(jobs)/now)

rows = [("FCFS", simulate()),
        ("RR q=2 cost=.15", simulate(2, .15)),
        ("RR q=1 cost=.15", simulate(1, .15))]
with open(sys.argv[1], "w") as f:
    f.write("policy,I_first_p99,I_completion_p99,B_completion_p99,switches,throughput\n")
    for name, r in rows:
        f.write(f"{name},{r['i_first_p99']:.2f},{r['i_p99']:.2f},"
                f"{r['b_p99']:.2f},{r['switches']},{r['throughput']:.4f}\n")
PY
sed -n '1,10p' "$LAB_DIR/result.txt"
rm -rf -- "$LAB_DIR"

리뷰 질문: FCFS는 switch가 적지만 interactive가 B0 뒤에 막힌다. RR은 first response를 줄이지만 switch cost로 makespan/goodput을 희생하고 batch completion이 늦어진다. 어떤 정책도 모든 지표에서 지배적이지 않다.

확장: SLO를 I completion p99≤8, batch completion p99≤35, throughput≥0.18로 정하면 FCFS는 I p99, RR q=2는 throughput, RR q=1은 세 guardrail을 일부 위반해 모두 탈락한다. 이때는 나쁜 정책 하나를 억지로 고르지 말고 capacity·admission·workload 분리를 바꾼다. arrival burst와 switch cost를 두 배로 바꿔 선택이 다시 달라지는지도 확인한다.

11. production 실패 시나리오

상황: API p99를 줄이려고 모든 worker를 더 높은 priority와 좁은 CPU affinity로 배포했다. canary p50은 좋아졌지만 장애 시 트래픽이 몰리자 한 CPU runqueue만 뜨거워지고 control-plane worker가 굶어 health check와 autoscaling까지 늦어진다.

원인: 평균 steady-state만 측정했고 failover arrival burst, per-CPU imbalance, lower-priority control path와 rollback channel을 SLO에 넣지 않았다.

증거: per-CPU runqueue/PSI, TID affinity·policy, schedstat wait, context switch/migration, API p99와 health-check age, cgroup throttle을 incident timeline에 맞춘다.

대응: affinity/priority 변경을 rollback하고 bounded admission으로 queue를 안정화한다. control-plane에 별도 최소 entitlement와 escape CPU를 두고 failover load canary를 release gate로 추가한다.

12. 대기업 면접 질문 3개

Q1. latency-sensitive API와 batch가 같은 host에 있습니다. scheduler를 어떻게 선택합니까?
답변 포인트: workload/SLO와 ρ부터 정하고 admission·headroom을 둔다. 기본 SCHED_OTHER에서 별도 cgroup weight/quota로 격리하고 batch에 양수 nice/BATCH를 검토한다. app p99·goodput과 schedstat/PSI/throttle을 canary로 검증한다.

Q2. SCHED_FIFO를 쓰면 p99가 가장 좋아지지 않나요?
답변 포인트: higher-class preemption은 가능하지만 runaway loop·lock·I/O/page fault와 normal task starvation이 있다. hard requirement와 WCET가 없으면 과도하다. runtime limit, watchdog, emergency path와 admission이 있어야 한다.

Q3. CPU 70%인데 p99가 나쁩니다. scheduler 문제입니까?
답변 포인트: 평균은 증거가 부족하다. per-core/affinity hot spot, burst, PSI, schedstat wait, cgroup throttle을 본다. wait가 정상이라면 I/O·lock·GC·dependency/app queue 가설로 이동한다. 반증 가능한 지표 순서를 제시한다.
