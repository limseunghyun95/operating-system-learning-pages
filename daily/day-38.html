OPERATING SYSTEM · DAY 38 / 63 · FILESYSTEM I/O

read/write, buffering, page cache, direct I/O

한 줄 요약: buffered I/O는 user buffer와 page cache 사이에서 data를 복사하고 dirty data를 나중에 writeback하며, direct I/O는 file data의 page-cache 경로를 우회한다. 둘 다 VFS·filesystem·block layer를 지나며, 성공한 write()는 전체 요청 완료나 영속 저장을 보장하지 않는다.

1. 초보자 용어 사전

user bufferapplication address space의 memory 영역. read()의 목적지이고 write()의 source다.
buffering작은 operation을 memory에 모아 syscall·I/O 횟수를 줄이는 전략. libc stdio buffer와 kernel page cache는 서로 다른 layer다.
page cachefile offset의 data를 RAM의 folio/page로 cache하는 kernel 구조. read hit와 buffered write를 처리하며 memory pressure 때 reclaim된다.
page / foliopage는 memory 관리의 기본 단위, folio는 하나 이상의 연속 page를 묶어 다루는 Linux kernel abstraction이다.
cache hit / miss요청 data가 page cache에 있어 storage I/O 없이 제공됨 / 없어 storage에서 채워야 함.
readahead순차 접근을 감지해 다음 file range를 미리 읽는 최적화. 무작위 접근에서는 불필요한 I/O가 될 수 있다.
dirtyRAM의 cached data가 backing storage보다 최신인 상태. 아직 durable하다는 뜻이 아니다.
writebackdirty folio를 filesystem·block layer를 통해 storage로 내보내는 kernel 작업.
direct I/OO_DIRECT처럼 file data transfer에서 page cache를 우회하는 I/O. kernel·VFS·filesystem·device cache까지 모두 우회한다는 뜻은 아니다.
alignmentbuffer address, file offset, length이 filesystem/device가 요구하는 배수 경계에 맞는 조건.
short I/O요청한 byte보다 적은 양을 성공적으로 전송한 결과. 반환값이 양수면 그만큼 progress가 있었다.
file offsetopen file description에 저장된 다음 read/write 위치. pread/pwrite는 shared offset을 바꾸지 않는다.
DMAdevice/controller가 CPU의 byte-by-byte copy 없이 main memory와 data를 전송하는 방식. syscall 전체가 zero-copy라는 뜻은 아니다.
durabilitypower loss 뒤에도 data가 남는 성질. write(), O_DIRECT, visibility와 별도 계약이며 Day 39에서 fsync·ordering과 연결한다.

2. mental model: 접수 창구와 직송 트럭

buffered write는 택배를 지역 물류센터(page cache)에 맡기고 접수증을 받는 것과 같다. 창구가 받았다고 목적지 storage에 도착한 것은 아니다. writeback이 묶어서 운송한다. direct I/O는 규격 pallet로 창고까지 직송하는 경로다. 중간 data cache를 줄일 수 있지만 pallet 크기·주소·도착 위치를 맞춰야 하고, 작은 random request를 자동으로 합쳐 주는 장점도 잃는다.

4. 상태 전이: buffered read·write와 direct I/O

                                   → filesystem mapping → device read
                                   → uptodate → copy_to_user → return n

[syscall] → folio lookup/allocate → copy_from_user → mark dirty → return n
                                                   │
              background threshold / age / pressure / fsync
                                                   ▼
                         writeback → block I/O → completion
                              └ error recorded → later write/fsync may see EIO

[syscall] → support/alignment check → map file blocks → pin/map user pages
          → flush/invalidate overlapping cache as needed → submit bio/DMA
          → completion/unpin → return transferred bytes or error

5. CS·kernel deep dive

5.1 libc buffering과 page cache를 분리하라

fwrite()가 user-space stdio buffer에만 쌓이면 syscall조차 아직 안 했을 수 있다. fflush()는 이를 kernel로 넘기지만 page cache에서 storage로 persist시키는 계약은 아니다. 반대로 raw write()는 stdio buffer를 건너뛰어도 일반적으로 page cache에는 들어간다.

5.2 read/write는 “최대 count byte” API다

read()와 write()는 요청 길이를 모두 채우겠다는 API가 아니다. regular file의 EOF, pipe/socket의 현재 가용량, signal, quota·disk-full, nonblocking 상태 때문에 양수의 짧은 결과가 정상이다. 정확한 record가 필요하면 반환된 byte만큼 offset을 진전시키며 loop해야 한다.

5.3 page cache의 key는 file mapping과 offset이다

VFS inode의 address_space가 file content의 cached folio를 관리하고 filesystem의 address_space_operations가 read, readahead, dirty, writeback을 연결한다. 여러 process가 같은 file을 buffered read하거나 shared mmap하면 이 kernel cache를 공유할 수 있다.

5.4 read miss와 readahead

cache miss에서는 filesystem이 logical file offset을 extent/block으로 map하고 I/O를 제출한다. 순차 패턴이면 kernel이 뒤 range를 미리 읽어 future fault/read latency를 숨길 수 있다. workload가 random으로 바뀌면 읽지 않을 data가 queue와 memory를 소비하므로 hit ratio·device read amplification을 같이 봐야 한다.

5.5 buffered write의 빠른 반환은 latency debt다

user data를 folio에 copy하고 dirty 표시한 뒤 write()가 돌아올 수 있다. background flusher는 dirty threshold와 age에 따라 writeback하고, dirty memory가 높은 limit에 닿으면 writer 자신이 writeback·throttling에 묶여 tail latency가 튈 수 있다. 빠른 평균 write latency만 보면 debt를 숨긴다.

5.6 delayed error는 성공을 취소하지 않고 나중에 보고된다

buffered write 뒤 발생한 storage error는 최초 write()가 반환할 때 알 수 없을 수 있다. Linux는 writeback error를 후속 write() 또는 fsync()에서 EIO로 보고할 수 있다. 따라서 durability contract가 있는 code는 sync 결과까지 처리해야 한다.

5.7 direct I/O는 page cache data path의 우회다

Linux iomap direct read는 storage에서 caller buffer로 I/O를 내고, direct write는 caller buffer에서 storage로 낸다. 그러나 extent allocation, COW, encryption·compression support, metadata, locking, bio 생성과 completion은 filesystem 구현에 남는다. “kernel bypass”나 “무조건 zero-copy”라고 말하면 틀리다.

5.8 O_DIRECT의 alignment는 상수가 아니다

buffer address, file offset, I/O length 제한은 filesystem·kernel version·file 특성에 따라 다르고 misaligned request는 EINVAL 또는 buffered fallback이 될 수 있다. Linux 6.1부터 지원 filesystem에서는 statx(STATX_DIOALIGN)의 memory·offset alignment를 우선 조회한다. “항상 4096”을 hard-code하지 않는다.

5.9 buffered와 direct를 섞으면 coherency 비용이 생긴다

동일 range에 dirty page cache와 direct write가 겹치면 stale data 방지를 위해 flush·invalidate·serialization이 필요하다. iomap direct path도 overlapping dirty cache를 flush하고 write 전후 invalidate할 수 있다. overlapping buffered I/O·mmap·O_DIRECT 혼용을 피하고 ownership boundary를 정한다.

5.10 direct I/O는 application이 cache policy를 소유할 때 유리하다

database/storage engine처럼 자체 buffer pool, eviction, checksum, batching, queue depth를 제어하면 이중 cache와 memory pollution을 줄일 수 있다. 일반 application은 page cache의 sharing·readahead·write coalescing을 잃고 alignment·tail 처리·retry 복잡성을 떠안으므로 benchmark 없는 O_DIRECT 도입은 위험하다.

5.11 shared offset과 positional I/O

dup/fork로 공유한 open file description은 file offset도 공유한다. 여러 worker가 독립 offset에서 병렬 I/O한다면 pread/pwrite를 사용해 seek+read/write race와 shared offset contention을 제거한다. 반환된 short count를 기준으로 요청 위치를 갱신해야 한다.

7. 실무 best practice

  • protocol·file format이 정확한 길이를 요구하면 read_exact/write_all helper를 만들고 progress, EOF, retryable error를 명시한다.
  • 동시 worker의 독립 offset은 pread/pwrite로 표현하고 shared seek offset에 의존하지 않는다.
  • buffer size와 batch는 syscall count, cache locality, device queue, cancellation latency를 함께 측정해 고른다. 무조건 큰 buffer가 정답은 아니다.
  • readv/writev로 scatter/gather를 줄여도 전체 iovec를 다 처리했다는 보장은 없으므로 반환 byte를 vector에 다시 배분한다.
  • DB가 자체 cache를 갖더라도 buffered와 O_DIRECT 양쪽을 실제 data set·memory pressure·failure injection으로 비교한다.
  • direct I/O는 statx(STATX_DIOALIGN)로 capability와 alignment를 탐지하고 aligned allocator·offset·length·EOF tail 정책을 한 module에 캡슐화한다.
  • 동일 file range의 buffered, direct, writable mmap 혼용을 피하고 mode 전환은 quiesce→flush→invalidate→verify 절차로 제한한다.
  • 관찰 지표는 application latency만 보지 말고 cache hit/miss, major fault, readahead, Dirty/Writeback, writeback throttle, PSI I/O, device latency·queue depth를 연결한다.
  • production benchmark에서 global drop_caches를 사용하지 않는다. 격리 환경에서도 cold/warm 조건과 cache state를 기록한다.
  • 성공 응답의 의미를 “kernel memory에 복사”, “device completion”, “power-loss durable” 중 무엇인지 API 계약에 적는다.

8. error handling runbook

  1. return value 우선: n > 0이면 n byte progress를 먼저 commit한다. 남은 slice만 재시도한다.
  2. read의 0: requested length가 0이 아니라면 EOF다. error로 무한 retry하지 않는다.
  3. EINTR: progress가 없는 실패만 현재 offset에서 재시도한다. wrapper가 일부 progress를 반환했는지 계약을 확인한다.
  4. EAGAIN/EWOULDBLOCK: busy loop하지 말고 readiness·deadline·cancellation과 연결한다. regular file과 socket의 의미가 다르다.
  5. ENOSPC/EDQUOT/EFBIG: retry budget을 태우지 말고 admission을 닫고 quota·capacity·file limit을 구분한다. 이미 기록된 prefix를 보존한다.
  6. EPIPE: SIGPIPE 정책과 함께 처리한다. process 종료를 원하지 않으면 signal을 block/ignore하고 error를 상위로 전달한다.
  7. EIO: 현재 request 또는 이전 buffered writeback에서 왔을 수 있다. file·filesystem·device evidence를 보존하고 durability를 성공으로 보고하지 않는다.
  8. O_DIRECT EINVAL: 지원 여부와 buffer address·offset·length alignment를 statx와 filesystem 문서로 확인한다. silent buffered fallback을 자체 구현하지 않는다.
  9. timeout/cancel: completion을 못 봤다고 write가 전혀 실행되지 않았다고 가정하지 않는다. idempotency·offset·record checksum으로 재조정한다.
  10. verify: byte count, logical offset, checksum, sync 결과, device error를 검증한 뒤에만 durable success를 응답한다.

9. 놓치기 쉬운 함정

  • write가 양수면 전체 요청 성공: 반환 byte만 성공이며 남은 suffix는 아직 쓰지 않았다.
  • write 성공은 disk durable: buffered path에서는 RAM의 dirty folio일 수 있고 direct도 O_SYNC 계약을 대신하지 않는다.
  • fflush와 fsync가 같다: 전자는 stdio→kernel, 후자는 kernel dirty data/metadata→storage 계약이다.
  • O_DIRECT는 kernel bypass: page-cache data path를 우회하지만 VFS·filesystem·block layer·metadata를 거친다.
  • O_DIRECT가 항상 빠르다: readahead·coalescing·shared cache를 잃고 small I/O나 alignment 처리로 더 느릴 수 있다.
  • direct alignment는 항상 4KiB: filesystem·kernel·file에 따라 다르므로 capability를 조회한다.
  • EOF는 일시적 error: regular file read 0은 EOF이며 retry loop는 CPU를 태운다.
  • 한 번의 read가 record 하나: byte-stream API에서는 framing을 application이 복원해야 한다.
  • buffered/direct/mmap 혼용은 공짜: cache flush·invalidate·serialization과 stale-read 위험이 생긴다.
  • drop_caches가 공정한 benchmark: system-wide workload를 교란하고 production cache behavior를 왜곡한다.

10. 30분 실습: short I/O와 page-cache state model

권한·platform에 의존하지 않는 교육용 model이다. short read/write를 강제로 만들고 buffered write가 dirty에서 writeback으로 이동하는 흐름을 검증한다. 실제 kernel timing이나 filesystem 구현을 재현하지 않는다.

python3 - <<'PY'
class ShortWriter:
    def __init__(self, limit): self.limit, self.data = limit, bytearray()
    def write(self, chunk):
        n = min(self.limit, len(chunk))
        self.data.extend(chunk[:n])
        return n

class ShortReader:
    def __init__(self, data, limit): self.data, self.limit, self.pos = data, limit, 0
    def read(self, count):
        if self.pos == len(self.data): return b""
        n = min(count, self.limit, len(self.data) - self.pos)
        out = self.data[self.pos:self.pos+n]; self.pos += n
        return out

def write_all(dst, data):
    done = 0
    while done < len(data):
        n = dst.write(data[done:])
        if n <= 0: raise OSError("no write progress")
        done += n
    return done

def read_exact(src, size):
    out = bytearray()
    while len(out) < size:
        chunk = src.read(size - len(out))
        if not chunk: raise EOFError(f"wanted {size}, got {len(out)}")
        out.extend(chunk)
    return bytes(out)

payload = b"page-cache-is-not-durability"
w = ShortWriter(limit=5)
assert write_all(w, payload) == len(payload) and bytes(w.data) == payload
r = ShortReader(bytes(w.data), limit=4)
assert read_exact(r, len(payload)) == payload

cache, dirty, storage = {}, set(), {}
def buffered_write(page, value):
    cache[page] = value; dirty.add(page)  # syscall return model
def writeback():
    for page in list(dirty): storage[page] = cache[page]; dirty.remove(page)
def direct_read(page):
    return storage.get(page)              # page cache data path bypass

buffered_write(7, b"new")
assert cache[7] == b"new" and direct_read(7) is None and 7 in dirty
writeback()
assert direct_read(7) == b"new" and not dirty
print("short_io_bytes", len(payload))
print("cache", cache, "storage", storage, "dirty", dirty)

  1. 0~10분: loop를 제거해 5 byte만 남는 실패를 관찰하고 byte progress invariant를 적는다.
  2. 10~20분: buffered write 직후 cache와 storage가 다른 이유를 state diagram으로 설명한다.
  3. 20~30분: zero progress, early EOF, writeback error를 model에 주입하고 상위 API의 응답 계약을 설계한다.

12. 실패 시나리오: 평균 1ms write, p99는 8초

upload service는 write() 반환 즉시 “저장 완료”를 응답했다. 평소에는 page cache copy만 측정돼 1ms였지만 storage가 느려지자 dirty memory가 limit에 닿고 request thread가 writeback에 throttling되어 p99가 8초가 됐다. 이후 device error가 fsync()에서 나타났지만 service는 sync 결과를 보지 않아 이미 성공을 응답했다. 대응은 admission control, per-file byte progress, Dirty·Writeback·PSI·device latency correlation, preallocation·quota alert, 명시적 durability boundary와 sync error 전파였다. O_DIRECT로 즉시 바꾸지 않고 workload replay로 cache·queue trade-off를 검증했다.
