OPERATING SYSTEM · DAY 39 / 63 · CRASH CONSISTENCY

durability, fsync, ordering, atomic rename

한 줄 요약: crash-safe file 교체는 temp file의 data·필수 metadata를 먼저 동기화하고, 같은 filesystem 안에서 rename으로 이름을 원자적으로 바꾼 뒤, parent directory를 fsync해 namespace 변경까지 durable하게 만든다. atomic visibility와 power-loss durability는 서로 다른 계약이다.

2. mental model: 원장과 색인 카드

file data는 창고의 원장이고 directory entry는 원장을 찾는 색인 카드다. 새 원장을 완성해 금고에 넣는 것이 file fsync, 색인 카드를 새 원장으로 한 번에 바꾸는 것이 rename, 바뀐 색인 카드 자체를 금고에 확정하는 것이 directory fsync다. 원장을 먼저 확정하지 않으면 색인은 빈 원장을 가리킬 수 있고, 색인까지 확정하지 않으면 reboot 뒤 예전 이름 관계로 돌아갈 수 있다.

4. 상태 전이: crash-safe replace protocol

[target = OLD, directory durable]
       │ 1. 같은 directory에 unique temp 생성(O_EXCL, safe mode)
       ▼
[temp inode allocated]
       │ 2. write_all + checksum/version + chmod/chown/xattr if required
       ▼
[temp dirty and complete]
       │ 3. fsync(temp) 또는 적합한 fdatasync
       ▼
[NEW contents retrievable after crash]
       │ 4. rename(temp, target) — runtime namespace atomic switch
       ▼
[lookup(target) = NEW, open OLD fd는 OLD inode 유지]
       │ 5. fsync(parent directory)
       ▼
[NEW name→inode relation도 durable] → success response

Crash A: 3 전 → OLD 유지, temp는 없거나 incomplete
Crash B: 3 후 4 전 → OLD 유지, complete orphan temp 가능
Crash C: 4 후 5 전 → 실행 중에는 NEW, reboot 후 name relation은 보장 못 함
Crash D: 5 후 → NEW가 durable contract

5. CS·kernel deep dive

5.1 write success, visibility, durability를 분리하라

buffered write()는 page cache에 copy된 byte count를 성공으로 돌려줄 수 있다. 다른 reader가 새 data를 볼 수 있어도 controller cache·media까지 persistence가 끝났다는 뜻은 아니다. API 성공 조건을 “memory accepted”, “namespace published”, “power-loss durable” 중 하나로 명시해야 한다.

5.2 fsync의 scope는 열린 file object다

fsync(fd)는 해당 file의 dirty data와 metadata를 flush하고 device가 완료를 보고할 때까지 기다린다. 그러나 그 file을 새 이름으로 연결한 parent directory entry까지 자동으로 sync한다고 일반화할 수 없다. 새 file 생성·unlink·rename의 durable namespace가 필요하면 directory fd도 fsync한다.

5.3 fdatasync는 “data만”보다 정확한 계약이다

후속 read에 필요한 metadata는 함께 sync한다. append로 늘어난 st_size는 필요하지만 단순 mtime 변경은 생략될 수 있다. metadata 보존이 correctness에 포함되거나 filesystem별 차이를 감당하기 어렵다면 fsync를 선택하고 측정한다.

5.4 O_SYNC는 per-write durability, fsync는 batching boundary다

O_SYNC는 매 write마다 file-integrity completion을 요구해 단순하지만 flush 횟수와 tail latency가 커질 수 있다. 여러 record를 쓰고 한 번 fsync하는 group commit은 throughput을 높이는 대신 마지막 sync 전 crash-loss window를 만든다. RPO·p99 SLO로 batch size와 interval을 정한다.

5.5 atomic rename은 runtime namespace atomicity다

같은 mounted filesystem 안에서 기존 newpath는 atomically replaced되어 lookup이 “없음”을 보는 순간이 없다. 하지만 기존 fd는 old inode를 계속 참조할 수 있고, 잠깐 oldpath와 newpath가 같은 inode를 가리킬 수 있다. cross-filesystem rename은 EXDEV로 실패한다.

5.6 rename atomicity와 crash durability는 독립 축이다

rename이 성공했어도 directory metadata가 stable하지 않으면 crash 후 새 name 관계를 요구할 수 없다. 반대로 file data를 fsync하지 않고 rename·directory fsync만 하면 이름은 새 inode를 가리키지만 content가 비거나 오래된 상태일 수 있다. 순서는 data before name이다.

5.7 block layer는 flush와 FUA로 volatile cache를 제어한다

device는 write completion을 non-volatile media 도달 전에 보고할 수 있다. Linux filesystem은 REQ_PREFLUSH로 이전 write를 먼저 stable하게 만들고 REQ_FUA로 특정 write의 stable completion을 요구한다. application은 raw command를 조립하기보다 filesystem이 제공하는 fsync/O_SYNC 계약을 사용한다.

5.8 filesystem journal을 application protocol 대신 쓰지 마라

journal·copy-on-write filesystem은 내부 metadata invariant와 ordering을 제공하지만 mode, mount option, kernel version, hardware flush correctness에 따라 보장 범위가 다르다. “ext4니까 rename만 해도 된다” 같은 undocumented dependency는 피하고 documented sync boundary를 호출한다.

5.9 temp file은 target과 같은 directory에 둔다

같은 directory면 동일 filesystem일 가능성을 확보하고 rename의 atomic replacement를 사용할 수 있다. /tmp에서 만들면 target과 mount가 달라 EXDEV가 날 수 있다. O_CREAT|O_EXCL 또는 지원 환경의 O_TMPFILE로 collision·symlink race를 줄인다.

5.10 두 directory 사이 rename은 둘 다 고려한다

source와 destination directory가 다르면 한 directory에서는 name이 제거되고 다른 곳에는 추가된다. crash-safe contract가 양쪽 namespace 변화를 포함한다면 관련 directory fd를 모두 sync하고 filesystem 문서를 검증한다. mount가 다르면 atomic rename 자체가 불가능하다.

5.11 network filesystem은 결과가 uncertain할 수 있다

NFS에서 server가 rename을 수행한 뒤 crash하고 client RPC가 재전송되면 call이 실패해도 rename은 이미 적용됐을 수 있다. timeout/error를 “아무 일도 안 일어남”으로 해석하지 말고 target version·checksum을 reread해 reconcile한다.

5.12 close는 durability primitive가 아니다

successful close도 disk 저장을 보장하지 않는다. close가 delayed error를 보고할 수는 있지만 fsync를 대신하지 않으며, Linux에서 close error 뒤 fd는 이미 재사용될 수 있어 retry close는 다른 fd를 닫는 위험이 있다. durability가 필요하면 fsync 결과를 먼저 확인하고 close error도 진단에 포함한다.

7. 실무 best practice

  • temp를 target과 같은 directory에 mode 0600·unique name·exclusive create로 만들고, 최종 permission·owner·xattr를 publication 전에 설정한다.
  • short write·EINTR을 처리하는 write_all과 checksum/version footer로 complete payload를 검증한다.
  • data와 required metadata 설정을 끝낸 뒤 temp fd를 fsync한다. fsync 뒤 metadata를 바꾸면 다시 sync한다.
  • rename 성공 뒤 parent directory fd를 fsync하고, 그 성공 뒤에만 durable success를 외부에 응답한다.
  • 동시 writer가 있으면 generation, lock, compare-and-swap policy 또는 RENAME_NOREPLACE 같은 명시적 conflict 규칙을 둔다.
  • RPO가 허용하면 group commit을 사용하되 batch interval·record count·fsync p99와 crash-loss window를 함께 공개한다.
  • posix_fallocate 등으로 space를 미리 확보해도 quota·device·writeback failure를 제거하지는 못한다. sync error path는 유지한다.
  • startup recovery는 owned temp naming pattern, embedded version/checksum, target state를 기준으로 orphan을 판별한다. 오래됐다는 이유만으로 임의 file을 삭제하지 않는다.
  • fsync latency histogram, EIO·ENOSPC·EDQUOT, dirty/writeback, device flush latency, queue saturation을 같은 trace에 묶는다.
  • filesystem·mount·storage stack별 crash test를 실제 power-cut/fault-injection 환경에서 수행하고, unsupported directory fsync나 network semantics를 문서화한다.

8. error handling runbook

  1. create: EEXIST는 temp collision/leftover를 조사하고 새 nonce를 사용한다. symlink를 따라가며 overwrite하지 않는다.
  2. write: positive short count는 progress로 보존한다. ENOSPC/EDQUOT/EIO면 target을 rename하지 않고 temp를 격리·진단한다.
  3. file sync: EINTR는 platform contract에 맞춰 재시도하고, EIO/ENOSPC/EDQUOT면 durable success를 금지한다. fsync가 이전 writeback error를 늦게 전달할 수 있다.
  4. rename: EXDEV면 copy+rename을 자동으로 atomic이라 가장하지 않는다. same-filesystem staging으로 다시 설계한다.
  5. conflict: EEXIST나 generation mismatch는 overwrite retry가 아니라 application conflict로 처리한다.
  6. uncertain result: timeout/NFS error 뒤 operation 미실행을 가정하지 말고 target version·inode·checksum을 reread해 reconcile한다.
  7. directory sync: unsupported EINVAL을 무시하고 durable이라 보고하지 않는다. filesystem별 adapter·documented guarantee 또는 다른 storage protocol이 필요하다.
  8. cleanup: rename 전이며 자신이 만든 temp name이라는 증거가 있을 때만 unlink한다. rename 후에는 target을 rollback 삭제하지 않는다.
  9. close: fsync 뒤 close error를 기록하지만 Linux에서 실패한 close를 retry하지 않는다.
  10. recovery: OLD/NEW 둘 중 어느 state가 valid한지 checksum·version invariant로 판별하고, 사람 승인 없이 “가장 최신 mtime”을 선택하지 않는다.

9. 놓치기 쉬운 함정

  • rename 성공 = durable: runtime namespace atomicity와 power-loss durability는 별개다.
  • file fsync 하나면 새 이름도 durable: containing directory entry는 별도 sync가 필요하다.
  • directory fsync만 하면 content도 안전: 먼저 new file data를 sync해야 한다.
  • close가 자동 flush: successful close도 disk 저장을 보장하지 않는다.
  • fflush가 storage flush: stdio user buffer를 kernel로 보낼 뿐이다.
  • O_DIRECT가 durability 제공: page cache 우회와 synchronized persistence는 다른 flag/contract다.
  • sync_file_range가 fsync 대체: metadata나 volatile device cache flush를 보장하지 않는다.
  • temp를 /tmp에 만들면 안전: target과 filesystem이 달라 atomic rename이 EXDEV로 실패할 수 있다.
  • journal filesystem이면 protocol 불필요: application invariant와 documented sync boundary를 대신하지 않는다.
  • close error는 같은 fd로 retry: fd가 이미 release·reuse됐을 수 있다.

10. 30분 실습: fault point별 safe replace 관찰

실제 같은-directory temp, file fsync, replace, directory fsync를 실행하고 child를 고의 종료한다. 이는 power-cut durability 증명이 아니라 visible state와 protocol 경계를 확인하는 실습이다.

python3 - <<'PY'
import os, pathlib, tempfile

def sync_dir(path):
    fd = os.open(path, os.O_RDONLY)
    try: os.fsync(fd)
    finally: os.close(fd)

def write_all(fd, data):
    view = memoryview(data)
    while view:
        n = os.write(fd, view)
        if n <= 0: raise OSError("no progress")
        view = view[n:]

def child_update(directory, phase):
    target = directory / "config"
    fd, temp = tempfile.mkstemp(prefix=".config.tmp-", dir=directory)
    try:
        write_all(fd, b"version=NEW\n")
        os.fsync(fd)                       # NEW content first
        if phase == "after_file_fsync": os._exit(70)
        os.close(fd); fd = -1
        os.replace(temp, target)           # atomic visibility switch
        if phase == "after_rename": os._exit(71)
        sync_dir(directory)                # durable namespace boundary
        os._exit(0)
    finally:
        if fd >= 0: os.close(fd)

for phase in ("after_file_fsync", "after_rename", "complete"):
    with tempfile.TemporaryDirectory(prefix="os-day39-") as raw:
        d = pathlib.Path(raw); target = d / "config"
        target.write_bytes(b"version=OLD\n")
        with target.open("rb") as f: os.fsync(f.fileno())
        sync_dir(d)
        pid = os.fork()
        if pid == 0: child_update(d, phase)
        _, status = os.waitpid(pid, 0)
        temps = sorted(p.name for p in d.glob(".config.tmp-*"))
        value = target.read_text().strip()
        print(phase, "exit", os.waitstatus_to_exitcode(status), value, temps)
        if phase == "after_file_fsync": assert value == "version=OLD" and len(temps) == 1
        else: assert value == "version=NEW" and not temps
PY
  1. 0~10분: file fsync 뒤 rename 전 종료에서 OLD와 orphan temp를 확인한다.
  2. 10~20분: rename 뒤 directory fsync 전 종료에서 runtime NEW는 보이지만 reboot durability는 아직 주장할 수 없는 이유를 설명한다.
  3. 20~30분: checksum mismatch·ENOSPC·concurrent writer를 추가하고 recovery decision table을 작성한다.

12. 실패 시나리오: config는 보였지만 reboot 후 되돌아왔다

배포 agent가 temp를 쓰고 rename한 직후 “성공”을 응답했다. 새 process는 NEW config를 읽었지만 parent directory fsync 전에 host가 power loss를 겪었다. reboot 뒤 target name은 OLD로 돌아왔고 control plane은 이미 성공으로 기록해 drift가 생겼다. 해결은 temp data fsync→rename→directory fsync를 하나의 transaction boundary로 만들고, target에 monotonic generation+checksum을 넣어 restart 시 control-plane expected version과 reconcile하는 것이었다. fsync p99가 SLO를 위협하자 durable group commit과 rollout admission을 적용하되 RPO를 명시했다.
