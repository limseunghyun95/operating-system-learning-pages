OPERATING SYSTEM · DAY 40 / 63 · FILESYSTEM RECOVERY

journaling, crash consistency, recovery

한 줄 요약: journaling은 home location을 덮기 전에 변경 의도를 journal에 transaction으로 기록하고 commit을 durable하게 만든 뒤 checkpoint하며, crash 후에는 완전히 commit된 transaction만 replay하여 metadata invariant를 복구한다.

1. 초보자 용어 사전

journalfilesystem 본래 위치를 고치기 전에 변경 내용을 순서대로 적는 복구용 log 영역.
WALWrite-Ahead Logging. 실제 data 구조를 바꾸기 전에 log를 먼저 durable하게 만드는 규칙.
transaction함께 commit되거나 모두 버려져야 하는 metadata update 묶음.
descriptor blocktransaction에 어떤 filesystem block이 들어 있는지 기술하는 journal block.
commit blocktransaction의 journal 기록이 완성됐음을 나타내는 마지막 marker. checksum으로 torn/corrupt log를 걸러낸다.
checkpointcommit된 journal image를 filesystem의 원래 home block에 반영해 log 공간을 재사용 가능하게 만드는 단계.
replay / redomount/recovery 때 commit이 확인된 update를 home block에 다시 적용하는 것. 반복 적용해도 결과가 같도록 설계한다.
revoke예전 transaction의 특정 block image를 replay하지 말라는 기록. freed·reused block에 오래된 data를 덮는 일을 막는다.

orphan inodelink는 사라졌지만 open fd 때문에 정리가 끝나지 않은 inode. crash recovery가 truncate/delete를 마쳐야 한다.
fsckfilesystem 구조를 검사하고 불일치를 수리하는 도구. journal replay와 같은 것은 아니며 mounted filesystem에 함부로 실행하면 위험하다.

2. mental model: 원본 장부와 봉인된 변경 봉투

home block은 원본 장부, journal transaction은 변경 서류가 든 봉투다. descriptor와 block image를 넣고 checksum이 있는 commit seal을 붙여 금고에 넣은 뒤에만 원본 장부를 고친다. crash 뒤 seal이 없거나 깨진 봉투는 폐기하고, 정상 seal이 있는 봉투만 다시 적용한다. journal은 모든 application data를 자동 보존하는 backup이 아니라 filesystem 내부 일관성을 빠르게 회복하는 mechanism이다.

3. architecture: ext4/JBD2 transaction path

application: write / create / rename / fsync
       │ syscall
       ▼
VFS → ext4: inode·bitmap·directory metadata 변경
       │ jbd2_journal_start(handle, credits)
       ▼
JBD2 running transaction
  descriptor → metadata images → revoke → commit block + checksum
       │ flush/FUA로 commit durability ordering
       ▼
committed journal transaction
       │ checkpoint (비동기 가능)
       ▼
filesystem home blocks on storage

crash → mount recovery scans journal
      → valid commit만 redo, incomplete/bad checksum은 discard
      → orphan cleanup → normal mount

4. 상태 전이와 crash point

[RUNNING] -- journal blocks 기록 --> [LOGGED, NOT COMMITTED]
    │ crash: commit marker 없음 → transaction 전체 폐기
    ▼
[COMMITTING] -- barrier/flush + commit block --> [COMMITTED]
    │ crash: checksum-valid commit → replay 대상
    ▼
[CHECKPOINTING] -- home blocks 반영 --> [CHECKPOINTED]
    │ crash: 일부 home block만 갱신돼도 journal redo로 완성
    ▼
[TAIL ADVANCED] -- journal space 재사용 가능

핵심 invariant: home block은 commit보다 먼저 새 상태에 의존해서는 안 된다.

5. CS·kernel deep dive

5.1 atomic sector 하나로는 multi-block invariant를 지킬 수 없다

file 생성은 inode allocation bitmap, inode table, directory block, free-count 같은 여러 block을 바꾼다. 중간에 crash가 나면 allocated-but-unreferenced 또는 referenced-but-free 같은 모순이 생긴다. WAL은 이 여러 write를 하나의 recoverable transaction으로 묶는다.

5.2 commit과 checkpoint를 분리하는 이유

commit은 journal 안에서 transaction 완료를 빠르게 확정하는 latency boundary이고, checkpoint는 느리게 home block으로 흩어 쓴다. commit 뒤에는 application에 진행을 허용하면서 home write를 batch할 수 있다. 다만 journal tail을 전진하려면 이전 transaction checkpoint가 끝나야 한다.

5.3 checksum과 sequence number가 torn/stale log를 구분한다

circular journal에는 오래된 transaction도 남아 있다. sequence number가 logical order를, checksum이 descriptor·data·commit의 완전성을 확인한다. commit block만 보인다는 이유로 payload까지 정상이라고 가정하면 안 된다.

5.4 revoke는 block reuse 문제를 막는다

transaction T1이 block X의 옛 metadata image를 기록한 뒤 T2에서 X를 free·재사용할 수 있다. recovery가 T1 image를 무조건 replay하면 새 owner를 오염시킨다. revoke record는 특정 sequence의 과거 image를 무효화한다.

5.5 handle credit는 resource reservation이다

ext4 operation은 JBD2 handle을 열며 최악의 metadata block 수를 credit으로 예약한다. credit을 과소평가하면 operation 도중 transaction extend/restart가 필요하고 lock ordering과 error path가 복잡해진다. production에서 journal full은 단순 성능 문제가 아니라 progress 문제다.

5.6 replay는 redo이고 application rollback이 아니다

JBD2는 commit된 metadata의 after-image를 다시 쓴다. unfinished application business transaction을 취소하지 않는다. database나 service는 별도 WAL, idempotency key, version/checksum으로 자신의 invariant를 복구해야 한다.

5.7 write ordering은 storage stack 끝까지 이어져야 한다

CPU에서 순서대로 submit해도 block layer와 device cache가 reorder할 수 있다. Linux는 flush와 FUA를 사용해 journal data가 durable해진 뒤 commit completion이 보고되도록 한다. cache가 flush를 거짓으로 완료하면 filesystem algorithm만으로는 보장을 만들 수 없다.

5.8 mount recovery도 write다

ext4 journal replay는 readonly mount 요청에서도 storage를 변경할 수 있다. 증거 보존이 목적이면 block-device snapshot 또는 ro,noload 같은 명시적 정책을 검토해야 한다. noload는 불일치를 숨길 수 있으므로 일반 운영 복구 옵션은 아니다.

5.9 journal replay와 fsck를 구분하라

정상적인 unclean shutdown이면 e2fsck는 먼저 journal을 replay하고 종료할 수 있다. checksum failure, device error, 구조적 corruption은 전체 scan과 수리가 필요하다. mounted filesystem에 e2fsck를 실행하면 kernel의 in-memory state와 충돌할 수 있다.

5.10 fast commit도 full journal을 대체하지 않는다

ext4 fast commit은 일부 변경의 최소 delta만 기록해 latency를 줄이고, 지원되지 않는 operation이나 공간 부족에서는 full commit으로 fallback한다. recovery는 fast-commit area와 full JBD2 transaction의 ordering을 함께 해석한다.

7. 실무 best practice

  • application durability boundary는 filesystem journal의 존재가 아니라 fsync/fdatasync 성공으로 정의한다.
  • filesystem type, mount options, kernel version, storage cache/flush contract를 incident evidence와 배포 inventory에 남긴다.
  • journal size·commit latency·space pressure와 block-device latency를 함께 관찰한다. journal이 작으면 checkpoint pressure와 tail latency가 커진다.
  • checksum, generation, idempotency key를 application record에 포함해 replay 뒤에도 중복 처리를 안전하게 만든다.
  • crash injection, VM hard reset, device error를 staging에서 시험하고 각 crash point의 허용 상태를 table로 작성한다.
  • 복구 전 snapshot·image를 만들고 원본에 대한 즉흥 수리를 피한다. 수리 도구의 version과 명령, exit code, 변경 내역을 보존한다.
  • RAID/controller의 battery-backed cache와 flush passthrough를 확인한다. “enterprise SSD”라는 이름만으로 power-loss protection을 가정하지 않는다.
  • shutdown path가 느리더라도 SIGKILL 의존 대신 admission 중단→drain→sync→unmount 순서를 둔다.

8. error handling·복구 runbook

  1. 격리: 반복 write를 멈추고 affected device/filesystem을 identify한다. I/O error가 계속되면 read-only 전환과 service failover를 우선한다.
  2. 증거: kernel log, mount options, device health, journal/e2fsck message, application checksum mismatch를 시각과 함께 수집한다.
  3. 복제: hardware failure가 의심되면 가능한 범위에서 block-level image/snapshot을 만들고 복구 작업은 copy에 수행한다.
  4. 정상 replay: clean storage라면 documented mount/e2fsck 흐름으로 journal replay한다. mount가 성공했는지만 보지 말고 application invariant도 검사한다.
  5. fsck: unmount 또는 offline replica에서만 실행한다. 자동 -y보다 dry evidence와 변경 범위를 먼저 검토한다.
  6. 재조정: business record의 generation/checksum과 upstream source of truth를 비교해 missing/duplicate work를 reconcile한다.
  7. 재개: read/write smoke test, error counter 안정, replay backlog 소진, backup/replica consistency를 확인한 뒤 단계적으로 traffic을 연다.

9. 놓치기 쉬운 함정

  • journal = backup: logical delete나 application bug도 정상 commit된다.
  • commit = checkpoint: commit 뒤 home block 반영이 덜 끝나도 recovery가 가능하다.
  • metadata journaling = user data durability: ordered mode의 ordering과 fsync 계약을 혼동하지 않는다.
  • replay가 business transaction 복구: filesystem은 application 의미를 모른다.
  • read-only mount는 절대 write 안 함: journal replay가 발생할 수 있다.
  • journal만 별도 device면 무조건 빠름: external journal 장애가 filesystem 전체 availability에 영향을 주며 latency path도 측정해야 한다.
  • fsck를 mounted production에 실행: live kernel state와 수리 결과가 충돌할 수 있다.
  • checksum이면 media fault가 해결: 탐지는 가능해도 원본 복구에는 replica/backup이 필요하다.

10. 30분 실습: redo journal simulator

python3 - <<'PY'
import hashlib, json
def checksum(txid, changes):
    raw=json.dumps([txid,changes],sort_keys=True,separators=(',',':'))
    return hashlib.sha256(raw.encode()).hexdigest()
def recover(home, journal):
    out=dict(home)
    for tx in journal:
        if tx.get('commit') == checksum(tx['id'],tx['changes']):
            out.update(tx['changes'])
    return out
old={'inode.size':0,'bitmap.block7':'free'}
incomplete={'id':1,'changes':{'inode.size':4096,'bitmap.block7':'used'}}
committed={'id':2,'changes':{'inode.size':8192,'bitmap.block7':'used'}}
committed['commit']=checksum(committed['id'],committed['changes'])
corrupt={'id':3,'changes':{'inode.size':12288},'commit':'torn-checksum'}
assert recover(old,[incomplete]) == old
after=recover(old,[incomplete,committed,corrupt])
assert after == {'inode.size':8192,'bitmap.block7':'used'}
assert recover(after,[committed]) == after       # replay idempotence
print('discarded=[1,3] replayed=[2] home=',after)
PY
  1. 0~10분: commit marker가 없는 transaction이 폐기되는지 확인한다.
  2. 10~20분: checksum corruption과 sequence gap을 추가한다.
  3. 20~30분: revoke set과 checkpoint 후 journal tail 이동을 구현하고 invariant를 적는다.

12. 실패 시나리오

host reset 뒤 ext4가 journal replay로 mount됐지만 일부 application event가 사라졌다. 팀은 “journal이 있으니 모든 write가 durable하다”고 믿고 성공 응답 전에 fsync하지 않았다. metadata invariant는 정상이라 fsck도 문제없었지만 page cache의 마지막 data는 commit되지 않았다. 재발 방지는 application ack 전에 명시적 fsync, record generation/checksum, group-commit RPO 문서화, crash-injection test였다. filesystem recovery 성공과 business recovery 성공을 별도 SLI로 만들었다.
