Operating System · Day 24 / 63 · Virtual Memory

demand paging, page fault, copy-on-write

한 줄 요약: page fault는 CPU가 현재 translation으로 access를 끝내지 못해 kernel에 도움을 요청하는 exception이며, kernel은 VMA 계약에 따라 page를 준비·복사·load하고 PTE를 갱신해 instruction을 재시작하거나 SIGSEGV·SIGBUS·OOM으로 실패시킨다.

1. 초보자 용어 사전

demand pagingvirtual range를 만들 때 모든 physical page를 준비하지 않고 실제 access가 생긴 page만 필요 시 준비하는 방식이다.
page faultMMU가 translation 또는 permission 문제로 memory access를 완료하지 못해 CPU가 kernel fault handler로 제어를 넘기는 synchronous exception이다.
exception / signalexception은 CPU가 현재 instruction 때문에 만드는 kernel 진입 사건이고, signal은 kernel이 process에 전달하는 비동기적 interface다. 복구 불가 fault가 SIGSEGV/SIGBUS로 변환될 수 있다.
minor faultI/O 없이 처리된 page fault. anonymous zero-fill, page-cache hit, COW copy처럼 kernel work와 memory copy가 있어도 minor일 수 있다.
major fault처리에 storage I/O가 필요했던 page fault. process가 잠들고 storage·queue latency를 기다릴 수 있다.
first touch예약된 virtual page를 처음 읽거나 쓰는 access. page allocation, zeroing, NUMA placement, fault 처리 비용이 이 시점에 나타날 수 있다.
zero page / zero-fill새 anonymous memory가 0으로 보이도록 하는 구현. read는 공유 read-only zero page로, write는 새로 0-cleared page를 할당하는 방식이 가능하다.
copy-on-write (COW)처음에는 physical page를 공유하고 write가 발생할 때 writer용 private copy를 만드는 지연 복사 기법이다.
write-protect faultwrite가 허용된 VMA라도 COW를 위해 PTE를 read-only로 둔 경우 발생하는 permission fault. kernel이 정상적으로 복구할 수 있다.
page cachefile 내용을 memory page/folio로 캐시하는 kernel 계층. file-backed fault가 cache hit면 I/O 없는 minor fault가 될 수 있다.
VMAVirtual Memory Area. address range의 backing, private/shared, read/write/execute 정책을 나타내는 kernel metadata다.
PTEPage Table Entry. 현재 page의 PFN, present, writable 등 hardware translation 상태를 담는다.
overcommitvirtual memory 요청 시점에 모든 future physical/swap backing을 즉시 보장하지 않는 정책. mmap/malloc 성공과 future touch 성공을 분리한다.
OOMOut Of Memory. reclaim 등으로 allocation을 만족시키지 못해 kernel 또는 memory cgroup이 victim을 종료하거나 allocation을 실패시키는 상태다.

2. mental model: 좌석 예약과 실제 입장

mmap은 공연장의 좌석 구역(VMA)을 예약하는 일에 가깝다. 모든 좌석에 관객과 물품(physical page)을 미리 배치하는 것은 아니다. 첫 access가 입장 요청이고 page fault는 안내 직원(kernel)을 부르는 벨이다.

  • anonymous first write: 빈 좌석에 0으로 초기화된 새 page를 배치한다.
  • file mapping: page cache에서 찾고 없으면 file에서 읽어 온다.
  • COW: parent와 child가 같은 책을 보다가 누군가 메모하려는 순간 그 사람에게만 복사본을 준다.
  • invalid access: 예약 범위가 없거나 계약된 권한이 없으면 kernel이 page를 만들지 않고 signal을 보낸다.

따라서 page fault 수가 0이어야 좋은 system이 아니다. fault 종류, 처리 latency, fault rate, SLO와 memory headroom을 함께 본다.

5. CS·kernel·hardware deep dive

5.1 VMA permission과 PTE permission은 같은 층이 아니다

VMA는 application 계약상 writable일 수 있지만 COW를 구현하려고 현재 PTE의 writable bit를 끌 수 있다. write-protect fault가 오면 kernel은 “VMA도 write 금지”인지 “VMA는 write 허용이고 PTE만 COW용 read-only”인지 구분한다. 전자는 SEGV_ACCERR, 후자는 정상 복구 경로다.

5.2 anonymous read와 write의 비용이 다를 수 있다

새 private anonymous range는 0으로 보여야 한다. read fault는 shared read-only zero page를 매핑해 private frame allocation을 미룰 수 있고, write fault는 process가 변경할 수 있는 zeroed page를 할당·charge한다. 구현과 huge-page 정책에 따라 세부는 달라지지만 “VA 예약=즉시 RSS 증가”가 아닌 이유다.

5.3 minor는 cheap의 동의어가 아니다

minor fault는 storage I/O가 없다는 뜻이다. 큰 page zeroing, COW copy, page-table allocation, memcg charge, NUMA allocation, lock contention과 TLB invalidation은 여전히 CPU time과 tail latency를 만든다. 수백만 minor fault/s가 startup이나 request hot path에 몰리면 실제 장애가 된다.

5.4 major는 file read 한 번과 1:1이 아니다

file-backed page가 page cache에 없으면 fault path가 I/O를 시작하고 task가 기다릴 수 있다. readahead가 주변 page도 가져오므로 다음 access는 minor가 될 수 있고, 여러 task가 같은 page를 기다리면 한 I/O에 합쳐질 수 있다. raw major count만으로 bytes나 storage operation 수를 계산하면 안 된다.

5.5 fork는 data page보다 metadata를 먼저 복사한다

Linux fork()는 child의 task/mm context와 page tables를 만들고 writable private mapping을 COW 공유 상태로 바꾼다. data page 전체 복사를 피하지만 page-table 복사, rmap/refcount, write-protection과 TLB work는 즉시 발생한다. 매우 큰 address space에서는 “아직 write 안 했으니 fork는 공짜”가 아니다.

5.6 COW의 copy는 최적화될 수 있다

fault 시점에 old page를 실제로 공유하는 mapping이 더는 없다면 kernel이 새 page 복사 없이 old page를 writable로 돌릴 수 있다. 반대로 shared라면 새 page/folio를 allocate하고 content를 copy한 뒤 writer PTE만 바꾼다. 그래서 “COW fault=항상 memcpy 한 page”도 정확한 설명은 아니다.

5.7 MAP_PRIVATE와 MAP_SHARED의 write 의미가 다르다

MAP_PRIVATE file mapping은 write가 process-private COW page를 만들며 변경이 underlying file에 기록되지 않는다. MAP_SHARED write는 다른 mapper와 file에 보이는 shared state를 바꾸며 page cache·dirty/writeback 경로로 연결된다. “mmap은 전부 COW”가 아니다.

5.8 mmap 성공은 future touch의 물리 자원 보장이 아니다

Linux overcommit mode 0/1에서는 큰 writable anonymous mapping이 성공해도 나중 first-write에서 memory가 부족할 수 있다. mode 2는 commit limit을 엄격히 검사하지만 stack growth 등 corner case가 남는다. 운영에서는 CommitLimit, Committed_AS, cgroup limit, swap, reclaim을 함께 본다.

5.9 page fault 중 allocation도 실패할 수 있다

anonymous/COW fault가 새 page를 요구할 때 kernel은 memory cgroup charge, reclaim, compaction을 시도할 수 있다. 만족하지 못하면 fault 결과가 OOM 경로로 이어져 current task 또는 다른 victim이 종료될 수 있다. application 관점에서 “malloc은 성공했는데 write하다 죽음”이 가능한 이유다.

5.10 THP는 fault와 COW의 granularity를 바꾼다

Transparent Huge Page는 fault 횟수와 TLB pressure를 줄일 수 있지만 한 번의 allocation·zero·copy가 커지고 작은 write에도 split/copy 판단이 필요할 수 있다. 일부 workload는 first-touch 또는 fork-after-large-heap p99가 나빠진다. page size별 latency와 RSS를 실제 workload로 비교해야 한다.

5.11 faulting instruction은 완료된 것이 아니다

recoverable fault에서 kernel이 PTE와 TLB 상태를 고친 뒤 user mode로 돌아오면 CPU는 같은 instruction을 다시 실행한다. 그래서 instruction은 application 관점에서 한 번의 load/store처럼 보인다. handler는 side effect가 중복되지 않도록 architecture가 정한 precise exception semantics에 의존한다.

7. 실무 best practice

  • SLO-sensitive first touch를 분리: startup warm-up이나 controlled pre-touch를 검토하되 peak RSS와 startup time을 함께 budget한다.
  • fault rate와 latency 동시 관찰: process minflt/majflt, wall latency, CPU, storage I/O, PSI, reclaim과 cgroup memory.events를 같은 timeline에 둔다.
  • fork 전 heap 크기와 write rate 확인: snapshot/checkpoint worker가 큰 writable heap을 공유한 채 오래 살면 COW RSS와 p99가 폭증할 수 있다.
  • headroom 계산: steady RSS뿐 아니라 COW burst, allocator metadata, page tables, page cache와 kernel memory까지 memory limit 안에 포함한다.
  • file mapping lifetime 계약: mapper가 살아 있는 동안 backing file을 truncate/replace하는 주체와 protocol을 명확히 한다. atomic rename은 열린 old inode를 자동 truncate하지 않는다.
  • madvise는 semantic review 후: MADV_DONTFORK는 child가 해당 range를 정말 사용하지 않을 때만, MADV_WIPEONFORK는 secret/lifecycle 요구와 함께 쓴다.
  • THP는 canary: fault latency, COW, RSS, compaction, NUMA를 baseline과 비교하고 명확한 rollback을 둔다.
  • overcommit 설정을 app이 바꾸지 않기: host policy는 fleet 전체에 영향이 있으므로 관찰하고 deployment memory contract로 흡수한다.

9. 놓치기 쉬운 함정

  • page fault=bug: demand paging과 COW의 정상 제어 경로일 수 있다.
  • minor=무료: zero/copy/allocation/lock/TLB 비용이 있어 hot path를 망칠 수 있다.
  • major=page가 RAM에 없음: 정의의 핵심은 처리에 I/O가 필요했는지이며 cache/readahead 상태가 관여한다.
  • fork가 process memory를 즉시 전부 복사: data page는 COW지만 page tables와 process metadata 비용은 즉시 든다.
  • COW는 child만 부담: parent든 child든 먼저 write한 mapping이 fault를 일으킨다.
  • COW fault는 항상 memcpy: page가 exclusive면 writable 복구만 할 수 있다.
  • mmap 성공=memory guarantee: overcommit과 cgroup limit 때문에 future first touch에서 OOM이 날 수 있다.
  • file mapping은 file size 변화에 안전: mapping 뒤 truncate된 범위를 access하면 SIGBUS가 날 수 있다.
  • MAP_SHARED도 private COW: shared write는 공유 page/cache와 file visibility 계약을 가진다.

10. 30분 실습: first-touch와 fork COW를 계수로 확인

Linux/macOS의 C11 환경에서 anonymous 32MiB를 예약하고 page마다 첫 write를 수행한 뒤, fork child가 모든 page를 다시 write하며 발생한 minor fault를 측정한다. exact count는 kernel·THP·page size에 따라 달라지므로 양수와 memory isolation이라는 불변식만 검증한다.

set -eu
lab_dir="$(mktemp -d)"
trap 'rm -rf "$lab_dir"' EXIT

cat > "$lab_dir/fault_lab.c" <<'C'
#define _GNU_SOURCE
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

#ifndef MAP_ANONYMOUS
#define MAP_ANONYMOUS MAP_ANON
#endif

typedef struct {
  long cow_minflt;
  unsigned char child_value;
} report_t;

static long minflt(void) {
  struct rusage r;
  if (getrusage(RUSAGE_SELF, &r) != 0) { perror("getrusage"); exit(2); }
  return r.ru_minflt;
}

static void full_write(int fd, const void *buf, size_t n) {
  const unsigned char *p = buf;
  while (n) {
    ssize_t k = write(fd, p, n);
    if (k < 0) { perror("write"); _Exit(3); }
    p += (size_t)k; n -= (size_t)k;
  }
}

int main(void) {
  long ps = sysconf(_SC_PAGESIZE);
  if (ps <= 0) return 4;
  size_t bytes = 32u * 1024u * 1024u;
  size_t pages = bytes / (size_t)ps;
  unsigned char *p = mmap(NULL, bytes, PROT_READ | PROT_WRITE,
                          MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
  if (p == MAP_FAILED) { perror("mmap"); return 5; }

  long before = minflt();
  for (size_t i = 0; i < pages; i++) p[i * (size_t)ps] = 1;
  long first_touch = minflt() - before;
  if (first_touch <= 0) return 6;

  int fd[2];
  if (pipe(fd) != 0) { perror("pipe"); return 7; }
  pid_t child = fork();
  if (child < 0) { perror("fork"); return 8; }
  if (child == 0) {
    close(fd[0]);
    long c0 = minflt();
    for (size_t i = 0; i < pages; i++) p[i * (size_t)ps] = 2;
    report_t report = { minflt() - c0, p[0] };
    full_write(fd[1], &report, sizeof(report));
    _Exit(report.cow_minflt > 0 && report.child_value == 2 ? 0 : 9);
  }

  close(fd[1]);
  report_t report;
  ssize_t got = read(fd[0], &report, sizeof(report));
  int status = 0;
  if (waitpid(child, &status, 0) != child) return 10;
  int child_ok = got == (ssize_t)sizeof(report) &&
                 WIFEXITED(status) && WEXITSTATUS(status) == 0;
  int parent_isolated = p[0] == 1;

  printf("page_size=%ld pages=%zu\n", ps, pages);
  printf("first_touch_minflt_delta=%ld positive=%d\n",
         first_touch, first_touch > 0);
  printf("child_cow_minflt_delta=%ld positive=%d\n",
         report.cow_minflt, report.cow_minflt > 0);
  printf("child_value=%u parent_value=%u isolated=%d child_ok=%d\n",
         report.child_value, p[0], parent_isolated, child_ok);

  if (munmap(p, bytes) != 0) { perror("munmap"); return 11; }
  return child_ok && parent_isolated && first_touch > 0 ? 0 : 12;
}
C

"$lab_dir/fault_lab"

기대 형태

page_size=4096 pages=8192
first_touch_minflt_delta=<환경별 양수> positive=1
child_cow_minflt_delta=<환경별 양수> positive=1
child_value=2 parent_value=1 isolated=1 child_ok=1
  1. 0~10분: mmap 직후가 아니라 page별 first write에서 minor fault가 늘어나는 이유를 VMA/PTE/frame으로 설명한다.
  2. 10~20분: fork 직후 shared page와 read-only COW PTE를 그리고 child write가 page마다 private copy를 만드는 경로를 표시한다.
  3. 20~30분: 32MiB를 256MiB로 바꿀 때 latency·temporary RSS·fault 수가 어떻게 변할지 예측한 뒤 memory limit 안에서만 실행한다.

안전 장치: 32MiB만 사용하고 child를 반드시 wait하며 임시 directory만 정리한다. 정확한 fault 수를 assertion하지 않아 THP·prefault·kernel 차이를 허용한다. production host에서 cold-cache를 만들려고 system cache를 drop하지 않는다.

11. Linux 관찰 명령: 설정을 바꾸지 않는 증거 수집

counter는 누적값이므로 interval delta/rate로 비교한다. min_flt와 maj_flt가 증가한 code path를 알기 위해 workload phase, latency trace, file I/O를 함께 기록한다.

12. 실패 시나리오: fork checkpoint가 memory limit을 터뜨림

8GiB writable heap을 가진 service가 checkpoint를 위해 child를 fork했다. “COW라 추가 memory는 거의 없다”고 예상했지만 child가 snapshot을 쓰는 동안 parent의 request thread가 heap을 빠르게 갱신했다. 수많은 COW fault가 private page를 만들고 THP split/copy와 memory charge가 겹쳐 cgroup memory.max에 도달했다. major fault는 적었지만 minor fault, RSS, memory PSI, p99가 급증한 뒤 OOM kill이 발생했다.

진단: fork 시점, child lifetime, parent write rate, minflt delta, private dirty/RSS, memory.events의 oom/oom_kill을 맞춘다. 대응: checkpoint concurrency를 제한하고 headroom을 확보하며 child lifetime을 줄인다. 재설계: incremental snapshot, application-level immutable data, 별도 process architecture를 검토한다.

13. 대기업 면접 질문 3개

  1. “page fault는 항상 disk I/O나 오류를 의미하나요?”
    답변 포인트: 아니다. present/permission으로 access를 완료하지 못한 CPU exception이다. anonymous demand-zero, page-cache hit, COW는 I/O 없는 minor fault로 정상 복구된다. I/O가 필요하면 major, VMA 없음/권한 위반은 SIGSEGV, backing 오류는 SIGBUS가 될 수 있다.
  2. “fork의 COW가 실제로 어떻게 동작하나요?”
    답변 포인트: child page tables/metadata는 만들되 private writable data page를 공유하고 양쪽 PTE를 write-protect한다. writer의 permission fault에서 VMA write 계약을 확인해 exclusive page는 재사용하거나 shared page는 allocate+copy하고 PTE/TLB를 갱신해 instruction을 retry한다.
  3. “mmap/malloc이 성공했는데 나중에 OOM으로 죽을 수 있나요?”
    답변 포인트: overcommit에서는 reservation과 physical commit이 분리된다. first write/COW fault에서 allocation·memcg charge·reclaim이 실패하면 OOM 경로가 가능하다. CommitLimit/Committed_AS, cgroup limit, swap, COW burst와 SLO headroom으로 운영 계약을 잡는다.

14. 퀴즈·누적 리뷰

  1. VMA는 writable인데 PTE는 read-only일 수 있는가? 가능하다. COW를 위한 write protection이며 write fault에서 kernel이 복구한다.
  2. COW fault는 minor인가? 보통 I/O 없이 처리되므로 minor지만 allocation/copy 비용은 작지 않을 수 있다.
  3. MAP_PRIVATE file write가 file을 바꾸는가? 아니다. writer의 private COW page를 만든다.
  4. major fault 수로 storage read 횟수를 알 수 있는가? 1:1로 알 수 없다. readahead, shared wait, page cache가 관여한다.
  5. Day 23 연결: recoverable fault 뒤 무엇이 필요한가? PTE를 설치/갱신하고 stale TLB를 처리한 뒤 faulting instruction을 retry한다.
  6. Day 22 연결: mmap 성공 직후 VMA·PTE·frame 중 확실히 생긴 것은? VMA 계약이며 leaf PTE/private frame은 first touch까지 지연될 수 있다.
