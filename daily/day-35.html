2. mental model: 응급실 triage

체온이 높다는 숫자 하나로 병명을 정하지 않듯 RSS 하나로 leak을 확정하지 않는다. 먼저 생명 징후인 사용자 SLO와 OOM을 안정화하고, 환자인 host·container·process를 특정한다. 그다음 혈액검사처럼 mapping 구성, allocator live bytes, PSI, reclaim/refault, buddy order, NUMA·TLB 증거를 모은다. 치료는 한 번에 하나, 되돌릴 수 있게 적용하고 p99·error rate·pressure가 함께 회복되는지 확인한다.

5. 10분 triage: 먼저 지켜야 할 불변식

  1. 영향: p50만 보지 말고 p99, timeout, error rate, throughput, restart 수를 같은 시간축에 둔다.
  2. 안전: 무제한 retry와 restart storm을 막고 admission·concurrency를 낮춰 증거를 보존할 시간을 번다.
  3. scope: host `MemAvailable`과 `/proc/pressure/memory`, cgroup `memory.current/max/events.local/pressure`, process `smaps_rollup`을 동시에 찍는다.

6. CS·kernel·hardware deep dive

6.1 사용량이 높아도 pressure가 아닐 수 있다

Linux는 남는 RAM을 page cache로 활용한다. reclaim 가능한 clean cache가 많고 stall이 없다면 높은 usage는 효율일 수 있다. 반대로 `memory.current`가 제한 아래여도 direct reclaim이 반복되면 request가 멈춘다. capacity는 byte, pressure는 경쟁, PSI는 그 결과인 stall 시간을 말한다.

6.2 RSS 합은 ownership 회계가 아니다

shared library와 shared memory page는 여러 process RSS에 각각 들어간다. `/proc/PID/smaps_rollup`의 PSS·Pss_Anon·Pss_File·Pss_Shmem으로 비례 소유량과 mapping 성격을 분리한다. `maps/smaps`는 읽는 동안 mapping이 변할 수 있으므로 snapshot 자체의 race도 기록한다.

6.3 leak, retention, cache는 시간축이 다르다

leak은 request가 끝나도 live reachable object가 회수되지 않아 baseline이 계속 상승한다. retention은 object는 free됐지만 arena·size class가 future reuse를 위해 page를 보유한다. bounded cache는 hit율을 위한 정책이며 limit·eviction 뒤 plateau가 있어야 한다. GC/trim 한 번 후 RSS만 떨어졌다고 root cause가 증명되지는 않는다.

6.4 reclaim은 allocation latency에 feedback을 만든다

free page가 low watermark 아래로 내려가면 `kswapd`가 비동기로 일하고, 더 부족하면 allocating task가 direct reclaim을 수행해 멈춘다. 회수한 page가 곧 refault되면 working set이 RAM보다 커졌다는 신호이며 I/O와 CPU를 소비해 처리량이 줄고 queue가 더 늘어나는 feedback loop가 된다.

6.5 swap 사용량과 thrashing은 같은 말이 아니다

차가운 anonymous page가 swap에 오래 머무는 것은 정상일 수 있다. thrashing은 hot page를 내보냈다가 빠르게 다시 읽는 반복이다. `pswpin/out`, major fault, workingset refault, memory PSI와 application latency의 delta를 함께 봐야 한다.

6.6 fragmentation은 세 layer를 구분한다

allocator internal fragmentation은 size-class 반올림, allocator external fragmentation은 arena free hole, physical fragmentation은 buddy higher-order block 부족이다. 일반 큰 `malloc`은 scattered frame을 연속 virtual address로 매핑할 수 있으므로 `/proc/buddyinfo` 악화가 곧 heap allocation 실패를 뜻하지 않는다.

6.7 THP는 TLB reach와 fault·compaction 비용을 교환한다

큰 translation은 TLB miss를 줄이지만 huge page 준비·zeroing·collapse·split·compaction이 tail latency와 footprint를 늘릴 수 있다. THP success rate가 아니라 p99, dTLB miss, `thp_*`와 compaction delta, RSS·headroom을 canary 전후 비교한다.

6.8 locality 문제는 byte graph만으로 보이지 않는다

RSS가 일정해도 thread가 remote NUMA node의 page를 읽거나 cache line ownership이 core 사이를 왕복하거나 TLB reach를 넘으면 latency가 커진다. CPU affinity만 고정하면 page가 이동하지 않으므로 first touch, memory policy, process의 `numa_maps`, PMU를 함께 확인한다.

6.9 OOM은 global과 memcg의 failure domain이 다르다

host에 여유가 있어도 cgroup이 `memory.max`를 넘고 reclaim에 실패하면 그 cgroup 안에서 OOM이 발생할 수 있다. `memory.events.local`의 `high`, `max`, `oom`, `oom_kill`, `oom_group_kill` delta와 kernel log, exit code를 함께 보존한다. `memory.high`는 hard kill보다 먼저 reclaim pressure를 거는 throttle boundary다.

6.10 correlation은 인과가 아니다

배포 시점에 RSS와 p99가 같이 올라도 code leak, traffic mix, GC phase, NUMA placement, storage slowdown 중 무엇이 원인인지 모른다. 한 번에 하나의 변수만 바꾸고 예상되는 중간 signal과 반증 조건을 미리 써야 한다.

8. 실무 best practice

  • service의 정상 phase별 baseline을 둔다. startup warmup, batch peak, steady state를 한 선으로 비교하지 않는다.
  • application trace, deploy, GC/allocator, cgroup, `/proc`, kernel log를 monotonic 또는 동기화된 timestamp로 묶는다.
  • `memory.high`를 pre-OOM pressure valve, `memory.max`를 최후 guardrail로 설계하고 `memory.events.local`과 per-cgroup PSI를 alert에 연결한다.
  • latency service에는 PSI threshold 기반 admission·load shedding과 hysteresis를 두어 oscillation을 막는다.
  • limit은 average가 아니라 peak working set, page cache·kernel charge, restart overlap, node failure headroom을 포함해 정한다.
  • OOM log, cgroup event, process exit, core/heap profile을 restart 전에 보존하되 민감 data와 profile overhead를 통제한다.
  • allocator·THP·NUMA·swappiness 변경은 canary 한 개, 명시적 success metric, 자동 rollback으로 검증한다.
  • restart는 memory를 비우는 완화일 뿐 원인 수정이 아니다. exponential backoff와 traffic drain으로 restart storm을 막는다.
  • counter 이름·단위·가용성은 kernel·libc·container runtime 버전별로 다르므로 수집기 시작 시 schema를 기록한다.

9. error handling runbook

  1. stabilize: timeout budget을 지키며 admission/concurrency를 낮추고 retry amplification을 차단한다. OOM loop면 traffic을 healthy replica로 drain한다.
  2. preserve: OOM kernel log, `memory.events.local`, PSI, vmstat·meminfo·smaps snapshot, deploy/traffic marker를 삭제·restart 전에 저장한다.
  3. scope: host global인지 cgroup limit인지, 한 process인지 fleet인지, 한 NUMA node/zone인지 구분한다.
  4. classify: usage composition과 delta를 근거로 leak·retention·cache·reclaim/thrashing·fragmentation·locality·OOM 중 하나를 1순위로 둔다.
  5. disprove: 후보가 맞다면 함께 변해야 할 signal 하나와 틀렸음을 보일 signal 하나를 정한다.
  6. mitigate: traffic 축소, cache cap, worker 수 감소, smaller-page fallback, rollout rollback 등 가역 조치 하나만 적용한다.
  7. verify: p99/error/throughput과 PSI·refault·OOM event가 정상 baseline으로 돌아오는지 충분한 workload cycle 동안 본다.
  8. prevent: capacity model·guardrail·alert·failure test를 고치고 owner와 rollback 조건을 incident record에 남긴다.

10. 놓치기 쉬운 함정

  • `MemFree`가 낮으면 장애: `MemAvailable`, reclaimability, PSI와 SLO를 먼저 본다.
  • RSS 증가 = leak: PSS mapping 구성, live object, allocator retention, cache bound를 분리한다.
  • swap 사용 = thrashing: swap-in/refault rate와 stall이 동반되는지 확인한다.
  • OOM = host RAM 0: memcg `memory.max`, ancestor limit, nodemask·cpuset scope도 가능하다.
  • 누적 counter 값이 크면 지금 장애: 두 snapshot delta를 workload rate와 함께 비교한다.
  • 평균 latency가 정상: direct reclaim·compaction은 일부 request의 p99/p999만 악화시킬 수 있다.
  • `malloc` 성공 = physical memory 보장: overcommit 환경에서는 first touch에서 allocation/OOM이 발생할 수 있다.
  • `drop_caches`, `compact_memory`, `swapoff`가 진단: production 전역 상태와 latency를 크게 바꾸므로 승인된 실험 없이 실행하지 않는다.
  • CPU가 높으면 compute: kswapd, compaction, page fault, GC가 원인일 수 있다.
  • 한 번에 여러 sysctl 변경: 인과와 rollback을 잃는다.

11. 30분 실습: evidence classifier

네 synthetic incident snapshot의 delta를 분류한다. 이 threshold는 교육용 heuristic이며 production universal rule이 아니다. 실제 alert는 자신의 baseline과 SLO로 calibration한다.

python3 - <<'PY'
def classify(s):
    if s["oom_kill_delta"] > 0:
        return "memcg_oom"
    if s["live_mb_delta"] > 128 and s["rss_mb_delta"] > 128:
        return "leak_or_unbounded_cache"
    if (s["psi_full_pct"] > 5 and s["refault_s"] > 1000
            and s["swapin_s"] > 100):
        return "thrashing"
    if (s["available_mb"] > 1024 and s["high_order_blocks"] == 0
            and s["compact_fail_delta"] > 0):
        return "physical_fragmentation"
    if s["rss_mb_delta"] > 128 and s["live_mb_delta"] <= 0:
        return "allocator_retention_candidate"
    return "insufficient_evidence"

base = dict(oom_kill_delta=0, live_mb_delta=0, rss_mb_delta=0,
            psi_full_pct=0, refault_s=0, swapin_s=0,
            available_mb=4096, high_order_blocks=8, compact_fail_delta=0)
cases = {
 "growth": dict(base, live_mb_delta=512, rss_mb_delta=600),
 "reclaim_loop": dict(base, psi_full_pct=12, refault_s=9000, swapin_s=800),
 "fragmented": dict(base, high_order_blocks=0, compact_fail_delta=37),
 "limited": dict(base, oom_kill_delta=1, available_mb=12000),
 "retained": dict(base, live_mb_delta=-5, rss_mb_delta=350),
}
expected = {
 "growth":"leak_or_unbounded_cache", "reclaim_loop":"thrashing",
 "fragmented":"physical_fragmentation", "limited":"memcg_oom",
 "retained":"allocator_retention_candidate",
}
for name, sample in cases.items():
    result = classify(sample)
    print(f"{name:12s} -> {result}")
    assert result == expected[name]
PY
  1. 0~10분: 각 branch가 요구하는 evidence와 오판 가능성을 표에 쓴다.
  2. 10~20분: threshold 경계값을 바꾸어 `insufficient_evidence`가 왜 필요한지 확인한다.
  3. 20~30분: 자신의 service 지표 이름으로 mapping하고, 자동 조치가 아니라 사람에게 보여 줄 evidence bundle을 설계한다.

13. 실패 시나리오: RSS leak으로 오판한 reclaim loop

배포 뒤 service RSS가 20% 늘고 p99가 8배 상승했다. 즉시 leak으로 보고 restart했지만 10분마다 재발했다. heap profile의 live bytes는 안정적이었고 Pss_File이 늘어났으며, cgroup `memory.high` event·memory PSI full·workingset refault·swap-in이 동시에 증가했다. 원인은 새 query가 큰 file working set을 순환해 cgroup 안에서 hot page를 반복 회수한 것이었다. query concurrency를 낮춰 loop를 끊고, cache/workload budget과 `memory.high` headroom을 조정한 canary에서 p99·PSI·refault가 함께 회복되는 것을 확인했다. restart는 잠시 cache를 비웠을 뿐 root cause를 고치지 못했다.
