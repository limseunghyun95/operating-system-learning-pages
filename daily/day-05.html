context switch와 저장·복원되는 상태

한 줄 요약 — context switch는 CPU가 실행할 task를 바꾸며 register·kernel stack·memory context를 전환하는 과정이고, cache·TLB·branch predictor는 논리적으로 저장하는 대상이 아니라 성능에 간접 비용을 남기는 microarchitecture 상태다.

1. 선수 용어 사전

context중단한 실행을 나중에 이어가기 위해 필요한 CPU·kernel 상태의 묶음.
taskLinux scheduler가 CPU에 배치하는 단위. process의 main thread와 각 thread가 모두 task다.
run queue특정 CPU에서 실행 가능하며 차례를 기다리는 task를 scheduler가 관리하는 자료구조.
preemption실행 중 task가 스스로 block하지 않았어도 scheduler가 CPU를 회수하는 것.
pt_regssystem call·interrupt·exception 진입 때 user register 상태를 표현하는 architecture별 kernel 구조.
switch_to선택된 next task의 architecture-specific CPU 상태와 stack으로 실제 전환하는 kernel 경계.
TLB / PCID·ASIDTLB는 address translation cache다. PCID/ASID는 서로 다른 address space의 entry를 tag해 불필요한 flush를 줄인다.
CPU migrationtask가 이전과 다른 logical CPU에서 다음 실행을 이어가는 것. context switch와 관련 있지만 같은 사건은 아니다.
FPU/SIMD statefloating point·vector register와 제어 상태. x86에서는 XSAVE 계열 형식으로 관리되는 확장 상태를 포함한다.

2. mental model: 책갈피를 꽂고 다른 실행 흐름을 펼친다

CPU core 하나는 한 순간에 하나의 instruction stream을 실행한다. task A를 멈추고 B를 실행하려면 A가 다시 돌아올 위치와 stack 등 architectural state를 보존하고 B의 state를 복원해야 한다.

하지만 모든 hardware 내부 상태를 파일처럼 저장하는 것은 아니다. cache line, TLB entry, branch predictor history는 남거나 밀려나며, 이 “따뜻함의 손실”이 직접 switch 코드보다 더 큰 간접 비용이 될 수 있다.

3. architecture: A에서 B로 전환되는 경계

User task A
  │ system call / exception / interrupt
  ▼
entry code: user registers → A의 kernel stack(pt_regs)
  │ block, need_resched, preemption point
  ▼
__schedule()
  ├─ A runtime accounting + state 갱신
  ├─ CPU run queue에서 next task B 선택
  └─ context_switch(A, B)
       ├─ address space가 다르면 mm/page-table context 전환
       ├─ switch_to(A, B)
       │    A의 kernel SP·callee-saved register 저장
       │    B의 kernel SP·register·TLS/FPU 등 복원
       └─ CPU-local current = B, B의 kernel stack 사용
  ▼
B가 과거 schedule 지점에서 재개
  │ 필요하면 return-to-user 경로
  ▼
User task B의 instruction pointer부터 실행

중요: scheduler에 들어갔다고 항상 다른 task로 바뀌는 것은 아니다. 다시 같은 task가 선택될 수 있다. 또한 interrupt·system call로 user→kernel mode가 바뀌어도 current task가 그대로면 task context switch가 아니다.

4. 비슷해 보이지만 다른 사건

mode switchuser↔kernel privilege level 전환. syscall 뒤 같은 task로 돌아오면 context switch는 없을 수 있다.
task context switchCPU의 current가 task A에서 B로 바뀐다. 같은 process의 thread 사이에서도 발생한다.
CPU migrationtask가 다른 CPU에서 재개한다. switch는 같은 CPU에서도 일어나므로 migration과 1:1이 아니다.
VM context switchhost↔guest 또는 vCPU 전환은 추가 virtualization state를 다루며 일반 task switch와 비용 구조가 다르다.

5. CS/kernel/hardware deep dive

5.1 register가 한 번에 한 구조체에 모두 저장되는 것은 아니다

x86-64를 예로 들면 user→kernel 진입에서 user-visible register 상태는 task의 kernel stack에 pt_regs 형태로 구성된다. 실제 switch_to 경로는 inactive task frame에 stack pointer와 ABI상 보존해야 할 register를 저장하고 next task의 stack으로 바꾼다. 다음에 A가 선택되면 과거 schedule() 호출이 반환되는 것처럼 이어진다.

즉 “PCB 전체를 CPU에 복사한다”가 아니라, 진입 경로·compiler ABI·architecture switch code가 나눠서 필요한 state를 보존한다. 정확한 register 목록은 architecture와 kernel 구현에 따라 달라진다.

5.2 address-space switch와 TLB

서로 다른 process로 전환하면 next의 mm_struct와 page-table root를 활성화해야 한다. 단순히 CR3를 바꾸고 TLB를 전부 비우는 모델만 외우면 부정확하다. 현대 x86 Linux는 PCID/ASID와 TLB generation을 이용해 유효한 translation을 재사용하고 필요한 경우에만 flush한다.

같은 address space를 공유하는 thread 사이 전환은 보통 page-table context가 같지만 register·kernel stack·TLS·scheduler state 전환은 여전히 필요하다. 따라서 “thread switch는 공짜”도 틀리다.

5.3 architecture-specific extra state

현재 x86-64 Linux의 __switch_to()는 FPU state, FS/GS base, TLS, segment, PKRU, CPU-local current task와 kernel stack top 등 architecture state를 다룬다. 다음 user→kernel 진입이 올바른 task stack을 쓰도록 privilege transition 정보도 맞춘다.

FPU/SIMD 확장 상태는 크고 CPU 기능마다 달라 비용이 고정되지 않는다. kernel은 사용 상태와 hardware 지원을 고려해 관리한다. “매 switch마다 모든 vector byte를 무조건 memcpy한다”처럼 단정하지 않는다.

5.4 무엇을 저장하지 않는가

L1/L2/L3 cache, TLB 전체, branch predictor를 task_struct에 직렬화하지 않는다. switch 뒤에도 일부는 남고 다른 task의 working set에 의해 교체된다. 보안 mitigation이나 address-space 변경이 선택적 flush를 유발할 수 있지만 일반적인 “모두 저장 후 모두 복원”은 아니다.

그래서 context switch 비용은 직접 비용(scheduler, register/mm 전환)과 간접 비용(cache/TLB locality, predictor warm-up, migration)을 함께 측정해야 한다.

5.5 voluntary와 nonvoluntary

task가 I/O, futex, timer 등 unavailable resource를 기다리며 block하면 voluntary switch로 집계된다. time slice 소진, higher-priority task wakeup 등으로 CPU를 빼앗기면 nonvoluntary switch다. 두 수치는 원인을 완전히 증명하지는 않지만 “대기 중심인지 CPU 경쟁 중심인지”를 좁히는 첫 단서다.

6. 실무 best practice

  1. 총량보다 rate와 SLO를 본다. lifetime 누적 counter의 시간당 delta를 p95/p99 latency, CPU utilization, run queue, off-CPU time과 함께 본다.
  2. voluntary/nonvoluntary를 분리한다. 전자는 I/O·lock·sleep, 후자는 oversubscription·CPU contention 가설을 먼저 세우되 trace로 검증한다.
  3. thread 수를 core 수 공식 하나로 결정하지 않는다. CPU-bound와 blocking 비율, cgroup CPU quota, latency target을 부하 실험으로 맞춘다.
  4. 작은 작업을 batch한다. 지나치게 짧은 task, 잦은 lock handoff, 1ms sleep polling은 useful work 대비 scheduling 비율을 키운다.
  5. affinity는 측정 후 적용한다. cache locality를 높일 수 있지만 load imbalance·NUMA 원격 접근·장애 시 capacity 손실을 만들 수 있다.
  6. 원인 규명에는 sched_switch와 sched_wakeup을 연결한다. switch 횟수만이 아니라 runnable→running까지의 wakeup latency와 off-CPU stack을 본다.

7. error handling과 관측 실패 대응

/proc PID 없음읽는 사이 task가 종료된 정상 race일 수 있다. PID와 시작 시간을 다시 확인하고 sample을 폐기한다.
pidstat 없음sysstat package 도구다. 설치 권한이 없으면 /proc/PID/status를 일정 간격으로 읽어 delta를 계산한다.
perf 권한 거부perf_event_paranoid, capability, container policy를 확인한다. 운영 host에 광범위한 권한을 상시 부여하지 말고 승인된 관측 경로를 사용한다.
tracefs 접근 실패tracefs mount·권한·kernel config를 확인한다. production에서는 bounded duration과 PID/cgroup filter로 trace 양을 제한한다.
taskset EINVALcontainer cpuset에서 허용되지 않은 CPU일 수 있다. /proc/self/status의 Cpus_allowed_list에서 대상 CPU를 고른다.

8. 놓치기 쉬운 함정

  • system call 횟수와 context switch 횟수는 같지 않다. syscall이 block하지 않으면 같은 task로 바로 돌아올 수 있다.
  • scheduler 진입과 실제 switch도 1:1이 아니다. next로 현재 task가 다시 선택될 수 있다.
  • 높은 context-switch rate 자체는 장애가 아니다. 높은 처리량의 event-driven service에서도 정상일 수 있다.
  • 반대로 rate가 낮아도 한 번의 migration 뒤 cache miss가 latency에 크게 영향을 줄 수 있다.
  • process switch만 세면 안 된다. thread가 scheduler의 task 단위이므로 thread 간 전환도 포함된다.
  • “context switch는 N ns”라는 고정값을 외우지 않는다. CPU, kernel, mitigation, working set, mm 공유, migration에 따라 달라진다.

9. 30분 실습: sleep task와 CPU 경쟁 task 비교

Linux 전용이다. 1ms sleep을 반복하는 task는 voluntary switch가, 같은 CPU를 두고 경쟁하는 두 busy-loop task는 nonvoluntary switch가 증가하는지 관찰한다.

LAB_DIR=$(mktemp -d)
CPU=$(sed -n 's/^Cpus_allowed_list:[[:space:]]*//p' /proc/self/status |
      sed 's/[-,].*//')

python3 -c 'import time; [time.sleep(.001) for _ in range(30000)]' &
SLEEPER=$!
taskset -c "$CPU" python3 -c 'while True: pass' &
HOG1=$!
taskset -c "$CPU" python3 -c 'while True: pass' &
HOG2=$!
trap 'kill "$SLEEPER" "$HOG1" "$HOG2" 2>/dev/null; wait 2>/dev/null' EXIT

snapshot() {
  pid="$1"
  printf 'PID=%s\n' "$pid"
  sed -n '/^voluntary_ctxt_switches:/p;
          /^nonvoluntary_ctxt_switches:/p' "/proc/$pid/status"
}

sleep 1
snapshot "$SLEEPER"
snapshot "$HOG1"
snapshot "$HOG2"
sleep 5
snapshot "$SLEEPER"
snapshot "$HOG1"
snapshot "$HOG2"

command -v pidstat >/dev/null &&
  pidstat -w -p "$SLEEPER,$HOG1,$HOG2" 1 3
command -v perf >/dev/null &&
  perf stat -e context-switches,cpu-migrations -p "$HOG1" sleep 3

예상: SLEEPER는 resource를 기다리며 voluntary counter가 빠르게 증가한다. 같은 허용 CPU에 고정된 HOG1/HOG2는 scheduler가 번갈아 CPU를 주어 nonvoluntary counter가 증가한다. 실제 수치는 kernel·scheduler·quota에 따라 달라진다.

실패 주입: HOG를 2개→8개로 늘리고 nvcswch/s, run queue, 처리량 변화를 함께 기록한다. 숫자만 올랐다는 이유로 개선/악화를 결론 내리지 않는다.

10. 실패 시나리오

상황: cgroup CPU quota가 4 core인 service에 worker thread를 400개 두었다. CPU 평균은 65%인데 p99가 급등하고 context switch와 migrations가 폭증했다.

진단: voluntary switch가 많으면 lock/queue/I/O 대기 stack을, nonvoluntary와 run queue가 높으면 oversubscription·quota throttling을 본다. sched_wakeup→sched_switch 지연과 off-CPU profile로 가설을 검증한다.

개선: bounded worker pool, request batching, blocking 구간 분리, queue backpressure를 적용하고 부하 실험에서 throughput과 p99를 함께 비교한다. 무작정 affinity나 realtime priority를 적용하지 않는다.

11. 대기업 면접 질문 3개

Q1. context switch 때 무엇을 저장하고 무엇을 저장하지 않나요?
답변 포인트: register/IP/SP, kernel stack, task·scheduler state, 필요 시 mm/TLS/FPU를 말한다. cache/TLB/predictor는 PCB에 저장하지 않으며 tag·선택적 flush·warm-up이라는 간접 비용을 설명한다.

Q2. system call과 context switch는 어떻게 다른가요?
답변 포인트: syscall은 privilege mode 전환이고 current task가 유지될 수 있다. block 또는 preemption 뒤 scheduler가 다른 task를 고를 때 task context switch가 발생한다.

Q3. process switch가 thread switch보다 항상 비싼가요?
답변 포인트: 다른 mm이면 page-table/TLB context 비용이 추가될 가능성이 있지만 PCID/ASID가 줄일 수 있다. 같은 mm thread도 register/FPU/TLS와 cache working-set 비용이 있어 workload 측정 없이는 “항상”이라 단정하지 않는다.
