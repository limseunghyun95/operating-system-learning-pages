Operating System · Day 16 / 63 · Concurrency

mutex, semaphore, condition variable

한 줄 요약 — mutex는 한 소유자의 임계 구역, semaphore는 N개의 permit, condition variable은 mutex로 보호된 predicate가 참이 될 때까지의 대기를 표현한다. 정확한 선택은 API 이름이 아니라 보호할 invariant와 wakeup 뒤 재검사 계약에서 시작한다.

1. 초보자 용어 사전

synchronization여러 thread가 공유 상태를 안전한 순서로 관찰·변경하도록 만드는 규칙과 도구.
mutexmutual exclusion lock. 성공적으로 잠근 한 thread가 소유자가 되고 그 소유자가 해제한다. 임계 구역의 invariant와 memory visibility를 보호한다.
semaphore0 이상의 permit 개수를 관리하는 동기화 객체. wait는 하나를 얻어 감소시키고, post는 반환해 증가시킨다. mutex와 달리 소유자 개념이 없다.
condition variable공유 상태의 어떤 조건(predicate)이 참이 되기를 기다리는 rendezvous 지점. 상태 자체를 저장하지 않으며 반드시 mutex와 predicate를 함께 쓴다.
permitsemaphore가 표현하는 사용 가능 수량. 예: DB connection 20개라면 초기 permit 20.
predicatemutex 아래서 평가하는 참/거짓 상태식. 예: queue_size > 0 || closed.
critical section공유 invariant를 읽고 바꾸는 동안 다른 실행자가 동시에 들어오면 안 되는 코드 영역.
spurious wakeup기다리던 predicate가 참이라는 보장 없이 condition wait가 돌아올 수 있는 현상. 경쟁자가 먼저 상태를 소비한 경우까지 포함해 실무에서는 항상 재검사한다.
lost wakeup대기 시작과 상태 변경 사이의 틈 때문에 wake signal을 놓치고 영원히 자는 버그. 같은 mutex 아래 predicate 변경과 atomic unlock-and-wait로 막는다.
futexfast userspace mutex의 기반이 되는 Linux 저수준 인터페이스. 평상시 user-space atomic으로 해결하고 실제로 재워야 할 때 kernel에 wait/wake를 요청한다.
priority inversion높은 priority thread가 lock을 가진 낮은 priority thread 때문에 막히고, 중간 priority가 낮은 thread의 실행까지 빼앗는 역전 현상.

2. mental model: 열쇠, 입장권, 초인종

mutex = 한 명에게 귀속되는 열쇠. 장부 invariant를 수정하는 동안 소유자가 열쇠를 가진다. 다른 사람이 대신 unlock하면 계약 위반이다.

semaphore = 수량이 남는 입장권. 누가 반납하는지는 중요하지 않고 전체 수량이 중요하다. API 호출이 한 번 빠지거나 중복되면 실제 resource 수와 permit가 어긋난다.

condition variable = 기억하지 않는 초인종. 초인종 소리가 상태가 아니다. 문을 열고 “queue가 비지 않았는가?”라는 predicate를 다시 봐야 한다.

면접에서 가장 강한 답은 “binary semaphore와 mutex가 둘 다 0/1처럼 보인다”가 아니라 ownership, protected invariant, stored count, wait predicate가 서로 다른 추상화임을 설명하는 것이다.

6. CS·kernel·hardware deep dive

6.1 mutex는 exclusion과 happens-before를 함께 준다

성공한 lock은 acquire, unlock은 release 성격을 가져 이전 소유자의 critical-section write를 다음 소유자가 보게 한다. 따라서 mutex는 단지 동시에 한 명만 통과시키는 문이 아니라 memory-ordering 계약이다.

보호 단위는 변수 하나가 아니라 invariant다. head, tail, size가 함께 queue 상태를 구성한다면 동일 mutex 아래 함께 바뀌어야 한다.

6.2 semaphore는 ownership 없는 accounting이다

sem_wait는 count가 양수면 하나 감소하고 즉시 성공하며, 0이면 permit가 생길 때까지 막힌다. sem_post는 count를 늘리고 waiter를 깨울 수 있다. producer가 post하고 consumer가 wait하는 것이 정상이라 소유자 일치가 없다.

초기값 1인 binary semaphore도 mutual exclusion처럼 보이지만 owner validation, priority inheritance, robust-owner-death 같은 mutex semantics를 자동으로 갖지 않는다. resource pool과 bounded concurrency에는 semaphore, 구조체 invariant에는 보통 mutex가 명확하다.

6.3 condition variable의 원자적 unlock-and-wait

naive하게 “mutex unlock → sleep 등록”을 두 단계로 하면 그 사이 producer가 상태를 바꾸고 signal한 뒤 지나갈 수 있다. consumer는 이미 온 signal을 놓치고 영원히 잔다.

POSIX condition wait는 caller가 mutex를 가진 상태에서 mutex 해제와 대기 진입을 다른 mutex 사용자에 대해 원자적으로 보이게 하고, 반환 전 mutex를 다시 획득한다. producer도 같은 mutex 아래 predicate를 변경하면 상태 확인과 변경 사이의 gap이 닫힌다.

6.4 futex fast path와 compare-and-block

uncontended mutex는 cache line의 atomic compare-and-swap만으로 끝날 수 있어 syscall이 없다. 실패해 실제 sleep이 필요할 때 library가 futex word의 예상값과 함께 FUTEX_WAIT를 호출한다.

kernel은 값이 여전히 예상값일 때만 wait queue에 넣는다. load·compare·block이 같은 futex word의 동시 operation과 원자적으로 정렬되므로, 값이 이미 바뀌었다면 sleep하지 않고 재시도한다. 이 compare-and-block이 lost wake 방지의 저수준 연결 고리다.

6.5 contention은 cache와 scheduler 비용을 함께 만든다

짧은 경쟁은 lock cache line ownership의 core 간 이동과 atomic RMW 비용을 만든다. 긴 경쟁은 futex syscall, task enqueue/dequeue, context switch, cache working-set 손실까지 이어진다. 그래서 평균 lock hold time만 보고 충분하지 않다.

지표는 wait time p95/p99, hold time, contention ratio, waiter 수, timeout, CPU와 run-queue pressure를 함께 본다. lock을 잘게 쪼개면 parallelism은 늘지만 invariant와 deadlock graph가 복잡해지는 trade-off가 있다.

6.6 priority inversion, PI, robust mutex

deadline/real-time 경로는 priority inheritance(PI) mutex를 검토한다. 높은 priority waiter가 막히면 lock owner의 effective priority를 잠시 올려 critical section을 마치게 한다. 일반 mutex의 fairness나 깨우는 순서는 portable하게 가정하지 않는다.

robust mutex에서 owner가 죽으면 다음 locker가 EOWNERDEAD와 함께 mutex를 획득할 수 있다. 이는 성공이 아니라 “보호 상태가 불일치할 수 있으니 repair 후 pthread_mutex_consistent를 호출하라”는 복구 트랜잭션이다.

7. 실무 best practice

  1. primitive보다 invariant를 먼저 쓴다. 보호 상태, owner, permit 단위, predicate, 종료 조건을 코드 옆 문서와 assertion으로 남긴다.
  2. condition wait는 항상 while(predicate false). wait 반환값을 처리한 뒤에도 mutex를 가진 채 predicate를 다시 평가한다.
  3. predicate 변경은 같은 mutex 아래서 한다. signal 자체보다 state transition이 진짜 사건이다. 일관된 규칙은 lost wake와 memory visibility 논쟁을 줄인다.
  4. signal과 broadcast를 의도로 선택한다. item 하나면 보통 signal, global shutdown이나 여러 predicate가 모두 바뀌면 broadcast. broadcast의 thundering herd 비용을 측정한다.
  5. lock 안에서 blocking I/O와 외부 callback을 피한다. 필요한 snapshot만 복사하고 unlock한 뒤 호출한다. callback 재진입과 lock-order inversion을 차단한다.
  6. timeout은 하나의 absolute deadline으로 전파한다. 단계마다 새 timeout을 주면 총 대기 시간이 증폭된다. condition clock 설정과 wall-clock jump도 확인한다.
  7. semaphore permit를 resource lifecycle에 묶는다. acquire 성공 뒤 모든 return/error/cancel 경로에서 정확히 한 번 release하도록 scope guard/cleanup handler를 둔다.
  8. shutdown을 predicate에 포함한다. queue_nonempty || closed처럼 wait가 종료될 조건을 만들고 close 때 broadcast한 뒤 waiter가 빠진 것을 확인하고 destroy한다.

8. error handling 매트릭스

9. 놓치기 쉬운 함정

  • binary semaphore를 mutex처럼 쓰며 다른 thread가 unlock해도 된다고 착각한다.
  • condition variable에 event가 저장된다고 생각해 predicate 없이 wait/signal만 사용한다.
  • if로 wait해 spurious wake나 다른 consumer의 선점 뒤 invalid state를 소비한다.
  • predicate를 mutex 밖에서 바꾸거나 서로 다른 mutex로 같은 condition variable을 동시에 기다린다.
  • return code를 무시하고 timeout을 success처럼, owner death를 정상 lock처럼 처리한다.
  • 모든 waiter가 빠지기 전에 mutex, semaphore, condition variable을 destroy한다.
  • realtime clock과 monotonic clock을 혼동하거나 단계별 timeout을 더해 SLO를 초과한다.
  • broadcast로 정확성을 덮고 thundering herd와 lock convoy를 만든다.
  • 특정 wake 순서나 fairness를 API 계약 없이 믿는다. correctness는 어느 waiter가 먼저 깨도 유지되어야 한다.

10. 30분 실습: noisy wakeup에도 안전한 bounded queue

목표: capacity 4 queue에 1..1000을 생산·소비한다. 별도 noise thread가 의미 없이 두 condition을 broadcast해도 while predicate 덕분에 정확한 합계 500500을 유지하는지 확인한다.

LAB_DIR=$(mktemp -d)
trap 'rm -rf "$LAB_DIR"' EXIT
cat >"$LAB_DIR/lab.c" <<'C'
#define _POSIX_C_SOURCE 200809L
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

enum { CAP = 4, N = 1000 };
typedef struct {
  int buf[CAP], head, tail, size, closed;
  long produced, consumed, sum;
  pthread_mutex_t mu;
  pthread_cond_t not_empty, not_full;
} queue_t;

static queue_t q = {
  .mu = PTHREAD_MUTEX_INITIALIZER,
  .not_empty = PTHREAD_COND_INITIALIZER,
  .not_full = PTHREAD_COND_INITIALIZER
};

static void check(int rc, const char *what) {
  if (rc != 0) { fprintf(stderr, "%s: %d\n", what, rc); exit(2); }
}

static void *producer(void *unused) {
  (void)unused;
  for (int value = 1; value <= N; value++) {
    check(pthread_mutex_lock(&q.mu), "producer lock");
    while (q.size == CAP)
      check(pthread_cond_wait(&q.not_full, &q.mu), "wait not_full");
    q.buf[q.tail] = value;
    q.tail = (q.tail + 1) % CAP;
    q.size++;
    q.produced++;
    check(pthread_cond_signal(&q.not_empty), "signal not_empty");
    check(pthread_mutex_unlock(&q.mu), "producer unlock");
  }
  check(pthread_mutex_lock(&q.mu), "close lock");
  q.closed = 1;
  check(pthread_cond_broadcast(&q.not_empty), "close broadcast");
  check(pthread_mutex_unlock(&q.mu), "close unlock");
  return NULL;
}

static void *consumer(void *unused) {
  (void)unused;
  for (;;) {
    check(pthread_mutex_lock(&q.mu), "consumer lock");
    while (q.size == 0 && !q.closed)
      check(pthread_cond_wait(&q.not_empty, &q.mu), "wait not_empty");
    if (q.size == 0 && q.closed) {
      check(pthread_mutex_unlock(&q.mu), "final unlock");
      return NULL;
    }
    int value = q.buf[q.head];
    q.head = (q.head + 1) % CAP;
    q.size--;
    q.consumed++;
    q.sum += value;
    check(pthread_cond_signal(&q.not_full), "signal not_full");
    check(pthread_mutex_unlock(&q.mu), "consumer unlock");
  }
}

static void *noise(void *unused) {
  (void)unused;
  const struct timespec pause = { .tv_sec = 0, .tv_nsec = 100000 };
  for (int i = 0; i < 200; i++) {
    check(pthread_mutex_lock(&q.mu), "noise lock");
    check(pthread_cond_broadcast(&q.not_empty), "noise empty");
    check(pthread_cond_broadcast(&q.not_full), "noise full");
    check(pthread_mutex_unlock(&q.mu), "noise unlock");
    nanosleep(&pause, NULL);
  }
  return NULL;
}

int main(void) {
  pthread_t p, c, n;
  check(pthread_create(&p, NULL, producer, NULL), "create producer");
  check(pthread_create(&c, NULL, consumer, NULL), "create consumer");
  check(pthread_create(&n, NULL, noise, NULL), "create noise");
  check(pthread_join(p, NULL), "join producer");
  check(pthread_join(c, NULL), "join consumer");
  check(pthread_join(n, NULL), "join noise");
  printf("produced=%ld consumed=%ld sum=%ld\n",
         q.produced, q.consumed, q.sum);
  return !(q.produced == N && q.consumed == N && q.sum == 500500);
}
C
cc -std=c11 -O2 -Wall -Wextra -pthread "$LAB_DIR/lab.c" -o "$LAB_DIR/lab"
"$LAB_DIR/lab"
# expected: produced=1000 consumed=1000 sum=500500
  1. 10분: 그림과 코드를 대조해 queue invariant(0≤size≤CAP)와 각 condition의 predicate를 적는다.
  2. 10분: 20회 실행해 결과가 항상 같은지 확인한다. noise broadcast가 correctness를 바꾸지 않아야 한다.
  3. 10분: 두 while 중 하나를 if로 바꾸고 CAP/N/noise 횟수를 늘려 실패를 관찰한 뒤 원복한다. 재현되지 않아도 잘못된 계약임을 상태 전이로 설명한다.

11. 실패 시나리오: 새벽에 worker가 모두 멈췄다

증상: CPU는 낮고 request queue만 증가한다. thread dump에서 worker는 condition wait, producer는 full queue를 기다리고 있다.

잘못된 구현: consumer가 if (empty) wait를 사용하고 cancellation 경로에서 semaphore permit를 반환하지 않았다. shutdown은 flag만 바꾸고 broadcast하지 않았다.

증거 수집: queue size/permit gauge, acquire·hold·wait histogram, waiter 수, timeout·cancel counter, thread stacks, futex wait 위치, 최근 state transition ID를 같은 timestamp로 묶는다.

즉시 완화: 신규 유입을 제한하고 안전한 restart로 leaked in-memory state를 재구축한다. live process의 semaphore 값을 임의로 올려 invariant corruption을 숨기지 않는다.

영구 수정: predicate while-loop, close+broadcast protocol, scope-bound permit release, absolute deadline, invariant assertion과 cancellation stress test를 추가한다.

12. 대기업 면접 질문 3개

  1. “mutex와 binary semaphore는 언제 같고 왜 대체재가 아닌가요?”
    답변 포인트: 둘 다 동시 진입을 1로 제한할 수 있지만 mutex에는 owner와 unlock discipline, acquire/release, 구현에 따라 PI·robust semantics가 있다. semaphore는 ownership 없는 permit accounting이라 다른 execution context가 post할 수 있다. protected invariant이면 mutex, resource count/event handoff이면 semaphore를 우선한다.
  2. “condition wait를 왜 if가 아니라 while로 감싸나요?”
    답변 포인트: wake는 predicate true의 소유권 이전이 아니다. spurious wake, broadcast, Mesa semantics에서 먼저 실행한 경쟁자의 상태 소비, timeout 때문에 mutex 재획득 후 predicate가 false일 수 있다. 같은 mutex 아래 state 변경과 atomic unlock-wait-relock이 lost wake를 막는다.
  3. “uncontended pthread mutex lock마다 syscall이 발생하나요?”
    답변 포인트: 일반적인 Linux 구현은 user-space atomic fast path로 끝내고 contention 시 futex wait/wake를 쓴다. FUTEX_WAIT는 futex word가 expected와 같은지 확인하고 compare-and-block해 race를 닫는다. 단, futex는 구현 mechanism이며 POSIX API 계약과 동일시하거나 특정 glibc 내부 값을 애플리케이션이 의존하면 안 된다.

13. 퀴즈·누적 리뷰

  1. DB connection 20개와 shared LRU map을 각각 어떤 primitive로 보호할 것인가? 이유는 ownership/count/invariant로 답하라.
  2. condition signal을 mutex 밖에서 호출하는 코드가 항상 틀렸다고 단정할 수는 없더라도, predicate 변경을 같은 mutex 아래 두는 규칙이 왜 안전한가?
  3. sem_wait가 EINTR이면 무조건 처음부터 새 5초 timeout으로 재시도해도 되는가?
  4. Day 15 복습: mutex unlock→다음 lock의 happens-before가 atomicity 외에 visibility를 어떻게 제공하는가?
  5. Day 10 복습: priority inversion의 세 역할(low owner, medium runner, high waiter)을 그리고 PI가 어느 edge를 바꾸는가?

정답 핵심: connection은 semaphore, LRU 복합 invariant는 mutex가 자연스럽다. timeout은 최초 absolute deadline을 유지한다. condition의 signal은 힌트이고 state가 truth source다. PI는 lock owner가 critical section을 마칠 수 있도록 effective priority를 올린다.

14. 다음 날 연결

Day 17에서는 spinlock, blocking lock, futex의 역할 경계를 다룬다. 기다리며 CPU를 태울지 scheduler에 양보할지, critical-section 길이·preemption·interrupt context·contention을 근거로 선택하고 adaptive spinning이 왜 만능이 아닌지 연결한다.
