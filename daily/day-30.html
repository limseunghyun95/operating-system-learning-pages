OPERATING SYSTEM · DAY 30 / 63 · KERNEL MEMORY

slab/slub과 kernel object allocation

한 줄 요약: buddy allocator가 page를 공급하면 SLUB은 이를 고정 크기 object로 잘라 per-CPU freelist에서 재사용한다. 빠른 할당의 대가는 partial slab 단편화·NUMA locality·GFP context·reclaim 가능성까지 함께 관리해야 한다는 것이다.

1. 초보자 용어 사전

page allocator / buddy물리 page를 2의 거듭제곱 묶음(order)으로 주고 합치는 하위 allocator. SLUB이 새 slab을 만들 때 page를 여기서 받는다.
slab하나 이상의 page를 같은 종류·크기의 kernel object 여러 개로 나눈 저장 단위.
cache / kmem_cache특정 object의 크기·정렬·생성 정책과 slab 목록을 관리하는 typed object cache.
objectinode·dentry·task_struct 같은 kernel 자료구조 한 개. 같은 cache의 object는 같은 allocation size를 쓴다.
kmalloc임의 byte 크기를 요청하면 알맞은 generic size-class cache에서 object를 주는 kernel API.
SLAB / SLUB서로 위아래 계층이 아니라 kernel build에서 선택하는 slab allocator 구현들. 현대 Linux는 보통 SLUB을 사용하지만 설정을 확인해야 한다.

partial / full slabfree와 in-use object가 섞인 slab / 모든 object가 사용 중인 slab. object 하나만 살아도 page 전체 반환이 막힐 수 있다.

memcg accountingallocation을 memory cgroup 사용량에 청구하는 것. kernel memory도 container limit과 OOM에 영향을 줄 수 있다.

2. mental model: 부품 전용 트레이

buddy는 창고에서 page 단위 선반을 준다. SLUB은 선반을 inode 전용, dentry 전용처럼 같은 크기의 칸(object)으로 나눈 트레이(slab)로 만든다. 현재 CPU의 트레이에 빈 칸이 있으면 lock 없이 빠르게 꺼내고, 없으면 node의 partial 목록이나 buddy까지 내려간다. 단, 트레이마다 부품 하나씩만 남으면 총 live object는 적어도 많은 page가 고정된다.

3. architecture: API에서 물리 page까지

kernel subsystem
  ├─ kmem_cache_alloc(cache, GFP_*)  typed object
  └─ kmalloc(bytes, GFP_*)           generic size cache
                 │
                 ▼
        CPU-local freelist ─ hit → object 반환       FAST PATH
                 │ empty
                 ▼
        node partial slab → freelist refill
                 │ 없음
                 ▼
        page allocator / buddy → 새 slab 구성        SLOW PATH
                 │ pressure
                 ├─ direct/kswapd reclaim, compaction (flag에 따라)
                 └─ 실패 → NULL 또는 호출 계약에 따른 치명적 결과

kfree / kmem_cache_free → CPU/node freelist → slab이 완전히 비면 page 반환 후보

중요: SLUB은 buddy 위의 object allocator다. SLAB과 SLUB은 순차 계층이 아니라 대체 구현이다.

4. object·slab 상태 전이

[EMPTY slab: all FREE]
       │ allocate object
       ▼
[PARTIAL: FREE + IN-USE] ─ 마지막 FREE 사용 → [FULL: all IN-USE]
       ▲                                      │ free one
       └──────────────────────────────────────┘
       │ 마지막 IN-USE free
       ▼
[EMPTY] ─ allocator 정책·cache 상태 → buddy에 page 반환 가능

금지 전이: FREE 후 접근, 다른 cache/API로 free, 두 번 free, cache destroy 전 live object 잔존.
주의: free object가 생겼다는 것과 물리 page가 즉시 회수됐다는 것은 다르다.

5. CS·kernel·hardware deep dive

5.1 왜 typed object cache인가

같은 크기·정렬의 object를 반복 사용하면 매번 page를 쪼개고 metadata를 찾는 비용이 줄고, 최근 사용한 cache line과 초기화된 구조를 재사용할 수 있다. custom cache는 constructor·alignment·debug 정책도 묶지만, 생성 자체가 공짜는 아니므로 generic kmalloc이면 충분한 작은 수요에 남발하지 않는다.

5.2 fast path의 핵심은 per-CPU locality

현재 CPU freelist의 head를 갱신하는 경로는 공유 lock·remote cache-line bouncing을 줄인다. 하지만 CPU별 free object가 분산되면 다른 CPU가 새 slab을 요청하는 동안 전체로는 빈 object가 남을 수 있다. 성능과 memory footprint의 교환이다.

5.3 kmalloc은 generic slab cache를 고른다

요청 byte는 정렬과 size class에 맞는 실제 allocation 크기로 반올림된다. Linux의 kmalloc_size_roundup() 같은 helper로 반복 요청 크기를 맞출 수 있지만, class 경계는 architecture·설정·버전 세부이므로 숫자를 ABI처럼 가정하면 안 된다.

5.4 두 종류의 공간 낭비

요청보다 큰 object slot·정렬·debug metadata는 내부 낭비다. live object가 여러 partial slab에 흩어져 page 반환을 막는 것은 slab-level 단편화다. active_objs × objsize만으로 실제 page·metadata 비용을 정확히 계산할 수 없다.

5.5 GFP flag는 성능 hint가 아니라 실행 문맥 계약

GFP_KERNEL은 일반적으로 sleep과 direct reclaim을 허용한다. atomic/interrupt 또는 lock 제약 문맥에서는 잠들 수 없는 flag가 필요하지만 GFP_NOWAIT·GFP_ATOMIC은 더 쉽게 실패하고 reserve를 소모할 수 있다. flag로 설계 결함을 숨기지 말고 preallocation·mempool·workqueue 전환을 검토한다.

5.6 reclaim recursion과 deadlock

filesystem·block layer가 lock을 잡고 allocation했는데 reclaim이 같은 경로로 재진입하면 deadlock이 생길 수 있다. Linux는 scoped nofs/noio API로 현재 문맥의 reclaim 범위를 제한하는 방식을 권장한다. 무작정 더 강한 flag로 바꾸는 대신 lock graph와 reclaim call chain을 확인한다.

5.7 NUMA에서는 어느 node의 slab인지도 성능이다

local node의 object는 remote memory보다 latency와 interconnect traffic이 낮다. allocating CPU와 consuming CPU가 다르거나 object가 오래 이동하면 locality가 깨진다. 단순 cache hit율뿐 아니라 NUMA placement, remote access, cross-CPU free를 함께 본다.

5.8 reclaimable은 즉시 free라는 뜻이 아니다

SReclaimable은 압박 시 회수 가능성이 있는 slab이고 SUnreclaim은 그렇지 않은 영역이다. reclaimable object도 참조·dirty state·shrinker 비용 때문에 바로 사라지지 않는다. cache별 growth와 reclaim throughput을 시간축으로 확인한다.

5.9 안전성 debug는 layout과 timing을 바꾼다

redzone, poisoning, user tracking, sanity check는 overflow·double free의 단서를 주지만 object 크기와 page당 object 수, latency를 바꾼다. 재현 환경·canary에서 목적에 맞게 켜고 결과에 debug overhead를 기록한다.

7. 실무 best practice

  • kmalloc/kfree, kmem_cache_alloc/free, vmalloc/vfree처럼 allocator와 free API를 정확히 짝짓는다.
  • 수량×크기는 kmalloc_array·kcalloc, flexible array는 struct_size 계열로 overflow를 막는다.
  • 초기화가 계약이면 kzalloc을 쓰고, 성능 때문에 생략할 때 모든 field의 초기화 증거를 남긴다.
  • allocation 실패는 정상 분기로 설계한다. partial object graph를 역순 rollback하고 bounded retry·backpressure·degradation을 둔다.
  • forward progress가 꼭 필요한 제한된 경로는 미리 할당한 pool/mempool을 검토하며 pool 고갈 정책도 테스트한다.
  • untrusted request로 만든 kernel memory는 적절히 account하고 per-tenant quota·상한을 둔다.
  • custom cache destroy 전 모든 object가 반환됐음을 refcount·drain 순서로 보장한다.
  • tuning 전 cache별 active/total, slab bytes, allocation latency, reclaim/PSI, cgroup events를 같은 시간축에 수집한다.

8. error handling runbook

  1. NULL: 요청 크기·GFP·call context를 기록하고 부분 생성 자원을 역순 해제한다. 무한 retry하지 않는다.
  2. atomic allocation 반복 실패: interrupt/lock 경로를 줄이고 preallocation, mempool, deferred work가 가능한지 검토한다.
  3. Slab 지속 증가: slabtop으로 cache를 좁히고 active/total·object lifetime·reference leak을 추적한다.
  4. SReclaimable인데 pressure: shrinker가 등록·진행되는지, ref pin·dirty dependency·reclaim recursion을 확인한다.
  5. corruption 경고: node 격리와 증거 보존 후 해당 cache의 debug 옵션·KASAN·fault injection을 staging에서 재현한다.
  6. tuning: 한 변수씩 canary하고 allocation p99·CPU·memory·reclaim stall을 함께 비교한다.

9. 놓치기 쉬운 함정

  • SLAB 위에 SLUB이 있다: 아니다. 대체 allocator 구현이다.
  • GFP_ATOMIC은 더 빠르다: sleep하지 않는 대신 제한된 reserve를 쓰며 실패 가능성이 높다.
  • kfree 후 page가 즉시 줄어든다: object는 cache로 돌아가며 slab 전체가 비어야 page 반환 후보가 된다.
  • SReclaimable은 여유 memory다: 회수 비용·참조·속도 제한이 있다.
  • active_objs×objsize가 총비용이다: free slot, padding, metadata, partial slab page를 빠뜨린다.
  • 큰 kmalloc도 vmalloc과 같다: kmalloc memory는 물리적으로 연속인 성질을 기대할 수 있지만 큰 연속 allocation은 실패하기 쉽고, vmalloc은 가상 연속이다.
  • custom cache는 항상 빠르다: 작은 사용량에서는 관리·fragmentation 비용이 이득보다 클 수 있다.

10. 30분 실습: partial slab 단편화 simulator

object 8개짜리 slab 두 개를 채운 뒤 각 slab에 하나만 남긴다. live object는 2개뿐이지만 두 slab 모두 page를 고정한다. 교육용 compaction 모델은 object를 한 slab에 모아 하나를 비운다.

set -eu
lab_dir="$(mktemp -d)"; trap 'rm -rf "$lab_dir"' EXIT
cat > "$lab_dir/slab_lab.py" <<'PY'
CAPACITY = 8
slabs = [set(range(0, 8)), set(range(8, 16))]
for object_id in list(range(1, 8)) + list(range(9, 16)):
    for slab in slabs:
        slab.discard(object_id)

def stats(label):
    live = sum(map(len, slabs)); capacity = len(slabs) * CAPACITY
    reclaimable = sum(not slab for slab in slabs)
    print(f"{label} live={live} slabs={len(slabs)} capacity={capacity} "
          f"utilization={100*live/capacity:.1f}% reclaimable={reclaimable}")

stats("before")
assert slabs == [{0}, {8}]
# 교육용 이동 모델: 실제 generic slab object는 임의 이동 불가일 수 있다.
slabs[0].add(slabs[1].pop())
slabs[:] = [slab for slab in slabs if slab]
stats("after_model_compaction")
assert slabs == [{0, 8}]
PY
python3 "$lab_dir/slab_lab.py"
# expected:
# before live=2 slabs=2 capacity=16 utilization=12.5% reclaimable=0
# after_model_compaction live=2 slabs=1 capacity=8 utilization=25.0% reclaimable=0
  1. 0~10분: allocate/free 후 각 slab의 empty·partial·full 상태를 그린다.
  2. 10~20분: capacity를 4·16으로 바꿔 pinned capacity와 내부 낭비를 비교한다.
  3. 20~30분: 실제 kernel이 임의 object를 이동하기 어려운 이유를 pointer 안정성·동시성·subsystem 계약으로 설명한다.

모델 한계: generic live slab object를 kernel이 마음대로 옮길 수 있다는 뜻이 아니다. 이 simulator는 “object 하나가 slab page를 pin한다”는 packing 문제만 보여준다.

11. production 관찰

grep -E '^(Slab|SReclaimable|SUnreclaim):' /proc/meminfo
sudo slabtop -o
sudo head -n 20 /proc/slabinfo

# tracefs가 mount되고 권한·kernel 설정이 허용할 때만 짧게 관찰
sudo sh -c 'echo 1 > /sys/kernel/tracing/events/kmem/kmalloc/enable'
# 짧은 구간 수집 후 반드시 disable; bytes_req와 bytes_alloc 차이를 확인
sudo sh -c 'echo 0 > /sys/kernel/tracing/events/kmem/kmalloc/enable'

cache 이름·active/total·object size를 시계열로 남기고 workload/QPS, cgroup memory.events, PSI, reclaim과 겹쳐 본다. tracepoint와 slab debug는 hot path 비용이 있으므로 production에서는 승인된 짧은 window와 rollback을 준비한다.

12. 실패 시나리오

metadata service의 kernel memory가 증가해 cgroup OOM이 발생했다. 팀은 SReclaimable이 크므로 안전하다고 판단했지만, slabtop에서 특정 dentry/inode 계열 cache의 active object와 partial slab가 계속 늘었고 PSI와 reclaim stall도 상승했다. traffic을 제한한 뒤 mount·namespace·open file reference를 추적해 ref leak을 수정하고, canary에서 cache growth·reclaim throughput·request p99를 함께 확인한다. 단순 drop_caches 반복은 원인을 고치지 못하고 latency만 만든다.

13. 대기업 면접 질문 3개

  1. buddy와 SLUB의 역할을 연결해 보세요.
    답변 포인트: buddy는 page/order, SLUB은 page를 typed fixed-size object로 분할·재사용, per-CPU fast path와 node partial slow path, 완전 empty일 때 page 반환 후보.
  2. GFP_KERNEL과 GFP_ATOMIC 차이는?
    답변 포인트: sleep/reclaim 가능 문맥 대 non-sleeping 문맥, reserve와 실패 확률, 무한 retry 금지, preallocation/mempool/deferred work 설계.
  3. Slab 증가를 어떻게 진단합니까?
    답변 포인트: SReclaimable/Unerclaim 분리, slabtop cache ranking, active/total과 object lifetime/ref leak, cgroup/PSI/reclaim 상관, debug/trace canary.

14. 퀴즈·누적 리뷰

  1. object 1개만 남은 partial slab의 page를 바로 반환할 수 있는가? 일반적으로 아니다. live pointer가 그 page를 사용한다.
  2. SLAB과 SLUB은 위아래 계층인가? 아니다. 같은 목적의 대체 구현이다.
  3. GFP_ATOMIC이면 allocation 성공이 보장되는가? 아니다. 제한된 reserve가 있어도 실패를 처리해야 한다.
  4. Day 29 연결: user allocator의 size class·thread cache·fragmentation을 kernel의 kmalloc cache·per-CPU freelist·partial slab와 비교한다.
  5. Day 22~24 연결: SLUB이 새 slab을 요청하면 buddy가 물리 page를 제공하며 pressure 시 reclaim·compaction·fault/OOM 경로와 경쟁한다.
