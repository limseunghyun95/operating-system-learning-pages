리뷰: thread-safe API 설계 리뷰

한 줄 요약: thread-safe API는 “lock을 썼다”가 아니라 상태·소유권·atomic contract·happens-before·lifecycle·실패 의미가 호출자에게 끝까지 닫혀 있어야 한다.

1. 초보자 용어 사전

thread-safe / MT-Safe여러 thread가 문서화된 방식으로 동시에 호출해도 내부 상태와 결과 계약이 깨지지 않는 성질이다.
reentrant함수가 끝나기 전에 signal handler·callback·재귀 호출로 같은 함수가 다시 들어와도 안전한 성질이다. thread-safe와 별개다.
async-signal-safe비동기 signal handler 안에서도 호출이 허용되는 성질. mutex를 쓰는 thread-safe 함수가 signal-safe인 것은 아니다.
invariant모든 공개 API 호출 전후에 반드시 유지돼야 하는 상태 조건. 예: size는 0 이상 capacity 이하다.
linearizability동시 호출 각각이 호출과 반환 사이의 어느 한 순간에 원자적으로 실행된 것처럼 설명 가능한 성질이다.
linearization point연산의 효과가 논리적으로 확정되는 한 지점. mutex 안의 상태 변경이나 성공한 atomic RMW가 예다.
synchronization boundary어떤 lock·atomic·message 전달이 어느 상태를 보호하고 다른 thread에 보이게 하는지 정한 경계다.
ownership / alias누가 객체를 생성·수정·해제할 책임이 있는지, 같은 객체를 가리키는 다른 참조가 존재하는지에 관한 계약이다.
lifetime객체를 안전하게 접근할 수 있는 기간. lock은 객체가 이미 해제된 use-after-free를 고쳐 주지 못한다.
check-then-act조건을 확인한 뒤 행동하기 전에 다른 thread가 상태를 바꾸는 경쟁. contains 뒤 insert가 대표적이다.
backpressure소비 능력보다 요청이 많을 때 무한 적재 대신 대기·거절·속도 제한으로 생산자에게 압력을 돌려주는 정책이다.
shutdown protocolOPEN→CLOSING→CLOSED 전이를 정의하고 신규 호출 차단, 실행 중 호출 drain, 자원 해제를 순서대로 수행하는 규약이다.

2. mental model: 금고가 아니라 금고 서비스의 계약

mutex는 금고 문 하나일 뿐이다. 좋은 API는 고객이 금고 내부 열쇠를 만지지 않아도 다음 질문에 답할 수 있어야 한다.

  • 어떤 상태가 함께 바뀌며, 호출 전후 invariant는 무엇인가?
  • 동시 호출의 순서는 어디에서 확정되고 결과는 무엇을 의미하는가?
  • 대기할 수 있는가, deadline과 cancellation은 누가 전달하는가?
  • close가 시작될 때 새 호출과 이미 실행 중인 호출은 어떻게 되는가?
  • 오류가 나면 state와 ownership이 어느 쪽에 남는가?

내부 lock 선택을 숨기는 것만으로는 encapsulation이 아니다. 호출자가 올바른 사용법을 추측하지 않아도 되는 semantic contract가 진짜 캡슐화다.

4. lifecycle 상태 전이: destroy는 마지막 단계다

UNINITIALIZED ──init/once──> OPEN ──close──> CLOSING ──active_calls==0──> CLOSED ──destroy──> DEAD
                              │                 │
                              │ new call: pin++ │ new call: reject(ECANCELED)
                              │ return: pin--   │ in-flight: finish or cancel by contract
                              └─────────────────┘

금지 전이 1: OPEN ──free──> DEAD while another thread has an alias
금지 전이 2: CLOSING ──mutex_destroy──> DEAD while waiter/owner exists
완료 불변식: accepting==false AND active_calls==0 AND waiters==0

6. CS·kernel·hardware deep dive

6.1 MT-Safe 함수 두 개를 이어도 atomic transaction은 아니다

GNU/Linux의 공식 safety 설명도 MT-Safe가 atomic을 뜻하지 않으며 MT-Safe 함수의 연속 호출이 atomic combination을 보장하지 않는다고 명시한다. get()과 set()이 각각 lock을 잡아도 get()+1→set() 사이에 다른 thread가 끼어 lost update가 난다. 호출자가 필요한 의미를 하나의 add(delta), put_if_absent(), transaction/guard API로 제공해야 한다.

6.2 linearization point는 구현 설명이자 테스트 oracle이다

mutex 기반 add라면 lock 안의 value 변경, CAS 기반 stack이라면 성공한 compare-exchange가 선형화 지점이 될 수 있다. 호출보다 앞이나 반환보다 뒤에 선형화되면 안 된다. 실제 history를 수집해 real-time order를 지키는 순차 history로 재배열 가능한지 검사하면 단순 final counter보다 강한 테스트가 된다.

6.3 mutex unlock→다음 lock은 state publication 경계다

writer가 mutex 안에서 여러 non-atomic 필드를 갱신하고 unlock한 뒤 reader가 같은 mutex를 lock하면, POSIX synchronization을 통해 reader는 일관된 상태를 관찰할 수 있다. 반면 내부 포인터를 반환해 lock 밖에서 읽게 하면 보호 경계가 무너진다. 복사본, immutable snapshot, reference-counted handle처럼 lifetime과 visibility가 함께 유지되는 반환 형태를 선택한다.

6.4 atomic 하나가 여러 필드 invariant를 대신하지 못한다

size와 head/tail, balance와 ledger처럼 함께 바뀌어야 하는 값은 개별 atomic만으로 일관된 snapshot을 만들기 어렵다. lock, versioned snapshot/seqlock, immutable state의 atomic pointer 교체 등 프로토콜이 필요하다. lock-free는 “lock이 없음”이지 wait-free나 단순함을 뜻하지 않으며 ABA와 memory reclamation 문제가 추가된다.

6.5 lock은 lifetime pin이 아니다

thread A가 객체 주소를 얻은 뒤 thread B가 객체와 그 안의 mutex를 destroy/free하면 A는 lock 호출 전에 이미 use-after-free다. reference count, hazard pointer/epoch, owner thread, join/drain 같은 별도 lifetime protocol이 필요하다. POSIX에서 사용 중이거나 다른 thread가 참조하는 mutex를 destroy하는 행위는 안전한 recovery API가 아니다.

6.6 초기화도 publish protocol의 일부다

lazy init flag를 plain load/store로 확인하면 두 번 초기화하거나 부분 초기화 상태를 노출할 수 있다. 정적 PTHREAD_MUTEX_INITIALIZER, pthread_once(), 언어의 thread-safe static initialization을 사용하고, 완성된 객체를 synchronization edge 뒤에 publish한다. “pointer가 non-NULL”만으로 payload 가시성이 증명되지 않는다.

6.7 callback을 lock 안에서 호출하면 lock graph가 API 밖으로 열린다

사용자 callback이 같은 객체로 재진입하거나 다른 lock을 잡으면 self-deadlock·ABBA·긴 critical section이 생긴다. lock 안에서 snapshot/작업 목록만 만들고 unlock 뒤 callback을 호출한다. 반드시 lock 안에서 호출해야 한다면 “callback은 재진입·blocking 금지”를 명시하고 테스트·lock hierarchy에 포함해야 하지만 가능한 한 피한다.

6.8 cancellation은 cleanup과 ownership을 포함한 API 계약이다

POSIX deferred cancellation은 cancellation point에서 발생하고 cleanup handler는 LIFO로 실행될 수 있다. 따라서 lock·permit·buffer를 얻은 역순으로 cleanup을 등록한다. 그러나 library가 내부에서 cancellation을 허용하는지, partial effect가 있는지, caller가 retry 가능한지는 문서화해야 한다. timeout 응답만으로 worker와 side effect가 끝난 것은 아니다.

6.9 thread-safe, reentrant, signal-safe는 서로 다른 축이다

mutex 기반 함수는 여러 thread 사이에서는 안전할 수 있지만, mutex owner thread를 중단한 signal handler가 같은 함수를 부르면 deadlock한다. signal handler에는 POSIX async-signal-safe 목록의 함수만 사용하고 flag/self-pipe 같은 최소 전달만 수행한다. fork 뒤 child에서도 다른 thread가 잡고 사라진 lock을 건드리지 않도록 exec 전 허용 동작을 제한한다.

6.10 kernel의 lockdep 관점으로 user API도 본다

Linux lockdep은 개별 lock instance보다 논리적 lock class와 획득 dependency를 추적한다. user-space 리뷰에서도 “이 함수는 어떤 lock class를 어떤 순서로 잡는가”를 API 문서에 남기면 callback·중첩 호출·모듈 조합에서 생기는 cycle을 설계 단계에 찾을 수 있다.

8. 실무 best practice

  • 헤더/API 문서에 thread-safety scope를 같은 객체, 다른 객체, global state로 나눠 쓴다.
  • 각 연산의 precondition, postcondition, invariant, linearization point를 한 문장으로 적는다.
  • 호출자에게 check-then-act를 강요하지 말고 업무 의미 단위의 atomic method를 제공한다.
  • 내부 lock과 mutable pointer를 노출하지 않고 snapshot 또는 명시적 scoped guard를 사용한다.
  • blocking 가능성, 최대 wait, interrupt/cancellation, fairness와 backpressure 정책을 계약에 넣는다.
  • close를 idempotent하게 만들고 신규 호출 차단→in-flight drain→destroy 순서를 강제한다.
  • callback, logging, allocator, RPC를 lock 안에서 호출하지 않는다.
  • 오류마다 state 변경 여부, 자원 ownership, retry/idempotency 조건을 표로 남긴다.
  • ThreadSanitizer·stress·fault injection과 함께 history/invariant assertion을 운영한다.
  • wait time, contention, queue depth, timeout, rejected-after-close를 metric으로 노출한다.

10. 놓치기 쉬운 함정

  • const method면 thread-safe: 내부 cache, global allocator, 반환 alias가 mutable일 수 있다.
  • getter/setter마다 lock: 호출 조합의 invariant는 보호하지 못한다.
  • recursive mutex로 재진입 해결: invariant가 중간 상태인 채 callback이 들어오는 논리 오류는 남는다.
  • rwlock이면 항상 빠름: 짧은 critical section, writer starvation, cache-line bouncing에서 더 느릴 수 있다.
  • atomic pointer publish 후 바로 free: reader가 이전 pointer를 쓰는 reclamation 문제를 놓친다.
  • close 후 mutex destroy: 이미 진입한 waiter와 alias를 drain하지 않았다.
  • ThreadSanitizer가 조용하면 증명 완료: 실행되지 않은 interleaving과 논리적 atomicity 위반은 못 잡을 수 있다.
  • MT-Safe와 signal-safe 혼동: signal handler의 재진입은 다른 제약이다.

11. 30분 실습: 함수는 안전하지만 조합은 깨지는 API 리뷰

다음 C11 프로그램은 모든 state 접근에 mutex를 쓰지만 get→set 조합에서 lost update가 난다. 이어 업무 의미 단위 add와 close 이후 호출 거절, join 뒤 destroy를 검증한다.

set -eu
lab_dir="$(mktemp -d)"
trap 'rm -rf "$lab_dir"' EXIT

cat > "$lab_dir/api_review.c" <<'C'
#include <pthread.h>
#include <stdatomic.h>
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>

typedef struct {
  pthread_mutex_t mu;
  long value;
  int closed;
} counter_t;

static atomic_int ready;
static counter_t *shared;

static void must(int rc, const char *what) {
  if (rc != 0) { fprintf(stderr, "%s rc=%d\n", what, rc); exit(1); }
}
static int counter_init(counter_t *c) {
  c->value = 0; c->closed = 0;
  return pthread_mutex_init(&c->mu, NULL);
}
static int counter_get(counter_t *c, long *out) {
  int rc = pthread_mutex_lock(&c->mu); if (rc) return rc;
  *out = c->value;
  return pthread_mutex_unlock(&c->mu);
}
static int counter_set(counter_t *c, long value) {
  int rc = pthread_mutex_lock(&c->mu); if (rc) return rc;
  if (c->closed) rc = ECANCELED; else c->value = value;
  int urc = pthread_mutex_unlock(&c->mu);
  return rc ? rc : urc;
}
static int counter_add(counter_t *c, long delta) {
  int rc = pthread_mutex_lock(&c->mu); if (rc) return rc;
  if (c->closed) rc = ECANCELED; else c->value += delta;
  int urc = pthread_mutex_unlock(&c->mu);
  return rc ? rc : urc;
}
static int counter_close(counter_t *c) {
  int rc = pthread_mutex_lock(&c->mu); if (rc) return rc;
  c->closed = 1;
  return pthread_mutex_unlock(&c->mu);
}
/* precondition: all callers joined; no alias can enter again */
static int counter_destroy(counter_t *c) { return pthread_mutex_destroy(&c->mu); }

static void *broken_increment(void *unused) {
  (void)unused; long snapshot;
  must(counter_get(shared, &snapshot), "get");
  atomic_fetch_add_explicit(&ready, 1, memory_order_release);
  while (atomic_load_explicit(&ready, memory_order_acquire) != 2) sched_yield();
  must(counter_set(shared, snapshot + 1), "set");
  return NULL;
}
static void *many_adds(void *unused) {
  (void)unused;
  for (int i = 0; i < 25000; ++i) must(counter_add(shared, 1), "add");
  return NULL;
}
int main(void) {
  counter_t broken; pthread_t x, y; long value;
  must(counter_init(&broken), "init"); shared = &broken; atomic_store(&ready, 0);
  must(pthread_create(&x, NULL, broken_increment, NULL), "create");
  must(pthread_create(&y, NULL, broken_increment, NULL), "create");
  must(pthread_join(x, NULL), "join"); must(pthread_join(y, NULL), "join");
  must(counter_get(&broken, &value), "get");
  printf("broken_composition final=%ld expected=2\n", value);
  must(counter_destroy(&broken), "destroy");

  counter_t fixed; pthread_t workers[4];
  must(counter_init(&fixed), "init"); shared = &fixed;
  for (int i = 0; i < 4; ++i) must(pthread_create(&workers[i], NULL, many_adds, NULL), "create");
  for (int i = 0; i < 4; ++i) must(pthread_join(workers[i], NULL), "join");
  must(counter_get(&fixed, &value), "get");
  printf("atomic_api final=%ld expected=100000\n", value);
  must(counter_close(&fixed), "close");
  int rejected = counter_add(&fixed, 1) == ECANCELED;
  must(counter_get(&fixed, &value), "get");
  printf("after_close rejected=%d value=%ld\n", rejected, value);
  int destroyed = counter_destroy(&fixed) == 0;
  printf("destroy_after_join ok=%d\n", destroyed);
  return 0;
}
C

  2. 10~20분: counter_add의 linearization point, precondition, postcondition, error ownership을 주석으로 작성한다.

핵심 리뷰: 이 샘플은 모든 worker를 join한 뒤 destroy하므로 안전하다. 실제 library가 caller lifetime을 통제하지 못한다면 reference pin, close/drain wait, opaque handle 같은 별도 protocol이 필요하다.

12. 실패 시나리오: 안전한 cache API가 만든 use-after-free

cache의 get(), put()은 모두 mutex를 사용했다. 하지만 get은 내부 entry pointer를 반환했고 caller는 lock 밖에서 이를 사용했다. eviction thread가 entry를 제거·free한 직후 caller가 pointer를 읽어 crash했다. race detector에서는 타이밍에 따라 잡히지 않았고, mutex 사용 여부만 본 리뷰도 통과했다.

원인: state mutation은 보호했지만 반환 alias의 lifetime 계약이 없었다. 복구: cache를 read-only 모드로 전환하고 crash dump의 object ID·eviction history를 보존한다. 재발 방지: owned copy/immutable refcount handle, eviction과 reader pin의 state machine, close→drain→destroy, history 기반 stress test를 도입한다.

13. 대기업 면접 질문 3개

  1. “모든 public method에 mutex를 걸면 thread-safe인가요?”
    답변 포인트: 개별 method의 data-race 방지는 가능하지만 method 조합의 atomicity, 내부 pointer lifetime, callback 재진입, init/destroy 경쟁은 남는다. invariant와 linearization point를 업무 연산 단위로 정의해야 한다.
  2. “thread-safe와 reentrant, async-signal-safe의 차이는?”
    답변 포인트: thread-safe는 여러 thread의 동시 호출, reentrant는 완료 전 동일 코드 재진입, signal-safe는 비동기 signal context 제약이다. mutex 기반 함수는 MT-Safe여도 signal handler에서 self-deadlock할 수 있다.
  3. “객체를 안전하게 destroy하는 API를 설계해 보세요.”
    답변 포인트: OPEN→CLOSING에서 신규 호출을 거절하고 lifetime pin/active count로 in-flight를 drain한 뒤 CLOSED에서만 destroy한다. owner/alias를 제한하고 close는 idempotent, 오류·deadline·callback 정책과 관측 지표를 명시한다.
