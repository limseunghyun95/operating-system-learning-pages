fork, exec, wait, exit status와 zombie

한 줄 요약 — fork()는 child를 만들고, execve()는 같은 PID의 program image를 교체하며, waitpid()는 종료 정보를 회수해 zombie의 생명주기를 닫는다.

1. 선수 용어 사전

parent / childprocess 생성 관계. child는 새 PID를 받고 parent의 여러 속성을 상속한다.
fork호출한 process를 기반으로 새 child process를 만드는 POSIX API.
execve현재 process의 address space와 program image를 새 executable로 교체하는 system call. 새 process를 만들지 않는다.
copy-on-writefork 직후 physical page를 복사하지 않고 읽기 공유하다가 한쪽이 쓸 때 page fault로 복사하는 기법.
wait / reapparent가 child의 상태 변화와 종료 정보를 회수하는 동작. 종료 child의 kernel 기록을 제거하는 것을 reap이라 부른다.
exit status정상 종료 코드 또는 signal 종료 정보를 담은 encoded status. 단순 정수처럼 바로 읽지 않고 macro로 해석한다.
zombie실행은 끝났지만 parent가 wait하지 않아 PID·status·resource usage 같은 최소 기록이 남은 상태.
orphan / subreaperparent가 먼저 끝난 child가 orphan이다. init 또는 가장 가까운 subreaper가 입양해 종료를 회수한다.
FD_CLOEXECexec 성공 시 해당 file descriptor를 자동으로 닫게 하는 flag. 의도치 않은 descriptor 유출을 막는다.

2. mental model: 복제, 교체, 영수증 회수

fork = 실행 주체 추가: child는 새 PID와 task_struct, 논리적으로 분리된 address space를 얻지만 page는 COW로 공유할 수 있다.

exec = 내용물 교체: 현재 PID는 유지한 채 code/data/heap/stack을 새 program image로 바꾼다. 성공하면 원래 코드로 돌아오지 않는다.

wait = 영수증 회수: child가 왜 끝났는지 parent가 확인하고 kernel이 보존한 종료 record를 제거한다.

3. architecture와 상태 전이

Parent RUNNING (PID 100)
       │ fork()
       ▼
kernel_clone() → copy_process()
       │
       ├── Parent: fork() returns 101
       │      └── waitpid(101, ...) ──► BLOCKED 또는 WNOHANG=0
       │
       └── Child: fork() returns 0, PID 101
              │ 별도 task/mm, page는 COW 공유
              ▼
          execve("/app", argv, envp)
              │ load ELF/interpreter, 새 stack·mm 준비
              │ PID 101 유지, FD_CLOEXEC 닫힘
              ▼
          New program RUNNING
              │ _exit(7) 또는 signal
              ▼
          EXIT_ZOMBIE
          PID + status + rusage만 보존
              │ SIGCHLD / parent waitpid()
              ▼
          EXIT_DEAD → kernel record 해제
                     waitpid returns PID 101 + encoded status

순서 보장 주의: fork 반환 뒤 parent와 child 중 누가 먼저 실행될지는 scheduler가 결정한다. 출력 순서에 의존하는 코드는 race다.

4. CS deep dive

4.1 fork는 무엇을 복사하고 무엇을 공유하는가

Linux의 glibc fork() wrapper는 NPTL 환경에서 fork와 같은 효과의 clone()을 사용한다. kernel은 child용 task 구조와 page table을 만들지만, anonymous physical page를 즉시 전부 복사하지 않는다. parent와 child PTE를 write-protected COW 상태로 연결하고 실제 write fault 때 해당 page만 분리한다.

file descriptor table은 논리적으로 복제되지만 각 descriptor는 같은 open file description을 참조하므로 file offset과 status flag를 공유한다. 반면 pending signal, CPU time, PID 등은 동일하지 않다. “fork는 process memory의 완전한 즉시 복사”도, “모든 자원을 그대로 공유”도 아니다.

4.2 exec는 새 process가 아니다

execve()는 executable을 열고 format handler를 선택해 ELF segment와 dynamic linker를 mapping하고 argv/envp용 새 user stack을 만든 뒤 새 entry point로 진입한다. PID, parent 관계, current working directory 같은 속성은 유지되지만 기존 memory mapping, caught signal handler, alternate signal stack 등은 사라지거나 reset된다.

multi-threaded process에서 한 thread가 exec하면 호출 thread만 새 program으로 이어지고 다른 thread들은 제거된다. 성공한 exec는 반환하지 않는다. 반환했다면 실패이며 errno가 원인이다.

4.3 exit와 _exit의 경계

C library의 exit()는 atexit handler를 실행하고 stdio buffer를 flush한 뒤 종료한다. fork 뒤 child에는 parent의 user-space buffer도 복제되어 있으므로 exec 실패 경로에서 exit를 쓰면 같은 buffer를 두 번 flush할 수 있다. child의 pre-exec 실패 경로는 보통 _exit()를 사용한다.

Linux의 glibc _exit() wrapper는 모든 thread를 종료하도록 exit_group을 사용한다. raw SYS_exit는 호출 thread만 끝낸다는 구현 경계도 구분한다.

4.4 zombie는 메모리 leak이 아니라 lifecycle leak이다

child가 exit하면 address space와 열린 file 같은 큰 자원은 정리되지만 parent가 결과를 읽을 수 있도록 PID, 종료 status, resource usage가 남는다. wait하지 않으면 process table/PID slot이 누적되어 결국 fork가 실패할 수 있다. zombie를 kill할 수 없는 이유는 실행할 task가 이미 없기 때문이다. parent가 reap하거나 parent를 종료해 subreaper/init가 입양 후 reap하게 해야 한다.

5. exit status를 정확히 해석하기

pid_t r;
int status;
do {
    r = waitpid(child, &status, 0);
} while (r == -1 && errno == EINTR);

if (r == -1) {
    /* ECHILD 등 처리 */
} else if (WIFEXITED(status)) {
    printf("exit=%d\n", WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
    printf("signal=%d core=%d\n",
           WTERMSIG(status), WCOREDUMP(status));
}

status == 7처럼 직접 비교하면 안 된다. shell의 128 + signal 관례도 wait status의 kernel encoding 자체와 동일한 표준은 아니다.

6. 실무 best practice

  1. fork 결과 세 갈래를 모두 처리한다. -1은 생성 실패, 0은 child, 양수는 parent가 받은 child PID다.
  2. child 생성 즉시 ownership을 정한다. 누가 wait할지, timeout 후 어떤 signal을 보낼지, shutdown 때 어떤 순서로 reap할지 명시한다.
  3. descriptor는 원자적으로 CLOEXEC로 연다. multi-thread 환경에서는 open(..., O_CLOEXEC), pipe2(O_CLOEXEC)를 사용해 open과 fcntl 사이 race를 피한다.
  4. exec 실패를 별도 channel로 전달한다. CLOEXEC error pipe를 만들고 child가 exec 실패 시 errno를 write한다. 성공 시 descriptor가 자동으로 닫혀 parent는 EOF를 본다. exit 127만으로는 program 자체의 127 종료와 구분되지 않는다.
  5. multi-threaded launcher는 posix_spawn을 우선 검토한다. fork와 exec 사이 실행할 코드가 제한적이면 deadlock surface와 구현 비용을 줄일 수 있다.
  6. container의 PID 1은 reaper 책임을 가진다. application이 직접 처리하지 않으면 tini 같은 init 또는 runtime의 init 기능을 사용하고 zombie 수를 관측한다.

7. error handling playbook

fork: EAGAINRLIMIT_NPROC, threads-max, pid_max, cgroup pids.max를 확인한다. 무한 즉시 재시도 대신 backoff와 admission control을 적용한다.
fork: ENOMEMkernel 구조·page table 할당 실패 또는 종료된 PID namespace init을 의심한다. memory/cgroup/namespace 증거를 보존한다.
exec: ENOENT대상 파일뿐 아니라 shebang interpreter와 ELF dynamic loader 경로도 확인한다.
exec: EACCES/ENOEXECexecute permission, mount noexec, directory search permission, binary format와 shebang을 구분한다.
exec: E2BIGargv+envp 총량과 ARG_MAX/RLIMIT_STACK 관계를 확인하고 대용량 payload는 file/pipe로 전달한다.
waitpid: EINTRsignal interruption은 loop로 재시도한다. 단, shutdown flag를 확인해야 하는 설계라면 무조건 재시도하지 않는다.
waitpid: ECHILD대상이 직접 child인지, 이미 다른 thread가 reap했는지, SIGCHLD=SIG_IGN/SA_NOCLDWAIT인지 확인한다.

8. 놓치기 쉬운 함정

  • exec 성공 뒤의 코드는 절대 실행되지 않는다. 성공 log를 exec 다음 줄에 두면 그 log는 실패 때만 찍힌다.
  • fork 전 flush되지 않은 stdio buffer가 양쪽에 복제될 수 있다. child에서 exit를 부르면 중복 출력 가능성이 있다.
  • multi-thread process에서 fork 후 child에는 호출 thread만 남지만 다른 thread가 잡고 있던 mutex 상태는 복제된다. 일반 library 호출이 deadlock할 수 있다.
  • WNOHANG에서 반환값 0은 “child가 없다”가 아니라 “대상 child는 있으나 아직 보고할 상태 변화가 없다”다.
  • SIGCHLD의 default ignore와 명시적 SIG_IGN은 Linux/POSIX의 zombie 처리에서 같은 의미가 아니다.
  • orphan과 zombie는 다르다. orphan은 살아서 실행 중일 수 있고, zombie는 이미 종료됐다.

9. 30분 실습: PID 유지와 zombie를 직접 관찰

Linux 전용이다. child는 exec 전후 PID를 출력한 뒤 exit 42로 종료하고, parent는 12초 동안 일부러 wait하지 않아 zombie 관찰 창을 만든다.

LAB_DIR=$(mktemp -d)
python3 - "$LAB_DIR" <<'PY' >"$LAB_DIR/run.log" 2>&1 &
import os, sys, time
lab = sys.argv[1]
child = os.fork()
if child == 0:
    print(f"before exec: pid={os.getpid()} ppid={os.getppid()}", flush=True)
    os.execl("/bin/sh", "sh", "-c",
             'echo "after exec:  pid=$$ ppid=$PPID"; exit 42')

with open(f"{lab}/child.pid", "w") as f:
    f.write(str(child))
print(f"parent={os.getpid()} child={child}; wait intentionally delayed", flush=True)
time.sleep(12)
got, status = os.waitpid(child, 0)
print(f"reaped={got} exited={os.WIFEXITED(status)} "
      f"code={os.WEXITSTATUS(status)}", flush=True)
PY

PARENT_PID=$!
sleep 2
CHILD_PID=$(sed -n '1p' "$LAB_DIR/child.pid")
ps -o pid,ppid,stat,wchan,cmd -p "$PARENT_PID" -p "$CHILD_PID"
grep -E '^(Name|State|Pid|PPid):' "/proc/$CHILD_PID/status"
wait "$PARENT_PID"
sed -n '1,20p' "$LAB_DIR/run.log"
test ! -e "/proc/$CHILD_PID" && echo "reaped: /proc entry removed"

관찰 포인트: before/after exec의 PID가 같고, wait 전 child의 STAT가 Z이며 State: Z (zombie)다. wait 뒤에는 /proc entry가 사라지고 exit code 42가 복원된다.

선택 확장: strace -f -e trace=clone,fork,vfork,execve,wait4,exit_group 뒤에 위 Python command를 붙여 libc→kernel 경계를 확인한다.

10. 실패 시나리오

상황: container service가 helper를 계속 실행하지만 wait하지 않는다. RSS는 안정적인데 몇 시간 뒤 fork: Resource temporarily unavailable가 발생한다.

증거: ps에 PPID 1과 STAT Z가 대량 존재하고 cgroup pids.current가 pids.max에 접근한다.

복구·예방: 올바른 parent/reaper가 wait하도록 수정하고, container에 init을 둔다. child 생성률·zombie 수·pids.current를 alert하며 fork 실패에 bounded backoff를 둔다. zombie에 SIGKILL을 반복하는 것은 해결이 아니다.

11. 대기업 면접 질문 3개

Q1. fork 직후 전체 메모리가 두 배가 되지 않는 이유는?
답변 포인트: 별도 virtual address space와 page table, shared read-only COW physical page, write fault 시 page 단위 복사를 구분한다. page table 복제 비용과 dirty workload에서는 결국 copy 비용이 생긴다는 trade-off도 말한다.

Q2. exec가 process 생성이 아니라는 것을 무엇으로 설명할 수 있나요?
답변 포인트: PID와 parent 관계는 유지되고 program image/address space가 교체된다. 성공 시 반환하지 않으며 FD_CLOEXEC, signal disposition, thread 제거 같은 보존/초기화 경계를 설명한다.

Q3. zombie가 생기는 원인과 production 대응은?
답변 포인트: child 종료 후 parent가 wait하지 않아 status record가 남는 lifecycle leak이다. PID slot 고갈을 연결하고, SIGCHLD/waitpid loop, subreaper/container PID 1, 관측 지표로 대응한다.
