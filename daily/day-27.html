실패 실습: RSS/VSZ/page fault/OOM 관찰

한 줄 요약: VSZ는 확보한 virtual address 범위, RSS는 현재 resident한 physical memory의 근사치이며, page fault는 둘 사이를 연결한다. OOM은 “RSS가 커졌다”가 아니라 reclaim·limit·allocation context가 실패해 kernel이 생존을 위해 task를 희생하는 마지막 결과다.

1. 초보자 용어 사전

VSZ / VmSizeprocess virtual address space에 잡힌 mapping의 총 크기. ps의 VSZ는 보통 KiB 단위이며 RAM 사용량과 같지 않다.
RSS / VmRSSResident Set Size. process에 연결되어 현재 RAM에 resident한 page의 크기 근사치. Linux VmRSS는 RssAnon+RssFile+RssShmem이다.
PSSProportional Set Size. shared page 비용을 이를 공유하는 process 수로 나눠 귀속한 값. multi-process 총비용 추정에 RSS보다 유용할 수 있다.
USSUnique Set Size라는 관찰 개념. process가 사라질 때 단독으로 회수될 private resident memory에 가깝지만 tool 정의를 확인해야 한다.
anonymous memoryfile content를 backing으로 하지 않는 heap, stack, anonymous mmap 등의 memory. reclaim하려면 free하거나 swap 같은 backing이 필요하다.
resident해당 virtual page를 접근할 때 현재 RAM에서 사용할 수 있는 상태. residency는 시간에 따라 바뀌는 snapshot이다.
minor faultstorage I/O 없이 해결되는 page fault. zero-fill anonymous allocation, COW, 이미 cache된 file page 연결 등이 대표적이다.
major fault해결에 I/O activity가 필요한 page fault. file read나 swap-in이 예이며 “반드시 물리 HDD”라는 뜻은 아니다.
first touchreserve된 virtual page를 처음 접근해 physical page/PTE 준비를 실제 유발하는 순간.
overcommit현재 RAM+swap보다 큰 virtual/commit 요청을 어느 정도 허용하는 정책. mmap/malloc 성공과 미래 touch 성공을 분리한다.
reclaimclean file cache drop, dirty writeback, anonymous swap 등으로 usable page를 확보하려는 kernel 작업.
memory pressurememory가 부족해 task가 reclaim·swap·compaction 등을 기다리며 latency와 throughput 손실을 겪는 상태. OOM 전부터 서비스가 망가질 수 있다.
OOM killerreclaim으로 allocation을 만족시키지 못할 때 system 또는 memory cgroup 생존을 위해 victim task를 선택해 죽이는 mechanism.
memory cgroupprocess 집합의 memory를 계층적으로 account·limit하는 Linux controller. cgroup OOM은 그 cgroup 밖 task를 죽이지 않는다.
PSIPressure Stall Information. resource shortage 때문에 task가 실제로 멈춘 시간 비율·누적 시간을 보여주는 Linux 지표.

2. mental model: 좌석 예약과 실제 착석을 분리한다

VSZ는 공연장 도면에서 잡아 둔 좌석 범위, RSS는 지금 실제 사람이 앉아 점유한 좌석이다. 1GiB anonymous mmap을 성공해도 아직 page를 touch하지 않았다면 큰 주소 범위만 예약하고 실제 RAM은 거의 쓰지 않을 수 있다.

  • reserve: VMA와 address range를 만든다. VSZ가 증가한다.
  • touch: page fault를 통해 zero-fill/COW/file load를 해결한다. RSS와 fault counter가 변할 수 있다.
  • pressure: 새 좌석을 만들 공간이 없어 reclaim/swap/writeback을 시도하며 task가 멈춘다.
  • OOM: 끝내 공간을 확보하지 못하면 공연장 전체 또는 제한된 cgroup 안에서 victim을 내보낸다.

5. CS·kernel·hardware deep dive

5.1 VSZ는 비용의 상한도, 현재 RAM도 아니다

VSZ에는 executable/library mapping, reserved anonymous range, stack, file mapping이 포함된다. shared library는 여러 process가 같은 physical page를 공유할 수 있고 untouched anonymous range는 RAM을 거의 쓰지 않는다. 반대로 page table·kernel stack 등 일부 kernel 비용은 application VSZ만으로 보이지 않는다.

5.2 RSS도 정확한 단독 비용이 아니다

Linux VmRSS는 RssAnon+RssFile+RssShmem이며 man-page도 일부 값이 부정확한 snapshot임을 명시한다. shared page는 각 process RSS에 반복 포함될 수 있어 process RSS 합은 physical RAM보다 커질 수 있다. workload 비용 배분에는 smaps의 PSS와 cgroup/system accounting을 함께 본다.

5.3 malloc success는 resident memory 보증이 아니다

allocator가 이미 확보한 arena를 나눌 수도 있고 kernel이 virtual range와 commit policy만 승인할 수도 있다. overcommit mode, mapping type, writable/private 여부에 따라 accounting이 다르며 미래 first touch에서 reclaim latency, fault, signal 또는 OOM을 만날 수 있다.

5.4 minor fault는 작아 보여도 폭풍이면 비싸다

minor fault는 storage I/O가 없다는 뜻이지 비용 0이 아니다. trap, VMA lookup, page allocation/zeroing, COW copy, page-table update, TLB invalidation과 lock contention이 포함될 수 있다. process startup·fork worker·large first touch에서 minflt rate와 latency가 함께 튈 수 있다.

5.5 major fault는 “disk fault”보다 넓은 I/O 분류다

getrusage의 majflt는 fault 해결에 I/O activity가 필요했다는 뜻이다. local SSD, network filesystem, swap 등 경로가 다를 수 있다. majflt가 0이어도 reclaim·compaction·minor COW 비용으로 느릴 수 있고, page cache hit라면 file access가 minor로 끝날 수 있다.

5.6 clean file, dirty file, anonymous의 reclaim 비용이 다르다

clean file cache는 drop 후 다시 읽을 수 있다. dirty file page는 Day 26 writeback이 필요하고, anonymous page는 process가 버리거나 swap backing이 필요하다. 따라서 같은 RSS라도 composition과 working-set activity에 따라 pressure 영향이 다르다.

5.7 pressure는 OOM보다 먼저 SLO를 파괴한다

reclaim이 성공해 OOM을 피하더라도 task가 page 확보를 기다리고 working set이 반복 eviction/refault되면 throughput이 붕괴한다. PSI memory의 some은 일부 task stall, full은 모든 non-idle task가 동시에 stall한 시간을 보여 주므로 RSS threshold보다 사용자 영향에 가깝다.

5.8 ENOMEM과 OOM kill은 다른 failure contract다

RLIMIT_AS나 strict commit 검사로 mmap/brk가 거절되면 caller가 ENOMEM을 처리할 수 있다. 반면 memory cgroup/global OOM에서 victim은 SIGKILL로 비동기 종료되어 application cleanup을 실행할 수 없다. 둘은 recovery와 data-integrity 설계가 완전히 다르다.

5.9 cgroup OOM과 global OOM의 피해 범위가 다르다

cgroup v2에서 memory.max를 넘고 reclaim에 실패하면 그 cgroup이 OOM state가 되며 밖의 task는 kill 대상이 아니다. memory.events의 high/max/oom/oom_kill과 memory.current/stat을 container 관찰의 source of truth로 삼는다.

5.10 victim 선택은 “가장 큰 RSS 하나” 규칙이 아니다

OOM killer는 호출 context에서 허용된 memory 범위와 task의 estimated memory/swap usage, oom_score_adj 등을 반영해 badness를 계산한다. -1000은 보호 효과가 있지만 무분별한 면제는 다른 핵심 process를 희생시킬 수 있다. cgroup의 memory.oom.group은 partial kill로 workload 무결성이 깨지는 것을 막는 선택지다.

5.11 allocator metric과 OS metric을 연결해야 leak을 찾는다

live object bytes가 늘면 application retention/leak 가능성이 크다. live bytes는 안정적인데 RSS만 높다면 allocator arena retention, fragmentation, page cache/mapping, COW, thread stack 등을 분해해야 한다. free 호출과 RSS 감소가 같은 사건이 아님을 Day 25와 연결한다.

7. 실무 best practice

  • process RSS 하나가 아니라 allocator live bytes, RssAnon/File/Shmem, PSS, cgroup memory.current/stat, system MemAvailable을 계층별로 수집한다.
  • counter는 절대값보다 rate와 배포·traffic·GC·cache warmup의 같은 시간축으로 본다.
  • memory PSI와 application latency를 alert에 포함해 OOM 이전의 reclaim/thrashing을 감지한다.
  • container limit에는 정상 working set+page cache+runtime native memory+headroom을 포함하고 request/limit을 실측으로 정한다.
  • bounded cache/queue, admission control, batch size 제한, streaming을 사용해 unbounded growth를 제거한다.
  • allocation 실패 가능 API는 size multiplication overflow, NULL/MAP_FAILED, partial state rollback을 처리한다.
  • OOM kill은 cleanup을 보장하지 않으므로 durable write protocol, idempotent restart, lease expiry를 설계한다.
  • oom_score_adj는 dependency와 blast radius를 검토해 최소한으로 사용하고, critical daemon을 모두 -1000으로 만들지 않는다.
  • 재현은 RLIMIT_AS 또는 전용 cgroup/container limit 안에서만 수행하고 production host global OOM을 유발하지 않는다.

9. 놓치기 쉬운 함정

  • VSZ가 크면 leak: untouched reservation, shared library, file mapping일 수 있다.
  • RSS 합=RAM 사용량: shared page가 여러 process에 중복 계산될 수 있다.
  • minor fault=무시 가능한 비용: fault storm은 CPU·zeroing·lock·TLB 비용을 만든다.
  • major fault=항상 swap: file I/O 등 다른 backing path도 있다.
  • malloc success=미래 touch 보장: overcommit에서는 분리될 수 있다.
  • exit 137=OOM: SIGKILL 결과일 뿐 원인은 timeout/manual kill일 수도 있다.
  • OOM victim=현재 RSS 최대 process: scope와 badness/oom_score_adj가 영향을 준다.
  • container RSS만 보면 limit 설명 완료: page cache·kernel memory·shared accounting과 memory.current를 봐야 한다.
  • production에서 stress로 확인: global OOM은 다른 workload를 죽일 수 있다. 격리된 limit이 필수다.

10. 30분 실패 실습: reserve→touch→ENOMEM

64MiB anonymous mapping을 reserve한 뒤 page마다 touch해 minor fault와 max RSS 변화를 관찰한다. Linux에서는 별도 child의 RLIMIT_AS를 128MiB로 낮춘 뒤 512MiB mmap을 시도해 system OOM 없이 ENOMEM을 재현하고, 다른 OS는 이 Linux-specific 단계만 명시적으로 skip한다.

set -eu
lab_dir="$(mktemp -d)"
trap 'rm -rf "$lab_dir"' EXIT

cat > "$lab_dir/memory_lab.c" <<'C'
#ifdef __APPLE__
#define _DARWIN_C_SOURCE
#else
#define _GNU_SOURCE
#endif
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

#ifndef MAP_ANONYMOUS
#define MAP_ANONYMOUS MAP_ANON
#endif

static long maxrss_kib(const struct rusage *u) {
#ifdef __APPLE__
  return u->ru_maxrss / 1024;
#else
  return u->ru_maxrss;
#endif
}

static void snapshot(const char *label, const struct rusage *base) {
  struct rusage now;
  if (getrusage(RUSAGE_SELF, &now) != 0) { perror("getrusage"); exit(2); }
  printf("%s minflt_delta=%ld majflt_delta=%ld maxrss_kib=%ld",
         label, now.ru_minflt - base->ru_minflt,
         now.ru_majflt - base->ru_majflt, maxrss_kib(&now));
#ifdef __linux__
  FILE *f = fopen("/proc/self/status", "r");
  char line[256];
  if (f) {
    while (fgets(line, sizeof(line), f)) {
      if (!strncmp(line, "VmSize:", 7) || !strncmp(line, "VmRSS:", 6)) {
        line[strcspn(line, "\n")] = '\0';
        printf(" %s", line);
      }
    }
    fclose(f);
  }
#endif
  putchar('\n');
}

int main(void) {
  long ps = sysconf(_SC_PAGESIZE);
  if (ps <= 0) return 3;
  size_t len = 64UL * 1024 * 1024;
  struct rusage base;
  if (getrusage(RUSAGE_SELF, &base) != 0) return 4;

  unsigned char *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
                          MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
  if (p == MAP_FAILED) { perror("mmap-reserve"); return 5; }
  snapshot("after_reserve", &base);

  for (size_t i = 0; i < len; i += (size_t)ps) p[i] = 0x5a;
  snapshot("after_touch", &base);
  if (p[0] != 0x5a || p[len - (size_t)ps] != 0x5a) return 6;
  if (munmap(p, len) != 0) { perror("munmap"); return 7; }

  pid_t child = fork();
  if (child < 0) { perror("fork"); return 8; }
  if (child == 0) {
#ifdef __linux__
    struct rlimit lim = {128UL * 1024 * 1024, 128UL * 1024 * 1024};
    if (setrlimit(RLIMIT_AS, &lim) != 0) _Exit(10);
    errno = 0;
    void *q = mmap(NULL, 512UL * 1024 * 1024, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (q == MAP_FAILED && errno == ENOMEM) _Exit(0);
    if (q != MAP_FAILED) munmap(q, 512UL * 1024 * 1024);
    _Exit(11);
#else
    _Exit(20); /* Linux RLIMIT_AS semantics test: explicit platform skip */
#endif
  }
  int status = 0;
  if (waitpid(child, &status, 0) != child) return 9;
  int enomem = WIFEXITED(status) && WEXITSTATUS(status) == 0;
  int skipped = WIFEXITED(status) && WEXITSTATUS(status) == 20;
  int ok = enomem || skipped;
  printf("page_size=%ld bytes_touched=%zu limit_enomem=%d platform_skip=%d child_ok=%d\n",
         ps, len, enomem, skipped, ok);
  return ok ? 0 : 12;
}

기대 형태

after_reserve minflt_delta=<작음> majflt_delta=0 maxrss_kib=<baseline> [Linux: VmSize↑ VmRSS≈]
after_touch minflt_delta=<약 64MiB/page_size> majflt_delta=0 maxrss_kib=<약 64MiB 증가> [Linux: VmRSS↑]
Linux:     page_size=<환경별> bytes_touched=67108864 limit_enomem=1 platform_skip=0 child_ok=1
non-Linux: page_size=<환경별> bytes_touched=67108864 limit_enomem=0 platform_skip=1 child_ok=1
  1. 0~10분: reserve와 touch 사이의 VSZ/RSS/fault 차이를 표로 기록한다.
  2. 10~20분: page size로 예상 fault 수를 계산하고 실제 minflt delta와 차이가 나는 이유를 적는다.
  3. 20~30분: child의 ENOMEM과 OOM kill의 차이, 각각의 rollback/restart 전략을 설명한다.

안전 장치: parent touch는 64MiB로 고정하고 즉시 munmap한다. Linux의 512MiB 요청은 RLIMIT_AS 128MiB인 child에서 allocation 단계에 실패시키며 page를 touch하지 않는다. swap·sysctl·oom_score_adj·global cgroup 설정을 변경하지 않고 system OOM을 유발하지 않는다.

12. 실패 시나리오: “Pod exit 137이니 memory leak”이라는 오진

배포 뒤 worker가 exit 137로 재시작했다. 팀은 RSS chart만 보고 leak으로 결론냈지만 allocator live bytes는 안정적이었다. 실제로는 batch 크기가 증가해 2GiB virtual mapping을 reserve하고 동시 first touch했으며, page cache와 native buffer까지 cgroup limit에 account됐다. memory PSI full이 먼저 상승한 뒤 memory.events의 max·oom·oom_kill이 증가했다.

대응: 재시작 폭주를 막고 cgroup event/peak/stat, process smaps_rollup, kernel/orchestrator reason, batch input을 보존한다. 재설계: streaming·bounded concurrency, preflight size limit, memory.high 기반 조기 backpressure, durable checkpoint, group-integrity가 필요하면 memory.oom.group을 검토한다.

13. 대기업 면접 질문 3개

  1. “VSZ는 큰데 RSS가 작은 이유를 설명해 보세요.”
    답변 포인트: VMA/address reservation과 resident page는 다르다. anonymous mmap은 demand allocation되어 first touch 전 VSZ만 증가할 수 있고, shared/file mappings도 VSZ에 포함된다. touch하면 minor fault, zero-fill/PTE install, RSS 증가가 나타날 수 있다.
  2. “RSS가 계속 증가하면 memory leak인가요?”
    답변 포인트: 가능성 중 하나일 뿐이다. RssAnon/File/Shmem, PSS, allocator live/retained bytes, cgroup memory.stat을 분해한다. live object 증가면 retention, stable live bytes+RSS 증가면 arena/fragmentation/cache/mmap/COW를 조사한다.
  3. “exit 137을 OOMKill로 확정할 수 있나요?”
    답변 포인트: 137은 SIGKILL 관례일 뿐이다. cgroup memory.events의 oom_kill delta, kernel log, orchestrator termination reason, timestamp를 결합한다. OOM이면 scope(global/cgroup), current/peak/stat, PSI 선행 pressure와 victim policy까지 설명한다.

14. 퀴즈·누적 리뷰

  1. 1GiB mmap 성공 직후 RAM 1GiB를 썼는가? 일반적으로 단정할 수 없다. mapping과 resident/touch를 분리한다.
  2. 두 process RSS 합이 physical 사용량보다 클 수 있는가? shared page가 각 RSS에 포함될 수 있어 가능하다.
  3. minor fault는 storage I/O가 필요한가? 아니다. major fault가 I/O activity를 요구한다.
  4. ENOMEM을 받으면 OOM killer가 실행된 것인가? 아니다. RLIMIT_AS나 commit/VMA 제한에서 caller에게 실패할 수 있다.
  5. Day 26 연결: file cache가 dirty하면 reclaim이 왜 늦어지는가? 먼저 writeback I/O가 필요하기 때문이다.
  6. Day 24 연결: first touch에서 무엇이 발생하는가? demand fault가 frame/zero-fill/COW/file load와 PTE install을 수행할 수 있다.
