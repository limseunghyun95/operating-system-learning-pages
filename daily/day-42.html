리뷰: “write 성공”과 “durable”의 차이

한 줄 요약: write() 성공은 kernel이 일부 또는 전부를 받아들였다는 뜻이고, runtime atomic visibility는 rename이, power-loss durability는 file fsync→rename→directory fsync와 storage flush 계약이 만든다. filesystem consistency와 application correctness도 별도의 복구 계층이다.

2. mental model: 여러 개의 “완료 도장”

택배 접수, 허브 도착, 수취인 전달은 모두 “완료”처럼 보이지만 보장 범위가 다르다. write return은 접수증, 다른 reader가 읽는 것은 허브 조회, fsync 성공은 storage 전달 확인, directory fsync는 주소록 변경 확인이다. 설계 문서와 API 응답에서 “성공” 대신 무엇이 어디까지 완료됐는지를 명시해야 한다.

4. 보장 사다리와 상태 전이

[0] caller memory only
  │ write_all 완료
[1] kernel accepted + current readers may see NEW
  │ fsync(temp) success
[2] temp data/필수 metadata durable
  │ same-filesystem rename
[3] target name atomically points to complete NEW at runtime
  │ fsync(parent directory) success
[4] NEW name→inode + content durable
  │ application checksum/version + business commit/reconcile
[5] application invariant durable
  │ replica/backup quorum·retention 확인
[6] node/storage loss에도 recoverable

낮은 단계의 성공은 높은 단계를 자동 포함하지 않는다.
API acknowledgment는 요구된 가장 높은 단계 뒤에만 반환한다.

6. CS·kernel deep dive

6.1 fd는 file 자체가 아니라 process-local handle이다

fd table entry는 open file description을 가리키고, OFD는 offset/status flag와 inode reference를 가진다. rename/unlink 뒤에도 열린 fd는 inode를 계속 참조할 수 있다. pathname 확인만으로 현재 writer가 어느 object에 쓰는지 단정하면 안 된다.

6.2 write return은 byte-level progress다

write는 최대 count만큼 쓰며 양수 n<count도 성공이다. caller는 n만큼만 pointer·offset을 전진한다. buffered write가 완료돼도 dirty page가 RAM에 있을 수 있고, delayed ENOSPC/EIO가 후속 write·fsync에서 나타날 수 있다.

6.3 visibility, atomicity, ordering, durability는 독립 축이다

다른 process가 page cache의 NEW를 읽는 것은 visibility다. rename은 target lookup의 runtime atomicity를 제공한다. fsync와 block flush/FUA는 persistence ordering을 만든다. 이 중 하나를 확인했다고 나머지를 주장할 수 없다.

6.4 file fsync와 directory fsync의 scope

file fsync는 data와 inode metadata를 storage로 동기화하지만 containing directory entry까지 자동으로 보장하지 않는다. 새 file 생성·rename·unlink의 durable namespace가 필요하면 관련 directory fd도 fsync한다.

6.5 journal은 multi-block metadata invariant를 보호한다

ext4/JBD2는 descriptor·metadata image·revoke·commit block을 journal에 쓰고 checksum-valid commit만 replay한다. checkpoint는 뒤에 home block을 갱신한다. metadata consistency를 빠르게 복구하지만 fsync 없는 user data나 business invariant를 보장하지 않는다.

6.6 block layer와 device는 write를 reorder할 수 있다

submission order만으로 persistence order가 되지 않는다. filesystem은 flush로 이전 write를 stable하게 만들고 FUA로 특정 write가 non-volatile해진 뒤 completion을 요구한다. device/controller가 flush contract를 지키지 않으면 상위 algorithm만으로 보장할 수 없다.

6.7 O_SYNC·O_DSYNC·fdatasync는 비용과 scope가 다르다

O_SYNC는 각 write마다 file-integrity completion, O_DSYNC는 data와 읽기에 필요한 metadata completion을 요구한다. fdatasync는 batching boundary를 caller가 선택한다. latency·throughput·RPO로 결정하고 실제 stack에서 측정한다.

6.8 close·fflush·O_DIRECT는 fsync의 동의어가 아니다

fflush는 user-space stdio buffer를 kernel로 보내며, close 성공은 disk persistence를 보장하지 않는다. O_DIRECT는 page cache 우회를 목표로 하며 partial error 뒤 range가 inconsistent할 수 있다. 기능 이름이 아니라 documented completion semantics를 선택한다.

6.9 local filesystem과 network filesystem의 failure semantics가 다르다

NFS는 server가 operation을 수행한 뒤 응답 전에 crash하면 client가 error를 받아도 rename이 이미 적용됐을 수 있다. timeout/error를 미실행으로 간주한 blind retry 대신 version·checksum reread와 reconciliation이 필요하다.

6.10 durability는 end-to-end contract다

application ack, kernel, filesystem, block layer, hypervisor, controller, media, replica가 각자 계약을 지켜야 한다. fsync가 성공해도 잘못 구성된 storage cache, snapshot 정책, replication acknowledgment가 end-to-end 목표를 깨뜨릴 수 있다.

8. 실무 best practice

  • API success를 accepted, visible, durable, replicated 중 하나로 명명하고 acknowledgment point를 sequence diagram에 표시한다.
  • whole-file update는 same-directory exclusive temp, write_all, checksum/version, file fsync, rename, directory fsync 순서를 library로 표준화한다.
  • record append는 length+checksum+generation을 넣고 torn tail을 detect/truncate/replay할 recovery rule을 갖춘다.
  • fsync p50/p95/p99, writeback EIO·ENOSPC·EDQUOT, dirty/writeback, block latency, journal pressure를 같은 dashboard와 trace에 연결한다.
  • group commit은 throughput 최적화가 아니라 명시적 RPO trade-off다. batch interval과 최대 loss를 사용자 계약에 포함한다.
  • filesystem type·mount option·volume type·controller cache·replication acknowledgment를 배포 inventory로 관리한다.
  • crash injection을 syscall 직후, file fsync 전후, rename 전후, directory fsync 전후에 배치하고 허용 상태를 자동 assertion한다.
  • startup은 checksum/generation으로 target·orphan temp를 검증하고, uncertain external result는 source of truth와 reconcile한다.
  • backup은 존재가 아니라 정기 restore 성공, checksum, retention, 접근권한까지 검증한다.

9. error handling·장애 진단 runbook

  1. 계약 확인: 실패한 API가 accepted·visible·durable·replicated 중 어디까지 약속했는지 먼저 고정한다.
  2. 대상 resolve: fd→inode, pathname→mount, filesystem type/options, block device·volume chain을 확인한다.
  3. return/error: short count, EINTR, EIO, ENOSPC, EDQUOT, EXDEV, timeout과 발생 단계(write/fsync/rename/dir fsync)를 기록한다.
  4. 격리: 반복 write가 손상을 확대하면 admission을 막고 read-only/failover를 검토한다. 원본 삭제·즉흥 fsck를 피한다.
  5. 증거: strace timing, application generation/checksum, mount info, kernel log, dirty/writeback, iostat/PSI, device health를 같은 시간축에 수집한다.
  6. 분류: partial syscall, delayed writeback, namespace publication, journal replay, device/cache, replication/application invariant 중 failure domain을 나눈다.
  7. 복구: snapshot/copy에서 journal replay 또는 offline fsck를 수행하고 application checksum·source of truth로 후속 reconcile한다.
  8. 재개: OLD/NEW invariant, no duplicate/missing business action, replica/backup 상태와 error counter 안정 후 traffic을 단계적으로 연다.
  9. 재발 방지: fault point test, acknowledgment 이동, capacity/quota headroom, flush contract 검증을 release gate로 만든다.

10. 놓치기 쉬운 함정

  • write ret>=0 = 전체 성공: 실제 반환 byte 수만큼만 progress다.
  • reader가 NEW를 봄 = reboot 뒤도 NEW: page cache visibility와 media durability는 다르다.
  • rename atomic = durable: file sync와 directory sync가 별도다.
  • journal = user data/DB transaction: filesystem metadata invariant가 application 의미를 모른다.
  • fsync error면 아무것도 적용 안 됨: 일부 persistence가 완료된 uncertain state일 수 있어 reconcile해야 한다.
  • read-only mount = write 없음: journal replay가 storage를 바꿀 수 있다.
  • O_DIRECT = durable: cache path와 persistence contract를 혼동한다.
  • backup 있음 = 복구 가능: restore를 검증하지 않은 backup은 가설이다.

11. 30분 실습: durability state machine 리뷰

각 step 뒤 crash를 삽입해 허용 state를 계산한다. 모델은 filesystem 구현 증명이 아니라 protocol invariant를 명시적으로 만드는 review 도구다.

python3 - <<'PY'
STEPS=('write_all','fsync_file','rename','fsync_dir','ack')

def crash_after(step):
    i=STEPS.index(step)
    visible='NEW' if i >= STEPS.index('rename') else 'OLD'
    durable=('NEW' if i >= STEPS.index('fsync_dir') else
             'OLD_OR_NEW' if i >= STEPS.index('rename') else 'OLD')
    acked=i >= STEPS.index('ack')
    return visible,durable,acked

expected={
 'write_all': ('OLD','OLD',False),
 'fsync_file':('OLD','OLD',False),
 'rename':    ('NEW','OLD_OR_NEW',False),
 'fsync_dir': ('NEW','NEW',False),
 'ack':       ('NEW','NEW',True),
}
for step in STEPS:
    got=crash_after(step)
    assert got == expected[step]
    print(f'{step:10} visible={got[0]:3} durable={got[1]:10} ack={got[2]}')

# 핵심: ack가 참이면 durable은 반드시 NEW
assert all(not crash_after(s)[2] or crash_after(s)[1]=='NEW' for s in STEPS)
PY
  1. 0~10분: 각 step의 visibility·durability·ack state를 말로 설명한다.
  2. 10~20분: directory fsync를 제거해 ack-before-durable assertion이 깨지는 test를 만든다.
  3. 20~30분: replication_ack와 application_commit 단계를 추가하고 RPO 0/1초 policy를 비교한다.

strace에서 기대하는 safe order는 모든 write return 누적=N→file fsync=0→rename=0→directory fsync=0→success response다. latency가 긴 syscall만 보지 말고 그 아래 block/device saturation과 위의 acknowledgment timing을 함께 본다.

13. 실패 시나리오: 성공 로그는 있는데 reboot 후 설정이 돌아왔다

service가 temp를 완성하고 rename한 직후 success log를 남겼지만 directory fsync 전에 host가 power loss됐다. 실행 중 reader는 NEW를 봤고 monitoring도 정상이라 배포 control plane은 성공으로 기록했다. reboot 뒤 pathname은 OLD로 복구되어 desired state와 drift가 생겼다. 대응은 success log/ack를 directory fsync 뒤로 옮기고 target에 generation+checksum을 넣어 startup reconciliation을 수행한 것이다. fsync p99 증가는 batch/RPO와 rollout concurrency로 조정했으며 durability 단계를 생략하지 않았다.
