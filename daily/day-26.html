Operating System · Day 26 / 63 · Virtual Memory

page cache, dirty page, writeback

한 줄 요약: buffered I/O의 write()는 보통 user buffer를 file의 page cache에 반영해 dirty로 만들고 먼저 끝날 수 있으며, writeback은 이를 storage로 내리는 비동기 흐름이다. 성공적으로 반환한 write와 crash 뒤 남는 durable write는 다른 계약이다.

1. 초보자 용어 사전

page cachefile content를 RAM에 보관하는 kernel cache. 일반 read/write와 file-backed mmap이 같은 cached data를 만나는 중심 계층이다.
folioLinux page cache가 memory를 관리하는 단위. base page 하나 이상을 묶을 수 있어 “항상 4KiB page 하나”로 단정하면 안 된다.
address_spaceinode 같은 cacheable object의 cached folio를 file offset index로 관리하고 Dirty/Writeback 상태와 filesystem operation을 연결하는 Linux kernel object.
buffered I/Oapplication과 storage 사이에 page cache를 사용하는 I/O. 대부분의 일반 file read/write가 해당한다.
cache hit / miss필요한 file range가 page cache에 있으면 hit, 없어 storage read가 필요하면 miss다.
dirty page/folioRAM의 cached content가 backing storage보다 새로워 아직 writeback이 필요한 상태. CPU cache line의 dirty bit와 구분한다.
writebackdirty cached data를 filesystem·block layer·device 방향으로 제출하고 완료를 추적하는 흐름.
dirty throttlingdirty data가 너무 쌓이면 writer가 무제한 RAM을 소비하지 못하도록 kernel이 write-producing task를 늦추는 backpressure.
reclaimmemory pressure에서 page를 재사용 가능하게 만드는 작업. clean file cache는 버리고 나중에 다시 읽을 수 있지만 dirty cache는 먼저 writeback해야 한다.
fsync / fdatasyncfile의 in-core 변경을 storage와 동기화하고 완료·오류를 기다리는 API. fdatasync는 이후 data retrieval에 불필요한 metadata를 생략할 수 있다.
fflushstdio user-space buffer를 kernel로 밀어내는 libc API. storage durability를 보장하지 않는다.
short write요청한 byte보다 적게 쓴 성공 반환. 남은 byte를 caller가 반복 처리해야 한다.
delayed errorwriteback 중 발견된 EIO/ENOSPC가 최초 write가 아니라 이후 write 또는 fsync에서 보고되는 현상.
volatile device cache전원 상실 시 사라질 수 있는 storage controller/device 내부 cache. 올바른 durability에는 filesystem의 flush/barrier와 device의 정직한 completion이 필요하다.

2. mental model: 주문서와 실제 창고 반영은 다른 사건

page cache를 매장의 작업대, storage를 외부 창고로 보자. 직원이 주문서의 변경을 작업대에 적어 둔 순간 application은 빠르게 돌아갈 수 있다. 그러나 창고 차량이 출발하고, 창고가 수령을 확인하기 전 정전이 나면 작업대의 변경은 사라질 수 있다.

  • write 반환: 변경 일부 또는 전부가 kernel이 관리하는 경계까지 받아들여졌다는 뜻이지, 항상 durable하다는 뜻은 아니다.
  • dirty: 작업대가 창고보다 최신이라 아직 배송해야 하는 상태다.
  • writeback: 배송을 제출·진행하는 상태다. 이때 application이 직접 기다리지 않을 수도 있다.
  • fsync 성공: 해당 file의 data와 필요한 metadata가 storage의 안정성 계약까지 도달했다고 filesystem/device가 보고한 사건이다.

5. CS·kernel·hardware deep dive

5.1 page cache의 key는 process VA가 아니라 file object와 offset이다

Linux의 address_space는 cacheable object의 folio를 index로 관리한다. 두 process가 같은 inode range를 read하거나 file-backed mmap하면 서로 다른 VA를 쓰더라도 같은 cached file data에 수렴할 수 있다. 따라서 page cache는 Day 25의 process-local address와 다른 전역 kernel 관점이다.

5.2 read hit는 storage I/O를 피하지만 memory copy까지 항상 피하는 것은 아니다

buffered read hit는 page cache에서 user buffer로 copy한다. file-backed mmap은 page fault 뒤 cached folio를 page table에 연결해 반복 read copy를 피할 수 있지만 fault, mapping 관리, lifetime와 random access trade-off가 있다. page cache hit와 CPU cache hit도 서로 다른 층이다.

5.3 write 성공은 byte count 계약부터 확인한다

regular file의 write는 요청보다 적은 양을 성공 반환할 수 있다. signal 뒤 일부만 썼거나 공간·quota·resource limit에 걸릴 수 있으므로 caller는 returned byte만큼 pointer/offset을 전진해 반복한다. 전부 page cache에 복사됐더라도 storage commit은 별도다.

5.4 dirty accounting은 RAM을 무한 write buffer로 쓰지 못하게 한다

Linux의 dirty_background_bytes/ratio는 background writeback 시작점이고, dirty_bytes/ratio는 write를 생성하는 process가 직접 writeback·throttling에 관여할 수 있는 상위 경계다. ratio의 기준은 단순 MemTotal이 아니라 free/reclaimable을 포함한 available memory 관점이다. bytes와 ratio counterpart는 동시에 독립 적용되는 값이 아니다.

5.5 storage가 느리면 write syscall latency가 뒤늦게 폭발한다

초기 burst는 RAM에 흡수돼 빠르지만 dirty production rate가 device writeback rate를 계속 넘으면 dirty limit에 접근한다. kernel은 writer를 늦춰 producer와 device 속도를 맞춘다. 그래서 “처음 30초는 빠르고 이후 write p99가 급상승”하는 장애는 CPU가 아니라 dirty throttling·device saturation일 수 있다.

5.6 PG_Dirty와 PG_Writeback은 겹치는 concurrency를 다룬다

filesystem writeback이 dirty 상태를 정리하고 writeback을 표시한 뒤 I/O를 제출한다. 그 사이 application이 같은 folio를 다시 수정하면 새 dirty 세대가 생길 수 있다. “I/O 하나 완료=그 page의 모든 미래 write도 clean”이 아니며, kernel은 tag와 locking으로 scan·redirty·completion을 조정한다.

5.7 writeback error는 원래 write와 시간·fd가 떨어져 보일 수 있다

page cache는 어느 file description이 각 byte를 dirty했는지 완벽히 보존하지 않는다. Linux generic error tracking은 mapping에 오류 sequence를 기록하고 관련 open file description의 이후 fsync에서 보고한다. 여러 writer가 있으면 자신의 write가 원인이 아니어도 EIO를 받을 수 있으므로 fsync 실패를 “재시도하면 끝”으로 취급하면 안 된다.

5.8 fsync, fdatasync, directory fsync는 범위가 다르다

fsync(file)은 data와 file metadata를, fdatasync는 data retrieval에 필요한 metadata를 동기화한다. 하지만 새 이름이나 rename 결과가 crash 뒤 directory에 남는지는 directory entry의 durability 문제다. crash-safe replace는 temp write→file fsync→rename→directory fsync처럼 namespace까지 포함해야 한다.

5.9 sync_file_range는 durability shortcut이 아니다

Linux 전용 sync_file_range는 range writeback 제어에 쓰이지만 metadata를 sync하지 않고 volatile disk cache flush도 보장하지 않는다. man-page도 portable data-integrity 용도로 위험하다고 경고한다. 데이터 보존 계약에는 fsync/fdatasync와 filesystem별 보장을 사용한다.

5.10 clean cache는 reclaim 자산, dirty cache는 I/O 부채다

clean file cache는 backing file에서 다시 만들 수 있어 pressure 시 discard하기 쉽다. dirty cache는 먼저 storage I/O가 필요하므로 memory pressure와 I/O pressure를 결합한다. writeback이 막히면 reclaim도 지연되고 allocation latency·direct reclaim·service p99까지 번질 수 있다.

5.11 device completion도 storage stack의 계약을 전제로 한다

filesystem은 ordering과 flush/FUA 같은 mechanism으로 device cache까지 제어하지만 hardware·virtualization·network storage가 completion을 잘못 보고하면 application의 fsync만으로 거짓말을 고칠 수 없다. 실제 durability는 application protocol, filesystem, block layer, controller power-loss protection의 end-to-end property다.

7. 실무 best practice

  • API 문서에 accepted, visible, durable, replicated의 성공 레벨을 분리하고 응답 시점을 명시한다.
  • write는 short count와 EINTR을 처리하는 loop로 감싸고 0 progress를 무한 retry하지 않는다.
  • durability가 필요한 transaction은 fsync/fdatasync의 return code까지 성공 조건으로 포함한다.
  • atomic file replace는 같은 filesystem의 temp file, file fsync, rename, directory fsync 순서를 사용하고 recovery test를 자동화한다.
  • batch/group commit으로 fsync 비용을 amortize하되 손실 가능 window와 tail latency SLO를 수치로 합의한다.
  • Dirty/Writeback, write latency, fsync latency, device queue/utilization, I/O error, memory pressure를 함께 모니터링한다.
  • producer rate를 bounded queue·backpressure로 제한한다. page cache를 무한 queue로 사용하지 않는다.
  • global dirty sysctl은 workload·RAM·device benchmark 없이 조정하지 않는다. container라면 cgroup writeback/accounting도 함께 본다.
  • O_DIRECT는 alignment·coherency·filesystem 지원을 포함한 별도 설계다. “cache가 나쁘다”는 이유만으로 켜지 않는다.

9. 놓치기 쉬운 함정

  • write 성공=durable: buffered write는 page cache에서 끝날 수 있다.
  • fflush=fsync: 전자는 libc buffer, 후자는 storage synchronization 계약이다.
  • file fsync=rename durable: directory entry에는 directory fsync가 필요할 수 있다.
  • close가 모든 오류를 해결: close 오류만으로 durability protocol을 대체하지 않는다. 명시적 fsync 결과를 확인한다.
  • Cached가 크면 leak: clean file cache는 reclaimable할 수 있어 MemAvailable과 pressure를 함께 본다.
  • drop_caches가 production fix: 원인·working set을 숨기고 latency를 악화할 수 있는 진단/benchmark 도구이지 치료제가 아니다.
  • sync_file_range=range fsync: metadata와 volatile device cache를 포함한 durability 보장이 아니다.
  • dirty page=dirty CPU cache line: filesystem backing과 RAM의 차이 vs CPU cache와 RAM의 차이라는 서로 다른 층이다.
  • dirty limit을 키우면 throughput 해결: burst를 늦출 뿐 stall 규모와 crash-loss window를 키울 수 있다.

10. 30분 실습: buffered write와 fsync 경계 관찰

16MiB temporary file을 full-write loop로 쓰고, Linux라면 /proc/meminfo의 Dirty/Writeback을 전후 관찰한 뒤 fsync latency와 content를 검증한다. global sysctl과 drop_caches는 건드리지 않는다.

set -eu
lab_dir="$(mktemp -d)"
trap 'rm -rf "$lab_dir"' EXIT

python3 - "$lab_dir/data.bin" <<'PY'
import errno
import os
import sys
import time

path = sys.argv[1]
chunk = b"P" * (1024 * 1024)
total = 16 * len(chunk)

def meminfo():
    try:
        rows = {}
        with open("/proc/meminfo", encoding="ascii") as f:
            for line in f:
                key, value = line.split(":", 1)
                if key in ("Cached", "Dirty", "Writeback"):
                    rows[key] = value.strip()
        return " ".join("{}={}".format(k, rows.get(k, "?"))
                        for k in ("Cached", "Dirty", "Writeback"))
    except FileNotFoundError:
        return "proc_meminfo=unavailable(non-Linux host)"

fd = os.open(path, os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o600)
try:
    print("before", meminfo())
    started = time.monotonic()
    written = 0
    while written < total:
        view = memoryview(chunk)
        while view:
            try:
                n = os.write(fd, view)
            except InterruptedError:
                continue
            if n == 0:
                raise RuntimeError("zero-progress write")
            view = view[n:]
            written += n
    write_ms = (time.monotonic() - started) * 1000
    print("after_write", meminfo())

    started = time.monotonic()
    os.fsync(fd)
    fsync_ms = (time.monotonic() - started) * 1000
    print("after_fsync", meminfo())
finally:
    os.close(fd)

st = os.stat(path)
with open(path, "rb") as f:
    first = f.read(1)
    f.seek(-1, os.SEEK_END)
    last = f.read(1)
assert st.st_size == total and first == b"P" and last == b"P"
print("bytes={} write_ms={:.3f} fsync_ms={:.3f} verified=1".format(
      total, write_ms, fsync_ms))

if os.path.exists("/dev/full"):
    full = os.open("/dev/full", os.O_WRONLY)
    try:
        try:
            os.write(full, b"failure-injection")
            raise AssertionError("/dev/full unexpectedly accepted write")
        except OSError as e:
            assert e.errno == errno.ENOSPC
            print("dev_full_errno=ENOSPC handled=1")
    finally:
        os.close(full)
PY

기대 형태

before Cached=<system value> Dirty=<value> Writeback=<value>
after_write ...
after_fsync ...
bytes=16777216 write_ms=<환경별> fsync_ms=<환경별> verified=1
dev_full_errno=ENOSPC handled=1   # Linux에서 /dev/full이 있을 때
  1. 0~10분: write loop가 short write·EINTR·zero progress를 어떻게 처리하는지 설명한다.
  2. 10~20분: write_ms와 fsync_ms 차이, Dirty/Writeback은 system-wide noisy 지표라는 점을 기록한다.
  3. 20~30분: /dev/full ENOSPC가 난 partial transaction을 publish하지 않는 rollback 설계를 적는다.

안전 장치: mktemp 전용 파일 16MiB만 만들고 종료 시 삭제한다. root 권한, sysctl 변경, drop_caches, raw device access를 사용하지 않는다. 결과 수치는 storage와 동시 workload에 따라 달라지므로 절대 성능 기준으로 쓰지 않는다.

12. 실패 시나리오: 로그 수집기는 빨랐지만 재부팅 뒤 40초가 사라짐

service가 append write 성공 직후 “저장 완료”를 응답했다. storage latency가 상승하자 RAM이 dirty burst를 흡수해 처음에는 정상처럼 보였고, 이후 dirty throttling으로 p99가 급등했다. 그 시점에 전원이 끊겨 아직 writeback되지 않은 tail이 사라졌다. 재기동 코드는 마지막 record의 partial frame도 정상으로 읽었다.

대응: 장애 중 Dirty/Writeback, fsync latency, device error, 마지막 durable sequence를 보존한다. 재설계: record length+checksum, batch fsync 뒤 durable watermark 응답, bounded ingest queue, torn-tail truncation recovery, ENOSPC/EIO 시 read-only·failover 전환을 사용한다.

13. 대기업 면접 질문 3개

  1. “write()가 성공했는데 데이터가 사라질 수 있나요?”
    답변 포인트: buffered write는 page cache의 dirty folio에서 반환할 수 있다. background writeback과 durability는 별도이며 short write·delayed EIO도 있다. transaction은 fsync/fdatasync 결과, rename이면 directory fsync까지 확인한다.
  2. “처음엔 빠른데 연속 write 후 latency가 급등하는 이유는?”
    답변 포인트: RAM이 burst를 흡수하지만 dirty production rate가 device drain rate를 넘으면 background threshold와 dirty throttling에 도달한다. Dirty/Writeback, write/fsync p99, device await/util, PSI로 증명하고 producer backpressure를 건다.
  3. “page cache가 메모리를 많이 쓰면 memory leak인가요?”
    답변 포인트: clean file cache는 reclaimable하고 성능 자산이다. MemAvailable, active/inactive file, pressure/reclaim을 봐야 한다. dirty cache는 writeback I/O가 필요한 부채이므로 Dirty 정체와 application allocation leak을 분리한다.

  1. fflush 뒤 전원 손실 안전한가? 아니다. libc buffer를 kernel로 보낼 뿐이다.
  2. clean page cache와 dirty page cache 중 reclaim이 쉬운 것은? backing에서 다시 읽을 수 있는 clean file cache다.
  3. fsync 실패 후 이미 보낸 성공 응답은 되돌릴 수 있는가? 없다. durable watermark 전에 성공을 약속한 protocol 결함이다.
  4. dirty_background_ratio의 분모는 단순 MemTotal인가? 아니다. kernel 문서의 available memory 관점을 사용한다.
  5. Day 25 연결: file-backed mmap store는 어디를 dirty하게 만드는가? 같은 file address_space의 cached folio이며 msync/fsync/lifetime 계약이 필요하다.
  6. Day 24 연결: mmap read miss는 무엇을 만들 수 있는가? page fault가 storage read와 page cache folio/PTE 연결을 유발할 수 있다.
