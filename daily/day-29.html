OPERATING SYSTEM · DAY 29 / 63 · ALLOCATION

allocator, arena, free list, fragmentation

한 줄 요약: allocator는 매 요청마다 kernel에서 page를 받지 않고 큰 영역을 arena로 관리하며, 크기별 free list에서 chunk를 재사용·분할·병합한다. 이 속도 최적화는 metadata·retention·내부/외부 fragmentation·arena contention이라는 비용을 만든다.

1. 초보자 용어 사전

allocatormalloc/new 요청에 block을 주고 free/delete된 block을 재사용하는 runtime/library 구성요소.
arenaallocator가 독립 관리하는 memory 영역과 metadata 집합. 여러 arena는 lock contention을 줄이지만 빈 공간을 고립시킬 수 있다.
chunk / blockallocator 관리 단위. user payload 외에 size·상태 metadata와 alignment padding이 붙을 수 있다.
free list / bin사용 가능한 chunk를 연결하거나 size class별로 분류한 자료구조.
size class요청을 8, 16, 32… 같은 bucket으로 반올림해 빠르게 재사용하는 분류.
split / coalesce큰 free chunk를 요청과 remainder로 나누는 동작 / 주소상 이웃한 free chunk를 합치는 동작.
internal fragmentation할당 chunk 내부에서 alignment·size class·metadata로 생기는 미사용 공간.
external fragmentation총 free byte는 충분하지만 작은 hole로 흩어져 큰 연속 요청을 만족하지 못하는 상태.
alignment주소를 특정 byte 배수에 맞추는 ABI/CPU 조건. padding을 만들 수 있다.
tcache작은 free chunk를 thread별로 보관해 lock 없이 재사용하는 cache. 속도 대신 retained memory가 늘 수 있다.
brk / mmapallocator가 OS에서 주소 공간을 얻는 대표 경로. 구현·크기 정책에 따라 선택한다.

2. mental model: 물류창고의 박스 재사용

매 주문마다 공장(kernel)에 박스를 새로 만들게 하면 느리다. allocator는 큰 창고(arena)를 빌려 반납된 박스(free chunk)를 크기별 선반(bin)에 둔다. 13짜리 물건을 16짜리 박스에 넣어 남는 3은 내부 fragmentation, 빈 공간 합은 48인데 16짜리 hole 셋으로 흩어져 24짜리를 못 넣는 것은 외부 fragmentation이다.

3. architecture: malloc fast path와 slow path

application malloc(request)
  │ overflow 검사 → alignment/metadata 포함 size class 계산
  ▼
thread cache ─ hit → pop chunk → user pointer
  │ miss
  ▼
arena 선택/lock → segregated free lists 탐색
  ├─ exact chunk → unlink
  ├─ larger chunk → split → remainder 재등록
  └─ 없음 → arena extend 또는 large mmap → user pointer

free(pointer)
  → metadata/owner 확인 → tcache/bin 등록 → 인접 free면 coalesce
  → top/extent 반환 조건이면 brk 축소·munmap·madvise 가능

POSIX가 보장하는 것은 API 계약이며 arena/bin/tcache는 구현 세부다.

4. chunk 상태 전이

[OS/arena free extent] ─ split ─→ [ALLOCATED: metadata|payload|padding]
                                    │ free exactly once
                                    ▼
[OS 반환] ← trim/unmap 조건 ← [CACHED/FREE] ─ adjacent free → [COALESCED]
                                │ reuse
                                └──────────────────────────→ [ALLOCATED]

금지 전이: FREE 후 접근(use-after-free), 두 번 free, payload overflow로 metadata 훼손,
realloc 실패 결과를 원본 pointer에 덮어써 allocation을 잃는 것. 모두 undefined behavior다.

5. CS·allocator·kernel deep dive

5.1 왜 malloc마다 syscall하지 않는가

syscall, VMA 변경, page-table 준비와 synchronization은 작은 object보다 비쌀 수 있다. allocator는 OS에서 큰 단위로 확보해 user-space metadata만으로 대부분 요청을 처리한다. malloc이 kernel 진입 없이 끝나도 first touch page fault는 나중에 발생할 수 있다.

5.2 size class는 탐색 시간을 공간으로 산다

제한된 class는 빠른 pop/push와 높은 재사용률을 주지만 request 17을 class 32로 반올림하는 내부 낭비를 만든다. 요청 크기와 allocator usable size를 구분해야 한다.

5.3 fit policy는 시간·공간·locality trade-off다

first-fit은 탐색이 짧지만 앞쪽에 hole을 남길 수 있고 best-fit은 더 탐색하며 tiny remainder를 만들 수 있다. segregated fit, buddy, slab은 workload의 size/lifetime 분포에 맞춰 다른 균형을 택한다.

5.4 coalescing에도 metadata가 필요하다

앞뒤 chunk의 size/free 상태를 알아야 병합할 수 있다. boundary tag 같은 metadata는 빠른 이웃 탐색을 주지만 공간을 쓰고 overflow 공격면이 된다. integrity check가 있어도 memory-safety bug가 안전해지는 것은 아니다.

5.5 arena는 contention을 fragmentation으로 교환한다

global heap lock 하나는 multicore에서 병목이다. 여러 arena와 tcache는 hot path lock 경쟁을 줄이지만 arena마다 free 공간과 cache가 고립된다. arena 수를 줄이면 RSS는 낮아져도 allocation p99가 나빠질 수 있다.

5.6 large allocation은 별도 mapping이 유리할 수 있다

큰 object를 작은 chunk와 섞지 않고 mmap extent로 분리하면 free 시 독립 unmap하기 쉽다. 대신 page alignment 낭비, VMA 수, syscall·TLB 비용이 늘 수 있다. threshold는 구현·버전별 정책이다.

5.7 total free와 largest free는 다르다

외부 fragmentation은 total_free보다 largest_free와 요청 크기의 관계다. 실제 allocator는 새 extent를 얻어 성공할 수 있지만 RSS/VA가 늘고 기존 hole은 남는다.

5.8 free와 OS 반환은 다른 계약이다

free는 allocator 재사용 가능 상태로 돌린다. OS 반환은 page/extent 경계, top chunk, decay/trim 정책에 달렸다. malloc_trim과 tunable은 correctness API가 아닌 구현별 최적화 수단이다.

5.9 lifetime interleaving이 fragmentation을 만든다

long-lived 작은 object 사이에 short-lived 큰 object가 반복되면 page 전체 반환이 막힌다. 평균 크기만 보지 말고 size×lifetime×thread 분포와 cross-thread free를 profile한다.

7. 실무 best practice

  • allocation rate, live bytes, size/lifetime/thread 분포, allocator retained, RSS를 같은 시간축에 둔다.
  • pool·cache에는 byte/count bound를 두고 임시 allocation은 batching/region/stack 가능성을 검토한다.
  • allocator 교체와 arena/tcache/decay 조정은 canary에서 throughput·p99·CPU·RSS를 함께 비교한다.
  • size multiplication overflow를 먼저 검사하고 C에서는 calloc/reallocarray 같은 checked 경로를 고려한다.
  • realloc 결과는 임시 pointer에 받고 성공했을 때만 원본을 교체한다.
  • ENOMEM은 partial rollback, backpressure, bounded retry, graceful degradation으로 처리한다.
  • ASan/LSan·fuzzing을 CI/staging에 사용하고 production overhead와 platform 조건을 확인한다.

8. error handling runbook

  1. NULL/ENOMEM: request size·overflow·limit을 기록하고 partial state를 rollback한다.
  2. realloc 실패: 원본 pointer를 보존하고 cleanup 또는 작은 대체 경로로 간다.
  3. live 안정·RSS 증가: arena/bin/size class, allocator retained, thread 수, PSS를 분해한다.
  4. heap corruption: traffic 격리·rollback 후 core/ASan stack을 보존한다. 손상 process를 계속 쓰지 않는다.
  5. allocation p99 증가: arena mutex, cache miss, syscall/fault, profile overhead를 나눠 한 변수씩 canary한다.

9. 놓치기 쉬운 함정

  • free 합이 충분하면 성공: largest contiguous chunk가 작을 수 있다.
  • free 즉시 RSS 감소: allocator 보관과 OS 반환은 별개다.
  • arena가 많을수록 빠름: contention은 줄지만 memory overhead가 커진다.
  • best-fit이면 해결: tiny remainder와 lifetime 문제가 남는다.
  • realloc을 원본에 바로 대입: 실패 시 pointer를 잃는다.
  • allocator metric을 구현 간 동일시: allocated/active/resident/retained 정의가 다르다.
  • tunable fleet 즉시 적용: 안정 ABI가 아니며 latency 회귀가 가능하다.

10. 30분 실습: split·hole·coalesce simulator

64-unit arena에 A16, B8, C16, D8을 할당한다. A와 C를 free하면 총 free 48, largest 16이라 request 24가 실패한다. B를 free해 coalesce하면 largest 40이 되어 성공한다.

set -eu
lab_dir="$(mktemp -d)"; trap 'rm -rf "$lab_dir"' EXIT
cat > "$lab_dir/lab.py" <<'PY'
class Arena:
    def __init__(self, size): self.blocks = [[0, size, None]]
    def alloc(self, owner, need):
        for i, (start, size, used) in enumerate(self.blocks):
            if used is None and size >= need:
                self.blocks[i] = [start, need, owner]
                if size > need: self.blocks.insert(i+1,[start+need,size-need,None])
                return start
        return None
    def free(self, owner):
        for b in self.blocks:
            if b[2] == owner: b[2] = None; self.coalesce(); return
        raise KeyError(owner)
    def coalesce(self):
        out=[]
        for b in self.blocks:
            if out and out[-1][2] is None and b[2] is None: out[-1][1]+=b[1]
            else: out.append(b[:])
        self.blocks=out
    def stats(self):
        holes=[size for _,size,used in self.blocks if used is None]
        return sum(holes),max(holes,default=0),len(holes)
    def show(self):
        return " | ".join(f"{s}:{n}:{o or 'FREE'}" for s,n,o in self.blocks)
a=Arena(64)
for owner,size in [("A",16),("B",8),("C",16),("D",8)]: assert a.alloc(owner,size) is not None
a.free("A"); a.free("C")
assert a.stats()==(48,16,3) and a.alloc("X",24) is None
print("before=FAIL total_free=48 largest_free=16",a.show())
a.free("B")
assert a.stats()==(56,40,2) and a.alloc("X",24) is not None
print("after=SUCCESS",a.show())
requests=[1,9,17,33]; classes=[8,16,32,64]
print("internal_requested=60 reserved=120 waste=60")
assert sum(requests)==60 and sum(classes)==120
PY
python3 "$lab_dir/lab.py"
  1. 0~10분: block map과 split 주소를 손으로 그린다.
  2. 10~20분: first-fit을 best-fit으로 바꿔 hole 분포를 비교한다.
  3. 20~30분: arena를 둘로 나누면 free 공간이 왜 합쳐지지 않는지 latency/RSS trade-off로 설명한다.

모델 한계: 실제 glibc·jemalloc 구조를 복제한 것이 아니라 split/coalesce와 fragmentation 불변식을 이해하는 결정적 모델이다.

12. 실패 시나리오

live heap은 2GiB인데 retained가 6GiB인 multi-threaded service에서 arena 수를 1로 줄이자 RSS는 감소했지만 arena mutex contention으로 allocation p99와 request latency가 급증했다. 즉시 rollback하고 size×lifetime×thread profile을 수집한다. buffer pool에 byte bound를 두고 worker 수를 검토한 뒤 arena 후보를 canary해 RSS, mutex wait, CPU, p99를 함께 비교한다.

13. 대기업 면접 질문 3개

  1. malloc은 어떻게 빠른가?
    답변 포인트: arena 확보, size class, tcache/bin fast path, split/coalesce, 부족 시 brk/mmap slow path. POSIX 계약과 구현 세부를 구분한다.
  2. internal/external fragmentation 차이는?
    답변 포인트: chunk 내부 round-up 대 free hole 분산. requested/usable과 total/largest free로 측정한다.
  3. arena를 늘리는 trade-off는?
    답변 포인트: lock contention 감소 대 metadata/cache/free-space 고립, RSS 증가. canary에서 p99·CPU·RSS를 함께 본다.

14. 퀴즈·누적 리뷰

  1. total free 1GiB인데 64MiB 요청이 실패할 수 있는가? largest suitable chunk가 작고 새 extent도 못 얻으면 가능하다.
  2. 17-byte 요청에 32-byte class면? 최소 15-byte internal fragmentation이다.
  3. free는 munmap과 같은가? 아니다. allocator 재사용과 OS 반환은 별도 전이다.
  4. Day 28 연결: live 안정·RSS 증가 원인에 arena/tcache retention과 fragmentation을 추가한다.
  5. Day 25 연결: OS 확보 경로는 brk 기반 heap과 mmap이며 구현 정책에 따라 다르다.
