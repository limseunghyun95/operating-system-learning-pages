Operating System · Day 17 / 63 · Concurrency

spinlock, blocking lock, futex의 역할 경계

한 줄 요약 — spin은 남은 대기가 park·wake·schedule보다 짧고 lock holder가 곧 실행될 때만 이득이며, blocking lock은 CPU를 scheduler에 돌려준다. futex는 둘 중 하나의 lock이 아니라 user-space atomic 상태와 kernel sleep/wake를 연결하는 저수준 mechanism이다.

1. 초보자 용어 사전

busy waiting기다리는 동안 sleep하지 않고 조건을 반복 확인해 CPU instruction을 계속 실행하는 방식.
spinlocklock이 풀릴 때까지 CPU에서 spinning하는 lock. sleep할 수 없는 kernel context나 매우 짧고 예측 가능한 임계 구역에서 사용한다.
blocking lock획득할 수 없으면 waiter를 sleep/blocked 상태로 보내 CPU를 다른 task에 양보할 수 있는 lock. pthread mutex와 Linux kernel mutex가 대표적이다.
futexfast userspace mutex. Linux에서 32-bit user-space word를 기준으로 wait/wake를 요청하는 syscall 인터페이스이며, 보통 pthread library 같은 구현자가 사용한다.
contention여러 execution context가 같은 lock/resource를 동시에 원해 경쟁하는 상태.
critical section공유 invariant를 보호하기 위해 lock을 가진 동안 실행하는 코드 구간.
park / unparkthread를 runnable queue에서 빼 재우고, 사건이 생기면 다시 runnable로 만드는 runtime/kernel 동작.
oversubscriptionrunnable thread 수가 실제 CPU 수보다 많은 상태. spinner가 CPU를 점유해 lock owner 실행을 늦출 수 있다.
cache-line bouncing여러 core가 같은 cache line을 write/RMW하려 해 exclusive ownership이 core 사이를 계속 이동하는 현상.
adaptive spinning항상 spin 또는 항상 sleep하지 않고 owner 실행 여부·과거 hold time·대기열 등을 보고 잠깐 spin한 뒤 block하는 hybrid 전략.
lock convoy긴 lock holder 뒤에 waiter가 줄을 서며 wake·획득·다시 sleep이 연쇄되어 throughput과 tail latency가 무너지는 현상.

2. mental model: 계산대 앞에서 서 있을까, 호출표를 받을까

spin: 앞사람이 카드 한 번만 찍으면 끝난다고 확실할 때 계산대 앞에서 기다린다. 자리를 떠났다 돌아오는 비용은 없지만 기다리는 동안 통로와 CPU를 점유한다.

block: 앞사람 일이 길 수 있으면 호출표를 받고 앉는다. park/wake 비용은 들지만 CPU는 다른 유용한 일을 한다.

futex: 계산대가 비었는지는 매장 안의 atomic 표지판으로 먼저 본다. 실제로 기다려야 할 때만 안내 데스크인 kernel에 “표지판이 아직 이 값이면 재워 달라”고 요청한다.

핵심 질문은 lock 이름이 아니라 “owner가 현재 실행 중인가, 남은 hold time은 얼마인가, CPU가 남는가, 이 context는 sleep 가능한가?”다.

5. CS·kernel·hardware deep dive

5.1 spinlock은 “context switch가 없는 빠른 mutex”가 아니다

spinlock은 wait를 CPU cycle로 지불한다. owner가 다른 core에서 곧 unlock하면 park/wake를 피할 수 있지만, owner가 preempt되거나 page fault·I/O를 만나면 waiter는 진전 없이 CPU를 태운다. 단일 CPU에서 owner를 실행시키지 못하는 spinner는 특히 치명적이다.

그래서 kernel spinlock critical section은 매우 짧고 bounded해야 하며 sleep 가능한 operation을 넣지 않는다. user-space application은 scheduler와 runtime 정보를 제한적으로만 알아 대개 검증된 pthread mutex를 기본값으로 삼는다.

5.2 Linux kernel context가 lock 종류를 제한한다

sleeping lock은 preemptible task context에서 사용한다. interrupt/atomic context는 schedule할 수 없으므로 blocking mutex를 잡을 수 없다. non-PREEMPT_RT의 spinning lock은 preemption을 암묵적으로 disable하며, interrupt handler와 공유하면 spin_lock_irqsave 같은 올바른 variant가 필요하다.

같은 CPU에서 lock을 가진 code가 interrupt되고 handler가 같은 lock을 spin하면 owner code가 재개되지 못해 self-deadlock이다. 단, PREEMPT_RT에서는 spinlock_t semantics가 sleeping rtmutex 기반으로 달라질 수 있고 raw_spinlock_t가 실제 spinning semantics를 유지하므로 kernel configuration까지 답해야 한다.

5.3 atomic RMW와 cache coherence 비용

test-and-set spinner가 매 loop마다 atomic write/RMW를 하면 lock cache line의 exclusive ownership이 core 사이를 왕복한다. core 수가 늘수록 useful work가 아니라 coherence invalidation에 interconnect bandwidth를 쓴다.

test-test-and-set은 먼저 read로 관찰하고 풀릴 때만 RMW하며, exponential backoff와 CPU의 pause/yield hint는 pressure를 줄인다. MCS 같은 queue lock은 각 waiter가 local node를 spin해 cache-line bouncing과 unfairness를 낮춘다. 하지만 어느 기법도 긴 hold time이나 descheduled owner를 해결하지는 않는다.

5.4 memory ordering도 lock 계약의 일부다

lock 획득은 acquire, 해제는 release ordering을 제공해야 이전 owner의 critical-section write를 다음 owner가 관찰한다. 단순히 atomic flag 값만 바뀐다고 protected data의 publication이 자동 보장되지는 않는다.

직접 spinlock을 구현할 때 C11 atomic_flag_test_and_set(..., memory_order_acquire)와 atomic_flag_clear(..., memory_order_release) 같은 language memory-model 계약이 필요한 이유다. 실무에서는 검증된 library primitive를 우선한다.

5.5 Linux mutex는 이미 hybrid다

kernel mutex 공식 설계는 세 경로를 설명한다. fastpath는 owner를 atomic cmpxchg해 uncontended lock을 얻고, midpath는 owner가 실행 중이고 reschedule 조건이 없을 때 optimistic spinning하며, slowpath는 wait queue에 들어가 sleep한다.

즉 “spinlock 대 mutex”를 이분법으로만 보면 실제 구현을 놓친다. 좋은 blocking lock도 짧은 경쟁은 user space 또는 optimistic spin으로 흡수하고, 길어지면 scheduler에 넘긴다.

5.6 futex는 lock도, 자동 fairness 보장도 아니다

futex word는 모든 64-bit platform에서도 32-bit이며 실제 lock state는 user space가 정의한다. kernel은 특정 address의 word가 expected value와 같을 때만 atomic하게 waiter를 재우고, wake 요청으로 일부 waiter를 runnable하게 만든다.

kernel이 application의 owner, recursion, predicate, fairness를 일반적으로 관리하는 것이 아니다. pthread mutex 구현이 owner bits와 waiter state를 설계하고 futex를 slow-path primitive로 사용한다. PI futex처럼 user/kernel value policy가 추가된 별도 operation은 예외적으로 더 강한 계약을 가진다.

5.7 compare-and-block이 lost wake를 닫는다

waiter가 user-space에서 “locked”를 본 뒤 syscall에 들어가기 전에 unlock이 일어날 수 있다. kernel이 무조건 sleep시키면 이미 지나간 wake를 놓친다.

FUTEX_WAIT는 word load, expected 비교, sleep 시작을 같은 futex word의 다른 operation과 원자적으로 정렬한다. 값이 이미 바뀌면 EAGAIN으로 즉시 돌아와 user-space protocol을 재검사한다. 0으로 정상 wake돼도 spurious wake일 수 있어 상태 loop가 필요하다.

7. 실무 best practice

  1. 일반 user-space는 pthread mutex부터 시작한다. 직접 futex/spinlock 구현은 owner death, cancellation, fairness, timeout, memory ordering을 모두 책임질 때만 한다.
  2. critical section에서 allocation·I/O·logging·callback을 빼낸다. unpredictable stall이 spin budget과 tail latency를 동시에 무너뜨린다.
  3. 평균이 아니라 분포를 계측한다. lock hold/wait p50·p95·p99·max, contention ratio, waiter count, timeout, CPU와 context switch를 함께 본다.
  4. adaptive spin에 상한과 탈출 조건을 둔다. owner가 not-running, need_resched, CPU quota/throttling, spin budget 소진이면 즉시 park한다.
  5. sharding과 ownership으로 공유를 줄인다. lock 알고리즘 최적화보다 per-CPU/per-shard state, message passing, immutable snapshot이 더 큰 효과를 낼 수 있다.
  6. wake-one을 기본으로 검토한다. 한 resource에 모든 waiter를 깨우면 thundering herd와 cache-line storm이 생긴다. correctness상 모두 깨워야 하는 사건만 broadcast한다.
  7. benchmark에 oversubscription과 NUMA를 포함한다. idle 2-core microbenchmark 승자를 production 기본값으로 일반화하지 않는다.

9. 놓치기 쉬운 함정

  • “임계 구역 코드가 세 줄”이라는 이유만으로 실제 hold time도 짧다고 가정한다. cache miss, page fault, allocator가 숨어 있다.
  • spinner와 owner가 같은 CPU quota 또는 single core를 경쟁해 owner가 unlock할 시간을 빼앗는다.
  • test-and-set loop가 lock cache line에 write storm을 일으키는데 thread 수만 늘려 benchmark한다.
  • futex syscall 횟수가 적다는 이유로 contention이 없다고 결론 낸다. user-space spinning 비용은 syscall trace에 안 보인다.
  • futex wake가 ownership을 넘긴다고 생각한다. 깨어난 waiter는 다른 thread와 lock word를 다시 경쟁한다.
  • 0 return을 predicate 성립으로 믿는다. FUTEX_WAIT는 spurious wake가 가능하다.
  • kernel spinlock_t 의미를 PREEMPT_RT와 일반 kernel에서 같다고 설명한다.
  • microbenchmark의 평균 throughput만 비교하고 CPU time, tail wait, fairness, context switch를 측정하지 않는다.

10. 30분 실습: 짧은 임계 구역과 긴 임계 구역 비교

교육용 C11 atomic spinlock과 pthread mutex를 같은 counter workload로 비교한다. 정확성은 모두 같아야 하며 성능 순위는 machine마다 달라질 수 있다. 특히 lock 안에 100µs stall을 넣었을 때 spin 횟수와 CPU 낭비를 관찰한다.

LAB_DIR=$(mktemp -d)
trap 'rm -rf "$LAB_DIR"' EXIT
cat >"$LAB_DIR/lock_lab.c" <<'C'
#define _POSIX_C_SOURCE 200809L
#include <errno.h>
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

enum { THREADS = 4 };
static atomic_flag spin = ATOMIC_FLAG_INIT;
static pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
static atomic_ulong total_spins;
static long counter;
static int use_spin, hold_us, iterations;

static void die(const char *what, int rc) {
  fprintf(stderr, "%s: %d\n", what, rc);
  exit(2);
}

static unsigned long spin_lock(void) {
  unsigned long tries = 0;
  while (atomic_flag_test_and_set_explicit(&spin, memory_order_acquire)) {
    tries++;
    if ((tries & 1023UL) == 0) sched_yield();
  }
  return tries;
}

static void spin_unlock(void) {
  atomic_flag_clear_explicit(&spin, memory_order_release);
}

static void hold_if_requested(void) {
  if (hold_us == 0) return;
  struct timespec ts = { .tv_sec = 0, .tv_nsec = hold_us * 1000L };
  while (nanosleep(&ts, &ts) != 0) {
    if (errno != EINTR) { perror("nanosleep"); exit(2); }
  }
}

static void *worker(void *unused) {
  (void)unused;
  unsigned long local_spins = 0;
  for (int i = 0; i < iterations; i++) {
    if (use_spin) {
      local_spins += spin_lock();
      counter++;
      hold_if_requested();
      spin_unlock();
    } else {
      int rc = pthread_mutex_lock(&mutex);
      if (rc != 0) die("mutex lock", rc);
      counter++;
      hold_if_requested();
      rc = pthread_mutex_unlock(&mutex);
      if (rc != 0) die("mutex unlock", rc);
    }
  }
  atomic_fetch_add_explicit(&total_spins, local_spins, memory_order_relaxed);
  return NULL;
}

static double seconds(struct timespec a, struct timespec b) {
  return (b.tv_sec - a.tv_sec) + (b.tv_nsec - a.tv_nsec) / 1e9;
}

int main(int argc, char **argv) {
  if (argc != 3 || (strcmp(argv[1], "spin") && strcmp(argv[1], "mutex"))) {
    fprintf(stderr, "usage: %s spin|mutex HOLD_US\n", argv[0]);
    return 2;
  }
  use_spin = !strcmp(argv[1], "spin");
  hold_us = atoi(argv[2]);
  iterations = hold_us ? 1000 : 50000;
  pthread_t threads[THREADS];
  struct timespec start, end;
  clock_gettime(CLOCK_MONOTONIC, &start);
  for (int i = 0; i < THREADS; i++) {
    int rc = pthread_create(&threads[i], NULL, worker, NULL);
    if (rc != 0) die("pthread_create", rc);
  }
  for (int i = 0; i < THREADS; i++) {
    int rc = pthread_join(threads[i], NULL);
    if (rc != 0) die("pthread_join", rc);
  }
  clock_gettime(CLOCK_MONOTONIC, &end);
  long expected = (long)THREADS * iterations;
  printf("mode=%s hold_us=%d counter=%ld expected=%ld seconds=%.3f spins=%lu\n",
         argv[1], hold_us, counter, expected, seconds(start, end),
         atomic_load_explicit(&total_spins, memory_order_relaxed));
  return counter == expected ? 0 : 1;
}
C
cc -std=c11 -O2 -Wall -Wextra -pthread "$LAB_DIR/lock_lab.c" -o "$LAB_DIR/lock_lab"
for hold in 0 100; do
  for mode in mutex spin; do
    /usr/bin/time -p "$LAB_DIR/lock_lab" "$mode" "$hold"
  done
done

# Linux에서만: blocking slow path가 보이는지 확인
if command -v strace >/dev/null 2>&1; then
  strace -f -e futex -c "$LAB_DIR/lock_lab" mutex 100
fi
  1. 10분: 네 실행에서 counter==expected를 먼저 확인한다. 성능보다 correctness가 선행한다.
  2. 10분: hold_us=0과 100에서 wall/user time과 spin 횟수를 표로 만든다. 장시간 spin이 CPU budget을 어떻게 쓰는지 설명한다.
  3. 10분: THREADS를 CPU 수의 2배로 바꾸어 oversubscription을 재측정한다. Linux라면 strace의 futex call은 상위 mutex slow path의 증거이지 전체 contention cost가 아님을 기록한다.

주의: 이 atomic_flag lock은 학습용이다. bounded backoff, cancellation, owner validation, fairness, robust recovery가 없어 production에 복사하지 않는다.

11. 실패 시나리오: latency 개선 spin이 장애를 키웠다

변경: queue lock의 99% 획득이 짧다는 microbenchmark를 보고 waiter가 최대 1ms spin하도록 배포했다.

사건: CPU quota가 걸린 container에서 lock owner가 deschedule됐다. 수십 spinner가 quota를 먼저 소진해 owner 실행과 unlock을 늦췄고, throughput은 0에 가까워지며 p99가 폭증했다.

증거: runnable thread와 CPU throttling 증가, off-CPU owner stack, on-CPU atomic retry hotspot, lock wait/hold max, context switch와 futex call 변화를 같은 배포 시점에 맞춘다.

즉시 완화: adaptive spin budget을 0 또는 이전값으로 rollback하고 admission control로 waiter 수를 제한한다. process 전체 restart 전에 thread dump와 profile을 보존한다.

영구 수정: owner-running/need-resched 탈출, CPU quota 환경 benchmark, hold-time max 경보, critical-section I/O 제거와 sharding을 적용한다.

12. 대기업 면접 질문 3개

  1. “spinlock과 mutex 중 무엇이 더 빠른가요?”
    답변 포인트: 절대 순위가 없다. remaining hold time과 park/wake/schedule 비용, owner 실행 여부, CPU 여유, contention과 topology를 비교한다. spin은 context switch를 피하지만 CPU·coherence를 쓰고, block은 scheduling 비용 대신 CPU를 양보한다. 실제 mutex는 adaptive hybrid일 수 있다.
  2. “futex는 mutex와 무엇이 다른가요?”
    답변 포인트: mutex는 ownership과 mutual-exclusion API/contract이고 futex는 Linux wait/wake mechanism이다. lock word와 fast path는 user space가 관리하며 kernel은 expected-value compare-and-block와 wake를 제공한다. uncontended mutex는 futex syscall 없이 끝날 수 있다.
  3. “kernel spinlock을 잡은 채 sleep하면 왜 안 되나요?”
    답변 포인트: non-RT spinning lock은 preemption/interrupt context와 결합되고 waiter는 owner가 곧 실행해 unlock한다고 가정한다. owner가 schedule-out되면 progress와 latency가 깨지며 atomic context에서 sleeping 자체가 불법이다. IRQ 공유라면 same-CPU interrupt self-deadlock 방지 variant가 필요하고 PREEMPT_RT의 spinlock_t 차이도 언급한다.

13. 퀴즈·누적 리뷰

  1. lock holder가 다른 core에서 RUNNING인 경우와 같은 single CPU에서 preempt된 경우, spin의 기대 이득은 왜 반대인가?
  2. FUTEX_WAIT가 expected와 달라 EAGAIN을 반환하는 것이 lost wake를 어떻게 막는가?
  3. futex syscall이 0건이어도 lock contention 또는 synchronization 비용이 존재할 수 있는 이유는?
  4. Day 16 복습: condition variable wait의 atomic unlock-and-wait와 futex compare-and-block은 어느 race를 닫는가?
  5. Day 11 복습: NUMA와 CPU affinity가 spinlock cache-line bouncing과 owner progress에 어떤 영향을 주는가?

정답 핵심: spin은 owner가 실제 실행돼야 progress한다. EAGAIN은 이미 바뀐 상태에서 sleep 진입을 거부한다. user-space atomic retry는 syscall trace 밖에 있다. 두 atomic transition은 “확인 후 sleep 전”의 lost-wakeup window를 닫는다.
