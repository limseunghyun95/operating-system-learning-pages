TLB, multi-level page table, page walk

한 줄 요약: TLB는 page-table 번역 결과를 CPU 가까이에 캐시하고, miss가 나면 MMU가 계층형 table을 walk하며, mapping 변경 뒤에는 모든 관련 CPU의 stale translation을 무효화해야 정확성과 보안을 지킬 수 있다.

1. 초보자 용어 사전

TLBTranslation Lookaside Buffer. virtual page→physical frame 번역과 권한을 저장하는 CPU의 작고 빠른 cache다. data 자체를 저장하는 L1 data cache와 다르다.
TLB hit / miss현재 VPN의 유효한 translation이 TLB에 있으면 hit, 없으면 miss다. miss는 보통 hardware가 처리하며 그 자체가 page fault는 아니다.
TLB reachTLB가 동시에 덮을 수 있는 memory 범위의 근사치. 단순 모델은 entry 수×page size지만 page-size별 TLB, associativity와 workload 분포도 영향을 준다.
page walkpage-table root에서 virtual address의 level별 index를 사용해 leaf PTE 또는 huge-page entry를 찾는 절차다.
page-walk cacheupper-level paging-structure 정보를 CPU가 선택적으로 캐시하는 구조. 구현은 microarchitecture마다 다르며 software가 존재를 가정하면 안 된다.
multi-level page table주소를 여러 index로 나누어 PGD→P4D→PUD→PMD→PTE처럼 단계적으로 찾는 sparse tree다. 비어 있는 큰 주소 범위의 하위 table을 만들지 않아도 된다.
leaf entry최종 PFN·권한을 담아 translation을 끝내는 entry. 보통 PTE지만 huge page는 PMD/PUD에서 walk를 끝낼 수 있다.
associativity한 VPN이 들어갈 수 있는 cache slot 집합의 수. capacity가 남아도 같은 set에 몰리면 conflict miss가 생길 수 있다.
ASID / PCIDtranslation을 address-space별 tag로 구분하는 식별자. x86의 PCID는 Process-Context Identifier이며 context switch 때 무조건 전체 TLB를 비우는 비용을 줄인다.
TLB invalidationpage table을 바꾼 뒤 기존 cached translation을 더 쓰지 못하게 만드는 동작. page, range, address space, 전체 범위로 수행할 수 있다.
TLB shootdown같은 address space를 실행한 다른 CPU에도 invalidation을 요청하고 완료를 동기화하는 SMP 작업. 보통 IPI와 원격 CPU 응답이 관여한다.
IPIInter-Processor Interrupt. 한 CPU가 다른 CPU에 즉시 처리할 일을 알리는 interrupt다.
huge page기본 page보다 큰 mapping. x86에서는 흔히 2MiB/1GiB이며 TLB reach와 page-table overhead를 개선하지만 memory waste·allocation·latency trade-off가 있다.
nested paging가상화에서 guest VA→guest PA와 guest PA→host PA의 두 translation을 조합하는 방식. TLB miss의 walk 비용이 확대될 수 있다.

2. mental model: 자주 쓰는 경로를 적어 둔 안내 데스크

page table은 건물 전체의 공식 주소 장부이고 TLB는 CPU 코어 안내 데스크의 작은 메모장이다. 요청한 virtual page가 메모장에 있으면 바로 physical frame과 권한을 얻는다. 없으면 장부의 상위 분류부터 leaf까지 찾아가 translation을 메모장에 채운다.

  • hit: 번역은 빨라도 이어지는 data-cache miss나 DRAM access는 여전히 느릴 수 있다.
  • miss: 장부에 mapping이 있으면 walk 후 TLB fill로 끝나며 kernel에 진입하지 않을 수 있다.
  • fault: leaf가 absent이거나 권한이 맞지 않으면 CPU exception으로 kernel에 진입한다.
  • mapping change: 공식 장부만 고치고 메모장을 지우지 않으면 CPU가 옛 frame·옛 권한을 계속 사용할 수 있다.

핵심 구분: TLB miss는 performance event, page fault는 architectural exception이다. 둘은 원인·관찰 지표·처리 주체가 다르다.

5. CS·kernel·hardware deep dive

5.1 왜 flat page table이 아니라 radix tree인가

4KiB page로 48-bit VA를 flat mapping하면 2^36개의 leaf entry가 필요하다. entry가 8 bytes라면 process 하나에 512GiB다. 계층형 table은 사용하지 않는 상위 range를 absent entry 하나로 표현하고, 실제로 touch/mapping한 경로만 하위 table page를 만든다. 비용은 sparse address space에 비례하지만 mapping이 무작위로 넓게 흩어지면 page-table page가 늘어난다.

5.2 TLB는 content cache가 아니라 translation cache다

TLB entry는 대략 VPN, PFN, page size, access permission, global/address-space tag를 가진다. hit 뒤에도 physical address로 L1/L2/LLC/data memory hierarchy를 접근해야 한다. 따라서 “TLB hit=load가 L1 latency”도 아니고 “cache miss=TLB miss”도 아니다. instruction fetch에는 iTLB, load/store에는 dTLB가 관여할 수 있고 더 큰 shared TLB가 뒤에 있을 수 있다.

5.3 page walk는 dependent memory chain이다

다음-level table의 physical address는 현재 entry를 읽어야 알 수 있어 walk access는 의존적이다. 냉각된 4-level walk를 단순히 “DRAM 4번”이라 부르기도 하지만 실제 latency는 paging-structure cache, 일반 data cache, memory-level parallelism, speculative walk에 크게 좌우된다. Intel은 paging-structure cache의 존재·부재를 software가 가정하지 말라고 명시한다.

5.4 TLB reach와 locality가 miss rate를 결정한다

64-entry TLB와 4KiB page의 단순 reach는 256KiB, 같은 entry 수에서 2MiB page면 128MiB다. 그러나 capacity만 보면 안 된다. reuse distance가 capacity보다 크거나 특정 set에 VPN이 몰리면 eviction이 발생한다. sequential scan, pointer chasing, random sparse access는 같은 byte 수라도 miss pattern이 다르다.

5.5 huge page는 walk를 일찍 끝내고 reach를 늘린다

x86의 2MiB mapping은 PMD leaf에서, 1GiB mapping은 PUD leaf에서 translation을 끝낼 수 있다. leaf 수와 page-table memory, TLB pressure가 줄어드는 대신 contiguous physical memory 확보, compaction latency, 내부 단편화, COW split, NUMA placement가 문제가 될 수 있다. “큰 page가 항상 빠르다”가 아니라 workload의 working set과 allocation lifecycle로 검증해야 한다.

5.6 PCID/ASID는 context switch의 collateral damage를 줄인다

address-space tag가 없으면 page-table root 교체 시 다른 process의 translation과 혼동하지 않도록 넓은 flush가 필요하다. PCID가 있으면 TLB entry를 context별로 구분해 재사용할 수 있다. 하지만 mapping이 unmap되거나 권한이 낮아지면 해당 PCID의 stale entry는 여전히 정확히 invalidate해야 한다. tag는 coherency를 자동 해결하는 마법이 아니다.

5.7 PTE update와 TLB invalidation은 하나의 correctness protocol이다

kernel이 munmap이나 mprotect로 PTE를 바꿨는데 TLB에 old PFN/writable permission이 남으면 use-after-unmap, 잘못된 frame access, protection bypass가 가능하다. Linux는 page-table 변경 뒤 flush_tlb_page/range/mm/all 계열을 통해 변경이 CPU에 보이도록 architecture contract를 제공한다.

5.8 shootdown은 shared-memory scale의 숨은 tax다

같은 mm_struct를 실행한 여러 CPU에 translation이 캐시될 수 있다. initiating CPU는 관련 CPU에 IPI를 보내고 local invalidation을 수행하게 하며 안전한 재사용 전에 완료를 기다릴 수 있다. CPU 수, target mask, 변경 빈도, IPI 지연이 tail latency를 만든다. Linux는 해당 mm을 실행한 적 없는 CPU를 target에서 제외하는 등의 최적화를 한다.

5.9 precise invalidation과 full flush는 trade-off다

x86 Linux는 작은 range를 page별 invlpg로 지우거나 TLB 전체를 flush할 수 있다. page별 invalidation은 instruction 수·IPI work가 늘고, full flush는 관계없는 hot translation까지 버려 refill miss를 만든다. 최적 threshold는 TLB 크기, range, current contents, microarchitecture와 workload에 따라 달라진다.

5.10 nested paging은 miss penalty를 곱셈적으로 키울 수 있다

VM에서는 guest page table로 GVA→GPA를 찾고 EPT/NPT 같은 second-stage table로 GPA→HPA를 찾는다. 각 guest table page 자체의 GPA도 host physical로 번역해야 하므로 naive walk는 많은 의존 access를 만든다. hardware의 combined TLB와 walk cache가 이를 완화하지만, VM에서 TLB miss·huge page·vCPU migration을 함께 보는 이유다.

7. 실무 best practice

  • measure first: latency 회귀를 TLB 탓으로 단정하지 말고 cycles, instructions, cache misses, page faults, working set, CPU migration과 함께 비교한다.
  • rate로 비교: raw miss count보다 miss/access, walk duration, runtime 대비 비율과 p95/p99를 같은 workload·CPU affinity에서 본다.
  • mapping churn 줄이기: hot path의 반복 mmap/munmap/mprotect를 피하고 lifetime이 맞으면 batch·pool·arena를 검토한다.
  • huge page는 실험: baseline과 메모리 낭비, allocation/compaction latency, NUMA locality, COW·split 비용을 함께 기록하고 rollback을 준비한다.
  • thread fan-out 인식: 하나의 mm을 많은 CPU에서 동시에 실행할수록 shootdown target과 tail risk가 커질 수 있다.
  • CPU pinning은 통제 변수: benchmark 재현에는 쓰되 production에서 무분별한 pinning으로 load balance·NUMA 문제를 만들지 않는다.
  • architecture 기록: CPU model, kernel, page size, THP/HugeTLB mode, VM/host 여부, perf event 이름을 결과와 함께 보존한다.
  • permission revoke는 correctness: kernel/driver 코드는 page-table update, ordering, invalidation API 계약을 임의로 생략하지 않는다.

9. 놓치기 쉬운 함정

  • TLB miss=page fault: valid PTE를 hardware walk로 찾으면 kernel exception 없이 끝난다.
  • 4-level miss=DRAM 네 번: page-walk cache와 일반 cache hit 때문에 고정 비용이 아니다.
  • 모든 64-bit VA bit 사용: paging mode와 canonical-address 규칙이 usable width를 정한다.
  • Linux 5-level=hardware 항상 5회: 사용하지 않는 level은 folded될 수 있고 huge leaf는 일찍 끝난다.
  • PCID가 flush 제거: context-switch flush를 줄일 뿐 mapping 변경의 invalidation 요구는 남는다.
  • huge page는 무조건 승리: memory waste, compaction, NUMA, COW split과 page-size별 TLB 구조를 봐야 한다.
  • perf event는 portable: 이름·의미·정확도·지원 여부가 CPU model에 종속될 수 있다.
  • full flush가 항상 나쁨: 큰 range에서는 page별 invalidation보다 전체 flush가 싸고 정확할 수 있다.

10. 30분 실습: TLB reach와 stale translation simulator

hardware counter 권한이나 CPU 종류에 의존하지 않는 Python 3 표준 라이브러리 실습이다. 같은 256개 access를 TLB capacity와 page size만 바꿔 비교하고, PTE 변경 뒤 invalidation을 누락하면 old PFN이 남는 failure를 재현한다.

python3 - <<'PY'
from collections import OrderedDict

def simulate(name, page_size, capacity, repeats=4, base_pages=64):
    # 4KiB 간격의 64개 주소를 4회 순회한다.
    addresses = [i * 4096 for _ in range(repeats) for i in range(base_pages)]
    tlb = OrderedDict()
    hits = misses = walks = 0
    for va in addresses:
        vpn = va // page_size
        if vpn in tlb:
            hits += 1
            tlb.move_to_end(vpn)
        else:
            misses += 1
            walks += 1
            tlb[vpn] = vpn  # identity mapping인 단순 page table
            if len(tlb) > capacity:
                tlb.popitem(last=False)  # LRU 한 개 제거
    print(f"{name} hits={hits} misses={misses} walks={walks}")

simulate("small_tlb_4k", 4096, 8)
simulate("large_tlb_4k", 4096, 128)
simulate("huge_page_2m", 2 * 1024 * 1024, 8)

# PTE를 바꿨지만 TLB를 invalidate하지 않은 버그를 모형화한다.
page_table = {3: 10}
tlb = {}
def translate(vpn):
    if vpn not in tlb:
        tlb[vpn] = page_table[vpn]
    return tlb[vpn]

assert translate(3) == 10       # old mapping을 TLB에 채움
page_table[3] = 99              # kernel이 PTE만 변경했다고 가정
stale = translate(3)            # flush가 없으므로 old PFN 10
del tlb[3]                      # local invalidate 모형
fresh = translate(3)            # 새 PTE에서 PFN 99를 refill
print(f"stale_without_flush={stale} fresh_after_flush={fresh}")

assert (stale, fresh) == (10, 99)
PY

기대 출력

small_tlb_4k hits=0 misses=256 walks=256
large_tlb_4k hits=192 misses=64 walks=64
huge_page_2m hits=255 misses=1 walks=1
stale_without_flush=10 fresh_after_flush=99
  1. 0~10분: 8-entry TLB에서 reuse distance 64가 capacity를 넘어 매 scan마다 eviction되는 과정을 손으로 설명한다.
  2. 10~20분: capacity 128은 compulsory miss 64개 뒤 hit가 되고, 2MiB page는 모든 주소를 VPN 하나로 묶는 이유를 계산한다.
  3. 20~30분: stale PFN 10이 실제 kernel에서 왜 data corruption/security bug가 되는지, remote CPU shootdown까지 포함한 고치는 순서를 적는다.

모델 한계: 이 simulator는 fully-associative LRU, 단일 TLB, zero walk-cache cost를 가정한다. 실제 CPU의 set associativity, multi-level/page-size별 TLB, speculative walk, PCID와 cache latency를 측정한 결과처럼 해석하면 안 된다.

12. 실패 시나리오: permission hot path가 p99를 무너뜨림

JIT/runtime이 작은 code range를 요청마다 RW→RX로 바꿨다. 기능은 맞았지만 동일 address space의 worker가 96개 CPU에 퍼져 있었고, 잦은 mprotect가 range invalidation과 shootdown IPI를 만들었다. 평균 CPU 사용률은 낮은데 p99만 튀었고 PMU의 TLB refill보다 IPI 대기와 mapping churn이 핵심이었다.

진단: permission-change rate, call stack, worker CPU fan-out, irq/scheduler trace, p99를 같은 timeline에 맞춘다. 개선: W^X는 유지하면서 compile batch, code-cache lifecycle, worker topology를 재설계하고 작은 canary에서 검증한다. 금지: 성능 때문에 RWX를 상시 허용하거나 flush를 생략하지 않는다.

13. 대기업 면접 질문 3개

  1. “TLB miss와 page fault의 차이는 무엇인가요?”
    답변 포인트: TLB miss는 cached translation 부재이며 hardware page walk로 valid PTE를 찾으면 kernel에 진입하지 않는다. page fault는 translation/permission으로 access를 완료하지 못해 발생하는 architectural exception이다. minor/major fault와 TLB PMU event도 분리한다.
  2. “4-level page table은 왜 필요하고, miss 때 memory access는 정확히 네 번인가요?”
    답변 포인트: sparse VA의 table memory를 줄이는 radix hierarchy다. 4KiB x86-64는 9+9+9+9+12 bit로 나눈다. cold 모델은 여러 dependent access지만 page-walk cache/data cache/huge leaf 때문에 실제 비용은 고정 네 번의 DRAM access가 아니다.
  3. “PTE를 바꾼 뒤 왜 TLB shootdown이 필요한가요?”
    답변 포인트: 다른 CPU에 old PFN·permission이 남을 수 있어 unmap·revoke의 correctness와 security가 깨진다. PTE update 후 관련 CPU의 entry를 invalidate하고 완료를 보장한 뒤 frame을 재사용한다. range와 full flush의 precision/collateral-damage trade-off도 설명한다.

14. 퀴즈·누적 리뷰

  1. 4KiB page에서 offset은 몇 bit인가? 12 bit. page size가 2^12이기 때문이다.
  2. TLB hit인데 load가 느릴 수 있는가? 그렇다. translation 이후 data cache miss, DRAM, dependency 등이 남는다.
  3. Linux generic P4D가 있으면 모든 CPU가 5-level walk를 하는가? 아니다. architecture가 쓰지 않으면 folded된다.
  4. huge page의 장점 두 개와 위험 두 개는? TLB reach 증가·table overhead 감소, 내부 단편화·allocation/compaction/NUMA/COW 비용 중 두 개.
  5. Day 22 연결: VMA가 존재하고 PTE도 present인데 TLB에는 entry가 없으면? hardware walk로 PTE를 찾아 fill할 수 있으며 page fault일 필요가 없다.
  6. Week 3 연결: PTE update와 shootdown completion 사이에는 어떤 사고가 필요한가? 다른 CPU와의 ordering·visibility·lifetime 불변식이며 stale reader가 사라지기 전 frame 재사용을 금지해야 한다.
