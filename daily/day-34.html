실패 실습: fragmentation과 locality benchmark

한 줄 요약: 총 free memory가 충분해도 필요한 크기의 연속 block이 없으면 allocation은 실패하거나 compaction으로 지연되고, 같은 byte를 같은 횟수만큼 읽어도 순서가 cache·TLB·prefetcher 친화적인지에 따라 시간이 달라진다. capacity와 shape, correctness와 locality를 각각 측정해야 한다.

2. mental model: 빈 좌석 총합과 붙어 있는 좌석

공연장에 빈 좌석 32개가 있어도 16명이 한 줄로 앉아야 하는데 빈자리가 8개씩 네 군데 흩어져 있으면 예약은 실패한다. 사람을 다른 자리로 이동시켜 16석을 붙이는 것이 compaction이다. 좌석을 확보한 뒤에도 관객이 순서대로 출구를 지나면 흐름이 좋지만 무작위로 건물을 왕복하면 같은 인원이어도 이동 시간이 늘어난다. 앞은 fragmentation, 뒤는 locality 문제다.

6. CS·kernel·hardware deep dive

6.1 fragmentation은 layer마다 별개다

user allocator free list가 조각나도 OS에는 page를 반환하지 않았을 수 있고, physical buddy가 조각나도 일반 `malloc`은 흩어진 page를 연속 VA로 map해 성공할 수 있다. allocator metric, RSS, `/proc/buddyinfo`를 한 숫자로 섞으면 안 된다.

6.2 virtual contiguous는 보통 physical contiguous를 요구하지 않는다

page table이 각 virtual page를 다른 frame에 연결할 수 있으므로 큰 user buffer가 곧 high-order physical allocation은 아니다. DMA, 일부 kernel object, HugeTLB/THP backing처럼 physical shape가 중요한 경로를 따로 본다.

6.3 buddy order는 capacity와 shape를 동시에 표현한다

`free_area[order]`의 각 block은 `2^order` page다. 작은 order block 총합이 커도 요청 order column이 0이면 즉시 만족할 block이 없다. `/proc/buddyinfo`는 node·zone별 shape를 보여 주지만 미래 allocation 성공을 보장하는 예약표는 아니다.

6.4 migratetype은 미래 compaction 가능성을 보존한다

Movable·Reclaimable·Unmovable page를 pageblock 단위로 가능한 한 분리하면 movable page를 옮겨 큰 hole을 만들기 쉽다. unmovable page 하나가 pageblock에 섞이면 많은 free page가 있어도 큰 연속 영역을 만들기 어려울 수 있다.

6.5 direct compaction은 성공률과 tail latency를 교환한다

`kcompactd`는 background에서 shape를 준비하지만 allocation 순간 부족하면 caller가 synchronous compaction을 할 수 있다. THP `defrag=always`는 immediate huge page 성공을 위해 application을 stall시킬 수 있고, `defer` 계열은 background 준비와 later collapse를 선호한다.

6.6 arena는 lock contention을 줄이고 footprint를 늘릴 수 있다

thread별/다중 arena는 allocator lock 경쟁을 줄이지만 free block이 arena 사이에서 즉시 합쳐지지 않아 각 arena에 작은 잔여 공간이 남을 수 있다. throughput만 보고 RSS·return-to-OS·tail allocation latency를 놓치지 않는다.

6.7 alignment는 correctness 요구와 performance hint가 다르다

direct I/O·DMA·SIMD API는 특정 alignment가 계약일 수 있지만, 모든 object를 cache-line/page 정렬하면 padding과 working set이 커진다. `posix_memalign`은 alignment가 2의 거듭제곱이면서 pointer 크기의 배수여야 하고 실패 시 errno가 아니라 return code를 확인한다.

6.8 sequential access는 hardware가 추측할 수 있다

연속 cache line은 spatial locality와 prefetcher를 활용하고 page walk도 규칙적이다. random order는 cache line reuse, prefetch, TLB set/level behavior를 불리하게 만들 수 있다. 연산 수와 결과가 같아도 memory-level parallelism과 stall 시간이 달라진다.

6.9 benchmark는 compiler와 scheduler도 측정한다

compiler가 unused load를 제거할 수 있어 sum을 검증해야 한다. first-touch fault, warm cache, CPU migration, frequency, SMT neighbor, NUMA placement, background process가 결과를 바꾼다. 반복·분포·PMU 증거 없이 한 번의 wall time을 결론으로 쓰지 않는다.

6.10 locality 최적화가 fragmentation을 키울 수 있다

cache-line padding, per-thread shard, huge page, NUMA-local pool은 접근 비용을 줄이지만 object·page footprint와 stranded free space를 늘릴 수 있다. Day 29~33의 allocator, NUMA, TLB, reclaim 지표를 함께 비교해야 한다.

8. 실무 best practice

  • allocation 실패 metric에 requested size, alignment, allocator/zone/node, errno 또는 return code를 구조화해 남긴다.
  • 큰 contiguous physical allocation은 boot-time reserve, CMA, scatter-gather, smaller chunk fallback 등 architecture 단계에서 줄인다.
  • object lifetime·size가 비슷한 것끼리 pool을 나눠 coalescing과 page 반환 가능성을 높인다.
  • arena·size-class·padding 변경은 throughput뿐 아니라 RSS/PSS, largest free, p99 allocation, reclaim·compaction을 함께 canary한다.
  • benchmark는 pre-touch, warmup, 동일 access 수, correctness checksum, 반복과 median/p95, CPU/node affinity를 명시한다.
  • PMU event는 CPU·kernel·virtualization마다 지원이 다르므로 `perf list`로 확인하고 wall time과 교차한다.
  • production에서 `compact_memory`·`drop_caches`를 임의 실행하지 않는다. workload stall과 cache cold-start를 만들 수 있다.
  • THP fallback을 정상 경로로 두고 huge-page 성공률보다 SLO와 memory headroom을 우선한다.

9. error handling runbook

  1. failure contract: `malloc` NULL+errno, `posix_memalign` return code, kernel allocation fallback 여부를 구분한다.
  2. scope: user allocator free-list 문제인지 physical buddy node/zone/order 문제인지 먼저 가른다.
  3. partial rollback: 여러 chunk 중간 실패 시 이미 얻은 block을 정확히 해제하고 external side effect를 commit하지 않는다.
  4. shape evidence: `/proc/buddyinfo`, `/proc/pagetypeinfo`, `compact_stall/fail/success`, THP fallback delta를 같은 시간축에 보존한다.
  5. latency evidence: allocator p99, memory PSI, CPU, page fault, cache/TLB miss를 배포 전후 같은 workload로 비교한다.
  6. safe mitigation: smaller chunks, scatter-gather, alignment 완화, concurrency/working-set 축소 중 계약에 맞는 하나를 canary한다.
  7. rollback: compaction·THP·arena tuning 뒤 p99나 RSS가 악화되면 즉시 이전 정책으로 돌아가고 background 회복 시간을 관찰한다.

10. 놓치기 쉬운 함정

  • MemFree가 크면 큰 allocation 성공: zone·node·order·migratetype shape가 맞아야 한다.
  • 큰 malloc은 연속 physical RAM: 일반 user mapping은 흩어진 frame을 연속 VA로 구성할 수 있다.
  • compaction은 memory를 free: 주목적은 movable page를 옮겨 free 공간을 모으는 것이다.
  • random이 느리면 cache miss 확정: order-array load, TLB, prefetch, branch, NUMA까지 포함된 후보이므로 PMU로 좁힌다.
  • 평균이 빨라지면 성공: allocation/compaction p99와 RSS·OOM headroom 회귀를 확인해야 한다.
  • 한 번의 microbenchmark가 production: 실제 data layout, concurrency, CPU topology, compiler flag를 반영하지 않는다.
  • malloc non-NULL이면 memory 확보 완료: Linux overcommit에서는 first touch 시점에 backing 실패·OOM이 가능하다.

11. 30분 실습 A: external fragmentation 재현

64-unit first-fit arena를 8-unit block 8개로 채우고 교대로 free한다. 총 32가 비어도 largest hole은 8이라 16 요청이 실패한다. 인접 block을 하나 더 free해 coalesce하면 성공한다.

python3 - <<'PY'
class Arena:
    def __init__(self, size):
        self.free, self.used = [(0, size)], {}
    def alloc(self, ident, size):
        for i, (start, length) in enumerate(self.free):
            if length < size: continue
            self.used[ident] = (start, size)
            self.free[i:i+1] = [] if length == size else [(start+size, length-size)]
            return (start, size)
        return None
    def release(self, ident):
        self.free.append(self.used.pop(ident)); self.free.sort()
        merged = []
        for start, length in self.free:
            if merged and merged[-1][0] + merged[-1][1] == start:
                a, n = merged[-1]; merged[-1] = (a, n+length)
            else: merged.append((start, length))
        self.free = merged
    def stats(self):
        return sum(n for _, n in self.free), max(n for _, n in self.free)

a = Arena(64)
for ident in range(8): assert a.alloc(ident, 8)
for ident in (1, 3, 5, 7): a.release(ident)
print("fragmented", a.stats(), "alloc16=", a.alloc("big", 16))
assert a.stats() == (32, 8) and "big" not in a.used
a.release(0)
print("coalesced", a.stats())
assert a.stats() == (40, 16) and a.alloc("big", 16) == (0, 16)
PY

12. 30분 실습 B: 동일 access 수의 locality 비교

64MiB의 모든 64B line을 8번 읽는다. sequential/random 모두 8,388,608번 읽고 checksum도 같게 해 correctness를 고정한다. 개발 장비에서만 실행하고 다른 workload와 결과 수치를 비교하지 않는다.

cat >/tmp/locality.c <<'C'
#define _POSIX_C_SOURCE 200809L
#include <inttypes.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
enum { LINE=64, MIB=1024*1024, BYTES=64*MIB, ROUNDS=8 };
static uint64_t ns(void){ struct timespec t; clock_gettime(CLOCK_MONOTONIC,&t);
  return (uint64_t)t.tv_sec*1000000000ULL+t.tv_nsec; }
static uint32_t rnd(uint32_t *s){ uint32_t x=*s; x^=x<<13; x^=x>>17;
  x^=x<<5; return *s=x; }
static double bench(volatile unsigned char *d,size_t *o,size_t n,int random,
                    uint64_t *sum){ uint64_t s=0,t=ns();
  for(int r=0;r<ROUNDS;r++) for(size_t i=0;i<n;i++)
    s+=d[(random?o[i]:i)*LINE];
  *sum=s; return (double)(ns()-t)/(n*ROUNDS); }
int main(void){ size_t n=BYTES/LINE,*o=malloc(n*sizeof *o); unsigned char *d=0;
  if(!o) return 1; int rc=posix_memalign((void**)&d,LINE,BYTES);
  if(rc){ fprintf(stderr,"posix_memalign=%d\n",rc); free(o); return 1; }
  for(size_t i=0;i<n;i++){ d[i*LINE]=1; o[i]=i; }
  uint32_t state=0x12345678U;
  for(size_t i=n-1;i>0;i--){ size_t j=rnd(&state)%(i+1),x=o[i];o[i]=o[j];o[j]=x; }
  uint64_t a,b; double seq=bench(d,o,n,0,&a),ran=bench(d,o,n,1,&b);
  printf("seq_ns=%.3f random_ns=%.3f ratio=%.2f sums=%"PRIu64"/%"PRIu64"\n",
         seq,ran,ran/seq,a,b); free(d);free(o); return a==b?0:2; }

cc -O2 -std=c11 -Wall -Wextra -Werror /tmp/locality.c -o /tmp/locality

검증 host의 한 실행은 `sequential=1.789ns`, `random=4.283ns`, ratio `2.39`, 두 sum 모두 `8,388,608`이었다. 절대값과 ratio는 hardware·OS·부하마다 달라진다. random mode는 permutation array load도 포함하므로 순수 cache penalty만 분리한 값이 아니다.

  1. 0~10분: simulator로 total free와 largest free 불변식을 확인한다.
  2. 10~25분: C benchmark를 5회 반복하고 median·범위를 기록한다.
  3. 25~30분: Linux라면 `perf stat -d -d -r 5 -- /tmp/locality`로 cache·TLB event 지원 여부와 변화를 확인한다.

14. 실패 시나리오

영상 처리 service가 배포 후 평균 RSS는 동일했지만 간헐적으로 2MiB buffer 준비에 200ms가 걸렸다. 팀은 “free RAM 20GiB”만 보고 storage 문제로 오판했다. 실제로는 새로운 per-thread pool이 많은 unmovable·짧은 수명 page를 섞어 higher-order block을 고갈시켰고 `compact_stall`과 p99가 함께 올랐다. global compaction을 강제하지 않고 pool 수를 제한하고 buffer를 smaller chunk+scatter-gather로 바꿔, order 분포·compact delta·p99가 동시에 회복된 변경만 채택했다.

15. 대기업 면접 질문 3개

  1. free memory가 충분한데 allocation이 실패할 수 있는 이유는?
    답변 포인트: allocator layer, largest contiguous block, node/zone/order/GFP constraint, migratetype, compaction, general malloc의 virtual contiguity와 구분.
  2. sequential access가 random보다 빠른 이유를 어떻게 증명할까?
    답변 포인트: 동일 work/checksum, cache line·prefetcher·TLB, warmup·affinity·NUMA 통제, 반복 분포, perf event 교차 검증.
  3. fragmentation을 줄이는 설계의 trade-off는?
    답변 포인트: lifetime/size pool, arena 수, compaction CPU·stall, padding footprint, huge page TLB 이득과 memory waste, chunk/scatter-gather 복잡도.

16. 퀴즈·누적 리뷰

  1. 4KiB page에서 order 9 block 크기는? `2^9 × 4KiB = 2MiB`.
  2. compaction과 reclaim의 핵심 차이는? compaction은 page를 이동해 연속 shape를 만들고 reclaim은 사용 page를 free 상태로 바꾼다.
  3. random benchmark checksum이 필요한 이유는? compiler 제거와 correctness 차이를 막아 동일 work를 비교하기 위해서다.
  4. Day 31 연결: per-thread padding/shard는 false sharing을 줄이지만 working set과 allocator fragmentation을 키울 수 있다.
  5. Day 32~33 연결: THP 성공에는 큰 physical block이 필요하고 direct compaction은 latency, fallback은 TLB reach와 교환된다.
