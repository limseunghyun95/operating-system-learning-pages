OPERATING SYSTEM · DAY 37 / 63 · FILESYSTEM

VFS, mount, filesystem namespace

한 줄 요약: VFS는 하나의 syscall API를 ext4·XFS·tmpfs·procfs·NFS의 operation table로 dispatch하고, mount는 filesystem subtree를 namespace의 특정 dentry에 붙이며, mount namespace는 process별로 “어떤 mount tree를 볼지”를 격리한다. 같은 pathname도 namespace·root·mount propagation에 따라 다른 object를 찾는다.

1. 초보자 용어 사전

VFSVirtual File System 또는 Virtual Filesystem Switch. 공통 syscall을 filesystem별 구현으로 연결하는 kernel 추상화 layer.
filesystem typeext4, XFS, tmpfs, proc, NFS처럼 data·metadata 저장과 operation을 구현하는 종류. `/proc/filesystems`에서 등록된 type을 볼 수 있다.

2. mental model: 같은 도시, 다른 지하철 노선도

inode·data는 건물이고 VFS는 모든 건물 유형에 공통 출입 규칙을 제공하는 교통 layer다. mount는 특정 역에서 다른 노선으로 갈아타는 연결이고, mount namespace는 각 process 집단이 받은 노선도다. 두 container가 `/data/report`라는 같은 문자열을 사용해도 각 노선도의 `/data`가 host disk, tmpfs, remote volume 중 어디로 연결됐는지에 따라 전혀 다른 file을 연다.

6. CS·kernel deep dive

6.1 VFS는 interface와 dispatch boundary다

application은 `open/read/write/stat`을 호출하지만 VFS는 pathname으로 dentry·inode를 찾고 `inode_operations`, `file_operations`, `super_operations`의 function pointer를 concrete filesystem 구현으로 dispatch한다. 같은 read syscall도 ext4는 page/block mapping, NFS는 network RPC, procfs는 kernel state 생성을 수행할 수 있다.

6.2 superblock과 mount는 같은 object가 아니다

superblock은 filesystem instance와 공통 상태를 나타내고, mount object는 그 filesystem의 특정 root dentry를 namespace tree의 mountpoint에 붙인다. bind mount는 새 data copy나 새 filesystem을 만들지 않고 같은 underlying subtree에 별도 mount path를 만든다.

6.3 mount crossing도 pathname resolution의 일부다

VFS path walk는 component별 dentry lookup만 하지 않는다. 현재 `(mount,dentry)`가 mountpoint이면 child mount root로 넘어가고 `..`에서는 namespace root와 mount boundary 규칙을 적용한다. 그래서 dentry만으로 global path identity를 표현할 수 없고 `struct path`가 mount와 dentry를 함께 가진다.

6.4 mount namespace는 data를 복제하지 않는다

새 namespace는 mount list의 view를 복사해 시작하지만 inode·page cache·superblock과 실제 storage data를 통째로 복제하지 않는다. namespace A와 B가 같은 filesystem을 mount하면 data 변경은 공유될 수 있고, 격리되는 것은 “어디에 무엇이 붙어 보이는가”다.

6.5 같은 pathname은 process context에 의존한다

resolution 시작점은 process root, cwd 또는 dirfd이고 mount namespace가 crossing 가능한 mount tree를 정한다. container의 `/proc`, `/etc`, `/data`가 host와 다른 이유다. pathname 문자열을 resource identity나 authorization 근거로 단독 사용하면 안 된다.

6.6 propagation은 namespace isolation의 예외 통로다

mount list가 분리돼도 shared peer group이면 자식 mount/unmount event가 namespace 사이에 복제된다. container runtime이 host volume을 container에 전달할 때 유용하지만, 예상치 못한 event 유출·미전파·unmount 실패의 원인이 된다. propagation은 per-mountpoint 설정이며 data write replication과 다른 개념이다.

6.7 bind mount와 symlink는 layer가 다르다

symlink는 pathname 문자열을 가진 inode이고 lookup이 그 문자열을 다시 해석한다. bind mount는 mount graph에 subtree 연결을 추가한다. bind target은 mount boundary가 되며 source rename과 namespace visibility, propagation semantics가 symlink와 다르다.

6.8 chroot는 mount namespace가 아니다

`chroot`는 process의 path resolution root를 바꾸지만 mount list를 분리하지 않고 독립 security boundary를 완성하지 않는다. open fd, cwd, privilege가 있으면 escape 가능성이 있다. container rootfs는 mount namespace, user/capability policy, `pivot_root` 또는 유사 setup, proc/sys mount 제한을 함께 설계한다.

6.9 unmount는 storage를 파괴하는 operation이 아니다

정상 unmount는 현재 namespace mount tree에서 연결을 제거하며 busy reference가 있으면 `EBUSY`일 수 있다. lazy unmount는 tree에서 먼저 떼고 open fd·cwd·submount reference가 사라질 때 cleanup한다. 문제를 해결했다기보다 관찰 경로에서 숨길 수 있어 default 복구 수단으로 쓰면 안 된다.

6.10 namespace 자체도 reference-counted resource다

일반적으로 마지막 member process가 떠나면 namespace가 사라지지만 `/proc/PID/ns/mnt`에 열린 fd나 bind mount가 namespace를 pin할 수 있다. debugger·orchestrator가 namespace fd를 닫지 않으면 mount와 resource 수명이 예상보다 길어질 수 있다.

8. 실무 best practice

  • 장애 분석은 host의 `/proc/self/mountinfo`가 아니라 대상 PID의 `/proc/PID/mountinfo`에서 시작한다.
  • mountpoint와 source만 보지 말고 mount ID·parent ID·major:minor·root·fs type·per-mount options·super options·propagation tag를 함께 기록한다.
  • container volume의 propagation을 `private/slave/shared` 중 명시하고, 실제 mount·unmount event가 어느 방향으로 가야 하는지 integration test한다.
  • root를 recursive shared로 만드는 범위를 최소화하고, host path bind는 allowlist·read-only·`nosuid,nodev,noexec` 등 defense-in-depth를 검토한다.
  • `/etc/mtab`보다 `/proc/PID/mountinfo` 또는 이를 해석하는 `findmnt`를 source of truth로 쓴다.
  • unmount 전 child mounts, cwd, open fd, mmap, namespace pin을 찾아 drain한다. lazy/force unmount는 승인된 마지막 수단으로 둔다.
  • network filesystem은 reconnect·timeout·stale handle·hard/soft mount policy가 request latency와 data correctness에 미치는 영향을 별도 SLO로 관리한다.
  • device path `/dev/sdX`보다 UUID·label 같은 stable identifier를 쓰고 boot ordering·automount failure를 검증한다.
  • namespace fd를 의도적으로 pin한다면 owner와 close lifecycle을 문서화하고 namespace·mount count leak을 모니터링한다.

9. error handling runbook

  1. scope: 실패한 process PID와 mount namespace ID를 먼저 고정한다. host에서 성공한다는 사실은 container에서도 성공함을 뜻하지 않는다.
  2. request 보존: source, target, fs type, options, propagation, credential/capability, kernel log를 secret 제거 후 기록한다.
  3. mount error 분류: `EPERM`은 capability/policy, `ENOENT`·`ENOTDIR`는 path, `ENODEV`는 fs/device support, `EINVAL`은 option/propagation 조합, `EBUSY`는 target/source 상태 후보이다.
  4. 현재 graph 확인: `findmnt -T`, `/proc/PID/mountinfo`, parent-child mount ID, shared/master tag로 실제 연결을 그린다.
  5. partial rollback: 여러 child mount 중 실패하면 생성 역순으로 unmount하고 parent를 마지막에 처리한다. 다른 namespace의 기존 mount를 건드리지 않는다.
  6. EBUSY 대응: cwd, open fd, mmap, child mount, namespace pin을 찾아 owner를 drain한다. 무작정 `umount -l` 또는 force를 쓰지 않는다.
  7. verify: operation 직후 대상 namespace 안에서 expected fs type·source·root·options·propagation을 다시 읽고 sentinel file identity를 확인한다.
  8. rollback guard: health check와 data path가 회복되지 않으면 원래 mount graph를 복원하고 traffic을 열지 않는다.

10. 놓치기 쉬운 함정

  • namespace마다 file data도 복사: mount view만 분리되며 같은 superblock/data를 공유할 수 있다.
  • mountpoint 아래 기존 file이 삭제: overmount 동안 가려질 뿐 unmount하면 다시 보인다.
  • bind mount는 symlink 별칭: mount graph edge이며 mount boundary·options·propagation이 있다.
  • container path를 host에서 조사: 같은 문자열이 다른 mount를 가리킬 수 있으므로 target PID namespace에서 본다.
  • private이면 data write도 격리: mount event만 격리하며 underlying filesystem write는 공유될 수 있다.
  • read-only bind 하나면 완전 격리: 다른 writable alias, submount, remount capability, device path를 함께 봐야 한다.
  • chroot가 container 보안 경계: mount namespace와 권한·capability isolation을 대신하지 않는다.
  • lazy unmount가 user를 종료: 새 lookup에서 숨길 뿐 기존 reference는 계속 동작할 수 있다.
  • `df`와 `du` 차이는 계산 오류: overmount로 가린 file, deleted-open inode, namespace 차이일 수 있다.

11. 30분 실습 A: namespace view simulator

권한 없이 실행 가능한 model이다. longest mountpoint match, bind subtree, namespace별 overmount를 검증한다. 실제 kernel의 lock·propagation 전체를 재현하지 않는 교육용 model이다.

python3 - <<'PY'
import posixpath

def resolve(mounts, path):
    candidates = [m for m in mounts
                  if path == m or path.startswith(m.rstrip("/") + "/")]
    target = max(candidates, key=len)
    fs, root = mounts[target]
    rel = path[len(target):].lstrip("/")
    inner = posixpath.normpath(posixpath.join(root, rel))
    return fs, inner, target

host = {"/": ("rootfs", "/"), "/srv": ("disk#10", "/")}
container = dict(host)  # mount list view로 시작; storage copy가 아님

host["/work"] = ("disk#10", "/app")  # /srv/app subtree의 bind model
assert resolve(host, "/srv/app/config")[:2] == ("disk#10", "/app/config")
assert resolve(host, "/work/config")[:2] == ("disk#10", "/app/config")

container["/srv"] = ("tmpfs#22", "/")  # container namespace만 overmount
assert resolve(container, "/srv/app/config")[:2] == ("tmpfs#22", "/app/config")
assert resolve(host, "/srv/app/config")[:2] == ("disk#10", "/app/config")

for name, view in (("host", host), ("container", container)):
    print(name, resolve(view, "/srv/app/config"))
print("bind_alias", resolve(host, "/work/config"))
PY

12. 30분 실습 B: 격리된 Linux mount namespace

개발용 Linux VM/container에서만 실행한다. unprivileged user namespace가 비활성화되면 `unshare: Operation not permitted`로 종료하고 host에서 sudo로 우회하지 않는다. 새 private mount namespace 안에서만 tmpfs overmount를 만들며 trap으로 정리한다.

unshare --user --map-root-user --mount --propagation private sh -eu <<'SH'
lab=$(mktemp -d /tmp/os-day37.XXXXXX)
cleanup(){ mountpoint -q "$lab/view" && umount "$lab/view" || true; rm -rf "$lab"; }
trap cleanup EXIT INT TERM

mkdir "$lab/base" "$lab/view"
printf 'underlying\n' >"$lab/base/value"
mount --bind "$lab/base" "$lab/view"
printf 'bind: '; cat "$lab/view/value"

mount -t tmpfs -o size=4m tmpfs "$lab/view"
printf 'overlay\n' >"$lab/view/value"
printf 'overmount: '; cat "$lab/view/value"
findmnt -T "$lab/view" -o TARGET,SOURCE,FSTYPE,OPTIONS,PROPAGATION

umount "$lab/view"
printf 'revealed bind: '; cat "$lab/view/value"
grep " $lab/view " /proc/self/mountinfo
SH

  2. 10~25분: Linux 실습이 가능하면 bind→tmpfs overmount→unmount reveal을 관찰한다.
  3. 25~30분: host shell과 namespace shell의 mountinfo가 다른 이유, data copy가 없다는 증거를 설명한다.

`mountinfo` parser는 ` - ` separator 앞 optional field가 늘어날 수 있으므로 unknown tag를 무시해야 한다. mount ID와 peer group ID는 수명 종료 뒤 재사용될 수 있어 영구 business ID로 저장하지 않는다.

14. 실패 시나리오: host에는 volume이 있는데 container에는 없다

node agent가 host `/var/lib/data/new`에 volume을 mount했지만 이미 실행 중인 container의 같은 path에는 빈 directory만 보였다. application 권한 문제가 아니라 container parent mount가 private여서 host의 새 child mount event가 전파되지 않은 것이었다. host에서 무작정 bind를 반복하지 않고 대상 PID `mountinfo`의 namespace ID와 shared/master tag를 비교했다. 필요한 경로만 host→container 단방향 slave propagation으로 재설계하고, mount event·source device·sentinel inode를 검증한 뒤 traffic을 열었다.
