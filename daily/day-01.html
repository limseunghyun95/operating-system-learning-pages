한 줄 요약
program은 저장된 명령과 데이터이고, process는 OS가 자원과 격리 경계를 부여한 실행 인스턴스이며, thread는 그 process 안에서 CPU가 실제로 스케줄하는 실행 흐름이다.

1. 먼저 용어부터

Program디스크에 저장된 실행 파일과 코드. 아직 CPU 시간을 쓰지 않는 정적 산출물.
Process주소 공간, 열린 파일, 권한, signal 상태 등을 가진 실행 자원 컨테이너.
Threadprogram counter, register, stack을 가진 스케줄 가능한 실행 흐름. 같은 process의 주소 공간과 열린 파일을 공유한다.
PID/TIDprocess와 thread를 식별하는 번호. Linux 구현 세부에서는 task ID와 thread group 개념이 함께 등장한다.
Address spaceprocess가 볼 수 있는 virtual address 범위. code, heap, stack, mapped file 등이 배치된다.
Context실행을 멈췄다가 이어가기 위해 보존할 CPU register와 kernel 상태.

2. Architecture: 실행 파일에서 CPU까지

Executablecode·data와 loader가 읽을 metadata
↓ load / exec
Processvirtual address space · file descriptors · credentials · signal disposition
↓ contains one or more
Threadprogram counter · registers · stack · scheduling state
↓ scheduler dispatch
CPU coreregister에 현재 thread state를 올리고 instruction을 fetch/decode/execute

핵심: CPU는 “process 전체”를 한꺼번에 실행하지 않는다. 특정 순간에는 한 core가 특정 thread의 instruction stream을 실행한다. process는 그 실행에 필요한 공유 자원과 보호 경계를 제공한다.

3. process와 thread가 공유하는 것

항목process 단위thread 단위
주소 공간격리 경계같은 process 안에서 공유
열린 파일descriptor table 보유보통 공유하므로 offset/close 경쟁 가능
CPU register직접 실행 단위 아님각 thread가 별도 context 보유
stack주소 공간 안에 존재호출 프레임을 위해 별도 영역 사용

공유는 빠른 통신을 가능하게 하지만 자동으로 안전하지 않다. 두 thread가 같은 heap object를 동시에 수정하면 race condition이 발생할 수 있다. 반대로 process 사이에는 주소 공간 경계가 있어 IPC가 필요하지만, 한 process의 메모리 손상이 다른 process로 바로 번지는 위험을 줄인다.

4. CS Deep Dive: “실행 가능”과 “실행 중”

thread는 대략 running, runnable, blocked/sleeping 상태를 오간다. runnable은 CPU만 받으면 실행할 수 있지만 run queue에서 기다리는 상태다. blocked는 I/O 완료, lock, timer 같은 사건이 없으면 진행할 수 없다.

Runnable
CPU 대기		 ⇄ Running
core에서 실행		 ⇄ Blocked
event 대기

따라서 process가 “살아 있다”와 CPU를 계속 쓰고 있다는 말은 다르다. 대부분의 서버 thread는 network I/O를 기다리며 잠들어 있을 수 있다. 성능 진단에서 CPU 사용률만 보고 병목을 단정하면 안 되는 이유다.

5. 실무 Best Practice와 오류 처리

  • process 격리: 신뢰 경계나 장애 blast radius가 중요하면 별도 process를 고려한다.
  • thread 공유: 공유 mutable state를 최소화하고 ownership, lock, shutdown 순서를 문서화한다.
  • 식별자 재사용: PID는 영구 ID가 아니다. PID 하나만 저장해 나중에 다른 process를 종료하는 사고를 피하려면 시작 시간이나 pidfd 같은 안전 장치를 함께 고려한다.
  • 종료 처리: parent는 child의 종료 상태를 회수해야 zombie 누적을 막는다. daemon/container에서는 PID 1의 reaping 책임도 확인한다.
  • 관찰: process 수, thread 수, runnable/blocked 상태, context switch, open descriptor를 함께 본다.
놓치기 쉬운 함정: thread 생성이 무조건 process 생성보다 “가볍다”는 문장만 외우지 말자. 실제 비용은 stack 예약, runtime, scheduler, TLS, contention, isolation 요구에 따라 달라진다.

6. 30분 관찰 실습

목표: 하나의 process 안에 여러 thread가 존재하고, process 식별과 실행 상태가 다르다는 것을 관찰한다.

# macOS/Linux 공통에 가까운 관찰
python3 -c 'import os,threading,time
print("pid=",os.getpid())
for i in range(3):
    threading.Thread(target=lambda: time.sleep(30),name=f"worker-{i}").start()
print("threads=",threading.enumerate())
time.sleep(30)'

# 다른 터미널에서 위 PID로 확인
ps -o pid,ppid,state,nlwp,command -p <PID>  # Linux
ps -M <PID>                                  # macOS

예상: PID는 하나지만 thread는 main을 포함해 여러 개다. sleeping thread는 살아 있으나 CPU instruction을 계속 실행하지 않는다.

오류 처리: macOS의 `ps`에는 `nlwp`가 없을 수 있다. 명령 실패를 개념 실패로 해석하지 말고 OS별 관찰 인터페이스 차이로 분류한다. Linux라면 `/proc/<PID>/task`의 entry 수도 확인한다.

7. 대기업 면접 질문

  1. Process와 thread의 차이는?
    자원·보호 경계와 scheduling context를 분리하고, 공유 항목 때문에 생기는 성능 이점과 race 위험을 함께 답한다.
  2. Thread가 1,000개면 1,000개가 동시에 실행되나?
    동시성(concurrency)과 병렬성(parallelism)을 구분하고 core 수, runnable 상태, scheduler, blocking을 설명한다.
  3. 서비스가 살아 있는데 응답하지 않는 이유는?
    모든 thread가 lock/I/O에 blocked, run queue 포화, deadlock, stop-the-world 등 상태 가설과 관찰 증거를 제시한다.
